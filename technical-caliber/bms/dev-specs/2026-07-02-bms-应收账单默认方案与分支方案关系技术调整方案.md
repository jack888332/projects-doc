### 2.2 核心业务变化

本次提交不是文案微调，而是改变应收账单配置和生成任务的核心归集模型。

1. 应收账单配置由“配置版本信息 + 默认方案 + 分支方案”组成。
2. 生效周期、启用状态、操作人、操作时间、变更原因属于配置版本信息。
3. 默认方案和每个分支方案都独立维护账期、履约节点、币种规则、信用规则及限定情形。
4. 默认方案不再是分支方案未命中后的兜底方案。
5. 默认方案和分支方案按各自账期、履约节点及限定情形独立判断是否到达出账时点，不存在固定执行优先级。
6. 只要存在分支方案，默认方案也必须配置限定情形；未限定的默认方案只能用于“没有任何分支方案”的配置版本。
7. 默认方案与分支方案、分支方案与分支方案之间均不得存在限定范围交集。
8. 限定情形至少覆盖业务板块（当前前端称“订单类型”）、目的国、集运仓等拆账维度。
9. 范围交集、必要限定缺失或无法判断互斥关系时，配置不得保存或启用。
10. 同一来源费项在同一客户、同一应收配置版本中只能命中一个方案，不能因方案账期或执行时间不同而重复进入多张应收账单。
11. 生成任务必须固化配置、范围、限定情形和费项规则快照。

### 2.3 PRD 生成流程变化

旧流程为：

```text
扫描默认配置
  -> 加载其分支
  -> 分支按优先级抢占来源数据
  -> 默认配置接收未被分支占用的剩余数据
```

新流程应为：

```text
扫描所有已启用方案
  -> 每个方案按自己的账期和履约节点判断是否到期
  -> 按方案自己的限定情形筛选来源费项
  -> 校验来源费项未被同一配置版本的其它方案占用
  -> 按当前方案独立生成账单
```

### 3.3 当前前端实际落点

`admin_shell/src/views/billing/billConfig/index.vue` 是 BMS 账单配置页面，负责列表、默认方案展开分支、抽屉和保存入口；应收配置表单通过组件复用：

```text
admin_shell/src/views/billing/billConfig/index.vue
  -> admin_shell/src/views/clientmgr/listofCustomers/SettlementSettingPanel.vue
```

因此，仅修改 `admin_shell/src/views/billing/` 目录无法完成本需求。后续实施若要修改实际表单，必须同步调整上述复用组件，并回归客户管理中的结算设置入口，防止两个入口行为不一致。

### 3.4 当前生成逻辑的直接风险

假设默认方案为月结、分支方案为周结，且二者范围没有提前拆开：

1. 周结分支先生成时，会把来源费项写入分支账单。
2. 月结默认方案后生成时，当前独立任务上下文无法可靠知道该来源在“同一配置版本”下已被另一方案占用。
3. 若源表标记或 `collect_type` 不能覆盖该来源费项的所有拆分粒度，仍可能产生重复归集或错误跳过。
4. 如果继续使用“先执行者占用”的策略，最终归属会被任务执行时间决定，而不是由互斥限定情形决定。

因此，保存时的强互斥校验是第一道防线，执行时的版本内来源费项唯一归属校验是必须保留的第二道防线，两者不能互相替代。

## 4. 目标模型

### 4.1 配置版本、方案与限定情形

建议保持现有表的父子结构，但统一概念：

```text
应收配置版本
  ├─ 默认方案（config_type=DEFAULT，版本根节点）
  ├─ 分支方案1（config_type=BRANCH，parent_config_id=默认方案ID）
  └─ 分支方案2（config_type=BRANCH，parent_config_id=默认方案ID）
```

默认方案只是版本根节点兼业务方案，不代表兜底或优先级。每个方案都拥有：

- 业务板块/订单类型；
- 目的国；
- 集运仓；
- 账期类型；
- 履约节点；
- 生效周期；
- 币种和费项规则；
- 信用及合同规则。

### 4.2 限定情形匹配语义

建议将单个方案解释为：

```text
业务板块 IN 方案业务板块集合
AND 目的国 IN 方案目的国集合
AND 集运仓 IN 方案集运仓集合
```

同一维度内多值是 `OR`，不同维度之间是 `AND`。两个方案同时满足下列条件即存在交集：

```text
业务板块集合有交集
AND 目的国集合有交集
AND 集运仓集合有交集
```

如果某维度允许为空，必须先明确“空集合”表示不限还是无法匹配。建议在本期采用强约束：存在多个方案时三个维度均必填，从根源上避免“不限”导致无法证明互斥；若产品确认集运仓可选，则空值按“不限”处理，冲突校验中必然与其它方案该维度相交。

### 4.3 独立调度模型

建议任务以单个方案为执行主体：

```text
扫描当前启用的 DEFAULT + BRANCH 方案
  -> 按方案账期计算最近一个应出账周期
  -> 检查方案生效周期和履约节点
  -> 创建 bill_config_id=当前方案ID 的任务
  -> 固化当前方案快照 + 所属配置版本范围摘要
  -> 仅按当前方案限定情形取数并生成账单
```

不再由一个默认方案任务同时执行全部分支。这样任务幂等键、失败重试、监控、手工补跑都能直接对应一个方案及其账期。

### 4.4 双层防重模型

第一层：配置保存时证明同一版本内方案范围互斥。

第二层：生成时按来源费项做版本内唯一归属校验。建议唯一业务键至少包含：

```text
bill_type
+ sc_id/shop_id/user_id/member_code
+ config_version_root（或稳定的配置组编号）
+ source_system/source_table/source_id
+ source_fee_identity
```

其中 `source_fee_identity` 不能只用订单 ID；一个订单可拆出多个来源费项，应优先使用来源费项 ID，缺少独立费项 ID 时使用稳定的 `来源订单 + 费项编码 + 来源行ID` 组合。

## 5. 技术调整方案

### 5.1 前端调整

主要文件：

- `admin_shell/src/views/billing/billConfig/index.vue`
- `admin_shell/src/views/clientmgr/listofCustomers/SettlementSettingPanel.vue`
- `admin_shell/src/api/billing.js`（接口若新增冲突预校验时调整）

调整内容：

1. 默认方案增加与分支方案相同的“限定情形”区域。
2. 没有分支方案时，允许默认方案不限定范围；一旦新增首个分支方案，默认方案的必要限定项立即变为必填。
3. 删除“不包含限制条件，默认直接生效”的旧提示，改为“无分支时可不限定；有分支时所有方案必须通过限定情形互斥”。
4. `applyBillConfigToForm()` 回填默认方案的业务板块、目的国和集运仓。
5. `buildCommonConfig()` 不再对默认方案固定提交空 `scopes`，默认和分支使用同一范围构建方法。
6. 冲突校验集合改为 `[defaultScheme, ...subSchemes]`，错误提示明确具体方案和交集维度。
7. 前端校验仅用于即时反馈，不能替代后端保存/启用校验。
8. 列表中默认方案也展示“限定范围”；分支数和折叠层级可以保留，但应避免优先级/兜底措辞。
9. 生成账单入口需要明确当前生成目标是某个方案；若主列表仍以默认方案为根，应在展开行给每个分支提供独立生成入口，或弹窗中选择方案。
10. 同一表单也被客户管理入口复用，必须同时回归两个入口。

### 5.2 Model 与接口调整

建议保持现有 `BillConfigSaveReqDTO.defaultConfig/branchConfigs` 结构，减少接口破坏，但补齐以下语义：

1. 默认方案允许携带 `scopes`。
2. 新增明确的配置范围冲突响应 DTO，禁止用 `Map` 返回冲突信息，例如：
   - `BillConfigScopeConflictDTO`
   - `BillConfigValidateRespDTO`
3. 如新增保存前校验接口，建议为 `POST /api/bms/bill-config/validate-scope`，请求复用或抽取明确 DTO。
4. 为 DTO、实体字段补齐 JavaDoc；当前 `BillConfig`、`BillConfigCreateReqDTO`、`BillConfigScopeDTO` 字段注释不完整，应在本次涉及修改时同步补齐。
5. 若“变更原因”纳入本期，应新增明确字段而不是继续塞入 `extra Map`；方案建议增加 `changeReason` 到保存请求和配置版本记录。

### 5.3 配置保存与启用校验

`BillConfigServiceImpl.save()` 保存前增加整版本校验：

1. 默认方案必须存在。
2. 每个方案的客户维度、账期、履约节点、生效周期和状态合法。
3. 存在分支方案时，默认方案和全部分支均必须满足限定情形必填规则。
4. 将默认方案与分支方案统一转换为规范化范围对象。
5. 全量两两比较方案，不再只调用 `validateBranchNoOverlap(branches)`。
6. 比较时必须同时考虑业务板块、目的国、集运仓和生效周期；只有生效周期有重叠时才需要判定范围冲突。
7. 对无法识别的范围类型、空编码、重复编码直接拒绝。
8. 保存后启用前再次执行相同校验，避免绕过保存接口或历史脏数据被直接启用。
9. 错误信息返回方案名称、冲突方案、冲突维度和交集值，便于前端定位。
10. 写操作继续使用 `@Transactional(rollbackFor = Exception.class)`。

建议将当前笛卡尔 key 去重改为集合相交算法。现有实现强制每个分支同时选择业务类型、目的国、仓库，但前端只强制业务类型和目的国，两端规则已经不一致，也应在本次统一。

### 5.4 Mapper 与 SQL 调整

1. `queryEnabledConfigs()` 改为查询所有当前、生效、启用的应收方案，不再限定 `config_type='DEFAULT'`。
2. 新增按方案 ID 查询所属配置版本全部方案及范围的方法，供快照和执行期防重校验使用。
3. 新增按客户、配置版本和来源费项查询已归属方案的方法。
4. 涉及动态查询和多行 SQL时迁移到 `bms/dao/src/main/resources/sqlmap/`，使用 `<sql>`、`<include>` 和显式 `resultMap`；不新增 `SqlProvider`。
5. WHERE 中账期、生效日期使用范围条件，不对列应用 SQL 日期函数。

### 5.5 任务创建与调度调整

`BillGenerateServiceImpl.enqueueCurrentPeriodForEnabledConfigs()` 调整为：

1. 扫描所有启用方案。
2. 根据每个方案的 `billing_period_type` 计算本次应处理周期，不再固定月初至月末。
3. 结合当前日期、账单发出偏移、生效周期判断是否应创建任务。
4. 每个方案独立创建任务，`bill_generate_task.bill_config_id` 指向实际方案。
5. 活动任务校验由“同客户同账期只能一个任务”调整为“同客户 + 同配置版本 + 同方案 + 同账期只能一个活动任务”。否则不同账期类型的互斥方案可能被错误互斥。
6. 手工生成允许选择默认或分支方案，不再由 `requireDefaultConfig()` 强制回根配置。
7. 配置监控、失败重试和任务详情显示方案类型、方案名称、配置版本根和限定情形摘要。

### 5.6 任务快照调整

建议快照拆分为：

```text
执行方案快照
  - 当前 bill_config 完整字段
  - 当前方案限定情形
  - 当前方案费项及币种规则

配置版本上下文快照
  - 配置版本根ID/稳定组编号/version
  - 同版本其它方案ID、名称、状态
  - 各方案规范化限定情形摘要
  - 保存时互斥校验结果摘要
```

现有 `bill_config_snapshot_json` 和 `bill_scope_snapshot_json` 可以承载上述结构，暂不必为“限定情形快照”新增单独数据库列；但 JSON 字段中的 key 应固定并形成 DTO，避免持续使用无约束 `Map`。

任务失败重试必须复用原快照，不能反查最新配置。新配置版本只影响新创建任务。

### 5.7 订单、附加费及费项归属调整

1. 删除 `assignOrdersToConfigGroup()` 中“遍历分支 -> assignedOrderIds -> 默认吃剩余”的逻辑。
2. 当前任务只处理一个方案，主订单候选必须同时满足该方案业务板块、目的国、仓库和履约时间范围。
3. 默认方案与分支方案调用同一个 `matchesConfigScope()`，不再存在 `matchesBranchScope()` 特例。
4. 附加费增量归集使用同一方案匹配逻辑。
5. 范围校验应落到来源费项级；若订单级字段可唯一决定订单下全部费项归属，可以批量优化，但唯一键仍需记录到费项粒度。
6. 在写 `fee_detail` 和 `bill_source_collect_mark` 前，检查同客户同配置版本下是否已被其它方案有效占用。
7. 发现重复占用时任务失败并记录冲突方案、账单号、来源表、来源 ID、来源费项标识，禁止静默跳过。
8. 当前任务内的 `assignedOrderIds/assignedAdditionalIds` 只能作为内存性能优化，不能继续承担业务幂等职责。

### 5.8 数据库调整建议

#### 5.8.1 `bill_config`

建议评估增加稳定的配置版本组标识，例如：

| 字段 | 说明 |
| --- | --- |
| `config_group_no` | 客户应收配置的稳定组编号，不随版本变化 |
| `change_reason` | 本配置版本变更原因 |

继续使用默认方案 ID 作为版本根也可实现本期功能，但历史版本、新版本和跨任务查询都需要多次绕 `parent_config_id` 推导，语义较弱。若不新增字段，必须明确：默认行 ID 即该版本的 `config_version_root_id`，分支通过 `parent_config_id` 归属该版本。

`priority` 字段可暂时保留兼容历史数据，但生成归属不得再依赖它；后续确认无其它用途后再废弃。

#### 5.8.2 `bill_config_scope`

当前表可以同时保存默认和分支范围，无需因本次需求新增表。若业务板块继续保存在 `business_type_codes`，必须在代码中统一组合为三维限定情形；若希望模型完全统一，可新增 `BUSINESS_SECTOR` 类型并迁移业务板块范围，但这会扩大数据迁移范围，本期不优先推荐。

#### 5.8.3 来源费项唯一归属

建议新增独立的“来源费项方案占用表”，比直接修改 `bill_source_collect_mark` 的既有唯一键更清晰，例如 `bill_source_config_assignment`：

| 字段 | 说明 |
| --- | --- |
| `bill_type` | 账单类型 |
| `sc_id/shop_id/user_id/member_code` | 客户与数据隔离维度 |
| `config_version_root_id` | 应收配置版本根 |
| `bill_config_id` | 实际命中方案 |
| `source_system/source_table/source_id` | 来源行标识 |
| `source_fee_key` | 来源费项稳定标识 |
| `bill_id/bill_no` | 最终账单 |
| `generate_task_id` | 生成任务 |
| `assignment_status` | `LOCKED/ASSIGNED/RELEASED/FAILED` |

唯一键建议为：

```text
(bill_type, sc_id, shop_id, user_id, member_code,
 config_version_root_id, source_system, source_table, source_id, source_fee_key)
```

如果决定复用 `bill_source_collect_mark`，则必须先验证现网 `collect_type`、返款账单复用及历史唯一键兼容性，再补充配置版本根和来源费项标识；不能直接替换唯一键。

所有最终 DDL 都需同步更新 `aidocs/technical-caliber/bms/sql/ddl/init.sql` 中对应表的完整结构，并提供历史数据迁移脚本。

### 5.9 历史配置迁移

上线前扫描所有当前启用应收配置：

1. 无分支且默认无范围：合法，保持全范围默认方案。
2. 有分支且默认无范围：新规则下非法，不允许直接继续启用。
3. 分支范围缺目的国、仓库或业务板块：按最终必填口径标记待修复。
4. 方案之间存在交集：标记待修复，禁止自动猜测如何切分。
5. 历史已生成任务及账单保持原快照和归属，不回写。
6. 建议提供只读检查 SQL/管理页面，输出客户、配置编号、版本、问题类型和冲突范围。
7. 对非法历史配置建议先设置“待修复/禁止新建任务”，而不是直接逻辑删除。

## 6. 接口建议

### 6.1 保存接口

继续使用现有整版本保存接口，默认和分支都提交范围：

```json
{
  "defaultConfig": {
    "configType": "DEFAULT",
    "businessTypeCodes": ["CONSOLIDATION"],
    "scopes": [
      {"scopeType": "DEST_COUNTRY", "scopeCode": "US", "scopeName": "美国"},
      {"scopeType": "WAREHOUSE", "scopeCode": "WH-A", "scopeName": "A仓"}
    ]
  },
  "branchConfigs": [
    {
      "configType": "BRANCH",
      "businessTypeCodes": ["CONSOLIDATION"],
      "scopes": [
        {"scopeType": "DEST_COUNTRY", "scopeCode": "JP", "scopeName": "日本"},
        {"scopeType": "WAREHOUSE", "scopeCode": "WH-A", "scopeName": "A仓"}
      ]
    }
  ]
}
```

### 6.2 范围预校验接口

可选增加：

```text
POST /api/bms/bill-config/validate-scope
```

响应返回是否合法及结构化冲突列表，前端在新增、删除或修改限定情形时调用；正式保存时后端仍必须执行同一校验服务。

### 6.3 生成接口

现有生成接口继续接收 `billConfigId`，但该 ID 可以是默认方案或分支方案。后端校验其为当前启用方案，并从其自身字段计算/校验账期，不再自动转换为默认方案。

## 7. 调整计划

### 阶段 0：口径确认与数据盘点

1. 确认限定情形各维度的必填和空值语义。
2. 确认配置版本根的稳定标识方案。
3. 确认来源费项唯一键。
4. 扫描历史配置和潜在重复归集数据。
5. 输出迁移影响客户清单。

交付物：确认纪要、历史数据检查报告、最终 DDL 草案。

### 阶段 1：配置模型与保存校验

1. 补 DTO/实体注释和必要字段。
2. 默认方案支持保存范围。
3. 后端实现全方案规范化、必填、周期重叠和范围交集校验。
4. 调整 Mapper/XML 和版本查询。
5. 增加历史非法配置阻断策略。

验收重点：默认/分支、分支/分支任意范围交集都无法保存或启用。

### 阶段 2：前端配置交互

1. 默认方案增加限定情形。
2. 前端统一全方案冲突校验和错误标记。
3. 请求与回填支持默认范围。
4. 列表展示默认范围和方案独立账期。
5. 回归 BMS 页面与客户管理复用入口。

验收重点：用户在保存前能准确定位冲突方案和交集维度，后端仍能拦截绕过前端的非法请求。

### 阶段 3：独立任务调度与快照

1. 扫描默认和分支全部启用方案。
2. 按方案账期计算出账周期和到期时点。
3. 调整任务幂等和活动任务校验维度。
4. 手工生成支持指定任意方案。
5. 快照固化当前执行方案与配置版本上下文。
6. 调整任务监控展示。

验收重点：同一配置版本中月结默认方案和周结分支方案可各自在正确时点创建任务，互不阻塞。

### 阶段 4：来源费项归属与数据库幂等

1. 去除分支优先、默认兜底分配逻辑。
2. 默认和分支统一按自身范围匹配。
3. 主订单、附加费、赔付等来源统一接入来源费项唯一归属。
4. 重试、重跑和源表打标复用原归属。
5. 增加冲突失败日志及补偿策略。

验收重点：改变任务先后顺序不会改变来源费项的方案归属，同一来源费项不会进入同版本多份账单。

### 阶段 5：迁移、联调和回归

1. 执行历史配置检查和迁移。
2. 验证旧任务/旧账单不受影响。
3. 前后端联调保存、编辑、启停、定时生成、手工生成和失败重试。
4. 验证不同账期、不同履约节点和增量附加费场景。
5. 同步 DDL、设计文档和部署说明。

## 9. 风险与回滚

### 9.1 主要风险

1. 历史配置普遍依赖默认兜底，直接启用强校验可能导致大量客户无法生成账单。
2. 来源费项唯一键定义不准会造成误判重复或漏判重复。
3. 任务从“配置组任务”改为“方案任务”后，监控统计口径和任务数量都会变化。
4. 不同方案账期重叠时，现有“同客户同账期活动任务”校验可能误拦截。
5. 前端复用组件不在 `billing` 目录内，遗漏客户管理入口回归会产生双入口差异。
6. 直接修改 `bill_source_collect_mark` 唯一键可能影响返款账单和历史补偿链路。

### 9.2 发布与回滚建议

1. 先上线历史检查和只读告警，再启用强阻断。
2. 新旧调度模型使用配置开关切换，灰度客户验证后全量启用。
3. 新增占用表时采用双写校验阶段，确认稳定后再作为唯一判断来源。
4. 回滚只关闭新任务创建，不删除已生成任务、账单、费项和占用记录。
5. 已按新模型成功生成的账单不得通过回滚脚本物理删除，应按现有冲正/调账规则处理。

## 10. 疑问点

以下问题会直接影响表结构、校验算法或任务模型，开发前需要确认。

### 10.1 产品口径

1. 有分支时，默认方案的限定情形是否也必须同时填写业务板块、目的国、集运仓三个维度？PRD 写“至少包括”，但当前前端只强制订单类型和目的国，后端现状又强制三者。
2. 某维度为空时表示“不限”，还是表示该方案配置不完整？建议有多个方案时禁止为空。
3. “业务板块”与当前前端“订单类型”、后端 `business_type_codes` 是否完全等价？若不等价，需要新增独立维度。
4. 默认方案为什么仍称“默认”？是否只代表配置版本根/基础方案，而非业务兜底？建议页面补充清晰定义。
5. 是否允许不同方案的生效周期不重叠但限定范围相同？建议允许，因为同一时点不会冲突。
6. 是否允许两个方案限定范围互斥，但账期窗口部分重叠？按新 PRD 应允许。
7. 返款账单是否明确不适用默认/分支方案规则？本次提交只写“应收账单配置必须支持”，建议确认本期不扩展返款配置。

### 10.2 生成与幂等

1. “同一来源费项”的稳定唯一标识具体是什么？主订单宽表的一列费用没有独立行 ID 时，是否采用 `source_order_id + fee_code + source_row_id`？
2. 配置版本唯一范围以默认方案 ID、`config_no` 根、还是新增 `config_group_no + version` 表达？
3. 一条来源费项从旧配置版本未归集，发布新版本后应按旧版本还是新版本归集？需要明确配置版本命中的时间基准。
4. 同一来源费项在不同配置版本是否允许再次归集？PRD 只限制“同一配置版本”，但通常历史已出账费项也不应因发布新版本再次收费。
5. 手工生成入口应选择单个方案，还是选择配置版本后由系统为所有到期方案分别创建任务？
6. 任务创建时是否以账期结束日、账单发出日或 `bill_send_offset_days` 到期作为触发时点？当前定时逻辑尚未按这些字段实现。
7. 若执行期发现配置范围交集，是整任务失败，还是只隔离冲突费项？建议整任务失败并阻止静默抢占。

### 10.3 数据与迁移

1. 历史“默认无范围 + 有分支”的配置由财务人工补齐，还是系统根据现有分支求补集自动生成默认范围？由于目的国/仓库全集动态变化，不建议系统自动求补集。
2. 是否需要新增配置状态 `DRAFT/ENABLED/DISABLED/INVALID`，还是继续用 `status=0/1` 并额外记录校验结果？
3. “变更原因”是否为本期必做字段？当前实体没有独立字段。
4. 是否允许修改当前未出账版本，还是任何已启用版本都只能复制新版本？当前保存逻辑每次创建新版本，但部分 `create(overwrite=true)` 能覆盖旧行，需要统一入口边界。
5. 来源费项占用记录在冲正、调账、账单作废或重跑时是否释放？建议历史归属不释放，仅通过状态和调整记录承接，避免原费项再次收费。

## 11. 建议实施结论

本需求应按 P0 账单归属正确性变更处理，不能只修改前端提示或增加默认方案范围字段。最小完整闭环必须同时包含：

1. 默认方案可配置限定情形；
2. 保存/启用时全方案强互斥校验；
3. 默认和分支按自身账期独立建任务；
4. 移除分支优先、默认兜底生成逻辑；
5. 默认和分支使用同一范围匹配算法；
6. 建立同客户、同配置版本、同来源费项的数据库级唯一归属；
7. 固化执行方案和配置版本上下文快照；
8. 迁移或阻断不符合新规则的历史配置。

在 10.2.1“来源费项唯一标识”和 10.2.2“配置版本稳定标识”确认前，不建议直接进入归属表 DDL 和生成主链路编码；前端与保存校验可以先行，但不能单独发布启用新口径。
