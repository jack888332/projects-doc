## 2. 背景

客户 `OG0370` 的返款配置中配置了“在应返货款中直接扣减的应收费项”：

1. 代收货款手续费。
2. 超材费。
3. 重出费。

业务期望是：这些费项不应进入应收账单核销金额，也不应在应收收款核销后触发来源支付状态回写；但仍应在应收账单详情中作为另一类明细展示，方便财务核对“本账单内存在但由返款侧扣减处理”的费用。

当前问题是，部分直接扣减类费用仍按普通应收费项进入 `MEMBER_AR` 账单汇总，最终进入 `ar_bill_currency_summary.unpaid_amount`，导致应收账单核销口径偏大。

### 3.5 当前代码口径

根据现有代码和 SQL：

1. 应收账单汇总主要从 `fee_detail` 按 `bill_id/bill_no + bill_type = 'MEMBER_AR'` 聚合 `amount_bill_currency`。
2. 应收核销按 `ar_bill_currency_summary.unpaid_amount` 做币种分配。
3. 核销完成后的来源回写候选从 `fee_detail` 中按 `bill_no + bill_type = 'MEMBER_AR' + bill_currency` 查询。
4. 返款账单详情已经有 `REFUND_DEDUCTION` 口径，并且前端汇总时会按“代收货款手续费 / 重出费 / 超材费”展示扣减项。

当前缺口是：返款配置选中的直接扣减应收费项，在应收账单生成和应收详情中没有被稳定拆分为“返款扣减口径”，导致其继续进入应收核销金额。

## 4. 调整目标

### 4.1 业务目标

1. 返款配置中配置为“在应返货款中直接扣减”的应收费项，不进入应收账单核销口径。
2. 这些费用仍保留在 `fee_detail`，不丢失原始费用来源、订单、运单、币种和金额。
3. 应收账单详情新增或拆分一个 tab 展示这些费用。
4. 返款账单生成后，这些费用可继续作为返款扣减明细参与返款金额计算和展示。
5. 已生成但未核销的问题账单，重算后金额口径应可修正。

### 4.2 技术目标

1. 使用现有 `fee_detail.bill_no` / `related_bill_no` 和 `settlement_role` / `related_settlement_role` 表达主账单与关联账单，不新增表结构。
2. 应收金额汇总、重算、核销、回写候选统一以 `bill_type = 'MEMBER_AR' AND settlement_role = 'RECEIVABLE'` 作为应收核销口径。
3. 返款直接扣减费用最终以返款账单为主归属：`bill_type = 'COD_REFUND' AND bill_no = 返款账单号 AND settlement_role = 'REFUND_DEDUCTION'`。
4. 扣减费用通过 `related_bill_no = 应收账单号`、`related_bill_type = 'MEMBER_AR'` 回指应收账单，供应收详情另一个 tab 展示。
5. 费项识别支持配置编码、标准扣减类型和名称兜底，避免同名费项编码差异导致漏判。

## 5. 目标数据口径

### 5.1 普通应收费项

普通应收费项继续作为应收核销口径：

```text
bill_type = MEMBER_AR
settlement_role = RECEIVABLE
fee_status <> VOID
```

参与：

1. `ar_bill.initial_receivable_amount`。
2. `ar_bill.receivable_amount`。
3. `ar_bill.unpaid_amount`。
4. `ar_bill_currency_summary.receivable_amount`。
5. 应收核销分配。
6. 应收核销来源回写。
7. 应收详情的普通费用明细 tab。

### 5.2 返款直接扣减费项

返款配置命中的直接扣减费项不作为应收账单主费用。最终口径应归属返款账单：

```text
bill_no = 返款账单号
bill_type = COD_REFUND
settlement_role = REFUND_DEDUCTION
fee_status <> VOID
```

如果该扣减费用与某张应收账单存在展示或追溯关系，通过关联字段回指应收账单：

```text
related_bill_no = 应收账单号
related_bill_type = MEMBER_AR
related_settlement_role = REFUND_DEDUCTION
```

参与：

1. 应收账单详情的“返款扣减费项”tab，通过 `related_bill_no = 当前应收账单号` 查询。
2. 返款账单生成或关联时的扣减明细。
3. 返款账单详情的扣减金额汇总。

不参与：

1. 应收账单应收金额。
2. 应收账单未核销金额。
3. 应收核销分配。
4. 应收核销来源支付状态回写。

### 5.3 关联返款账单后的口径

关联返款账单后，直接扣减费项应以 COD 返款账单作为主账单归属，应收账单作为关联账单：

```text
bill_no = 返款账单号
bill_type = COD_REFUND
settlement_role = REFUND_DEDUCTION
related_bill_no = 应收账单号
related_bill_type = MEMBER_AR
related_settlement_role = REFUND_DEDUCTION
```

这样同一条费用的资金处理主语是返款账单，符合“在应返货款中直接扣减”的业务语义；应收账单只承担关联展示和追溯，不承担核销金额。

现有代码也更适配该方向：

1. `RefundFeeUnion` 优先支持 `fd.bill_type = 'COD_REFUND' AND fd.bill_no = #{billNo}` 的返款主归属查询。
2. `BillGenerateMapper.queryRefundFeesForArWeakLink()` 已按 `bill_type = 'COD_REFUND' AND settlement_role = 'REFUND_DEDUCTION' AND related_bill_no IS NULL` 查询待关联返款扣减费用。
3. `BillGenerateMapper.linkArBillToRefundFee()` 已具备将返款扣减费用补挂到应收账单 `related_bill_no` 的能力。

## 6. 技术调整方案

### 6.1 返款扣减费项识别

新增或收敛一个服务端识别方法，输入应收账单客户维度、账期和费用明细，输出该费用是否属于返款直接扣减费项。

识别优先级建议：

1. 查询同客户当前生效的 `refund_bill_config`。
2. 解析 `config_snapshot_json.directDeductFeeItems`。
3. 将配置项转换为标准扣减类型：
   - `COD_SERVICE_FEE`：代收货款手续费。
   - `OVERSIZE_FEE`：超材费。
   - `REISSUE_FEE`：重出费。
4. 按标准扣减类型匹配实际费用：
   - 优先匹配配置中的真实 `feeCode`。
   - 再匹配 `fee_index.fee_name`。
   - 最后按已确认的别名表兜底。

建议将别名维护为常量或枚举，不在 SQL 中散落中文字符串。

初始建议：

| 标准扣减类型 | 确认可匹配名称 |
| --- | --- |
| `COD_SERVICE_FEE` | 代收货款手续费 |
| `OVERSIZE_FEE` | 超材费 |
| `REISSUE_FEE` | 重出费 |

`货到付款手续费` 是否归入 `COD_SERVICE_FEE` 暂不默认纳入，等待业务确认。

### 6.2 账单生成落表

应收账单生成时，命中返款直接扣减配置的费用不应再作为 `MEMBER_AR + RECEIVABLE` 主费用落入应收账单。

推荐处理：

1. 未命中返款直接扣减费项：
   - `settlement_role = RECEIVABLE`。
   - `bill_type = MEMBER_AR`。
   - `bill_no = 应收账单号`。
2. 命中返款直接扣减费项且本期存在对应 COD 返款账单：
   - `settlement_role = REFUND_DEDUCTION`。
   - `bill_type = COD_REFUND`。
   - `bill_no = 返款账单号`。
   - `related_bill_type = MEMBER_AR`。
   - `related_bill_no = 应收账单号`。
   - `related_settlement_role = REFUND_DEDUCTION`。
3. 命中返款直接扣减费项但返款账单尚未生成：
   - 不进入应收汇总和核销。
   - 可先进入待关联处理队列，或在返款账单生成时统一采集并落为 `COD_REFUND + REFUND_DEDUCTION`。
   - 不建议长期保留为 `MEMBER_AR + REFUND_DEDUCTION` 主归属，避免主账单语义和返款详情查询口径不一致。

如果现有生成链路已默认写入 `MEMBER_AR + RECEIVABLE`，命中扣减配置时应在写入前分流，而不是写入后仅改 `settlement_role`。

### 6.3 应收汇总口径

所有应收金额汇总 SQL 增加结算角色条件：

```sql
AND settlement_role = 'RECEIVABLE'
```

重点包括：

1. 生成后创建 `ar_bill_currency_summary` 的来源查询。
2. 生成后刷新 `ar_bill` 金额的 SQL。
3. 应收账单汇率保存后的重算。
4. 应收账单调账或重整后重算。
5. 任务重跑后重建汇总。

主表本位币金额也必须使用相同条件，避免 `receivable_amount` 和 `receivable_amount_fin` 口径不一致。

### 6.4 应收核销口径

应收核销无需感知具体费项，只要 `ar_bill_currency_summary` 已排除 `REFUND_DEDUCTION`，核销分配自然只会落在普通应收金额上。

但核销后来源回写候选必须同步排除扣减项：

```sql
AND settlement_role = 'RECEIVABLE'
```

避免某个币种被普通应收核销完成后，将同币种下的返款扣减费用也回写为已支付。

### 6.5 应收账单详情

应收账单详情建议拆两个费用 tab：

| Tab | 查询口径 | 金额含义 |
| --- | --- | --- |
| 应收费项 | `bill_no = 当前应收账单号 AND bill_type = MEMBER_AR AND settlement_role = RECEIVABLE` | 参与应收和核销 |
| 返款扣减费项 | `related_bill_no = 当前应收账单号 AND related_bill_type = MEMBER_AR AND bill_type = COD_REFUND AND settlement_role = REFUND_DEDUCTION` | 不参与应收核销，由返款侧扣减 |

接口层可以采用两种实现：

1. 方案 A：新增独立分页接口 `deductionFeeDetailPage`。
2. 方案 B：复用现有费用明细分页接口，新增 `settlementRole` 查询参数。

推荐方案 B，改动更小，也便于以后扩展其他结算角色。

前端展示建议：

1. 普通费用 tab 默认展示原有字段。
2. 返款扣减 tab 展示费项编码、费项名称、业务单号、尾程运单、来源表、来源金额、返款账单币种金额、返款账单号。
3. 返款扣减 tab 顶部展示按币种汇总的扣减金额。
4. 返款扣减 tab 不展示“待核销”语义。

### 6.6 返款账单关联

返款账单生成时，直接扣减费项应作为返款账单明细落表：

1. `bill_id = 返款账单ID`。
2. `bill_no = 返款账单号`。
3. `bill_type = COD_REFUND`。
4. `bill_config_id = 返款配置ID`。
5. `settlement_role = REFUND_DEDUCTION`。
6. `bill_currency`、`amount_bill_currency`、`amount_fin_currency` 使用返款账单口径。

如果已存在对应应收账单，同步补充：

1. `related_bill_id = 应收账单ID`。
2. `related_bill_no = 应收账单号`。
3. `related_bill_type = MEMBER_AR`。
4. `related_bill_config_id = 应收配置ID`。
5. `related_settlement_role = REFUND_DEDUCTION`。
6. `related_bill_currency`、`related_amount_bill_currency`、`related_amount_fin_currency` 可按应收展示需要保存应收侧换算结果。

如果返款账单先生成、应收账单后生成，应使用现有类似 `queryRefundFeesForArWeakLink()` + `linkArBillToRefundFee()` 的链路补挂应收账单关联字段。

如果应收账单先生成、返款账单后生成，应避免把扣减费项作为 `MEMBER_AR` 主明细长期保存；更推荐在返款账单生成时落 `COD_REFUND` 主明细，并补挂已存在应收账单。

### 6.7 历史账单修正

对已经生成但尚未核销的问题账单，可以提供一次性重算或重跑：

1. 先识别应从应收核销口径剔除的明细。
2. 若已有对应返款账单，将这些明细迁移或重建为 `COD_REFUND + REFUND_DEDUCTION` 主归属，并通过 `related_bill_no` 指回应收账单。
3. 若暂无对应返款账单，先从应收汇总和核销口径剔除，并记录待返款账单生成后补落返款明细的任务。
4. 删除并重建 `ar_bill_currency_summary`。
5. 刷新 `ar_bill` 金额。
6. 刷新任务或操作日志，记录本次口径修正原因。

已核销账单不能直接静默修正，应走反核销或财务确认流程，避免历史核销流水和主表金额不一致。

## 8. 调整计划

### P0：口径确认

1. 确认 `货到付款手续费` 是否属于返款配置中的 `代收货款手续费`。
2. 确认同名费项编码是否都应按费项名称归并，例如 `FEE0005/FEE0045/FEE0053` 均视为 `超材费`。
3. 确认已生成未核销账单是否允许直接重算，还是必须重新生成。
4. 确认已核销历史账单是否纳入本次修正范围。

### P1：后端生成口径

1. 增加返款配置直接扣减费项解析能力。
2. 增加费项标准扣减类型匹配能力。
3. 应收账单生成时对命中费用做分流，不写入 `MEMBER_AR + RECEIVABLE`。
4. 普通应收费项继续写入 `MEMBER_AR + RECEIVABLE`。
5. 返款账单生成时将命中费用写入 `COD_REFUND + REFUND_DEDUCTION`。
6. 已存在应收账单时，返款扣减费用通过 `related_bill_no = 应收账单号` 补挂关联。
7. 补充生成任务快照中与扣减规则相关的留痕，便于排查。

### P2：后端汇总与核销口径

1. 调整生成后币种汇总来源，只汇总 `RECEIVABLE`。
2. 调整应收账单主表刷新，只汇总 `RECEIVABLE`。
3. 调整应收汇率保存后的重算口径。
4. 调整重整调账或重跑后的汇总口径。
5. 调整来源支付状态回写候选，只选择 `RECEIVABLE`。

### P3：应收详情接口与前端

1. 应收费用明细分页请求增加 `settlementRole`，普通费用 tab 查询 `MEMBER_AR + RECEIVABLE`。
2. 新增或扩展扣减费用查询，按 `related_bill_no = 当前应收账单号 AND bill_type = COD_REFUND AND settlement_role = REFUND_DEDUCTION` 查询。
3. 前端详情增加“返款扣减费项”tab。
4. 原费用明细 tab 默认只展示 `RECEIVABLE`。
5. 扣减 tab 展示扣减金额汇总、返款账单号和返款账单状态。

### P4：返款账单联动

1. 返款账单生成时落 `COD_REFUND + REFUND_DEDUCTION` 主明细。
2. 若对应应收账单已存在，补齐指回应收账单的 `related_bill_*` 字段。
3. 确保返款详情中的扣减明细仍能展示这些费用。
4. 确保返款汇率重算以 `amount_*` 为返款主口径，并按需刷新 `related_amount_*` 应收展示口径。

### P5：历史数据处理

1. 针对未核销的问题账单提供重算脚本或内部修正入口。
2. 修正前输出影响清单：账单号、费项、币种、金额、调整前后应收。
3. 若已有返款账单，将扣减费用迁移或重建为 `COD_REFUND + REFUND_DEDUCTION`，并指回应收账单。
4. 若暂无返款账单，先修正应收汇总，并记录待返款生成后补落明细。
5. 修正后校验 `ar_bill`、`ar_bill_currency_summary`、`fee_detail` 三方金额一致。
6. 对已核销账单只输出影响清单，等待财务确认处理方式。

### P6：联调验收

1. 使用 `OG0370` 当前账单作为回归样例。
2. 新生成一张含超材费、代收货款手续费、重出费的应收账单和对应返款账单。
3. 验证普通应收 tab、返款扣减 tab、币种汇总、核销分配和来源回写。
4. 验证扣减明细主归属为返款账单，应收账单通过 `related_bill_no` 展示。
5. 修改汇率并重算，验证应收口径和返款扣减口径均一致。

## 9. 验收标准

| 编号 | 验收项 | 预期结果 |
| --- | --- | --- |
| ARD-01 | 生成应收账单 | 返款配置命中的扣减费项不写入 `MEMBER_AR + RECEIVABLE`。 |
| ARD-02 | 应收币种汇总 | `ar_bill_currency_summary` 只汇总 `RECEIVABLE`。 |
| ARD-03 | 应收主表金额 | `receivable_amount/unpaid_amount` 不包含返款扣减费项。 |
| ARD-04 | 应收详情普通费用 tab | 只展示参与核销的应收费项。 |
| ARD-05 | 应收详情返款扣减 tab | 展示 `related_bill_no = 当前应收账单号` 的返款扣减费项，不展示待核销语义。 |
| ARD-06 | 应收核销 | 核销金额上限不包含返款扣减费项。 |
| ARD-07 | 来源回写 | 应收核销后不回写返款扣减费项来源支付状态。 |
| ARD-08 | 返款账单 | 扣减费项以 `COD_REFUND + REFUND_DEDUCTION` 为主归属，并参与应返金额扣减。 |
| ARD-09 | 费项别名 | 同名超材费编码可正确归入扣减口径。 |

## 10. 风险点

1. 费项编码和费项名称不一致，如果只按编码匹配，会漏掉本次问题中的 `FEE0045 超材费`。
2. 如果直接按中文名称兜底，可能把业务含义相同但结算口径不同的费项误归并，需要确认别名白名单。
3. 已核销账单不能直接改金额，否则 `payment_writeoff_detail`、`ar_bill_currency_summary` 和主表状态可能不一致。
4. 返款账单和应收账单生成顺序不固定，需要支持先应收后返款、先返款后应收两种关联补链。
5. 扣减费项主归属调整为返款账单后，历史 `MEMBER_AR + REFUND_DEDUCTION` 形态需要迁移或兼容查询，否则应收扣减 tab 可能查不到旧数据。
6. 汇率重算同时存在主账单金额字段和关联账单金额字段，必须分别处理 `amount_*` 与 `related_amount_*`。
7. 前端如果只在详情页过滤，后端汇总和核销仍会错误，因此必须优先修正后端金额口径。

## 11. 疑问点

1. `FEE0025 货到付款手续费` 是否业务上等同于返款配置中的“代收货款手续费”？
2. `FEE0005/FEE0045/FEE0053` 都叫“超材费”，是否都应归入返款扣减项？
3. `FEE0051 代收货款手续费` 是否也应归入返款扣减项？
4. 返款配置中的 `directDeductFeeItems.feeCode` 当前保存的是实际费项编码，还是前端枚举编码？后续是否应改为保存标准扣减类型？
5. 已生成但未核销的应收账单，是否允许通过后台重算直接修正金额？
6. 已经发生核销的历史账单，如果存在这类费用，财务侧希望走反核销、调账，还是仅从新账单开始生效？
7. 应收账单详情中的返款扣减 tab 是否需要展示“返款账单号”和“返款账单状态”？
8. 返款账单未生成时，这些扣减费项是否暂不展示在应收详情中，还是展示为“待生成返款账单”？
9. 如果某个扣减费项金额为负数，应按返款配置中的 `negativeAmountPolicy` 处理，还是仍按应收账单调账口径处理？
10. 是否需要在任务流水或账单生成结果中展示“本次转入返款扣减口径的费用数量和金额”？

## 12. 最终建议

本次建议按“返款主归属 + 应收关联展示”而不是“删除费用”处理：

1. `fee_detail` 保留全部费用明细。
2. 普通应收用 `MEMBER_AR + RECEIVABLE`。
3. 返款直接扣减用 `COD_REFUND + REFUND_DEDUCTION`。
4. 扣减费用通过 `related_bill_no = 应收账单号` 回指应收账单。
5. 应收汇总、核销、来源回写统一只看 `MEMBER_AR + RECEIVABLE`。
6. 应收详情新增返款扣减 tab，展示通过 `related_bill_no` 指向当前应收账单的返款扣减明细。

这样可以同时满足财务核销口径、详情可追溯和返款扣减展示，且不需要新增数据库表结构。
