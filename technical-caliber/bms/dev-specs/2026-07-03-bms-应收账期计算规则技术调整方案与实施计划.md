# BMS 应收账期计算规则技术调整方案与实施计划

## 1. 调整背景

应收账单定时任务当前在 `BillGenerateServiceImpl.enqueueCurrentPeriodForEnabledConfigs()` 中统一使用运行日所在自然月的首日和末日作为账期，没有根据方案的 `billing_period_type` 计算账期。

以任务运行日 `2026-07-03` 为例，周账期当前错误生成为 `2026-07-01 ~ 2026-07-31`，正确结果应为运行日所在自然周的 `2026-06-29 ~ 2026-07-05`。

本次调整目标是建立唯一的应收账期计算规则，使定时生成、任务监控、手工生成和后续补跑校验使用相同算法，避免同一方案在不同入口得到不同账期。

## 2. 本次范围

### 2.1 包含范围

1. 应收账单 `DAY/WEEK/HALF_MONTH/MONTH/SEVEN_DAYS/TEN_DAYS/FIFTEEN_DAYS` 的账期计算。
2. 定时任务按方案账期类型和方案生效日起算账期。
3. 任务监控按同一算法查询目标账期任务。
4. 手工生成账期选择和后端账期合法性校验与定时任务统一。
5. 默认方案和分支方案均按自身账期字段独立计算；具体独立调度改造仍依赖已有“默认方案与分支方案关系”调整方案落地。

### 2.2 不包含范围

1. 返款账单 `WEEK/HALF_WEEK` 规则，本次不修改其独立算法。
2. 账单发出偏移日、信用期、逾期日的计算。
3. 来源费项归集、汇率、核销和调账规则。
4. 数据库表结构调整；按当前模型可直接使用 `billing_period_type`、`effective_start_date`、`effective_end_date`。

## 3. 已确认业务口径

账期开始日和结束日均为包含边界。任务运行日只用于定位“当前所在账期”，允许账期结束日晚于运行日。

| 账期类型 | 计算口径 | `2026-07-03` 运行结果 |
| --- | --- | --- |
| 日 `DAY` | 运行日当天 | `2026-07-03 ~ 2026-07-03` |
| 周 `WEEK` | 自然周，周一至周日 | `2026-06-29 ~ 2026-07-05` |
| 半月 `HALF_MONTH` | 每月 1~15 日、16~月末 | `2026-07-01 ~ 2026-07-15` |
| 月 `MONTH` | 自然月首日至月末 | `2026-07-01 ~ 2026-07-31` |
| 7 天 `SEVEN_DAYS` | 从方案生效日开始，每 7 个自然日为一个连续账期 | 生效日 `2026-05-05` 时为 `2026-06-30 ~ 2026-07-06` |
| 10 天 `TEN_DAYS` | 从方案生效日开始，每 10 个自然日为一个连续账期 | 依方案生效日滚动计算 |
| 15 天 `FIFTEEN_DAYS` | 从方案生效日开始，每 15 个自然日为一个连续账期 | 依方案生效日滚动计算 |

注意：`FIFTEEN_DAYS` 与 `HALF_MONTH` 不是同一种算法。前者是以方案生效日为锚点的固定 15 个自然日，后者是自然月上半月/下半月。

## 4. 当前实现问题

### 4.1 定时任务固定按月

`BillGenerateServiceImpl.enqueueCurrentPeriodForEnabledConfigs()` 当前直接使用：

```java
YearMonth yearMonth = YearMonth.now();
periodStartDate = yearMonth.atDay(1);
periodEndDate = yearMonth.atEndOfMonth();
```

因此除月账期外，其余应收账期均可能生成错误范围。

### 4.2 任务监控算法不完整

`BillGenerateTaskMonitorServiceImpl.resolvePeriodStart/resolvePeriodEnd()` 当前只单独处理日和周，其余类型全部回退为自然月，导致半月及 7/10/15 天的监控目标账期错误。

### 4.3 手工生成与目标规则不一致

`admin_shell/src/views/billing/billConfig/index.vue` 当前存在以下口径：

1. `SEVEN_DAYS` 按所选自然月拆分；
2. `TEN_DAYS` 按每月上旬、中旬、下旬拆分；
3. `FIFTEEN_DAYS` 与 `HALF_MONTH` 共用每月上下半月逻辑。

这与“7/10/15 天均从方案生效日按连续自然日滚动”的规则冲突，必须同步调整，否则定时生成和手工生成会产生不同账期。

### 4.4 枚举与历史值存在兼容风险

模型层使用 `DAY/WEEK/HALF_MONTH/MONTH/SEVEN_DAYS/TEN_DAYS/FIFTEEN_DAYS`，部分旧接口枚举描述和值存在中文值。实现时需先盘点数据库现存值，并在统一解析入口兼容确认仍在使用的历史值，禁止未知值静默回退为月账期。

## 5. 统一账期算法

### 5.1 输入与输出

建议建立 BMS biz 层统一账期计算组件，例如 `ReceivableBillingPeriodResolver`。

输入：

- `billingPeriodType`：方案账期类型；
- `effectiveStartDate`：方案生效开始日；
- `baseDate`：定位账期的基准日，定时任务取业务时区当天；
- `effectiveEndDate`：用于判断方案在基准日是否仍有效，不参与常规账期锚点计算。

输出使用明确值对象，例如 `BillingPeriodRange`，包含 `startDate` 和 `endDate`，不得使用 `Map` 或长度为 2 的数组表达账期。

### 5.2 日、周、半月、月

1. `DAY`：`start = end = baseDate`。
2. `WEEK`：`start = baseDate` 所在周周一，`end = start + 6 天`。
3. `HALF_MONTH`：
   - `baseDate.day <= 15`：当月 1 日至 15 日；
   - `baseDate.day >= 16`：当月 16 日至月末。
4. `MONTH`：当月 1 日至月末。

### 5.3 固定自然日账期

`SEVEN_DAYS/TEN_DAYS/FIFTEEN_DAYS` 分别映射周期长度 `N = 7/10/15`，以 `effectiveStartDate` 为第一个账期的开始日。

当 `baseDate >= effectiveStartDate` 时：

```text
elapsedDays = DAYS.between(effectiveStartDate, baseDate)
periodIndex = floor(elapsedDays / N)
periodStart = effectiveStartDate + periodIndex * N 天
periodEnd = periodStart + N - 1 天
```

示例：生效日 `2026-05-05`，运行日 `2026-07-03`，7 天账期：

```text
elapsedDays = 59
periodIndex = floor(59 / 7) = 8
periodStart = 2026-05-05 + 56 天 = 2026-06-30
periodEnd = 2026-07-06
```

当 `baseDate < effectiveStartDate` 时不创建任务，并返回明确的“方案尚未生效”结果，不能倒推生效日前的账期。

### 5.4 生效周期处理建议

1. 基准日早于 `effective_start_date`：不创建任务。
2. 基准日晚于 `effective_end_date`：不创建新任务。
3. 方案在固定周期中途生效时，周、半月、月等固定周期的账期开始日不截断，但来源数据的履约节点时间不得早于 `effective_start_date`。
4. 账期结束日超过 `effective_end_date` 时，末期账期结束日截断为 `effective_end_date`，来源数据也不得晚于该日期。
5. 基准日已经超过失效日，但失效日前最后一个账期尚未生成时，调度需要扫描并补生成该末期账期，不能因方案当前已失效而漏账。
6. 因此调度查询不能只返回“运行日当天有效”的配置，还需覆盖存在未生成末期账期的刚失效配置，并通过任务幂等键避免重复补建。

### 5.5 时间基准

禁止在多个方法中散落调用 `LocalDate.now()`。统一由调度入口按系统约定业务时区取得一次 `baseDate` 并传入计算器，便于测试和避免午夜跨日导致同批配置计算出两个日期。

## 6. 技术调整方案

### 6.1 Common/Model

1. 复用 `BillingPeriodTypeEnum`，为账期编码增加严格解析方法和固定自然日长度属性，消除业务代码中的字符串判断和数字魔法值。
2. 新增带字段 JavaDoc 的 `BillingPeriodRange` 明确对象。
3. 对历史中英文编码是否兼容建立显式映射；无法识别的编码抛出业务异常并记录配置 ID。

### 6.2 Biz 层统一计算

1. 新增 `ReceivableBillingPeriodResolver.resolve(config, baseDate)`。
2. 将日、周、半月、月、固定自然日算法集中在该组件中。
3. `BillGenerateServiceImpl.enqueueCurrentPeriodForEnabledConfigs()` 删除固定 `YearMonth.now()` 逻辑，逐方案调用统一计算器。
4. `BillGenerateTaskMonitorServiceImpl` 删除自有 `resolvePeriodStart/resolvePeriodEnd()`，改用同一计算器。
5. 后端手工生成接口增加账期校验：前端提交的开始、结束日期必须等于该方案在所选基准日对应的标准账期；补跑/重跑仍复用原账单账期，不重新按今天计算。
6. 定时创建继续依赖现有任务幂等校验，同一方案同一账期重复扫描不得创建重复任务。

### 6.3 调度触发

当前方法语义明确为“生成当前进行中的账期”，即使账期尚未结束也会创建任务。`2026-06-29 ~ 2026-07-05` 是一个完整自然周账期，不属于跨账期。

同一账期存续期间，后续进入且履约节点属于该账期范围的数据必须增量同步至本期账单；该期间为账单起草期，不能等待下一账期再归集。`bill_send_offset_days` 仅决定账单预定发出时间，不影响当前账期任务创建和增量同步。

建议定时扫描流程为：

1. 计算每个方案当前进行中的标准账期；
2. 若本期任务/草稿账单不存在则创建；
3. 若已存在则触发现有增量采集逻辑，只采集尚未打标且履约时间属于本期的数据；
4. 对已失效但末期漏生成的方案，补建截断至 `effective_end_date` 的最后一期；
5. 已确认、已发送等不可增量状态按现有业务规则处理，不把本期新数据顺延到下一账期。

### 6.4 前端手工生成

涉及：

- `admin_shell/src/views/billing/billConfig/index.vue`
- 本次仅调整 `admin_shell` 应收账单生成入口，不调整 `admin-front`

调整建议：

1. 日/周/半月/月可继续按日历语义选择，但由统一前端函数展示范围。
2. 保留现有标准账期范围选择交互；7/10/15 天展示结果必须改为按方案锚点滚动得到的标准范围。
3. 前端仅负责展示和选择，后端必须重新计算并校验，不能信任任意日期范围。
4. `FIFTEEN_DAYS` 不再复用 `HALF_MONTH` 的上下半月控件。

优先建议增加后端“按方案与基准日预览账期”接口，响应使用明确 DTO。这样前端无需复制锚点算法，也能避免方案版本和生效日变化造成差异。

### 6.5 新旧版本账期重叠与数据归集幂等

新配置版本以自身 `effective_start_date` 作为 7/10/15 天账期锚点重新滚动。若新版本首期与上一版本末期在日期上重叠，必须保证同一来源数据只归集一次：

1. 来源数据先按履约节点时间匹配配置版本生效范围；新版本不得采集早于其生效日的数据，旧版本不得采集晚于其失效日的数据。
2. 若版本生效范围本身重叠，必须按明确版本优先规则唯一选中一个版本；建议当前版本生效日更晚者优先，但正式实现前需与配置发布规则保持一致。
3. 继续使用来源采集标记/来源费项唯一键做数据库级幂等，唯一判断不能只依赖账期开始、结束日期。
4. 同一来源费项已归属上一版本账单后，新版本任务应跳过或复用既有归属，禁止重复生成费用明细。
5. 任务重试、当前账期增量同步和历史重跑均复用原任务配置快照及来源标记。

### 6.6 Mapper 与数据库

本次预计不变更表结构。`queryEnabledConfigs()` 必须确保返回 `billing_period_type/effective_start_date/effective_end_date`，当前已有这些字段。

若后续独立调度默认和分支方案，查询需覆盖全部启用方案；该事项在既有 `2026-07-02-bms-应收账单默认方案与分支方案关系技术调整方案.md` 中实施，本方案不重复扩表。

### 6.7 监控与日志

1. 监控列表目标账期必须来自统一计算器。
2. 创建任务失败日志增加配置 ID、账期类型、生效日、基准日和计算失败原因。
3. 未生效、已失效、末期待补生成与非法账期配置应区分记录，不能都吞并成普通 WARN 后继续无提示。
4. 可在任务快照中保留计算所用账期类型、生效日和基准日，便于审计。

## 9. 已确认口径

以下口径已确认，后续设计和编码按本节执行。

### 9.1 生效周期边界

1. 固定周期的首期账期不因中途生效而截断，但来源数据不得早于方案生效日。
2. 账期跨越 `effective_end_date` 时，末期结束日截断到方案失效日。
3. 运行日超过失效日但失效日前最后一期尚未生成时，定时任务必须补生成。

### 9.2 定时触发语义

1. 定时任务只生成当前进行中的账期；自然周跨自然月仍是同一个账期，不属于跨账期。
2. 同一账期处于账单起草期，所有履约节点属于该账期的新数据都要持续增量同步到本期账单，不等待下一期。
3. `bill_send_offset_days` 不影响任务创建和账期计算。

### 9.3 固定自然日账期

1. 10 天和 15 天与 7 天相同，以方案 `effective_start_date` 为锚点连续滚动，不采用自然月上中下旬或上下半月。
2. 新配置版本以自身生效日重新起算；若新旧版本账期日期重叠，通过配置生效范围匹配和来源采集唯一标记解决归集幂等。
3. `effective_start_date` 为空时优先使用配置 `created_at` 的日期作为锚点；若创建时间也为空，则使用任务运行日所在月 1 日兜底。兜底来源需写入任务快照和告警日志。

### 9.4 历史数据与入口

1. 历史错误账期任务和账单本次不处理。
2. 手工生成只允许使用标准账期范围，沿用并校正现有前端实现，后端仍执行标准范围校验。
3. 本次前端只调整 `admin_shell` 应收账单生成入口。

## 10. 风险与回滚

1. 新旧配置版本的账期日期可能重叠，若只按账期去重而不按来源数据唯一标记，会发生重复归集。
2. 7/10/15 天锚点改为生效日后，必须同步修正 `admin_shell` 既有自然月分段展示，否则手工生成与定时生成不一致。
3. 定时任务、监控和手工入口若分批上线，会短暂产生口径不一致，建议后端计算器、调度、监控和后端校验同批上线，前端紧随同一发布窗口。
4. 回滚仅关闭新算法的任务创建开关，不删除已经生成的任务和账单。

## 11. 建议实施结论

本调整不应只在定时任务中增加 `if/else`。账期属于任务幂等、监控定位、手工生成和来源数据过滤的共同基础，必须收敛为一个后端统一计算器。

最小完整闭环包括：

1. 按方案类型正确计算日、周、半月、月账期；
2. 7/10/15 天以方案生效日为锚点连续滚动；
3. 定时任务和任务监控复用同一算法；
4. 手工生成不再按自然月拆分固定自然日账期；
5. 后端强校验手工提交范围；
6. 支持失效方案最后一期漏生成补偿，并保证新旧配置版本账期重叠时来源数据不重复归集。
