# 2026-07-01 BMS 金额汇兑技术调整方案与实施计划

## 1. 文档说明

本文对照 `aidocs/product-caliber/bms/prd/财务系统.PRD.md` 第 13 章“金额汇兑”，静态核查当前工作区的 BMS 后端、Admin Shell 前端及 `aidocs/technical-caliber/sql/ar_bill.sql`，给出差异、技术调整方案、实施计划和待确认问题。

本次仅新增技术方案，不修改业务代码、前端代码和数据库结构。当前 `bms`、`admin_shell` 已存在未提交修改，且 `dev-specs` 下已有同日汇率方案；本文以当前工作区实际内容为“现状实现”，不覆盖既有文件。未连接运行库、未执行接口联调，因此数据库存量质量和生产行为需在实施前另行验证。

## 2. PRD 第 13 章目标口径

第 13 章要求形成一条完整且可追溯的金额链路：

```text
费项原始金额/币种
  -> 命中费项结算币种规则及模板快照
  -> 按货币对生成账单汇率列表
  -> 逐费项换算为结算币种金额
  -> 按 bill_no + currency 汇总
  -> 必要时换算财务本位币
  -> 核销落到具体 currency_summary_id
  -> 历史账单、核销和汇率快照不可回写
```

核心规则包括：

1. 结算币种优先级：账单配置显式费项规则 > 已选择模板 > 目的国公共模板 > 账单默认结算币种。
2. 汇率优先级：费项级 > 账单级锁定 > 客户级默认 > 基准汇率 > 店铺汇率 > 异币种缺失按 `1`。
3. 汇率行只能由账单实际费项货币对 `DISTINCT` 生成，同一货币对方向和值在账单内保持一致。
4. 金额必须先逐费项换算，再按结算币种汇总，不能跨币种直接相加。
5. 核销必须关联具体币种汇总行，V1 不自动跨币种抵扣。
6. COD 回款汇率和返款汇率按不同业务时点分别锁定，并据此计算汇兑损益。

### 3.2 必须调整的差异

#### P0：账单汇率关闭语义错误

`ArBillServiceImpl.effectiveRate(...)` 在汇率行 `enabled = 0` 时直接返回 `1`。第 13.3.3(7) 要求关闭后回显并继续使用账单生成时命中的客户级默认汇率，不是无条件按 `1`。当前行为会直接改写费项结算金额和本位币金额，是最高优先级财务风险。

结合已有同日方案中的确认结论“账单级锁定汇率无法关闭”，建议最终取消账单详情的启用/关闭业务语义：系统默认快照始终有效，人工编辑只是形成更高优先级的账单级覆盖。若产品坚持保留开关，则必须保存“生成时默认快照值”和“人工覆盖值”两套字段，关闭时恢复默认快照，不能返回 `1`。

#### P0：生成、应收重算、返款重算使用三套解析逻辑

账单生成由 `BillGenerateServiceImpl.resolveBillExchangeRate(...)` 解析；应收重算由 `ArBillServiceImpl.resolveRateDecision(...)` 解析；返款账单还有一套相似逻辑。三套逻辑对快照、费项级、客户/基准、店铺直连/反向、按 `1` 兜底和来源持久化的处理不完全一致，可能导致“首次生成一个金额，点击重算后变成另一个金额”。

必须抽取统一汇率决策服务，生成与两类账单重算只消费同一个决策 DTO。

#### P0：主表直接汇总不同币种金额

`ArBillMapper.refreshBillAfterCurrencySummary`、`BillGenerateMapper` 等逻辑会对 `ar_bill_currency_summary.receivable_amount/paid_amount/unpaid_amount` 直接 `SUM` 回写主表。若一张账单同时存在 USD、TWD 等多个结算币种，该合计没有合法币种含义，与第 13.4“按币种分组”和“财务本位币只用于内部统计”冲突。

主表金额字段需明确语义：

- 客户侧真实金额只能由 `currencySummaries` 展示；
- 跨币种总览只能汇总 `*_amount_fin`；
- 旧的无币种主表金额不得作为核销、状态或导出依据；单币种账单可兼容回填，多币种账单应置空或只标记“多币种”，具体需产品确认。

#### P0：回款与返款两时点汇率快照未形成稳定领域模型

第 13.7 要求正常签收 COD 包裹分别保留回款时点和返款时点汇率，并计算：

```text
回款金额 = 到付金额 × 回款汇率
返款金额 = 到付金额 × 返款汇率
汇兑损益 = 回款金额 - 返款金额
```

现有页面包含回款汇率、返款汇率及汇兑损益展示，但服务层仍存在源表拼装、账单级回退和页面兜底推导，未看到独立、不可变、可按包裹追溯的“两时点汇率快照”模型。需新增或明确包裹级快照落点，禁止详情页临时用当前市场/店铺汇率重算历史结果。

#### P1：费项级汇率口径冲突

第 13.3.1 明确“费项级 > 账单级”，当前重算代码仍识别 `FEE` 层级并优先沿用；但同日既有方案记录的已确认口径是“费项级仅预留，本期不开发，账单级 > 客户 > 基准 > 店铺 > 1”。两者冲突，无法同时验收。

实施前必须由产品决定：

- 若按 PRD：定义哪些来源可产生费项级汇率、如何录入、谁可修改、是否进入 `bill_exchange_rate`；
- 若按已确认范围：修改第 13.3.1、13.3.3(11) 和验收标准，代码只保留历史兼容读取，不再生成新 `FEE` 快照。

#### P1：汇率行关闭规则与既有确认结论冲突

第 13.3.3(6)-(8) 描述汇率行可启用/关闭；已有方案已确认“账单级锁定汇率无法关闭，应清理旧入口”。需要先统一 PRD，否则前端开关、后端 `enabled`、重算含义无法定稿。

#### P1：货币对列表不是严格由实际费项 DISTINCT 驱动

当前详情查询优先读 `bill_exchange_rate`，为空时读 `fee_detail`，仍为空时由费项/汇总拼装兜底。这会产生以下问题：

1. 历史残留或人工写入的 `bill_exchange_rate` 行可能在账单已无对应费项时继续展示。
2. 新增费项后依赖重算流程才可能补齐，缺少统一的“同步账单货币对集合”动作。
3. 当前通用 `BillExchangeRateService.save` 可直接新增任意货币对，不符合“不允许人工新增账单内不存在货币对”。

应以 `fee_detail` 为事实来源计算规范货币对集合，只允许编辑集合内汇率；重算前执行增量补齐和废弃标记，不能物理删除历史快照。

#### P1：CNY 锚点交叉推导不完整

PRD 允许 `USD -> TWD = (USD -> CNY) / (TWD -> CNY)`，并要求保存参与推导的原始货币对。当前客户汇率配置与生成链路已具备直接、反向和部分推导字段，但代码核查仍显示外币交叉推导未成为所有入口共用的稳定能力；店铺汇率生成阶段主要匹配直连，应收重算另有反向逻辑。

统一决策服务需支持 `DIRECT/REVERSE/CNY_CROSS/FALLBACK_ONE`，统一精度、除零校验和来源快照。

#### P1：费项模板兜底策略多出“通用模板”

当前生成快照记录的策略为：

```text
EXPLICIT_RULE_FIRST_THEN_SELECTED_TEMPLATE_THEN_DEST_COUNTRY_TEMPLATE_THEN_GENERIC_TEMPLATE
```

PRD 第 13.2.2 的第四级是 `bill_config.billing_currency`，未定义“通用模板”层级。需确认通用模板是既有兼容规则还是应删除；若保留，应补入 PRD 并明确它与账单默认币种的先后顺序。

#### P1：核销币种校验和跨币种口径需收紧

应收核销当前以请求 `currency` 查找相同币种汇总行，基本实现同币种核销；但接口允许缺省币种回退到主表 `billCurrency`，多币种账单可能选择错误。第 13.5.2 又描述“到付币种与结算币种不一致时可按锁定汇率折算”，与“收款币种必须与结算币种一致”和“V1 不做跨币种自动抵扣”存在边界歧义。

V1 建议强制：收款币种必须显式传入且等于目标汇总行币种，不做接口内部自动换算。若需要人工指定跨币种核销，应作为独立动作，显式传目标 `currencySummaryId`、核销汇率及快照，不可复用当前自动分配流程。

#### P1：账单折返后部分核销保护需要专项校验

PRD 第 13.5.2(5) 要求从待结清折返待审核时保留既有部分核销流水，只重算未核销余额。当前有核销和反核销流水，但汇率重算/汇总重建存在删除再插入 `ar_bill_currency_summary` 的实现路径。若汇总 ID 被重建，历史 `payment_writeoff_detail.currency_summary_id` 会失联或指向已删除记录。

汇总重算必须改成按 `bill_no + currency` UPSERT，并保留原 ID；已发生核销的币种行禁止删除。重算结果应以“新应收 - 历史有效核销”计算余额。

#### P2：金额精度与展示单位不统一

数据库金额普遍为 `DECIMAL(18,4)`、汇率为 `DECIMAL(18,8)`，Java 多处按金额 4 位、倒数 12 位处理；前端又使用 JavaScript `Number` 做倒数和格式化。应明确：

1. 汇率存储 8 位还是 12 位；
2. 中间乘除精度和最终金额舍入时点；
3. 是否始终 `HALF_UP`；
4. 前端只展示/录入字符串，最终计算必须由后端 `BigDecimal` 完成。

PRD 示例使用 `RMB`，系统字段固定 `CNY`，建议文档和接口统一使用 ISO 代码 `CNY`。

#### P2：代码规范债务会阻碍本轮调整

金额链路 Mapper 中存在大量注解长 SQL，生成服务大量使用 `Map<String,Object>` 传递持久化数据，和项目“显式 DTO/实体、复杂 SQL 放 XML、显式 resultMap”的约定不一致。此次重构应按业务切片逐步迁移，避免继续复制同类实现；不建议为本需求一次性改完整个 5000 行生成服务。

### 3.3 PRD 自身需修订

1. 第 13.7.3(1) 引用“12.7.1”，应为“13.7.1”。
2. 第 13.6.4 示例写 `RMB`，而第 8 章和系统统一使用 `CNY`。
3. 第 13.3.2 同时写“生成或审核时必须锁定”，需明确是生成即锁定、审核再确认，还是审核时才最终锁定。
4. 第 13.3.3 的开关语义与已有确认结论冲突。
5. 第 13.3.1 的费项级优先级与已有“本期不开发”结论冲突。
6. 第 13.5.2 同时要求收款币种一致，又允许不一致折算，需要明确 V1 是否提供跨币种人工核销。
7. 第 13.2 未定义模板适用维度的唯一性、版本、生效时间、目的国缺失和多规则冲突处理。
8. 第 13.7 未定义“回款时点”“返款时点”的准确事件和时区，也未定义异常签收后恢复正常的补算规则。

## 4. 建议技术设计

### 4.1 统一金额汇兑领域服务

新增统一服务，禁止三条业务链分别解析：

```text
ExchangeRateResolveService
  ├─ resolveDefaultRate(req)       默认来源解析
  ├─ resolveBillEffectiveRate(req) 费项/账单有效汇率解析
  ├─ syncBillCurrencyPairs(req)    根据费项同步账单货币对
  └─ convertAmount(req)            BigDecimal 换算与舍入
```

使用显式 DTO：

- `ExchangeRateResolveReqDTO`
- `ExchangeRateDecisionDTO`
- `BillCurrencyPairSyncReqDTO`
- `AmountConvertReqDTO/RespDTO`

决策结果至少包含最终有效汇率、来源层级、原始方向、客户规则 ID、基准汇率 ID、店铺来源标识、推导类型/表达式、按 `1` 原因和快照时间。

### 4.2 汇率解析算法

在费项级是否开发确认后固化一条算法。若按当前已确认范围，建议：

```text
1. 同币种：1 / DIRECT
2. 已存在账单快照：沿用快照；人工覆盖优先
3. 固定客户特调：CUSTOMER
4. 基准直接、反向或 CNY 交叉结果
5. 百分比/固定差客户规则：仅在第 4 步有基础汇率时计算
6. 未命中客户特调时使用基准结果：BASE
7. 店铺直连或经确认允许的反向：SHOP
8. 均未命中：1 / FALLBACK_ONE，并记录原因
```

账单生成后不得因为客户、基准或店铺配置变化自动更新。所谓“重算”只能使用账单中已固化的系统默认快照和人工覆盖，不重新读取最新外部配置；若产品需要刷新默认来源，应设计独立“刷新默认汇率”动作并限制状态、展示差异、记录操作日志。

### 4.3 账单货币对同步

由 `fee_detail` 生成两个集合：

```text
DISTINCT (fee_currency -> bill_currency, FEE_TO_BILL)
DISTINCT (bill_currency -> fin_currency, BILL_TO_FIN)
```

规则：

1. 同币种对保留为可解释的 `DIRECT=1` 或不落表但稳定回显，二选一统一。
2. 新增费项后补齐缺少货币对。
3. 已不存在于费项的货币对若从未参与历史金额可标记失效；已参与历史账单或核销的必须永久保留。
4. 保存接口拒绝不在规范集合内的货币对。
5. 同一账单、类型、源币种、目标币种只允许一个快照记录。

### 4.4 金额与汇总模型

费项逐行计算：

```text
amount_bill_currency = round(amount_fee_currency × effective_rate_to_bill, 4)
amount_fin_currency  = round(amount_bill_currency × effective_rate_to_fin, 4)
```

汇总按 `bill_no + bill_currency` UPSERT：

```text
original_receivable = SUM(本期费项结算币种金额)
receivable          = original_receivable + prior_adjustment + current_adjustment
unpaid              = receivable - SUM(有效核销金额)
```

禁止删除后重建已有汇总 ID。主表仅保存状态和总览；跨币种财务总览使用本位币字段，客户金额通过 `currencySummaries` 返回。

### 4.5 核销模型

应收核销请求应显式传 `currencySummaryId`，服务端校验其属于目标账单、币种与收款币种一致、未收余额充足，并 `SELECT ... FOR UPDATE`。流水必须保存收款币种金额、结算币种金额、本位币金额和实际使用的汇率快照。

账单折返或金额重算时：

1. 不删除、覆盖、重新生成历史核销流水；
2. 不改变历史流水的汇率和金额；
3. 按有效流水重新计算汇总行已核销与未核销金额；
4. 若重算后应收小于已核销，进入人工异常处理，不能把余额静默截为 0。

### 4.6 COD 两时点快照

建议新增独立表或将现有来源表明确升级为不可变快照，至少包含：

- 尾程包裹/业务订单标识；
- 到付原始金额和币种；
- 货款结算币种；
- 回款事件时间、汇率、来源、结算币种金额；
- 返款事件时间、汇率、来源、结算币种金额；
- 汇兑损益；
- 异常签收标记、快照状态和审计字段。

回款管理只读取快照结果，不在查询时重新计算。异常签收不生成金额快照；若后续恢复正常，必须以明确的恢复事件作为计算时点。

### 4.7 前端调整

Admin Shell 需要：

1. 根据最终确认删除汇率启用开关，或改为“使用人工覆盖/恢复生成快照”。
2. 汇率行只展示实际费项产生的货币对，禁止新增任意行。
3. 补全 `CUSTOMER/BASE/SHOP/FALLBACK_ONE/DIRECT/REVERSE/CNY_CROSS` 中文来源和推导说明。
4. 多币种主列表不再展示无币种含义的合计，改为币种标签分组；内部总览明确标注 `CNY`。
5. 核销弹窗提交 `currencySummaryId`，多币种账单必须先选择具体币种桶。
6. 前端不使用 `Number` 作为最终汇率计算依据；倒数预览仅供展示，保存后以服务端结果回显。
7. 回款管理展示两时点、两份汇率快照及汇兑损益来源。

## 5. 数据库调整建议

实施前先以运行库结构为准做结构检查。预计至少涉及：

| 表 | 建议调整 |
| --- | --- |
| `bill_exchange_rate` | 固化唯一键；区分系统默认快照与人工覆盖；保留来源、推导、兜底原因和快照时间；废弃含义不清的关闭逻辑 |
| `fee_detail` | 明确两层有效汇率和来源字段；必要时增加所引用 `bill_exchange_rate_id`，保证追溯 |
| `ar_bill_currency_summary` | 保持 `bill_no + currency` 稳定 UPSERT；禁止重算删除已有 ID；补充本期原始应收与冲正拆分字段时需迁移 |
| `payment_writeoff_detail` | `currency_summary_id` 改为业务上强制非空；增加必要外键/一致性检查策略和汇率快照追溯字段 |
| COD 包裹汇兑快照表 | 若现有表不能完整承载回款/返款两时点，则新增显式快照表 |
| 模板相关表 | 增加/校验版本、生效状态、目的国和业务场景唯一性，保存账单命中快照引用 |

所有表结构调整必须同步：

1. 提供增量迁移 SQL、存量重复和孤儿数据检查 SQL；
2. 更新 `aidocs/technical-caliber/sql/ar_bill.sql` 中完整最新 DDL；
3. 保证实体、DTO、Mapper resultMap 和 SQL 归档一致；
4. 金额字段使用 `DECIMAL(18,4)`，汇率精度按产品确认统一；
5. 迁移前检查历史 `currency_summary_id` 为空、汇总重复、货币对重复和相反方向并存数据。

## 7. 实施计划

### 阶段 0：口径冻结与数据体检

1. 确认第 9 节所有阻塞问题。
2. 核对运行库真实 DDL、数据量、重复货币对、空 `currency_summary_id` 和历史孤儿引用。
3. 用现有账单抽样还原“原始金额 -> 结算金额 -> 本位币 -> 汇总 -> 核销”链路。
4. 冻结汇率精度、舍入方式和业务时点。

### 阶段 1：统一决策服务

1. 新增显式请求/决策 DTO 和枚举。
2. 实现同币种、账单快照、客户、基准直接/反向/CNY 交叉、店铺和按 `1`。
3. 统一来源、推导表达式和缺失原因。
4. 生成、应收重算、返款重算接入同一服务，先保持接口兼容。

### 阶段 2：货币对与快照治理

1. 从 `fee_detail` DISTINCT 同步账单实际货币对。
2. 禁止人工新增无费项货币对。
3. 处理系统默认快照与人工覆盖关系，移除“关闭即 1”。
4. 输出 DDL、增量 SQL、数据回填和回滚方案。

### 阶段 3：金额汇总治理

1. 所有金额按逐费项、两层换算、每层舍入规则重算。
2. 币种汇总改稳定 UPSERT，保留汇总 ID。
3. 分离本期原始应收、冲正、最终应收和本位币总览。
4. 清理主表跨币种直接求和及其状态判断依赖。

### 阶段 4：核销与折返保护

1. 核销请求改传 `currencySummaryId` 并加强行锁和币种校验。
2. 历史流水只读，汇总余额由有效流水重算。
3. 验证待结清折返待审核后部分核销仍完整可追溯。
4. 建立“重算后应收小于已核销”的人工异常机制。

### 阶段 5：COD 两时点汇兑

1. 明确回款和返款事件并落独立快照。
2. 正常/异常签收按统一规则生成或不生成快照。
3. 返款账单和回款管理只读取快照结果。
4. 校验包裹级、账单级汇总与汇兑损益一致。

### 阶段 6：前端与文档

1. 调整汇率编辑、来源说明、多币种展示和核销弹窗。
2. 统一 `CNY` 文案和金额/汇率格式。
3. 修订 PRD 第 13 章错误和冲突，并同步多币种设计、账单生成、核销、COD 流程文档。
4. 补充接口清单、字段字典、状态矩阵和操作权限。

### 阶段 7：验证与上线

项目当前没有测试框架，至少准备可重复执行的服务级验证脚本和 SQL 对账脚本，覆盖：

1. 单币种、同币种汇率 `1`。
2. 多币种费项先逐行换算再分桶汇总。
3. 客户固定、客户调整、基准直连、反向、CNY 交叉、店铺、按 `1`。
4. 同一账单同一货币对只使用一个快照。
5. 人工覆盖、恢复默认快照及状态权限。
6. 新增费项自动补充货币对，删除/冲正不破坏历史快照。
7. 部分核销、反核销、折返审核、汇率重算后流水不丢失。
8. 禁止跨币种自动核销和超额核销。
9. COD 正常签收、异常签收、恢复正常、回款与返款汇率不同。
10. 汇兑损益、财务本位币合计和导出结果一致。
11. 历史已审核、待结清、已结清账单不被新配置回写。

上线建议先影子计算：新旧逻辑同时计算但只读旧结果，输出差异报表；财务确认样本后再切换写入。出现汇总或核销差异时可按账单维度回退，不修改历史流水。

## 8. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 缺失异币种汇率按 `1` 造成重大金额偏差 | 快照保存明确原因；审核页可筛选 `FALLBACK_ONE`；是否需要告警按已确认范围执行 |
| 重算读取最新配置导致历史漂移 | 默认只读账单快照；刷新默认值设计独立动作 |
| 删除重建汇总造成历史核销失联 | 稳定 UPSERT、保留 ID、迁移前查孤儿数据 |
| 跨币种主表求和误导财务 | 客户金额按币种展示，跨币种只汇总本位币 |
| Java/SQL/JS 舍入不一致 | 后端 BigDecimal 为唯一计算结果，SQL/前端不做最终财务计算 |
| 在途未提交代码被覆盖 | 实施前逐文件比对和小步提交，不重置现有工作树 |
| 生成服务体量过大导致回归 | 先抽统一领域服务，再按应收/返款/COD 分批接入 |

## 9. 待确认问题

### 9.1 阻塞开发

1. 费项级汇率本期是否实现？若不实现，是否同意同步修改第 13.3.1 和 13.3.3(11)？
2. 账单汇率行是否允许关闭？若已有结论“不能关闭”有效，是否删除前端开关和后端 `enabled=0` 业务入口？
3. 多币种账单主表 `receivable_amount/paid_amount/unpaid_amount` 应置空、保留首个/默认币种，还是改为本位币含义？建议不再承载客户侧金额。
4. V1 是否完全禁止跨币种核销？第 13.5.2(2) 的“不一致时折算”是指人工核销能力，还是仅用于到付/返款金额计算？
5. 回款时点和返款时点分别以哪个事件为准：渠道到账、财务确认到账、返款账单生成、返款审核还是实际打款？
6. 汇率存储精度是 8 位还是 12 位？每层换算后立即四舍五入 4 位，还是保留中间高精度到最终金额再舍入？
7. 目的国公共模板之后是否存在“通用模板”？若存在，它与 `bill_config.billing_currency` 谁优先？

### 9.2 影响实现范围

1. `admin-front` 的应收账单页面是否仍是生产入口，还是以 `admin_shell` 为唯一正式入口？
2. 同币种货币对是否需要在账单汇率表中显示一行 `1`，还是仅在费项上显示“同币种，无需换算”？
3. 人工修改账单汇率后，允许修改到哪个状态：待审核、已审核、待结清？已有部分核销时是否禁止修改？
4. 缺失汇率按 `1` 是否需要筛选、导出标记或审核阻断？既有方案记录“不告警、不二次确认”，需确认该决定仍适用于第 13 章整体。
5. 异常签收后恢复正常时，回款汇率取原签收时间、恢复时间还是实际回款时间？
6. 账单新增费项后，已有人工覆盖汇率是否继续沿用，还是要求财务再次确认？
7. 历史数据缺少汇率来源或汇总 ID 时，是只做兼容展示，还是要求补录/回填后才能继续核销？

## 10. 验收完成定义

只有同时满足以下条件，金额汇兑调整才算完成：

1. PRD 冲突项已修订并完成产品确认。
2. 生成、应收重算、返款重算使用同一汇率决策服务。
3. 账单实际货币对、费项金额、汇率快照和币种汇总可双向追溯。
4. 多币种金额不再无币种直接相加。
5. 核销均落到稳定的 `currency_summary_id`，折返和重算不破坏历史流水。
6. COD 回款/返款两时点快照和汇兑损益可按包裹追溯。
7. 数据库增量 SQL、完整 DDL、实体和 Mapper 同步。
8. 前端、导出和接口字段口径一致。
9. 关键场景验证和新旧结果差异对账通过。

## 11. 结论

当前代码已具备金额汇兑的主要数据表、账单生成、两层金额快照、多币种汇总、账单详情和分币种核销骨架，不需要推倒重建。但它尚未形成统一、稳定、可验证的领域闭环。

建议按“先冻结冲突口径，再统一汇率决策，再治理稳定汇总 ID 和核销，最后补 COD 两时点快照”的顺序实施。首个必须修复的问题是“关闭汇率直接按 `1`”和“跨币种主表直接求和”；在这两点解决前，不建议将现有多币种重算能力直接用于正式财务结算。
