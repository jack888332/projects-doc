# 2026-07-22 BMS 订单单号关联业务订单号与子运单号现状分析

**日期：** 2026-07-22  
**需求依据：** `aidocs` 提交 `7368cc71caf6021790aacd8a91d61f2a08b9c338`（优化“单号追溯关系”章节）  
**核查范围：** `aidocs`、`bms`、`scc-ecp-core-ois`  
**文档性质：** 基于当前代码的只读现状分析，不代表单号统一追溯能力已经在 BMS 落地。

## 1. 分析目标

供应商账单或业务报表可能携带不同类型的订单、物流、报关和运输单号。本次分析需要确认：基于当前代码，通过哪些单号能够找到以下两个归属字段：

1. **业务订单号**：当前 OIS 运单对象中的 `biz_order_no`，以及业务订单主表中的 `sale_order_header.order_code`；在产品口径中对应集运单号或中转单号。
2. **尾程子运单号**：当前 OIS 运单对象中的 `waybill_no`；在明确创建子运单的代码分支中，承运商返回的 `subWaybillNo` 会写入该字段。

分析时区分以下三个层级：

- **BMS 已实现**：BMS 当前代码已经实际使用该关联路径。
- **OIS 已具备**：OIS 已有查询接口和返回字段，但 BMS 尚未接入统一追溯。
- **仅设计提出**：产品文档描述了追溯能力，但现有通用代码接口尚未完整支持。

提交形成的产品口径为：

1. 集运单号和中转单号共用业务订单号字段，通过订单类型区分。
2. 尾程包裹保存业务订单号、主运单号和子运单号。
3. 子运单号用于标识具体尾程包裹；主运单号可能覆盖多个包裹或业务订单。
4. 单号能查到数据不等于能唯一确定归属对象。
5. 业务订单级单号必须唯一命中一个业务订单；包裹级单号必须唯一命中一组“业务订单号 + 子运单号”。
6. 清关、清关袋、提单、柜、航班、托盘和交接单等范围型单号不能单独作为直接成本唯一归属依据。

## 3. 当前核心数据关系

### 3.1 OIS 运单对象

当前 OIS 的 `tms_waybill_order` 一行同时保存：

| 字段 | 当前代码含义 | 追溯用途 |
| --- | --- | --- |
| `biz_order_no` | 业务单号 | 追溯目标：业务订单号。 |
| `waybill_no` | OIS 运单号 | 在子运单创建分支中保存 `subWaybillNo`，可作为尾程子运单号。 |
| `master_waybill_no` | OIS 系统主运单号 | 用于圈定同一主运单下的包裹，不能默认唯一。 |
| `declaration_order_no` | 报关单号 | 可查询运单行并取得业务订单号和子运单号，但可能命中多行。 |
| `clearance_order_no` | 清关单号 | 清关范围标识，通常可能命中多行。 |
| `bundle_barcode` | 袋中袋号 | 包裹集合标识，通常可能命中多行。 |
| `first_lading_order_no` | 一程提单号 | 干线范围标识。 |
| `second_lading_order_no` | 二程提单号 | 干线范围标识。 |
| `flight_code` | 航班/航次 | 干线范围标识。 |
| `outbound_delivery_no` | 出库交接单号 | 作业范围标识。 |
| `erp_order_no` | ERP 订单号 | 来源存在多种赋值口径，只能条件追溯。 |
| `out_order_no` | 外部物流订单号 | 外部引用号，只能条件追溯。 |

在 `WaybillOrderServiceImpl#creatOrderBySubWaybillNos2` 中，代码明确执行：

```java
tmsWaybillOrderDTO.setWaybillNo(subWaybillNoDTO.getSubWaybillNo());
tmsWaybillOrderDTO.setMasterWaybillNo(...);
```

因此，在当前 OIS 代码中，可将 `waybill_no` 作为尾程子运单号使用，但必须注意部分普通面单场景会把 `waybill_no` 和 `master_waybill_no` 写成同一个值，不能仅根据字段非空判断该记录一定属于“一主多子”模式。

### 3.2 BMS 当前业务订单关联

BMS 当前未调用 OIS 的通用单号查询接口。应收、返款导出补充订单信息时直接连接来源库，使用以下关系：

```text
sale_order_header.order_code
    = cxms.ob_shipping_package_header.platform_order_no
```

随后从包裹记录读取：

- `sub_waybill_no`；
- `declaration_order_no`；
- `clearance_order_no`；
- `platform_order_no`。

这条路径证明当前 BMS 已能从业务订单号关联到子运单号，但当前 SQL 按 `platform_order_no` 分组后只取 `MAX(id)`，不会返回同一业务订单的全部包裹。

## 4. 单号追溯能力清单

### 4.1 当前可以直接形成目标关系的单号

| 单号类型 | 当前查询路径 | 可得到业务订单号 | 可得到子运单号 | 使用结论 |
| --- | --- | --- | --- | --- |
| 业务订单号（集运单号/中转单号） | BMS 按 `sale_order_header.order_code` 查询，并关联 `ob_shipping_package_header.platform_order_no` | 是 | 是，但当前只取一条包裹记录 | BMS 已实现正向关联，但一对多处理不完整。 |
| 尾程子运单号 | OIS 按 `tms_waybill_order.waybill_no` 精确查询 | 是，读取 `biz_order_no` | 是，查询值即 `waybill_no` | 当前最接近直接唯一追溯的单号，仍需限定业务范围并检查唯一命中。 |

### 4.2 当前可以条件追溯的单号

以下单号已被 OIS 通用接口 `TmsWaybillOrderClient#queryList` 的查询请求支持。查询结果对象同时返回 `bizOrderNo` 和 `waybillNo`，因此技术上可以归并出“业务订单号 + 子运单号”候选集合。

| 单号类型 | 查询请求字段 | OIS 查询列 | 结论 |
| --- | --- | --- | --- |
| 系统报关单号 | `declarationOrderNos` | `declaration_order_no` | 条件可追溯；只有唯一命中一组目标时才能作为唯一归属依据。 |
| ERP 订单号 | `erpOrderNoList` | `erp_order_no` | 条件可追溯；代码中存在不同赋值来源，不应预设唯一。 |
| 外部系统订单号 | `orderNoList` | `out_order_no` | 条件可追溯；必须检查返回目标数量。 |
| 集运交接单号 | `outboundDeliveryNoList` | `outbound_delivery_no` | 可查询候选集合，属于作业范围型单号。 |
| 一程提单号 | `firstLadingOrderNoList` | `first_lading_order_no` | 可查询候选集合，属于干线范围型单号。 |
| 二程提单号 | `secondLadingOrderNoList` | `second_lading_order_no` | 可查询候选集合，属于干线范围型单号。 |
| 航班号/航次 | `flightCodes` | `flight_code` | 可查询候选集合，属于干线范围型单号。 |
| 清关单号 | `clearanceOrderNos` | `clearance_order_no` | 可查询候选集合，属于清关范围型单号。 |
| 袋中袋号/合包号 | `bundleBarcodes` | `bundle_barcode` | 可查询候选集合，属于包裹集合型单号。 |

上述接口同时支持前缀模糊查询，但 BMS 单号追溯不能使用模糊结果建立直接成本归属。用于归属判定时必须使用完整标准化单号执行精确查询。

### 4.3 当前有独立查询路径的范围型单号

| 单号类型 | 当前路径 | 结论 |
| --- | --- | --- |
| 尾程主运单号 | `TmsWaybillOrderClient#queryWaybillOrMaster`，实际按 `master_waybill_no + warehouse_code` 查询 | 可以返回该主运单下的业务订单号和子运单号列表，但通常是一对多，不能直接认定唯一归属。 |
| OIS 系统物流订单号 | Mapper 和部分内部 Service 可按 `ois_order_no` 查询 | OIS 内部可关联，但通用 `queryList` 请求没有开放该条件，BMS 不能直接复用统一接口查询。 |
| 内部出库单号 | BMS 按 `sale_order_header.delivery_order_code` 兜底查询 | 当前只能补到业务订单号及订单基本信息，没有继续关联包裹表，所以得不到子运单号。 |

### 4.4 当前通用接口未完整支持的单号

| 单号类型 | 现状 | 结论 |
| --- | --- | --- |
| 平台订单号 | `TmsWaybillOrder` 实体存在 `platform_order_no`，但 OIS 通用查询请求没有对应查询字段，通用响应 DTO 也未暴露该字段 | 产品设计认为可条件追溯，但当前统一接口未落地。 |

| 包裹号 | OIS 实体和返回 DTO 存在 `package_no`，通用查询请求未开放 | 只能通过内部代码路径查询，不能直接作为 BMS 通用追溯入口。 |

| 业务订单号 | OIS 返回 `bizOrderNo`，但通用查询请求没有 `bizOrderNoList` | OIS 通用接口当前只能返回业务订单号，不能按业务订单号反查。BMS 通过来源库 SQL 实现了另一条查询路径。 |

## 5. 当前代码的最终判定

按现有代码成熟度排序：

1. **尾程子运单号**：OIS 可以精确查询运单行并返回业务订单号和子运单号，是当前最可靠的反向追溯入口。
2. **业务订单号（集运单号/中转单号）**：BMS 可以关联包裹并取得子运单号，但当前只取最新一条包裹记录，尚未正确处理一单多包裹。
3. **系统报关单号**：OIS 可以返回业务订单号和子运单号候选；只有结果唯一时才可认定直接归属。
4. **ERP 订单号、外部系统订单号**：OIS 已支持查询，但字段来源或业务关系可能是一对多，只能条件追溯。
5. **尾程主运单号、清关单号、袋中袋号、提单号、航班号、交接单号**：可以查出关联列表，但属于范围型单号，不能单独作为唯一直接成本归属依据。
6. **平台订单号、客户单号、客户报关单号等**：设计文档已有目标口径，但当前 OIS 通用查询契约尚未完整支持。

## 6. 现有实现与提交要求的差距

| 编号 | 当前实现 | 提交要求 | 差距结论 |
| --- | --- | --- | --- |
| G-01 | BMS 没有统一单号追溯 Service、DTO、Feign 和持久化关系。 | BMS 对供应商关键单号执行标准化、精确查询和唯一命中判定。 | 尚未落地。 |
| G-02 | BMS 仅从业务订单号正向查询订单和一条包裹快照。 | 业务订单与尾程包裹是一对多。 | `MAX(id)` 会丢失同订单下其他子运单。 |
| G-03 | OIS 通用查询返回原始行列表。 | 必须按业务订单号或“业务订单号 + 子运单号”归并并计算匹配对象数量。 | 缺少统一归并与唯一命中逻辑。 |
| G-04 | OIS 通用查询未自动过滤取消、测试或其它无效记录。 | 必须按有效状态和必要业务范围排除无效、跨范围记录。 | 有效状态规则尚未实现。 |
| G-05 | 查询条件支持仓库、货主和承运商，但没有完整的供应链、店铺等统一隔离参数。 | 在所属供应链、店铺、承运商等必要业务范围内判定唯一性。 | 现有查询范围不足以直接满足 BMS 唯一归属要求。 |
| G-06 | OIS 同时提供精确和前缀模糊条件。 | 直接归属只能使用标准化后的完整单号精确查询。 | BMS 接入时必须禁用模糊查询进行归属判定。 |
| G-07 | 平台订单号等字段存在于实体，但未进入统一查询契约。 | 平台订单号、客户单号等应具备条件追溯能力。 | 需要补充查询契约或建设专用追溯接口。 |
| G-08 | `biz_order_no` 在部分下单流程中由承运商响应或业务订单数据写入，不保证所有历史记录都有值。 | 包裹级结果必须能归并到业务订单。 | 上线统一追溯前需验证历史数据完整率和空值处理。 |

## 7. 建议的后续技术口径

如果后续实施 BMS 单号追溯，建议不要由 BMS 直接拼接 OIS 表查询条件，而是在 OIS 增加明确的批量追溯接口，由 OIS 负责当前对象关系和有效状态口径。

建议请求至少包含：

- 单号类型；
- 标准化单号列表；
- 供应链、店铺、货主、仓库、承运商等必要范围；
- 是否只查询有效记录；
- 最大候选数量。

建议每个原始单号返回：

- 原始单号；
- 标准化单号；
- 单号类型；
- 匹配业务范围；
- 候选业务订单号；
- 候选子运单号；
- 去重后的匹配对象数量；
- 匹配状态：`UNMATCHED`、`UNIQUE`、`MULTIPLE`、`RANGE_ONLY`；
- 不能唯一命中的原因。

统一判定规则：

```text
业务订单级单号
    → 按业务订单号去重
    → 仅 1 个有效业务订单时 UNIQUE

包裹级单号
    → 按“业务订单号 + 子运单号”去重
    → 仅 1 组有效对象时 UNIQUE

范围型单号
    → 无论当前偶然返回几条，默认 RANGE_ONLY
    → 不自动建立直接成本唯一归属
```
