# BMS 本期冲正仅触发本期账单重跑技术调整方案（2026-06-27）

## 1. 文档目的

本文基于 `aidocs/product-caliber/bms/prd/财务系统.PRD.md` 在提交 `8f82dbd28c506c6daa8edd57dbba0e33afe59af0` 中的变更，结合当前仓库代码现状，整理以下内容：

1. 本次 PRD 变更在 BMS 中的真实技术落点。
2. 现有代码已经满足的部分和仍有缺口的部分。
3. 推荐的技术调整方案与实施计划。
4. 调整影响范围。
5. 已确认事项与剩余边界说明。

本方案只讨论“本期账单冲正本期/往期费项时，只触发本期账单重跑/重算，不触发往期账单重跑”这一条主链路，不扩展到无关模块。

已确认边界：

1. 本轮先不处理【账单重跑机制】主流程改造，不改 `BillGenerateServiceImpl` 的整单重跑逻辑。
2. 本轮主实施面聚焦“费用冲正审核入账、账单详情展示、来源/目标账单留痕、入口锁定规则”。

## 2. 需求来源

### 2.1 PRD 变更来源

- 来源文档：`aidocs/product-caliber/bms/prd/财务系统.PRD.md`
- 来源提交：`8f82dbd28c506c6daa8edd57dbba0e33afe59af0`
- 提交主题：`在本期账单冲正本期账单或往期账单的费项，只会触发本期账单重跑，即使在本期账单冲正往期账单的费项，不会触发往期账单重跑`

### 2.2 PRD 核心变化摘要

结合 PRD 第 `10.4`、`10.5`、`10.8`、`10.9.3`、`10.12` 节，本次变化可以收敛为 4 条：

1. 本期账单冲正本期费项时，只刷新本期账单。
2. 本期账单冲正往期费项时，仍只刷新本期账单。
3. 被引用的往期账单只保留追溯关系，不允许触发往期账单重跑、重算、汇率快照刷新、币种汇总刷新或审核状态变更。
4. 页面、审计和验收口径都要明确保留“来源往期账单号、来源费项、差异原因”，但结果只落到本期账单。

## 3. 现状盘点

## 3.1 已经符合 PRD 方向的部分

当前代码并不是“每次冲正都去重跑账单生成任务”，这一点与 PRD 方向基本一致。

1. 手动重跑账单入口仍是独立链路。
   - `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/BillGenerateServiceImpl.java`
   - `regenerate()` 只允许对 `DRAFT / GENERATED` 账单做整单重跑。
   - 费用冲正审核链路没有直接调用 `regenerate()`。

2. 费用冲正审核通过后，当前实际影响的是“归属账单”金额，而不是自动重建来源账单。
   - `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/FeeAdjustmentRecordServiceImpl.java`
   - `applyApprovedAdjustment()` 会根据 `assignedBillNo` 找到归属账单，再调用：
     - `arBillMapper.insertAdjustmentOrder(...)`
     - `arBillMapper.applyAdjustmentWithFin(...)`
   - 这条链路不会去触发来源账单的生成任务重跑。

3. 账单重整的“往期重整”链路已经是“只刷新目标账单”思路。
   - `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/ArBillServiceImpl.java`
   - `rebuildAdjustment()` 在 `PREVIOUS` 场景下：
     - 校验来源账单
     - 生成 `fee_adjustment_order`
     - 最后只执行 `refreshBillAmount(targetBill.getBillNo(), operator)`
   - 这里已经没有“顺带刷新来源往期账单”的动作。

4. 应收账单详情页已经有“本期调账 / 往期调账”两个页签。
   - `admin_shell/src/views/billing/receivableBill/index.vue`
   - 前端当前按 `adjustmentPeriodType === 'PREVIOUS'` 来区分往期调账。

## 3.2 当前实现与新版 PRD 的关键差距

虽然主方向基本一致，但当前代码还没有把“往期冲正只影响本期账单”完整落到展示、留痕和约束层。

### 3.2.1 费用冲正审核入账时，没有完整保留“来源账单 -> 目标账单”关系

当前费用冲正审核通过后，`insertAdjustmentOrder(...)` 只写了最小字段：

- `adjustment_no`
- `adjustment_type`
- `trigger_bill_id`
- `trigger_bill_no`
- `adjustment_currency`
- `adjustment_amount`
- `reason`

对应代码：

- `bms/dao/src/main/java/com/szt/supplychain/bms/dao/mapper/ArBillMapper.java`
- `insertAdjustmentOrder(...)`

问题在于：

1. `fee_adjustment_order` 表其实已经有 `adjustment_period_type`、`source_bill_no`、`target_bill_no` 字段。
2. 但费用冲正审核入账这条链路没有把这些字段写进去。
3. 结果就是“本期账单冲正往期费项”虽然账务上只改了本期账单，但落库后看不出：
   - 来源是不是往期账单
   - 计入的是哪张本期账单
   - 这条记录应展示在“本期调账”还是“往期调账”

### 3.2.2 应收账单详情页当前读取的是 `fee_adjustment_order`，不是“费用冲正主记录 + 重整记录”的合并结果

当前详情接口：

- `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/ArBillServiceImpl.java`
- `detail()` 中直接执行 `arBillMapper.selectAdjustmentsByBillNo(billNo)`

而 `selectAdjustmentsByBillNo()` 读取的是 `fee_adjustment_order`，这会带来两个问题：

1. 费用冲正记录本身在 `fee_adjustment_record` 中才有：
   - 被冲正费项
   - 挂靠对象
   - 业务订单号 / 运单号
   - `trigger_bill_id`
   - `assigned_bill_no`
2. 账单详情页当前无法准确展示“本期账单引用了哪张往期账单的哪个费项”，因为这些关键信息没有从 `fee_adjustment_record` 透出来。

### 3.2.3 前端“本期调账 / 往期调账”的分流依赖 `adjustmentPeriodType`，但费用冲正链路没有稳定写入这个字段

当前前端逻辑：

- `admin_shell/src/views/billing/receivableBill/index.vue`
- `currentAdjustRows = adjustRows.filter(item => item.adjustmentPeriodType !== 'PREVIOUS')`
- `previousAdjustRows = adjustRows.filter(item => item.adjustmentPeriodType === 'PREVIOUS')`

这意味着：

1. 如果审核通过的费用冲正没有正确写入 `adjustmentPeriodType`，前端就会被错误分到“本期调账”。
2. 即使这条冲正本质上是“本期账单引用往期费项”，页面上也无法落到“往期调账”页签。

### 3.2.4 调账中心自动归属规则可能把“往期费项冲正”错误收口到来源账单

当前自动归属规则：

- `bms/dao/src/main/resources/sqlmap/ArBillMapper.xml`
- `selectAutoAssignCandidates`

规则是：

1. 同客户
2. 同账期
3. 优先 `GENERATED`，其次 `DRAFT`

这个规则适用于“普通本期调账”，但对“本期账单冲正往期费项”不够精确。

风险在于：

1. 如果操作入口是“当前本期账单详情 -> 往期调账”，业务语义上目标账单已经明确是“当前这张本期账单”。
2. 这时如果仍走自动归属，理论上存在被改派到别的候选账单的风险。
3. 一旦目标账单不被锁死，就无法保证“只刷新当前本期账单”。

### 3.2.5 `fee_adjustment_order` 与 `fee_adjustment_record` 当前缺少稳定关联键，审计追溯不够顺

当前现状：

1. `fee_adjustment_record.adjustment_no` 是调账中心主记录编号。
2. 审核通过后插入 `fee_adjustment_order` 时，又重新生成了一个新的 `adjustment_no`。

这会导致：

1. 账单详情中的已入账记录，很难反查回具体哪条调账中心记录。
2. 若后续要解释“为什么这条往期费项只影响了本期账单”，审计链路不够直。

## 4. 技术调整目标

本轮建议把目标明确为 5 条：

1. 明确“费用冲正审核入账”和“整单生成任务重跑”是两条链路。
2. 当本期账单冲正本期或往期费项时，后端只允许刷新本期目标账单金额，不允许联动刷新来源往期账单。
3. 对于“本期引用往期费项”的场景，必须稳定保留：
   - 来源账单号
   - 目标账单号
   - 费项/挂靠对象/业务单号
   - 差异原因
4. 账单详情页必须把“本期调账”和“往期调账”展示口径与真实落账口径对齐。
5. 当前账单详情发起的“往期调账”必须锁定到当前账单，不能再走模糊自动归属。

## 5. 技术调整方案

## 5.1 总体原则

本轮建议采用“后端规则收口 + 展示口径补齐 + 尽量复用现有表结构”的策略。

原则如下：

1. 不改账单生成任务主框架。
2. 不把“往期费项冲正”实现成“往期账单整单重跑”。
3. 优先复用 `fee_adjustment_order` 已有字段：
   - `adjustment_period_type`
   - `source_bill_no`
   - `target_bill_no`
4. 详情展示优先从“可追溯性”出发，而不是继续把所有场景都硬塞进一个旧查询里。

## 5.2 后端调整方案

### 5.2.1 审核入账规则收口

建议调整 `FeeAdjustmentRecordServiceImpl.applyApprovedAdjustment()` 的入账规则：

1. 账单金额变更永远只作用于 `assignedBillNo` 对应的账单。
2. 当 `triggerBillNo == assignedBillNo` 时，视为“本期调账”。
3. 当 `triggerBillNo != assignedBillNo` 且账单类型为应收账单时，视为“往期调账 / 往期费项冲正计入本期账单”。
4. 对第 3 种情况：
   - 只更新 `assignedBillNo` 对应账单金额
   - 不更新 `triggerBillNo` 对应账单金额
   - 不触发 `BillGenerateServiceImpl.regenerate()`
   - 不触发来源账单的汇率重算、币种汇总刷新、审核状态回退

说明：

这条规则在当前代码里“账务行为”其实已经大体满足，但还需要把判断条件和日志口径显式化，避免后续开发误把这条逻辑改回“同步动两张账单”。

### 5.2.2 费用冲正审核通过后，补齐 `fee_adjustment_order` 的关系字段

建议为费用冲正审核通过后的插单逻辑增加一个新的写入版本，至少补齐以下字段：

1. `adjustment_period_type`
   - `CURRENT`：`triggerBillNo == assignedBillNo`
   - `PREVIOUS`：`triggerBillNo != assignedBillNo`

2. `source_bill_no`
   - 统一写 `triggerBillNo`

3. `target_bill_no`
   - 统一写 `assignedBillNo`

4. `voucher_url`
   - 透传当前调账中心记录的费用凭证

推荐改造点：

1. `bms/dao/src/main/java/com/szt/supplychain/bms/dao/mapper/ArBillMapper.java`
   - 新增 `insertAdjustmentOrderWithRelation(...)`
2. `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/FeeAdjustmentRecordServiceImpl.java`
   - 审核通过时根据 `triggerBillNo / assignedBillNo` 计算 period type

这样做后，哪怕详情页短期内仍读 `fee_adjustment_order`，至少“来源账单/目标账单/本期往期分类”不会再丢。

### 5.2.3 补齐调账中心主记录与账单承接记录的关联关系

这里建议两种方案，推荐第一种。

方案 A：新增关联字段，推荐。

1. 在 `fee_adjustment_order` 增加 `source_adjustment_record_id`
2. 或增加 `source_adjustment_no`

优点：

1. 账单详情页可以直接追到调账中心原记录。
2. 审计时能解释“来源费项来自哪张往期账单、最终入到了哪张本期账单”。

方案 B：不改表，靠现有字段反查，不推荐作为长期方案。

1. 通过 `assigned_bill_no + amount + reason + created_by + created_at` 近似匹配。
2. 这种方式后续容易在并发或批量导入场景中误关联。

### 5.2.4 账单详情接口改为“费用冲正记录 + 重整记录”合并返回

建议调整 `ArBillServiceImpl.detail()` 的调账明细组装方式：

1. 保留 `fee_adjustment_order` 查询，用于承接：
   - 订单重整
   - 账单级重整
   - 已存在的账单侧承接记录

2. 新增读取 `feeAdjustmentRecordMapper.selectLinkedRowsByBill(...)`，用于承接：
   - 从调账中心审核通过并实际归属到当前账单的费用级冲正记录

3. 在 Service 层合并两类数据，统一转成详情页使用的 `adjustments` 列表。

合并后的分流规则建议：

1. `来自 fee_adjustment_record`：
   - `triggerBillNo == assignedBillNo` -> 本期调账
   - `triggerBillNo != assignedBillNo` -> 往期调账

2. `来自 fee_adjustment_order`：
   - `adjustment_period_type == PREVIOUS` -> 往期调账
   - 其他 -> 本期调账

这样可以解决两个问题：

1. 当前“往期费项冲正”在详情页被误归到本期页签的问题。
2. 当前详情页看不到真实费项、挂靠对象、业务订单号的问题。

### 5.2.5 当前账单详情发起的“往期调账”必须锁定目标账单

当入口是：

- `admin_shell/src/views/billing/receivableBill/index.vue`
- 当前账单详情页的“往期调账”页签

建议做两层收口：

1. 前端收口
   - 发起往期调账时，自动带上当前详情账单号作为目标账单号
   - 不允许在该入口下把目标账单改成别的账单

2. 后端收口
   - 如果请求明确带了“当前详情账单号/目标账单号”，则不再走自动归属
   - 直接以该账单作为 `assignedBillNo`

这样能保证：

1. 当前账单详情页里做的往期冲正，只会回到当前账单。
2. 不会因为调账中心自动归属规则而误改派到其他账单。

### 5.2.6 账单生成任务链路本轮不纳入实施

已确认本轮不处理【账单重跑机制】主流程改造，因此：

1. `BillGenerateServiceImpl.regenerate()` 不纳入本轮代码调整范围。
2. 本轮只在方案口径上明确“费用冲正审核入账”和“整单重跑”是两条链路。
3. 真正落地的代码改动，仅聚焦调账/冲正审核入账与账单详情展示口径。

## 5.3 前端调整方案

前端主实施面仍然是：

- `admin_shell/src/views/billing/receivableBill/index.vue`

建议调整如下：

1. “本期调账 / 往期调账”页签的数据来源改为后端合并后的 `adjustments`。
2. 往期调账表格至少补齐展示：
   - 来源账单
   - 计入账单
   - 被冲正费项
   - 挂靠对象
   - 业务订单号/运单号
   - 冲正理由
   - 审核状态
3. 当前账单详情页发起“往期调账”时，隐藏或禁用“归属账单号”的自由输入，改为只读显示当前账单号。
4. “导入冲正”若属于往期调账入口，也应默认锁定到当前详情账单。

说明：

`admin-front` 当前不是本轮主前端，不建议纳入实施范围。

## 5.4 数据库与 DDL 调整建议

### 5.4.1 可不改表即可先落地的部分

以下字段在 `fee_adjustment_order` 中已经存在，可以直接复用：

1. `adjustment_period_type`
2. `source_bill_no`
3. `target_bill_no`
4. `voucher_url`

因此最小可落地方案是：

1. 不新增表
2. 不改现有主表结构
3. 仅改审核通过后的写入逻辑和详情页查询逻辑

### 5.4.2 推荐补充的表结构调整

如果希望追溯链路更稳，已确认可接受在 `fee_adjustment_order` 补字段，建议二选一新增字段：

1. `fee_adjustment_order.source_adjustment_record_id`
2. `fee_adjustment_order.source_adjustment_no`

推荐优先新增 `source_adjustment_record_id`，这样与主记录的关系最直接。

## 6. 调整计划

建议按 4 步执行。

### Step 1：后端规则与留痕收口

1. 梳理 `FeeAdjustmentRecordServiceImpl.applyApprovedAdjustment()` 的入账规则
2. 新增费用冲正专用的 `insertAdjustmentOrderWithRelation(...)`
3. 审核入账时补齐：
   - `adjustment_period_type`
   - `source_bill_no`
   - `target_bill_no`
   - `voucher_url`
4. 补 `source_adjustment_record_id` 或等价关联字段

交付物：

1. `bms`
2. 可选 DDL 脚本

### Step 2：账单详情查询口径改造

1. `ArBillServiceImpl.detail()` 改为合并：
   - `fee_adjustment_order`
   - `fee_adjustment_record`
2. 统一生成详情页 `adjustments`
3. 明确本期/往期分流规则

交付物：

1. `bms`
2. `platform-admin` 透传 DTO 如有变化则同步

### Step 3：Admin Shell 页面联动

1. 当前账单详情页“本期调账 / 往期调账”改为消费新口径
2. 往期调账页签补齐来源账单、目标账单、费项信息展示
3. 当前账单详情页发起往期调账时锁定目标账单为当前账单

交付物：

1. `admin_shell/src/views/billing/receivableBill/index.vue`
2. `admin_shell/src/api/billing.js`

### Step 4：联调与回归验证

至少验证以下场景：

1. 本期账单冲正本期费项，只有本期账单金额变化。
2. 本期账单冲正往期费项，只有本期账单金额变化。
3. 往期账单被引用后：
   - 不触发整单重跑
   - 不刷新汇率快照
   - 不刷新币种汇总
   - 不改变审核状态
4. 当前账单详情页“往期调账”能准确展示来源账单和目标账单。
5. 调账中心审核记录可以回溯到账单详情中的承接结果。

## 8. 风险与注意事项

1. 当前代码的真正风险不是“会不会真的触发往期账单整单重跑”，而是“页面和留痕看不出它只影响了本期账单”。
2. 如果只改前端页签、不补后端关系字段，后续数据仍会分错类。
3. 如果只补 `source_bill_no / target_bill_no`，但不补主记录关联键，审计追溯依然会比较弱。
4. 自动归属规则不收口时，当前账单详情页发起的往期调账仍存在目标账单漂移风险。
5. `fee_adjustment_order` 当前确认没有历史数据，因此本轮不需要考虑存量兼容、迁移回填或历史修复脚本。

## 9. 已确认事项

以下事项已确认，可直接按确认结论推进。

1. “本期账单冲正往期费项”需要锁定目标账单。
   - 当前按收紧口径处理为：不只是在“当前账单详情页入口”锁定，凡是落入该场景的录入/导入/审核链路，都必须明确指定并锁定目标本期账单，不能再走模糊自动归属。

2. `fee_adjustment_order` 目前没有数据。
   - 本轮不需要做历史数据修复，也不需要补回填脚本。

3. 账单详情页展示按原型来。
   - 即按原型补齐被冲正费项、挂靠对象、业务订单号/运单号、来源账单、计入账单等字段，不做弱化展示。

4. 接受给 `fee_adjustment_order` 新增 `source_adjustment_record_id` 或等价关联字段。

5. 本轮先不处理【账单重跑机制】。
   - 不改整单重跑主流程，只处理调账/冲正审核入账和详情展示口径。

## 10. 结论

这次 PRD 变更对当前代码的真实影响，不在“账单生成任务”主框架，而在“费用冲正审核入账后的承接关系、详情页展示口径和目标账单锁定规则”。

建议本轮按以下优先级推进：

1. 先补齐费用冲正审核后的 `source_bill_no / target_bill_no / adjustment_period_type` 留痕，并增加主记录关联字段。
2. 再把账单详情页改成“费用冲正记录 + 重整记录”合并展示，字段按原型对齐。
3. 最后收口往期调账入口和导入/审核链路，确保目标账单被明确指定并锁定。

这样可以在最小改动下，把“本期冲正只触发本期账单重跑/重算，不触发往期账单重跑”真正落实到代码、页面和审计链路中。
