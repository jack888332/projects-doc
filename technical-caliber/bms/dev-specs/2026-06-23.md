# 2026-06-23 开发计划

> 2026-06-24 变更说明：`数据源检阅标记机制补齐` 方向已撤回，本文件中所有与 `检阅标记 / 行级锁定 / 归集轨迹 / bms_review_status` 相关的设计、已完成项与验收结论均作废，不再纳入当前开发范围；当前有效范围仅保留 `回款管理` 与 `汇率换算修正`。

## 一、今日开发目标

结合 `aidocs/product-caliber/bms/prd/财务系统.PRD.md` 与当前 BMS / Admin Shell 现状，今日开发聚焦以下三个方向：

1. 完善数据源的 BMS 检阅标记作用机制，避免 BMS 费项池原始金额与数据源产生偏差。
2. 实现回款管理功能，按尾程包裹粒度展示 COD 回款、返款、汇兑损益和账单关联结果。
3. 修正汇率换算功能，补齐汇率级别校验、状态边界校验和保存后的重算一致性。

## 二、总体实施顺序

建议按以下顺序推进，避免返工：

1. 先完成“数据源检阅标记/行级锁定”底座。
2. 再完成“回款管理”后端与前端联调。
3. 最后完成“汇率级别与换算校验”修正。

原因：

- 回款管理依赖稳定的源数据口径。
- 汇率重算依赖返款账单、费用明细、回款金额汇总口径先稳定。
- 若先改页面或汇率，不先统一源数据锁定规则，后续仍会出现账单金额与源数据偏差。

## 三、开发代办清单

### 3.1 P0：数据源 BMS 检阅标记机制

#### 任务 1：明确并落地行级标记模型

目标：

- 将 PRD 中的 `null / locked / synced` 行级状态落地为统一的源数据处理状态口径。
- 补齐失败原因、变化来源、操作人、变化时间等留痕字段。

实施内容：

- 梳理当前 `bms_billed_flag`、`bms_bill_no`、`bill_source_collect_mark` 的职责边界。
- 确认哪些字段继续承担“是否已挂账”职责，哪些字段升级为“是否已进入 BMS 采集链路”职责。
- 设计并补充行级状态字段及状态流转规则。

交付物：

- 行级标记字段方案说明。
- 对应表结构调整方案。
- 状态流转说明文档。

#### 任务 2：改造账单生成链路为“先锁定、再采集、再回写同步”

目标：

- 避免账单生成过程中源数据被并发修改。
- 保证本次账期内参与采集的数据范围可审计、可回溯。

实施内容：

- 调整账单生成任务入口，先锁定本次参与处理的源数据。
- 锁定成功后再执行采集、归集、写 `fee_detail`、写账单明细。
- 成功后统一回写 `synced`，失败保留失败状态和失败原因。

交付物：

- 账单生成链路改造代码。
- 失败补偿及重试说明。

#### 任务 3：冻结已进入 BMS 识别链路的原始金额

目标：

- 一旦源数据进入 `locked/synced` 状态，不允许继续直接修改影响 BMS 费项池的原始金额字段。

实施内容：

- 识别受影响的费项横表金额字段。
- 在相关更新入口增加状态校验。
- 明确“调整已冻结金额”只能通过补录、冲正、调账、重新生成等方式处理。

交付物：

- 金额冻结校验代码。
- 异常提示文案和处理口径说明。

#### 任务 4：补充检阅标记查询与异常队列能力

目标：

- 让财务或开发可以直接查看待采集、锁定中、失败待补偿的数据。

实施内容：

- 增加检阅标记分页查询接口。
- 增加失败原因、来源表、来源主键、账单号、任务号等字段输出。
- 视需要补一个 Admin Shell 页面或在现有任务页面增加入口。

交付物：

- 后端查询接口。
- 前端查询入口。

3. 检查返款账单详情与回款管理的汇率、金额、损益展示是否一致。

## 五、风险与注意事项

1. 行级标记改造涉及账单生成链路，需重点防止历史账单重跑和当前增量采集冲突。
2. 回款管理若继续复用返款账单接口，会导致包裹级口径与 PRD 不一致，因此建议独立建接口。
3. 汇率修正必须与返款账单、费用明细、汇总表同步校验，否则页面金额仍可能前后不一致。
4. 涉及库表结构调整时，需同步更新相关 SQL 归档文档。

## 六、验收标准

1. 源数据进入 BMS 采集链路后，原始金额不能被直接修改。
2. 账单生成任务执行时，能够先锁定源数据，再采集，再回写同步状态。
3. 回款管理可以按尾程包裹粒度正确展示回款状态、返款状态、关联账单和汇兑损益。
4. 汇率修改后，账单详情、费用明细、回款管理展示金额一致。
5. 已结清或历史账单不会被新的汇率保存动作错误改写。

## 十、补挂方案设计

### 10.1 设计背景

当前回款管理详情已经具备独立 `/receipt/detail` 接口，但“关联回款记录”仍然只能按返款账单维度返回。

现状原因：

- `refund_payment_allocation` 仅挂到 `bill_id / bill_no / currency_summary_id`。
- 当前分配记录没有 `tailWaybillNo`、`businessOrderNo` 等包裹或订单维度字段。
- 因此现有 SQL 只能按 `billNo` 查询账单级打款轨迹，不能准确下钻到单个尾程包裹。

### 10.2 设计目标

本次补挂方案目标不是改变返款账单主流程，而是在保留账单级打款分配能力的前提下，补齐包裹级追踪锚点，使回款管理详情可以真正展示“某个尾程包裹参与过哪些打款分配”。

目标结果：

1. 返款打款分配既保留账单级汇总关系，也能挂到业务订单 / 尾程包裹维度。
2. 回款管理详情可按 `tailWaybillNo` 查询真实付款轨迹。
3. 老数据兼容保留，未补挂历史记录时仍可回退到账单级轨迹展示。

### 10.3 表结构补挂建议

建议在 `refund_payment_allocation` 表增加以下字段：

1. `business_order_no`
   - 含义：本次打款分配关联的业务订单号。
   - 用途：支持订单维度联查和后续校验。
2. `tail_waybill_no`
   - 含义：本次打款分配关联的尾程运单号。
   - 用途：作为回款管理详情查询包裹级付款轨迹的核心锚点。
3. `source_fee_detail_id`
   - 含义：本次分配命中的 `fee_detail` 主键。
   - 用途：保留最细粒度资金轨迹与费用快照映射关系。
4. `allocation_scope`
   - 含义：分配作用域。
   - 建议值：`BILL / ORDER / WAYBILL`
   - 用途：区分历史账单级分配与新包裹级分配。

建议索引：

1. `idx_tail_waybill_no`
2. `idx_business_order_no`
3. `idx_bill_scope`
   - 组合建议：`(bill_no, allocation_scope, allocation_status)`

### 10.4 写入链路改造方案

当前打款登记逻辑是按账单币种汇总写入 `refund_payment_allocation`。

补挂后建议改为“两层结果同时保留”：

1. 第一层仍保留账单级分配逻辑
   - 用于维持现有账单金额汇总、账单状态推进、返款已分配金额口径。
2. 第二层展开到包裹 / 订单维度写入补挂字段
   - 以返款账单命中的 `fee_detail` 或 `RefundBillFeeSummaryDTO` 为基础
   - 将本次分配结果按 `businessOrderNo + tailWaybillNo` 展开
   - 每条展开记录写入 `refund_payment_allocation`
   - 同时写入 `allocation_scope = 'WAYBILL'`

推荐优先级：

1. 能直接命中 `tailWaybillNo` 时优先写包裹级。
2. 无尾程运单号但有业务订单号时写订单级，`allocation_scope = 'ORDER'`。
3. 两者都无法识别时保留账单级，`allocation_scope = 'BILL'`。

### 10.5 查询链路改造方案

回款管理详情新增真正的包裹级付款轨迹查询时，建议按以下顺序查询：

1. 先按 `tailWaybillNo + allocation_scope = 'WAYBILL'` 查询。
2. 未命中时，再按 `businessOrderNo + allocation_scope = 'ORDER'` 查询。
3. 若仍未命中，再回退到当前账单级 `billNo + allocation_scope = 'BILL'` 查询。

返回字段建议至少包含：

1. `paymentNo`
2. `paymentDate`
3. `paymentCurrency`
4. `allocationAmountBillCurrency`
5. `tailWaybillNo`
6. `businessOrderNo`
7. `allocationScope`
8. `allocatedBy`
9. `allocationStatus`
10. `remark`

这样前端可以明确区分：

- 这是一笔真实命中的包裹级分配
- 还是历史兼容回退的账单级轨迹

### 10.6 历史兼容策略

该改造必须允许历史数据继续可用，不能因为补挂字段上线导致旧打款记录不可查。

兼容策略建议：

1. 新增字段允许为空。
2. 历史记录默认视为 `allocation_scope = 'BILL'`。
3. 新详情页优先查包裹级 / 订单级，再回退到账单级。
4. 当回退到账单级时，前端继续展示“当前为关联返款账单维度轨迹”的提示。

### 10.7 实施顺序建议

建议按以下顺序推进，风险最低：

1. 先补表结构和 Model 字段。
2. 再改返款打款写入逻辑。
3. 再新增包裹级付款轨迹查询 SQL 与接口。
4. 最后切换回款管理详情展示逻辑。

### 10.8 当前结论

1. “包裹级付款轨迹”需求来源于回款管理主粒度为尾程包裹的 PRD 口径。
2. 当前代码未实现的根因，不在详情接口，而在 `refund_payment_allocation` 缺少包裹 / 订单维度锚点。
3. 若要真正实现包裹级付款轨迹，下一轮必须进入库表改造，而不是继续在现有账单级记录上做前端拼装。
