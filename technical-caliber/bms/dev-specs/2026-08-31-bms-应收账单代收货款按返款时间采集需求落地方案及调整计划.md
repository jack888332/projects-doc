## 1. 背景与目标

### 1.1 问题背景

当前应收账单 `MEMBER_AR` 主单链路中，所有订单级费项共用同一个“账单配置履约节点”时间窗口扫描源订单：

- `WEIGHT_MEASURED` 核重时间 → `h.measure_time`
- `WEIGHT_OUTBOUND` 出库时间 → 公共配置默认 `h.delivery_time`
- `ORDER_COMPLETED` 订单完结 → `e.order_completed_time`
- `SIGN / SIGNED` 签收时间 → `h.signed_time`

代收货款 `FEE0022` 当前也按上述订单履约节点采集，而不是按“返款/回款时间”采集。财务希望应收账单代收货款不再按核重、出库、完结等履约时间入账，而是像返款账单一样，按返款时间落入对应账期。

### 1.2 需求目标

1. 应收账单代收货款相关费项按返款时间 `sale_order_header_extend.recovery_time` 落在任务账期内采集。
2. 普通运费、附加费、理赔等非代收货款费项继续沿用现有账单配置履约节点，不随本次调整。
3. 同一订单可能因为“履约时间”和“返款时间”不同而分属不同账期，系统需要支持同一订单在应收账单中出现多张快照。
4. 代收货款独立采集需要独立的防重轨迹，避免与现有 `MAIN_ORDER` 打标互相污染。
5. 保留订单快照、费项明细、币种汇总、账单追加、任务快照、源表清理与重跑能力。

### 1.3 需求边界

- 本次只调整 `MEMBER_AR` 应收账单链路。
- `COD_REFUND` 返款账单链路维持现状，不因本次需求改变。
- 附加费独立按 `a.create_time` 采集的链路维持现状。
- 理赔、记账单附加费、非费项链路不在本次范围；`FEE0023 / FEE0024` 等衍生费项本次不调整，后续扩展时另行评估。
- `FEE0023`、`FEE0024`、`FEE0040`、`FEE0060` 本次不纳入调整，但代收货款费项清单需要按集合设计，便于后续扩展。
- 本次不修改 `fee_source_rule`、`fee_source_dataset` 的业务配置，不修改源库，不修改 `env.md`。

### 1.4 术语约定

- 本文“返款时间”已确认对应 `sale_order_header_extend.recovery_time`，源库注释为“回款时间”。
- 本文“代收货款”本次仅指订单级 `FEE0022`；后续扩展 `FEE0023 / FEE0024` 等费项时，只需在代收货款费项编码集合中追加，不再改链路。

## 2. 现状分析

### 2.1 应收主单采集维度

应收主单候选由 `BillGenerateServiceImpl.queryCandidateOrderRows()` 调用 `queryOrderWideRowsFromSource()` 扫描：

```text
resolveOrderTimeField(billConfig)
  -> resolveCommonOrderTimeField(contractNode)
  -> defaultOrderTimeFieldByContractNode(contractNode)
  -> buildOrderWideQuerySql(orderTimeField, orderTypes)
      -> orderTimeExpr("h", orderTimeField)
      -> AND <时间表达式> >= 账期开始 AND <时间表达式> < 账期结束
```

`buildOrderWideQuerySql()` 只接收一个 `orderTimeField`，因此一次主订单扫描内所有 order-wide 费项共享同一个时间窗口：

```sql
SELECT h.id AS h_id, ...,
       <billingTime> AS h_billing_node_time,
       ...
FROM sale_order_header h
LEFT JOIN sale_order_header_extend e ON e.sale_order_id = h.id
WHERE h.member_code = ?
  AND h.shop_id = ?
  AND (h.sc_id = ? OR h.sc_id IS NULL)
  AND COALESCE(h.order_type, '') <> 'BILL'
  AND h.order_type IN (...)
  AND <billingTime> >= ?
  AND <billingTime> < ?
ORDER BY h.id LIMIT ? OFFSET ?
```

同一个 `h_billing_node_time` 会被继续写入：

- `fee_detail.source_fee_time`：`buildOrderFee()` 取 `orderRow.h_billing_node_time`
- `main_order.billing_node_time`：`buildMainOrder()` 取 `orderRow.h_billing_node_time`

所以如果只改 `resolveOrderTimeField()` 或账单配置的 `contractNode`，会导致整张应收账单所有订单级费项全部改到返款时间账期，不能只调整代收货款。

### 2.2 代收货款费项配置

只读查询 `tmall_bms` 当前配置：

| 费项 | 名称 | 费项类型 | 业务类型 | 数据集 | 来源表 | source_time_column |
| --- | --- | --- | --- | --- | --- | --- |
| `FEE0022` | 代收货款 | `AR_COLLECT` | `CONSOLIDATION / PEER / COD_ORDER` | `CONSOLIDATION_ORDER` | `sale_order_header` | `create_time` |
| `FEE0023` | 代收货款手续费 | `AR` | `CONSOLIDATION / PEER / COD_ORDER` | `CONSOLIDATION_ORDER` | `sale_order_header` | `create_time` |
| `FEE0024` | 到付金额 | `NON_FEE` | `CONSOLIDATION / PEER` | `CONSOLIDATION_ORDER` | `sale_order_header` | `create_time` |
| `FEE0040` | 代客收台币 | `AR_COLLECT` | `CONSOLIDATION / PEER` | `CONSOLIDATION_ADDITIONAL_FEE` | `sale_order_additional_matter` | `a.create_time` |
| `FEE0060` | 代收货款手续费 | `AR` | `CONSOLIDATION / PEER` | `TAIL_PACKAGE_FEE` | `sale_order_package_fee` | `p.create_time` |
| `FEE0061` | 返款汇率 | `NON_FEE` | `CONSOLIDATION / PEER` | `TAIL_PACKAGE_FEE` | `sale_order_package_fee` | `p.create_time` |

注意：

1. `FEE0022 / FEE0023 / FEE0024` 的 `source_time_column` 是 `create_time`，但当前应收主单实际过滤时间并不使用该字段，而是使用账单配置履约节点时间。
2. `FEE0024` 是 `NON_FEE`，当前只做来源拉取留痕，不写账单金额。
3. `FEE0060 / FEE0061` 挂在 `TAIL_PACKAGE_FEE` 数据集，来源是 `sale_order_package_fee`，属于包裹级/返款侧费项；本次已确认不纳入，后续如需扩展再单独评估。
4. `FEE0040 代客收台币` 也是 `AR_COLLECT`，但来源是 `sale_order_additional_matter` 附加费；本次已确认不纳入，后续如需扩展再单独评估。

### 2.3 返款账单的返款时间口径

返款账单主单已有固定实现：

```java
// BillGenerateServiceImpl.resolveRefundOrderTimeField()
if (refundMode == REFUND_MODE_RECEIVED) {
    return "recovery_time";
}
```

`fee_source_dataset` 当前配置：

| dataset_code | received_time_column | sign_time_column | weight_outbound_time_column |
| --- | --- | --- | --- |
| `CONSOLIDATION_ORDER` | 未配置 | `h.signed_time` | `h.measure_time` |
| `COD_REFUND_MAIN_ORDER` | `e.recovery_time` | `h.signed_time` | `h.measure_time` |

因此返款账单 `RECEIVED` 模式已经是“只认 `e.recovery_time`”，且 `orderTimeExpr("h", "recovery_time")` 会解析为 `e.recovery_time`。这正是应收代收货款可以复用的时间表达式。

返款账单还依赖包裹级事实：

- `sale_order_package_fee.recovery_money > 0` 判定有效回款。
- `sale_order_package_fee.receivable_collection_amount` 采集包裹级代收货款手续费。

但本次应收代收货款金额来源仍是订单级 `sale_order_header.collection_price / collection_premium_amount / cod_price`，不是 `sale_order_package_fee`，因此不能直接照搬返款账单整条链路。

### 2.4 打标与防重现状

`bill_source_collect_mark` 唯一键：

```text
uk_source_collect (source_system, source_table, source_id, collect_type, bill_type)
```

因此同一来源行可以分别按 `MAIN_ORDER`、`ADDITIONAL_FEE`、`COD_COLLECTION` 等不同 `collect_type` 留痕，也能同时被 `MEMBER_AR` 和 `COD_REFUND` 两类账单占用。

当前只读样例：

| bill_type | collect_type | 状态 | 数量 |
| --- | --- | --- | --- |
| `MEMBER_AR` | `MAIN_ORDER` | `MARKED` | 194 |
| `MEMBER_AR` | `ADDITIONAL_FEE` | `MARKED` | 29 |
| `MEMBER_AR` | `ADDITIONAL_INCREMENT` | `MARKED` | 4 |
| `COD_REFUND` | `MAIN_ORDER` | `MARKED` | 12 |

当前 `queryOrderWideRowsFromSource()` 在查询已打标来源时硬编码 `SOURCE_COLLECT_TYPE_MAIN_ORDER`，如果代收货款独立链路复用该方法，需要把 `collectType` 参数化。

### 2.5 源数据现状

只读查询结论：

1. `sale_order_header_extend` 没有独立“返款时间”字段，现有 `recovery_time` 注释为“回款时间”，字段类型 `datetime`。
2. `sale_order_header_extend` 已有索引 `idx_collection_flag_recovery_time (collection_premium_fee_calc_flag, recovery_time, sale_order_id)`，但首列不是成员/店铺/供应链，直接按 `member_code + shop_id + sc_id + recovery_time` 扫描不一定能高效使用该索引。
3. 抽样客户 `81815` 的 450 张源订单中，COD 子集 16 张的 `recovery_time` 当前均为空；说明当前开发/测试库的回款时间填充可能不完整，上线前需要核对生产数据。
4. `sale_order_package_fee` 有 `recovery_money`、`receivable_collection_amount`、`collection`、`payment_collect` 等字段，但没有 `recovery_time`。

## 3. 目标口径

### 3.1 采集时间

代收货款独立采集时间固定为：

```text
sale_order_header_extend.recovery_time
```

任务账期条件与返款账单一致：

```text
e.recovery_time >= 账期开始时间
AND e.recovery_time < 账期结束时间（不包含）
```

不再使用：

- 账单配置 `contractNode` 对应的核重/出库/完结时间
- `fee_source_rule.source_time_column = create_time`
- 附加费 `a.create_time`

### 3.2 候选订单

推荐候选条件：

```text
1. h.member_code / h.shop_id / h.sc_id 命中当前账单配置
2. h.order_type 命中当前账单配置的订单类型，且排除 BILL 虚拟订单
3. e.recovery_time 落在任务账期
4. COALESCE(h.collection_price, 0) > 0
```

已确认：不额外要求 `sale_order_package_fee.recovery_money > 0`，只按“订单头代收货款金额 > 0 + 订单级回款时间”采集，避免把订单级与包裹级事实强耦合。

### 3.3 费用范围

本次确认范围：

| 费项 | 处理 |
| --- | --- |
| `FEE0022 代收货款` | 独立按 `recovery_time` 采集，金额照常入应收账单 |
| `FEE0023 代收货款手续费` | 本次不调整，继续走现有链路；后续如需纳入，追加到代收货款费项编码集合 |
| `FEE0024 到付金额` | 本次不调整，继续走现有链路；后续如需纳入，追加到代收货款费项编码集合 |
| `FEE0040 代客收台币` | 本次不调整；当前是附加费来源，后续如需纳入需单独评估 |
| `FEE0060 包裹级代收货款手续费` | 本次不调整；当前属于 `TAIL_PACKAGE_FEE` 包裹级链路，后续如需纳入需单独评估 |

### 3.4 归属与账期

- 账期归属：`recovery_time` 所在账期。
- 客户/供应链/店铺：沿用账单配置 `member_code / sc_id / shop_id / user_id`。
- 分支配置：沿用现有 `matchesBranchScope()` 按目的国、仓库等维度匹配。
- 账单分组：沿用 `resolveBillGroupKey()` 按业务板块 + 目的国分组。

### 3.5 快照口径

代收货款独立采集生成费项和订单快照时：

```text
fee_detail.source_fee_time = e.recovery_time
独立代收货款账单新建 main_order 时，billing_node_time = e.recovery_time
同一账单已有主链路 main_order 快照时，不覆盖 billing_node_time
ar_bill.billing_period_start_date / end_date = recovery_time 所在账期
```

### 3.6 缺失回款时间

推荐处理：

```text
e.recovery_time 为空或不在账期 -> 不进入代收货款独立采集，打印诊断日志
```

不推荐回退到 `signed_time` / `measure_time` / `delivery_time`，否则又会混入履约节点口径。

## 4. 推荐落地方案

### 4.1 总体架构

参考已落地的“应收附加费独立按创建时间采集”链路，把代收货款从应收主订单宽表扫描中拆出：

```text
MEMBER_AR executeTaskInternal
  1. assignOrdersToConfigGroup()
     按 contractNode 履约节点扫描，仅保留非代收货款 order-wide 费项
  2. assignCodCollectionOrdersToConfigGroup()
     新增，按 e.recovery_time 独立扫描代收货款候选订单
  3. executeConfigOrderGroups()
     主订单建账/追加时跳过 FEE0022；费项清单集合化，后续扩展只需追加编码
  4. executeCodCollectionGroups()
     按 recovery_time 账期创建或追加应收账单
  5. 汇总任务统计、写任务快照
```

这样普通费项仍然跟随 `contractNode`，代收货款单独跟随 `recovery_time`，避免“一张主单只用一个时间窗口”的限制。

### 4.2 目标取数 SQL

推荐复用 `buildOrderWideQuerySql("recovery_time", orderTypes)`，因为 `orderTimeExpr("h", "recovery_time")` 已经返回 `e.recovery_time`，宽表列也会自动把该时间放进 `h_billing_node_time`：

```sql
SELECT h.id AS h_id,
       h.order_code AS h_order_code,
       h.delivery_order_code AS h_delivery_order_code,
       h.member_code AS h_member_code,
       h.shop_id AS h_shop_id,
       h.sc_id AS h_sc_id,
       h.country_code AS h_country_code,
       h.warehouse_code AS h_warehouse_code,
       h.collection_price AS h_collection_price,
       h.cod_price AS h_cod_price,
       h.collection_premium_amount AS h_collection_premium_amount,
       e.recovery_time AS h_billing_node_time,
       ...
FROM sale_order_header h
LEFT JOIN sale_order_header_extend e ON e.sale_order_id = h.id
WHERE h.member_code = ?
  AND h.shop_id = ?
  AND (h.sc_id = ? OR h.sc_id IS NULL)
  AND COALESCE(h.order_type, '') <> 'BILL'
  AND h.order_type IN (...)
  AND e.recovery_time >= ?
  AND e.recovery_time < ?
  AND COALESCE(h.collection_price, 0) > 0
ORDER BY h.id
LIMIT ? OFFSET ?
```

实施说明：

1. 若直接复用 `buildOrderWideQuerySql()`，可新增一个只读参数或在 Java 层过滤 `collection_price > 0`，不要为每个客户硬编码新 SQL。
2. 分页继续沿用现有 `queryWindowDays / queryPageSize` 策略，避免深翻页。
3. 本地 `bill_source_collect_mark` 过滤使用新的 `COD_COLLECTION` 类型。

### 4.3 任务编排

`executeTaskInternal()` 调整建议：

```text
1. assignOrdersToConfigGroup(snapshotContext, startDate, endDate)
2. assignCodCollectionOrdersToConfigGroup(snapshotContext, startDate, endDate, taskId)
3. assignAdditionalFeesToConfigGroup(...)
4. assignLedgerAdditionalToConfigGroup(...)
5. executeConfigOrderGroups(...)
6. executeCodCollectionGroups(...)
7. executeAdditionalFeeGroups(...)
8. executeLedgerAdditionalGroups(...)
```

代收货款独立分配逻辑可以参照 `assignAdditionalFeesToConfigGroup()`：

- 分支配置优先匹配，其余归默认配置。
- 同一订单被履约节点主链路和代收货款独立链路同时命中时，允许生成两个 `main_order` 快照，分别落在不同 `bill_no`。
- 同一订单在同一账期同时命中时，复用同一账单，由 `main_order` upsert 和 `fee_detail.dedupe_key` 控制重复。

### 4.4 建账与追加

代收货款独立链路建账逻辑可复用 `executeAdditionalFeeGroup()` 的模式：

```text
1. 按 billConfig + startDate + endDate + groupKey 查可追加账单
2. 可追加则 prepareReceivableBillForAppend + 使用原 billId / billNo
3. 不可追加则新建 ar_bill
4. 对候选订单 insertMainOrder + persistOrderWaybillSnapshots
5. 对 FEE0022 规则 buildOrderFee + insertFeeDetail
6. 重建币种汇总、刷新账单金额和状态
7. 写 COD_COLLECTION 打标轨迹
```

注意事项：

1. 主链路生成 `main_order` 时已经对订单调用了 `markOrderSource()`，写入了源表 `bms_billed_flag / bms_bill_no`。
2. 代收货款独立链路不能再次用 `markSaleOrderExtendFromSource()` 覆盖该值，否则源表账单号会从主订单账单变成代收货款账单。
3. `fee_detail.dedupe_key` 保持不变，主链路跳过代收货款费项后不会与独立链路在同一账单内撞 key。
4. 同一账单已有主链路 `main_order` 快照时，只新增 `fee_detail`，不更新该快照的 `billing_node_time`；仅独立代收货款新建账单时写入 `recovery_time`。

### 4.5 打标与防重

建议新增常量：

```java
public static final String SOURCE_COLLECT_TYPE_COD_COLLECTION = "COD_COLLECTION";
```

打标记录：

```text
bill_type   = MEMBER_AR
collect_type = COD_COLLECTION
source_system = OFP
source_database = ofp_ofdb1
source_table    = sale_order_header_extend
source_id       = h_id
bill_id / bill_no / generate_task_id = 代收货款账单
```

推荐实现“仅本地轨迹、不覆盖源表”的打标：

```text
persistSourceCollectPending(mark)
persistSourceCollectSuccess(mark)
```

不调用：

```text
markSaleOrderExtendFromSource(orderId, codBillNo)
```

这样 `sale_order_header_extend.bms_billed_flag / bms_bill_no` 仍然只表达主订单履约账单的最近入账信息，代收货款独立归集由 `bill_source_collect_mark` 权威防重。

现有清理逻辑 `unmarkSourcesByBillNoAndType()` 已经按“同一来源是否仍被其他 MARKED 轨迹占用”决定是否清理源表标记，因此对 `COD_COLLECTION` 清理时不会误清 `MAIN_ORDER` 的源表标记，但需要补充回归测试。

### 4.8 存量数据处理

当前生产已有按履约节点采集的 `FEE0022` 等费项。已确认当前不处理存量，但发布前需要盘点以下两类影响，便于后续跟踪：

1. 已生成历史账单中的代收货款是否需要按返款时间重新归集。
2. 旧账单中的 `MAIN_ORDER` 打标不会阻止新的 `COD_COLLECTION` 打标，因此直接重跑可能造成同一订单代收货款重复入账。

只读盘点 SQL：

```sql
SELECT b.bill_no,
       b.billing_period_start_date,
       b.billing_period_end_date,
       fd.fee_code,
       fd.source_order_id,
       fd.source_fee_time,
       mo.billing_node_time
FROM tmall_bms.fee_detail fd
JOIN tmall_bms.ar_bill b ON b.id = fd.bill_id
JOIN tmall_bms.main_order mo
  ON mo.bill_id = b.id
 AND mo.order_no = fd.business_order_no
WHERE fd.bill_type = 'MEMBER_AR'
  AND fd.fee_code = 'FEE0022'
ORDER BY b.billing_period_start_date, b.bill_no;
```

存量修正方式已确认：当前不进行处理，先只保留只读盘点能力。

- 新账期发布后按新口径生成。
- 历史已生成账单不自动迁移、不自动重跑、不自动补差。
- 若后续财务要求补历史，再按作废重跑或调整中心方式单独排期。

### 4.9 风险

1. `recovery_time` 数据不完整会导致代收货款漏采，需要先核对源数据。
2. 同一订单在履约节点账单和返款时间账单各出现一次，报表、导出、回款管理可能看到多张 `main_order`，需要按账单维度隔离。
3. 代收货款独立链路与旧 `MAIN_ORDER` 链路并存时，重复采集风险最高，必须验证 `COD_COLLECTION` 打标和主链路跳过逻辑。
4. `bill_source_collect_mark` 新增 `COD_COLLECTION` 类型后，现有清理、重跑、恢复脚本需要兼容。
5. 后续如扩展 `FEE0023 / FEE0024` 到独立链路，需要重新验证非费项留痕和金额方向，本次不涉及。

## 7. 疑问点确认结果

1. 财务所说的“返款时间”是否就是 `sale_order_header_extend.recovery_time`？
   - 已确认：是，采集时间固定为 `e.recovery_time`。

2. 费用范围如何界定？
   - 已确认：本次仅调整 `FEE0022 代收货款`。
   - 已确认：建议把代收货款费项编码做成集合，后续补充 `FEE0023 / FEE0024` 等时只追加编码，不改链路。

3. `recovery_time` 为空时如何处理？
   - 已确认：跳过并记录日志，不回退到履约节点时间。

4. 是否要求包裹级 `sale_order_package_fee.recovery_money > 0` 才采集？
   - 已确认：不要求，只按订单级 `recovery_time + collection_price > 0`。

5. 同一订单的普通费项和代收货款在同一账期时，是否允许同一账单并存？
   - 已确认：允许，主链路跳过代收货款，代收货款独立链路追加同一账单。

6. 同一订单因为履约时间和返款时间不同而进入两张账单，是否接受？
   - 已确认：接受，参照附加费独立采集已确认的“同一订单可出现在多张账单”结论。

7. 代收货款独立链路是否覆盖源表 `sale_order_header_extend.bms_billed_flag / bms_bill_no`？
   - 已确认：不覆盖，仅写 `bill_source_collect_mark`。

8. 同一账单内已有该订单 `main_order` 快照时，`billing_node_time` 是否更新为 `recovery_time`？
   - 已确认：按默认处理。代收货款费项新增时 `fee_detail.source_fee_time` 固定为 `recovery_time`；不覆盖既有主链路 `main_order.billing_node_time`。

9. 存量历史账单如何处理？
   - 已确认：当前不处理，不自动迁移、不自动重跑、不自动补差。

10. 是否保留配置开关，允许按客户/费项临时切换新旧口径？
    - 已确认：不需要开关，不做新旧双链路长期并存。
