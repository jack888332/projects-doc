# BMS ARAP 代收代付费项拆分技术调整方案与计划

## 1. 背景

当前 BMS 费项类型中存在 `ARAP`，用于笼统表示“代收代付”。按 `612baf870c4f4a957ccf03b570905ae4a1c0abdc` 提交补充后的 PRD 口径，代收资金与代付资金在应收账单中的金额方向不同：

1. `应收扣减类`：应收账单记为负数。
2. `代收类`：应收账单记为负数，用于冲减客户应付金额。
3. `代付类`：应收账单记为正数，表示客户应补偿我方垫付或支付的金额。
4. `非费项`：不纳入任何账单核销范围，仅在返款账单、回款管理等特定位置展示或核对。

因此，`ARAP` 需要拆成两个明确类型，避免同一类型下既有负向资金又有正向资金，导致应收账单生成、汇总、核销和前端筛选口径不一致。

## 2. 指定提交口径摘要

提交 `612baf870c4f4a957ccf03b570905ae4a1c0abdc` 对 PRD 的关键补充如下：

| 业务类型 | 业务含义 | 应收账单金额方向 |
| :--- | :--- | :--- |
| 应收类 | 客户应支付给我方的服务费、运费、附加费等 | 正数 |
| 应收扣减类 | 优惠、赔付等冲减客户应付金额 | 负数 |
| 应付类 | 我方对外成本或供应商侧应付 | 不进入客户应收 |
| 代收类 | 我方代客户收取的资金 | 负数 |
| 代付类 | 我方代客户垫付或支付的资金 | 正数 |
| 非费项 | 事实金额、核对金额、展示金额 | 不进入核销汇总 |

PRD 中与本次拆分直接相关的来源映射如下：

| 来源字段或来源条件 | 费项名称 | 新费用类型 |
| :--- | :--- | :--- |
| `ofp_ofdb1.sale_order_header.collection_price` | 代收货款 | 代收类 |
| `ofp_ofdb1.sale_order_header.advance_amount` | 垫付金额 | 代付类 |
| `ofp_ofdb1.sale_order_fee_detail.collection` | 应返货款 | 代收类 |
| `ofp_ofdb1.sale_order_additional_matter where fee_item_type="代客收台币"` | 代客收台币 | 代收类 |
| `ofp_ofdb1.sale_order_additional_matter where fee_item_type="代客付台币"` | 代客付台币 | 代付类 |
| `ofp_ofdb1.sale_order_header.cod_price` | 到付金额 / COD金额 | 非费项 |
| `ofp_ofdb1.sale_order_header.cod_amount` | 货到付款手续费 | 非费项 |
| `ofp_ofdb1.sale_order_fee_detail.recovery_money` | 实收回款 | 非费项 |

## 3. 当前代码与数据现状

### 3.1 代码现状

1. `BmsConstants` 当前定义了 `AR`、`ARD`、`AP`、`ARAP`、`NON_FEE`，其中 `ARAP` 未拆分代收/代付。
2. `BillGenerateServiceImpl#signedAmount` 当前仅对 `ARD` 取负，对 `NON_FEE` 返回 0，其他类型按正数处理。
3. 应收账单生成过程中，部分内存汇总调用了 `signedAmount`，但 `fee_detail` 落库金额仍可能沿用来源原始正数，后续 `ar_bill_currency_summary` 又从 `fee_detail.amount_bill_currency` 汇总，存在“内存计算方向”和“落库汇总方向”不一致风险。
4. `BillGenerateMapper` 中汇总口径排除了 `NON_FEE`，但没有区分 `AR_COLLECT` 和 `AR_PAY`。
5. 前端 `admin_shell/src/views/billing/feeItem/index.vue` 当前仍展示 `ARAP: 代收代付`。
6. `FeeIndex`、`FeeDetail`、`FeeDetailDTO`、`FeeDetailSaveDTO` 等注释仍是旧口径。

### 3.2 当前数据库样例

按现有测试库观察，`business_type_fee_index` 中仍存在以下 `ARAP` 配置：

| 业务场景 | 费项编码 | 费项名称 | 当前类型 | 调整后类型 |
| :--- | :--- | :--- | :--- | :--- |
| `PEER` / `CONSOLIDATION` | `FEE0022` | 代收货款 | `ARAP` | `AR_COLLECT` |
| `PEER` / `CONSOLIDATION` | `FEE0026` | 垫付金额 | `ARAP` | `AR_PAY` |
| `PEER` / `CONSOLIDATION` | `FEE0040` | 代客收台币 | `ARAP` | `AR_COLLECT` |
| `PEER` / `CONSOLIDATION` | `FEE0041` | 代客付台币 | `ARAP` | `AR_PAY` |
| `COD_ORDER` | `FEE0050` | 代收货款 | `ARAP` | `AR_COLLECT` |

## 4. 目标口径

### 4.1 新增费用类型

| 类型编码 | 展示名称 | 说明 |
| :--- | :--- | :--- |
| `AR_COLLECT` | 代收类 | 代客户收取的资金，在应收账单按负数处理 |
| `AR_PAY` | 代付类 | 代客户垫付或支付的资金，在应收账单按正数处理 |

`ARAP` 作为待迁移配置值处理，不再作为账单生成可用费用类型。数据迁移完成后，配置主档和业务场景绑定表不应再存在启用状态的 `ARAP`。

### 4.2 应收账单金额方向

| 费用类型 | 落库金额方向 | 汇总金额方向 |
| :--- | :--- | :--- |
| `AR` | 正数 | 正数 |
| `ARD` | 负数 | 负数 |
| `AR_COLLECT` | 负数 | 负数 |
| `AR_PAY` | 正数 | 正数 |
| `AP` | 不进入客户应收账单 | 不进入客户应收账单 |
| `NON_FEE` | 不进入可核销明细；如需展示，使用非核销展示明细 | 不汇总 |
| `ARAP` | 不允许参与新账单生成；生成前应通过基础数据迁移拆分为 `AR_COLLECT` 或 `AR_PAY` | 不汇总 |

建议在账单生成写入 `fee_detail` 前统一规范金额方向，确保 `amount_fee_currency`、`amount_bill_currency`、`amount_fin_currency` 三个金额字段方向一致。后续汇总 SQL 直接按已规范的 `fee_detail` 金额求和，避免同一金额在不同环节重复取反。

## 5. 技术调整方案

### 5.1 后端常量与模型

1. 在 `BmsConstants` 新增：
   - `FEE_TYPE_AR_COLLECT = "AR_COLLECT"`
   - `FEE_TYPE_AR_PAY = "AR_PAY"`
2. 保留 `FEE_TYPE_ARAP = "ARAP"` 仅用于识别未迁移配置并阻断生成；账单生成时不按费项编码/名称做方向兜底。
3. 更新 `FeeIndex`、`FeeDetail`、`FeeDetailDTO`、`FeeDetailSaveDTO` 的费用类型注释。
4. 如存在费用类型枚举或接口返回字典，补充 `AR_COLLECT`、`AR_PAY`，隐藏或禁用 `ARAP` 新增入口。

### 5.2 账单生成

1. 在 `BillGenerateServiceImpl` 中新增统一金额方向方法，例如 `normalizeAmountDirection(rule, amount)`。
2. 规则如下：
   - `ARD`、`AR_COLLECT`：统一取绝对值后转负数。
   - `AR`、`AR_PAY`：统一取绝对值后转正数。
   - `NON_FEE`：不进入应收汇总；如当前链路仍需展示，必须明确标记为非核销展示。
   - `ARAP`：不参与新账单生成；读取到启用中的 `ARAP` 配置时应阻断任务并提示先完成基础数据迁移。
3. 在构建 `fee_detail` 落库对象时即完成方向规范，不只在内存汇总处处理。
4. `ar_bill_currency_summary`、账单主表金额、未收金额均基于已规范后的 `fee_detail` 金额计算。
5. 账单重算时：
   - 草稿中、待审核账单可重算并按新口径重写明细。
   - 待结清账单如需重算，应先折返到待审核后再重算。
   - 已结清账单不得重算，只能通过调账中心冲正。

### 5.3 数据访问层

1. 检查 `BillGenerateMapper` 中所有应收金额汇总 SQL，确保排除 `NON_FEE`，并不再对 `AR_COLLECT` / `AR_PAY` 额外重复取反。
2. 若存在直接从来源数据临时表或 Map 汇总金额的 SQL，需要同步调用统一金额方向逻辑或迁移到 Java 层规范后再入库。
3. 数据迁移后，不应再存在新生成或可重算账单使用 `ARAP` 明细的场景。

### 5.4 前端

1. `admin_shell` 费项管理页面费用类型字典调整：
   - 新增 `AR_COLLECT: 代收类`
   - 新增 `AR_PAY: 代付类`
   - 移除旧 `ARAP: 代收代付` 选项，不作为新增、编辑、筛选或展示字典项保留。
2. 筛选区支持按新类型筛选，不保留 `ARAP` 筛选项。
3. 列表展示、详情展示、导出字段同步展示新类型名称。

### 5.5 数据归档

涉及表字段注释调整时，需要同步更新 `aidocs/technical-caliber/sql/ar_bill.sql` 中以下表的完整结构：

1. `fee_index`
2. `business_type_fee_index`
3. `fee_detail`

## 9. 已确认口径

1. `sale_order_fee_detail.collection` / 应返货款视为代收类，按 `AR_COLLECT` 处理。
2. 新类型编码确认采用 `AR_COLLECT` / `AR_PAY`。
3. 不需要兼容任何历史账单数据，因为当前不存在这方面的历史数据；数据调整只处理当前配置与后续生成。
4. `NON_FEE` 保留非核销展示明细，但不得进入可核销明细、账单汇总金额或核销范围。
5. `FEE0022` 与 `FEE0050` 都是“代收货款”，分别出现在普通集运/同行和 COD 场景，统一按 `AR_COLLECT` 处理。
6. `collection_premium_amount` / `receivable_collection_amount` 是代收货款手续费，仍按应收类处理；返款配置中选择直接扣减时，由返款配置规则决定排除应收账单，不改成代收类。
7. 如果目标库缺少 `代客收台币` / `代客付台币` 对应的 `fee_source_rule`，本方案 SQL 只补充费项主档，不猜测创建来源规则。
8. 前端“费用类型”筛选不保留 `ARAP`，新增、编辑、筛选、展示字典均只使用拆分后的新类型。
