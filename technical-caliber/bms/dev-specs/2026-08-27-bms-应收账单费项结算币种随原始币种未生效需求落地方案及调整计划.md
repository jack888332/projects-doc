### 1.3 PRD 口径

`PRD.账单系统.md` 第 488 行：

> 费项结算币种规则至少保留一行，且末行固定为兜底规则。当仅有一行时，兜底规则的费项口径为`全部`；存在明确费项规则时，兜底规则的费项口径自动变为`其他`。兜底规则的费项只读，不允许人工修改；其结算币种默认为`随原始币种`，也可以指定为其他币种。

`PRD.账单系统.md` 15.2.3 账单读取口径：

1. 首次生成账单时，系统只读取任务锁定的应收账单配置中已经保存的费项结算币种，不再查询币种模板。
2. 账单任务和账单结果只保存最终费项结算币种快照，不保存模板编号、模板版本或模板快照。
3. 补充生成和账单重算沿用目标账单已经锁定的费项结算币种。

因此，本次修复的最终口径应为：

- 费项结算币种规则是客户级账单配置的一部分，必须整体落库保存。
- 兜底规则必须和明确费项规则一样持久化，且默认结算币种为“随原始币种”。
- 账单生成只能读取配置中已经保存的最终规则，不能依赖模板实时匹配。
- 账单任务需要保存最终费项结算币种快照，保证补充生成、重试、重算口径稳定。

### 1.4 需求目标与边界

需求目标：

1. `ARB-OG0863-Scheme-1787793589-v2` 的兜底规则“随原始币种”真正生效。
2. 未配置明确费项结算币种的费用，按原始币种生成 `bill_currency`，不再被默认换算为 CNY。
3. 已有配置和新增配置都具备完整、可校验、可回显、可快照的费项结算币种规则集合。
4. 新账单生成、补充生成、重试、重算均能使用同一套最终规则。

需求边界：

- 本方案不修改导出的展示逻辑；导出显示 CNY 是数据结果导致的表象，不是导出代码缺陷。
- 本方案不自动修正已生成的历史账单；已生成账单需要按生产数据修复流程重新生成或替换生成。
- 本次以应收账单 `MEMBER_AR` 为修复范围；返款账单已有独立币种账户矩阵，不纳入本次。
- 已确认同批修复“生成时仍查询币种模板”的 PRD 偏差，生成只读取配置已保存的最终规则。

## 2. 现状分析

### 2.1 配置保存链路

前端保存应收账单配置时，页面上的规则集合本身包含末行兜底规则，但提交到后端的 `feeCurrencyRules` 被过滤掉了兜底规则：

`admin_front/src/views/clientmgr/listofCustomers/SettlementSettingPanel.vue`

```js
buildFeeCurrencyRules(scheme) {
  return this.normalizeFeeCurrencyRules(scheme.feeCurrencyRules)
    .filter((rule) => !rule.fallback && rule.feeCode)
    .map((rule) => ({
      ...
    }));
}
```

同时，前端把兜底规则单独放到了 `extra.fallbackFeeCurrencyRule` 和 `settlementProfile.defaultPlan.fallbackFeeCurrencyRule`。

后端保存规则时，又对 `feeCode` 为空的行直接跳过：

`bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/BillConfigServiceImpl.java`

```java
private void saveFeeCurrencyRules(Long billConfigId, BillConfigCreateReqDTO reqDTO) {
    List<BillConfigFeeCurrencyRuleDTO> rules = resolveFeeCurrencyRules(reqDTO);
    if (billConfigId == null || rules == null || rules.isEmpty()) {
        return;
    }
    for (BillConfigFeeCurrencyRuleDTO ruleDTO : rules) {
        if (ruleDTO == null || !hasText(ruleDTO.getFeeCode())) {
            continue;
        }
        ...
        billConfigMapper.insertFeeCurrencyRule(rule);
    }
}
```

后端解析规则时，只读取请求中的 `feeCurrencyRules`、模板或 `extra.feeCurrencyRules`，没有把 `extra.fallbackFeeCurrencyRule` 转成正式规则：

```java
private List<BillConfigFeeCurrencyRuleDTO> resolveFeeCurrencyRules(BillConfigCreateReqDTO reqDTO) {
    ...
    if (reqDTO.getFeeCurrencyRules() != null && !reqDTO.getFeeCurrencyRules().isEmpty()) {
        return reqDTO.getFeeCurrencyRules();
    }
    ...
}
```

结论：无论页面是否配置“随原始币种”，`bill_config_fee_currency_rule` 都不会保存兜底规则。

### 2.2 账单生成链路

账单生成时只查询 `bill_config_fee_currency_rule` 和币种模板：

`bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/BillGenerateServiceImpl.java`

```java
Map<String, BillConfigFeeCurrencyRule> feeCurrencyRuleMap =
        feeCurrencyRuleMap(billGenerateMapper.queryFeeCurrencyRules(billConfig.getId()));
```

`bill_config_fee_currency_rule` 查询 SQL：

`bms/dao/src/main/java/com/szt/supplychain/bms/dao/mapper/BillGenerateMapper.java`

```sql
SELECT id, bill_config_id, business_type_code, fee_index_id, fee_code, fee_name,
       charge_currency_mode, charge_currency, enabled
FROM bill_config_fee_currency_rule
WHERE bill_config_id = #{billConfigId} AND enabled = 1 AND is_deleted = 0
```

当前生成的规则映射：

```java
private Map<String, BillConfigFeeCurrencyRule> feeCurrencyRuleMap(List<BillConfigFeeCurrencyRule> currencyRules) {
    ...
    for (BillConfigFeeCurrencyRule currencyRule : currencyRules) {
        if (currencyRule == null || !hasText(currencyRule.getBusinessTypeCode()) || !hasText(currencyRule.getFeeCode())) {

```

规则匹配只按 `businessTypeCode:feeCode` 精确匹配，没有兜底规则维度：

```java
private BillConfigFeeCurrencyRule resolveCurrencyRule(FeeCollectRule rule,
                                                      Map<String, BillConfigFeeCurrencyRule> ruleMap) {
    ...
    return ruleMap.get(feeCurrencyRuleKey(rule.getBusinessTypeCode(), rule.getFeeCode()));
}
```

匹配不到规则时，生成代码直接使用配置默认币种：

```java
private String resolveChargeCurrency(BillConfig billConfig, BillConfigFeeCurrencyRule currencyRule, String sourceCurrency) {
    String defaultCurrency = resolveChargeCurrency(billConfig);
    if (currencyRule == null) {
        return defaultCurrency;
    }
    ...
    if (BmsConstants.FEE_CHARGE_CURRENCY_MODE_SOURCE.equals(mode) && hasText(sourceCurrency)) {
        return sourceCurrency.trim().toUpperCase(Locale.ROOT);
    }
    return defaultCurrency;

```

由于配置 86 没有任何规则行，167 条 TWD 费用全部命中 `currencyRule == null`，因此 `chargeCurrency` 被设置为 `billingCurrency=CNY`，并走 `TWD -> CNY` 的 `FEE_TO_BILL` 汇率换算。

### 2.3 任务快照链路

当前 `FeeRuleSnapshot` 只包含：

- `feeRules`：费项采集规则
- `selectedTemplateFeeCurrencyRules`：选中的币种模板规则
- `templateFeeCurrencyRules`：按业务类型查询的币种模板规则

`FeeRuleSnapshot` 没有保存配置自身的 `feeCurrencyRules`。生成时即使存在任务快照，`feeCurrencyRuleMap` 仍直接查询当前 `bill_config_fee_currency_rule`。

影响：

1. 兜底规则补齐后，重试历史任务会读取当前配置，而不是任务创建时的规则快照。
2. 如果配置在任务创建后被修改，旧任务重试可能使用新规则，不符合 PRD 15.2.3。
3. 本次修复应同步把最终费项结算币种规则写入 `fee_rule_snapshot_json`，避免同类问题再次出现。

### 2.4 导出链路

导出任务的数据快照来自账单明细，`settlementCurrency` 对应 `fee_detail.bill_currency`。当前 `fee_detail.bill_currency` 已经是 CNY，因此导出显示 CNY 是正确的数据透传，不是导出代码问题。

## 3. 根因结论

根因是“费项结算币种兜底规则没有被持久化为正式规则”，具体包括：

1. 前端 `SettlementSettingPanel.buildFeeCurrencyRules()` 提交规则时过滤掉了兜底规则。
2. 后端 `saveFeeCurrencyRules()` 跳过 `feeCode` 为空的行。
3. 后端 `resolveFeeCurrencyRules()` 没有读取 `extra.fallbackFeeCurrencyRule` 并合成兜底规则。
4. 账单生成只按 `businessTypeCode:feeCode` 精确匹配规则，没有兜底规则匹配逻辑。
5. 未命中规则时，`resolveChargeCurrency()` 返回配置默认币种 CNY。

最终：配置 86 的 `bill_config_fee_currency_rule` 为空，TWD 费用全部按 CNY 结算并换算，账单明细、币种汇总、导出结果都显示 CNY。

## 4. 推荐落地方案

### 4.1 总体原则

把“兜底规则”作为费项结算币种规则的第一等公民，与明确费项规则一起落库、回显、校验和快照。

```text
费项结算币种规则 = 明确费项规则 N 条 + 末行兜底规则 1 条
唯一数据源 = bill_config_fee_currency_rule
生成匹配顺序 = 明确费项规则 -> 该业务类型兜底规则 -> 配置默认币种
```

`extra_json.fallbackFeeCurrencyRule` 保留为兼容字段和页面展示字段，但不再作为账单生成的唯一依据。

### 4.2 数据库方案

在 `bill_config_fee_currency_rule` 增加 `is_fallback` 标记，兜底规则使用 `fee_code='FALLBACK'` 作为统一约定，避免空字符串和唯一键的歧义。

```sql
ALTER TABLE `bill_config_fee_currency_rule`
    ADD COLUMN `is_fallback` tinyint(1) NOT NULL DEFAULT 0
    COMMENT '是否兜底规则：0否，1是' AFTER `fee_name`;
```

实施时同步将 `aidocs/technical-caliber/sql/ar_bill.sql` 中 `bill_config_fee_currency_rule` 的完整 `CREATE TABLE` 更新为最新结构。

兜底规则行约定：

| 字段 | 值 |
|---|---|
| fee_code | FALLBACK |
| fee_name | 兜底规则 |
| fee_index_id | NULL |
| business_type_code | 配置适用业务类型；当前生产配置均为 CONSOLIDATION |
| charge_currency_mode | SOURCE 或 FIXED |
| charge_currency | FIXED 时必填，SOURCE 时为空 |
| enabled | 1 |
| is_fallback | 1 |

不修改 `ar_bill`、`fee_detail`、`bill_exchange_rate` 等账单结果表。

#### 4.3.1 Model / DTO

1. `BillConfigFeeCurrencyRule` 增加 `isFallback` 字段。
2. `BillConfigFeeCurrencyRuleDTO` 增加 `isFallback` / `fallback` 字段。

#### 4.3.2 配置保存

调整 `BillConfigServiceImpl`：

1. `resolveFeeCurrencyRules()`：
   - 优先使用请求 `feeCurrencyRules` 中携带的完整规则集合，包括兜底行。
   - 兼容旧请求：若 `feeCurrencyRules` 只有明确费项规则，则从 `extra.fallbackFeeCurrencyRule` / `settlementProfile.defaultPlan.fallbackFeeCurrencyRule` / `settlementProfile.branchPlanList[].fallbackFeeCurrencyRule` 合成兜底规则。
   - 合成后的兜底规则默认 `chargeCurrencyMode=SOURCE`，与 PRD 一致。
2. `saveFeeCurrencyRules()`：
   - 不再用 `!hasText(feeCode)` 过滤兜底行。
   - 兜底规则统一写入 `fee_code='FALLBACK'`、`is_fallback=1`。
   - 校验每个配置至少一条兜底规则、至多一条同业务类型兜底规则。
   - 校验明确费项规则不得使用 `FALLBACK` 作为费项编码。
3. `toFeeCurrencyRuleDTOList()`：
   - 返回兜底规则，并设置 `isFallback=true`，保证编辑回显时前端能恢复末行兜底。

#### 4.3.3 账单生成匹配

调整 `BillGenerateServiceImpl`：

1. 在原有 `feeCurrencyRuleMap` 之外，新增 `fallbackFeeCurrencyRuleMap`，按 `businessTypeCode` 保存 `is_fallback=1` 的规则。
2. `feeCurrencyRuleMap()` 继续处理明确费项规则；`is_fallback=1` 或 `fee_code='FALLBACK'` 的行不再进入明确规则映射。
3. `resolveCurrencyRule()` 增加兜底规则入参，匹配顺序调整为：

```text
明确费项规则（businessTypeCode:feeCode）
-> 该业务类型兜底规则（businessTypeCode:FALLBACK）
-> null，最终由 resolveChargeCurrency 使用配置默认币种
```

4. `resolveChargeCurrency()` 无需修改，现有 `SOURCE` 分支已经能返回原始币种；关键是让兜底规则能够被命中。
5. 三个费项组装入口 `executeConfigOrderGroups()`、`executeAdditionalFeeGroups()`、记账单/理赔入口统一传入兜底规则 Map。

#### 4.3.4 快照

1. `FeeRuleSnapshot` 增加 `feeCurrencyRules` 字段。
2. `buildCurrentFeeRuleSnapshot()` 查询并保存当前配置的完整费项结算币种规则。
3. `buildFeeRuleSnapshot()` / `buildConfigGroupFeeRuleSnapshot()` 把 `feeCurrencyRules` 写入 `fee_rule_snapshot_json`。
4. `toFeeRuleSnapshot()` 解析 `feeCurrencyRules`。
5. 生成各入口优先使用 `feeRuleSnapshot.feeCurrencyRules`，快照缺失时再回退查询当前配置。

PRD 要求生成时不再实时查询币种模板。当前代码仍按 `businessTypeCodes` 查询模板并参与匹配，属于既存偏差。建议本批一并进行：

2. 不再查询 `queryTemplateFeeCurrencyRules()` 作为生成期实时规则。
3. 模板仅作为配置编辑页的快捷填充工具。

### 4.5 存量配置修复

代码发布前，需要对生产 19 条未删除配置补齐兜底规则行。修复原则：

1. 以 `extra_json.fallbackFeeCurrencyRule` 或 `settlementProfile.defaultPlan.fallbackFeeCurrencyRule` 中的值作为兜底规则来源。
2. `chargeCurrencyMode=SOURCE` 时写 SOURCE；`FIXED` 时写对应 `chargeCurrency`。
3. 已确认：旧配置没有保存兜底字段时，默认按 `SOURCE`（随原始币种）补齐。
4. 每个配置按 `business_type_code` 插入一条 `fee_code='FALLBACK'`、`is_fallback=1` 的行。
5. 修复 SQL 需可重复执行，建议使用 `NOT EXISTS (is_fallback=1)` 过滤，避免重复插入。

示意 SQL：

```sql
INSERT INTO `bill_config_fee_currency_rule`
  (`bill_config_id`, `business_type_code`, `fee_index_id`, `fee_code`, `fee_name`,
   `charge_currency_mode`, `charge_currency`, `enabled`, `is_fallback`, `remark`, `created_by`, `updated_by`)
SELECT
  c.id,
  'CONSOLIDATION',
  NULL,
  'FALLBACK',
  '兜底规则',
  COALESCE(
    NULLIF(JSON_UNQUOTE(JSON_EXTRACT(c.extra_json, '$.fallbackFeeCurrencyRule.chargeCurrencyMode')), ''),
    'SOURCE'
  ),
```

### 4.7 候选方案对比

候选方案 A（推荐）：兜底规则落库为一等公民。

- 优点：符合 PRD“保存最终费项结算币种规则”，可校验、可回显、可快照、可追溯；不依赖 `extra_json` 解析。

候选方案 B：仅在生成时读取 `extra_json.fallbackFeeCurrencyRule`。

## 7. 风险与回归

1. 存量配置补齐兜底规则会影响后续新生成账单的币种口径；旧配置缺失 fallback 已确认按 SOURCE 补齐，执行前仍需在测试环境验证。
2. 已生成账单不会自动修正，需要重新生成或替换生成；账单状态、核销、汇率快照一致性需要按现有流程处理。
3. `bill_config_fee_currency_rule` 表结构变更涉及归档文件同步，不能遗漏。
4. 生成期实时模板匹配已确认同批下线，仍需回归“模板套用后保存为最终规则”的编辑场景。
5. 任务快照补充 `feeCurrencyRules` 后，历史任务快照仍缺失该字段；已确认暂不回补，重试时回退当前配置。
6. 兜底规则按业务类型保存，配置适用多个业务类型时可能有多条兜底行，前端和后端校验需按该粒度实现。

## 8. 疑问点及确认结果

1. 兜底规则粒度：推荐“每个配置一条兜底规则，按 `business_type_code` 保存”；当前生产配置均为单一 `CONSOLIDATION`。已确认按推荐实施；页面费项口径“其他”代表未明确配置费项的兜底，不映射为具体费项编码。
2. 旧配置未保存 fallback 字段时的默认口径：已确认按 PRD 默认 `SOURCE`（随原始币种）处理，不再按配置默认币种兜底。
3. 生产账单修复方式：`ARB-OG0863-20260801-81FF` 当前为 `GENERATED`；已确认调整后由人工重新生成，按现有重新生成/替换流程执行。
4. 是否同批下线“生成期实时查询币种模板”：已确认按推荐同批下线，生成时只读取配置已保存的最终费项结算币种规则。
5. 兜底规则编码：已确认统一使用 `fee_code='FALLBACK'` 加 `is_fallback=1`；当前前端确实未把兜底行传入 `feeCurrencyRules`，本次前端改造会补上。
6. 历史任务快照缺失 `feeCurrencyRules`：已确认暂时不管，旧任务重试回退当前配置即可，不回补历史快照。
