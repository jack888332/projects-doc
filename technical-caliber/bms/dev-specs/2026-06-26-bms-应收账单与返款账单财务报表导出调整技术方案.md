# 2026-06-26 BMS 应收账单与返款账单财务报表导出调整技术方案

## 1. 文档目的

本文基于以下资料，结合当前仓库实现，整理“应收账单导出、返款账单导出与财务实际使用表格不一致”问题的技术调整方案、实施计划与待确认问题：

1. `aidocs/product-caliber/bms/prd/财务报表导出格式.md`
2. `aidocs/product-caliber/bms/prd/uml/secondary/订单费用报表财务字段.md`
3. `admin_shell/src/views/billing/receivableBill/index.vue`
4. `admin_shell/src/views/billing/refundBill/index.vue`
5. `platform-admin/web/src/main/java/com/szt/supplychain/platform/admin/web/controller/BmsArBillController.java`
6. `platform-admin/web/src/main/java/com/szt/supplychain/platform/admin/web/controller/BmsRefundBillController.java`
7. `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/ArBillServiceImpl.java`
8. `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/RefundBillServiceImpl.java`

本方案只讨论“财务导出报表”这条链路，不扩展到账单状态机、汇率编辑、账单重跑等无关改造。

## 1.1 本轮已确认口径

结合最新确认结果，本轮方案按以下口径直接落地：

1. 应收账单、返款账单都按“一行一个订单”导出，底层 `fee_detail` 竖表数据需要转成固定金额列横表。
2. 返款账单不拆多套模板，统一使用一套模板。
3. 当前没有额外财务样本文件，本轮直接以 `aidocs/product-caliber/bms/prd/财务报表导出格式.md` 为准。
4. 汇率链路全部保留，且统一按“结算币种”口径命名，不再使用“账单币种”表述：
   - 应收账单：费项原始币 -> 费项结算币；费项结算币 -> 财务本位币
   - 返款账单：货款原始币 -> 货款结算币；费项原始币 -> 货款结算币；货款结算币 -> 财务本位币
5. 字段补数规则已确认：
   - 收件地址取 `ofp_ofdb1.sale_order_header.declaration_address`
   - 末条信息相关字段本轮先留空
   - 报关单号本轮先留空
6. 汇总 sheet 暂不要求增加付款凭证、备注、支付/返款流水摘要。
7. 历史账单重新导出不要求严格还原“账单生成时快照”，允许按当前业务表实时数据导出。

## 2. 结论先行

结合当前代码，先给出 4 个直接结论：

1. `admin_shell` 页面不是导出内容的主实现层，只负责触发下载；真正的导出内容拼装发生在 `platform-admin`。
2. 应收账单当前导出仍是“账单信息 + 费项小计 + 订单维度动态费项横表”，核心粒度偏运营看板，不是财务实际核账表。
3. 返款账单当前导出仍是“历史遗留固定表头 + 大量空白列 + 业务单聚合行”，与 PRD 中整理出的财务使用表差异更大。
4. 本轮最合理的改造方式不是继续在 Controller 里手写 HTML 伪 Excel，而是保持前端入口不变，把 `platform-admin` 导出改成固定模板的真实 `.xlsx`，同时让 `bms` 提供“一行一个订单”的结构化横表数据。

## 3. 现状盘点

## 3.1 当前导出调用链

### 应收账单

1. `admin_shell/src/views/billing/receivableBill/index.vue`
   - 点击导出时调用 `/portal/bms/arBill/export`
2. `platform-admin/.../BmsArBillController.java`
   - `export()` 调用 `arBillRemoteService.exportData()`
   - `writeExcel()` 用字符串拼 HTML 表格，再以 `.xls` 响应下载
3. `bms/.../ArBillServiceImpl.java`
   - `exportData()` 从 `fee_detail` 查询费用明细
   - 按 `businessOrderNo` 聚合成一行订单，多列费项

### 返款账单

1. `admin_shell/src/views/billing/refundBill/index.vue`
   - 点击导出时调用 `/portal/bms/refundBill/export`
2. `platform-admin/.../BmsRefundBillController.java`
   - `export()` 实际调用的是 `refundBillRemoteService.detail()`
   - `writeExcel()` 用固定旧表头手写 HTML 表格，再以 `.xls` 响应下载
3. `bms/.../RefundBillServiceImpl.java`
   - `detail()` 先拉取 `feeDetails`
   - 再聚合生成 `feeSummaries`
   - Portal 导出使用的是 `feeSummaries`，不是 `RefundBillExportRespDTO`

结论：当前导出的主要改造面不在前端，而在 `platform-admin + bms`。

## 4. 调整方案

## 4.1 总体设计原则

本轮建议遵循以下原则：

1. 保持前端入口不变
   - `admin_shell` 继续调用现有 `/portal/bms/arBill/export`
   - `admin_shell` 继续调用现有 `/portal/bms/refundBill/export`
2. 保持 Portal 路由不变，避免前端联动范围扩大
3. 导出文件从当前 HTML 伪 `.xls` 调整为真实 `.xlsx`
4. 导出模板改为固定字段，不再使用动态费项列和大量空白占位列
5. `bms` 负责准备结构化导出数据，`platform-admin` 负责生成最终 Excel
6. 全链路使用显式 DTO，不使用 `Map` 作为服务接口出参
7. 优先输出财务真实使用字段，无法落地的字段单独列入“待确认/待补数”清单

## 4.2 推荐实现形态

### 4.2.1 生成真实 `.xlsx`

推荐将 `platform-admin` 两个导出 Controller 从“字符串拼 HTML”改为“Workbook 输出”。

原因：

1. 当前导出是伪 Excel，本质是 HTML 表格，适合临时查看，不适合固定模板维护
2. PRD 已经明确建议固定 sheet 结构为：
   - `明细`
   - `汇总`
3. 当前仓库中已有 `ExcelCreater`、`Workbook`、`POIUtil` 等能力，技术上可以直接复用

### 4.2.2 Sheet 结构建议

建议统一为 2 个 sheet：

1. `明细`
   - 放财务对账主表
   - 固定列顺序
   - 一次导出即可直接筛选、透视、核账
2. `汇总`
   - 放账单头部信息
   - 放汇总金额
   - 放汇率、备注、凭证等非明细字段

如财务坚持“头部信息必须出现在明细 sheet 顶部”，则保留：

1. `明细` sheet 顶部 2 到 4 行账单头
2. `汇总` sheet 再放一份统计汇总

## 4.3 应收账单调整方案

## 4.3.1 数据粒度建议

应收账单推荐以 `fee_detail` 为主线生成导出明细，但最终导出结果必须是一行一个订单的固定金额列横表，而不是当前动态费项列。

建议规则：

1. 导出最终粒度按“一个订单一行”组织，建议主键以 `businessOrderNo` 为主，必要时辅以尾程单号兜底。
2. 底层仍以 `fee_detail` 为主线取数，但要先按订单聚合，再把纵向费项转成固定金额列横表。
3. 每一行保留该订单维度的完整追溯链路。
4. 固定金额列按费项类型落位
   - 命中“运费”则填“运费”列
   - 命中“派送费”则填“派送费”列
   - 命中“代收手续费”则填“代收手续费”列
   - 其他未单列费项统一进入“其它费用”

这样做的好处：

1. 符合 PRD “一行一个订单”的使用习惯
2. 保留 `fee_detail` 作为底层来源，不破坏现有数据主线
3. 不再因为动态费项列导致不同账单列头变化
4. 财务可以按固定列做汇总透视

## 4.3.2 BMS 后端调整

4. `ArBillFinanceExportSummaryDTO`

建议新增专用导出查询，不复用当前 `ArBillExportRespDTO` 的动态横表结构。

导出行至少应覆盖以下字段：

1. 账单级字段
   - 账单编号
   - 账期开始/结束
   - 客户名称
   - 业务板块
   - 目的国
   - 结算币种
   - 锁定汇率
   - 制表日期
2. 费项级字段
   - 费项编码
   - 费项名称
   - 挂靠对象
   - 业务主单号
   - 尾程单号
   - 首程单号
   - 来源系统
   - 来源表
   - 来源单据号
3. 金额级字段
   - 费用币种
   - 原币金额
   - 费项原始币 -> 费项结算币汇率
   - 费项结算币金额
   - 费项结算币 -> 财务本位币汇率
   - 财务本位币金额
   - 运费
   - 派送费
   - 进店
   - 打包
   - 应收货款
   - 代收手续费
   - 代收回款
   - 其它费用
4. 追溯级字段
   - 核重时间
   - 末条时间
   - 末条信息
   - 凭证
   - 录入时间
   - 录入人
   - 备注
5. 收件/物流字段

    - 收件地址
   - 商品品名

   - 所属仓库
   - 所属店铺

### 4.3.3 字段来源优先级建议

应收账单建议按以下优先级取值：

1. `ar_bill` / `ar_bill_currency_summary`
2. `fee_detail` 已有显式字段
3. `fee_detail.source_extra_json` 快照字段
4. 来源订单/来源业务表补充查询
5. 本轮已确认的补数口径：
   - 收件地址取 `ofp_ofdb1.sale_order_header.declaration_address`
   - `lastTrajectoryStatus`、`lastTrajectoryDesc`、`lastTrajectoryTime` 先留空
   - `declarationOrderNos` 先留空
6. 仍无法获取时输出空值，并在开发阶段记录缺口字段

## 4.4 返款账单调整方案

## 4.4.1 数据粒度建议

返款账单推荐按“一行一个订单”组织导出，不再使用当前遗留空白模板，也不继续使用当前只识别 3 类扣减项的 `feeSummaries`。

原因：

1. PRD 给出的返款样例本身更接近“一个订单一行”
2. 返款账单当前存在本金项、扣减项、回款项，多条 `fee_detail` 需要合并后才符合财务操作习惯
3. 当前 `feeSummaries` 聚合能力过弱，只能满足极少量费用列
4. 本轮已确认不拆模板，因此所有返款模式都要收口到同一套横表字段中

建议按 `businessOrderNo` 为主、`lastMileWaybillNo` 为辅作为聚合键，扩展以下固定金额列：

1. 运费
2. 派送费
3. 代收款
4. 代收手续费
5. 回款
6. 退款金额/应退金额
7. 超商取件费
8. 附加服务项目/其他收入
9. 其他费用

## 4.5 平台导出层调整方案

`platform-admin` 两个 Controller 建议统一做以下改造：

1. 保留现有 URL 不变
   - `/portal/bms/arBill/export`
   - `/portal/bms/refundBill/export`
2. 把 Controller 中的 `writeExcel()` HTML 拼接逻辑迁出
3. 改为固定 DTO + Workbook 输出
4. 文件后缀统一改为 `.xlsx`

1. Controller 继续保留
2. 新增导出构建类或导出服务类
3. 单独封装“应收导出”和“返款导出”的 Workbook 生成逻辑

## 4.6 Admin Shell 调整方案

`admin_shell` 本轮不承担模板拼装，只需要做最小联动：

1. 保持导出按钮和入口位置不变
2. 如果后端改为 `.xlsx`，前端下载文件名同步改成 `.xlsx`
3. 若财务要求区分模板版本，可把下载名改为：
   - `应收账单明细-{billNo}.xlsx`
   - `返款账单明细-{billNo}.xlsx`

除下载文件名外，`admin_shell` 不建议做额外业务逻辑改造。

## 6. 风险与注意事项

1. 当前实际样本文件不在仓库中，本轮完全以 `财务报表导出格式.md` 为准，因此后续若财务再给出真实样本，可能还会有列顺序微调。
2. 返款账单目前很多目标字段在现有 DTO 中不存在，可能需要从 `source_extra_json` 或来源业务表补数，工作量不只是导出模板替换。
3. 当前 Portal 导出是 HTML 伪 Excel，切到真实 `.xlsx` 后，单个大账单导出耗时和内存占用会增加，需要关注。
4. 历史账单重新导出不要求严格还原生成时快照，因此本轮允许使用业务表实时数据；需要接受“历史重导结果与历史人工文件不完全一致”的业务前提。

## 7. 疑问点确认结果

以下疑问点已经确认，可直接按确认口径开发：

1. 明细粒度确认：
   - 应收账单、返款账单都按“一行一个订单”
   - 底层 `fee_detail` 竖表转固定金额列横表

2. 模板策略确认：
   - 返款账单不拆多模板
   - 统一一套模板，按字段有值则展示、无值则留空

3. 样本来源确认：
   - 当前没有额外财务样本
   - 直接按 `财务报表导出格式.md` 落地

4. 汇率展示确认：
   - 应收账单保留两层汇率：费项原始币 -> 费项结算币；费项结算币 -> 财务本位币
   - 返款账单保留三层口径：货款原始币 -> 货款结算币；费项原始币 -> 货款结算币；货款结算币 -> 财务本位币

5. 字段补数确认：
   - 收件地址取 `sale_order_header.declaration_address`
   - 末条轨迹状态、末条轨迹描述、末条轨迹时间先留空
   - 报关单号先留空

6. 汇总展示确认：
   - 本轮先不额外增加付款凭证、备注、支付/返款流水摘要

7. 历史重导确认：
   - 不要求与账单生成时快照完全一致
   - 可直接使用当前业务表实时数据

## 8. 结论

本问题不是单纯的“改几个列名”，而是导出职责边界和数据粒度都需要调整：

1. `admin_shell` 只是下载入口，不是导出模板主实现层。
2. `platform-admin` 当前两套导出都是历史 HTML 模板，已经不适合承接财务正式报表。
3. `bms` 当前导出 DTO 也不足以支撑财务使用字段，需要补一套结构化导出模型。

建议本轮按“先确认字段和粒度，再改 `bms` 数据模型，最后改 `platform-admin` 模板”的顺序推进，这样最稳，也最符合当前仓库的实际实现边界。
