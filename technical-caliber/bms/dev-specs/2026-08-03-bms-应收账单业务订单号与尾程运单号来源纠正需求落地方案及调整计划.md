# BMS 应收账单业务订单号与尾程运单号来源纠正需求落地方案及调整计划

> 日期：2026-08-03  
> 页面路由：`/billing/receivableBill`  
> 前端范围：`admin_front/src/views/billing`  
> 文档状态：业务规则及 CXMS 有效状态口径已确认，待技术评审  
> 本文只形成落地方案，不包含业务代码、DDL 或环境配置变更。

## 1. 结论摘要

应收账单详情页“费用明细”中的字段来源统一纠正为：

| 页面字段 | BMS 落库字段 | 正确来源 | 关联规则 |
| --- | --- | --- | --- |
| 业务单号 | `fee_detail.business_order_no`、`main_order.order_no` | `ofp_ofdb1.sale_order_header.delivery_order_code` | 直接取当前 OFP 订单行 |
| 尾程运单号 | `fee_detail.last_mile_waybill_no`、`main_order.last_mile_waybill_no` | `cxms.ob_shipping_package_header.sub_waybill_no` | `delivery_order_code = erp_order_no` 且 OFP/CXMS `warehouse_code` 相等 |
| 首程运单号 | `fee_detail.first_mile_waybill_no`、`main_order.first_mile_waybill_no` | 维持现状：`sale_order_header.master_waybill_no` | 本次不调整 |

OFP 与 CXMS 必须使用两个独立连接、两段 SQL 查询，禁止在 OFP SQL 中直接 `JOIN cxms...`。以 `warehouse_code + erp_order_no` 作为 CXMS 查找键；同一组合对应多条 CXMS 数据时，在 Java 内按 CXMS `id` 升序、去空、去重后用英文逗号拼接，再写入 BMS 快照表。

已确认的关键落地约束：

1. BMS 两个尾程字段均由 `varchar(64)` 扩容为 `varchar(1000)`。
2. 同一账单不会出现重复 `delivery_order_code`；继续保留 `main_order` 账单内业务单号唯一约束，并在生成前做防御性校验。
3. 只保留 CXMS 有效、未归档且 `sub_waybill_no` 非空的数据；有效状态以 CXMS `sys_dict/sys_dict_detail` 的 `PACKAGE_STATUS` 字典为准，排除 `990=重置装箱`。
4. 需要支持按单个 `sub_waybill_no` 严格检索，因此除逗号快照外增加规范化子运单关系表和索引。
5. COD 返款账单及返款导出同步调整，统一字段来源和跨库拆分方式。

## 2. 需求边界与字段语义

### 2.1 本次范围

- 应收账单生成时，纠正业务单号和尾程运单号的数据来源。
- 同步写入 `main_order` 与 `fee_detail`，保证详情查询、横向/纵向展示、手工费用关联及导出读取到同一份快照。
- 移除应收相关代码中现存的 OFP SQL 直接跨库关联 CXMS 的实现，改为分段批量查询。
- COD 返款账单、返款导出同步使用相同来源和批查组件，删除现有直接跨库关联。
- 增加单个尾程号规范化检索能力，并补充 CXMS 数据源配置。

### 2.2 不在本次默认范围

- 首程运单号来源调整。
- 修改 `aidocs/technical-caliber/bms/deployment/env.md`。
- 任何历史账单数据回填；本次只影响发布后新生成的账单及发布后由业务主动重跑生成的数据。

### 2.3 字段语义约定

- `business_order_no`/`main_order.order_no`：业务展示号，固定使用 OFP `delivery_order_code`，不再回退到 `biz_order_no` 或 `order_code`。
- `source_biz_no`：保留来源订单追溯语义，可继续记录 OFP `order_code`，不应因为展示号纠正而覆盖。
- `last_mile_waybill_no`：保存该业务单号对应的全部非空 CXMS `sub_waybill_no` 快照，以英文逗号分隔。
- CXMS 无有效匹配或只有空 `sub_waybill_no` 时写 `NULL`，不回退到 OFP `waybill_no`。

## 3. 当前代码链路与问题

### 3.1 页面读取链路

1. `admin_front/src/views/billing/receivableBill/index.vue` 调用费用明细分页接口。
2. 接口为 `/platform/portal/bms/arBill/feeDetail/page`。
3. `ArBillMapper` 从 `fee_detail.business_order_no`、`last_mile_waybill_no`、`first_mile_waybill_no` 返回页面。
4. 前端横向视图以 `businessOrderNo` 分组，并取该组第一条费用的尾程/首程字段。

因此根因在账单生成快照口径，页面不是字段来源的真实计算位置。前端仅需修正不合规的回退和展示兼容。

### 3.2 当前生成口径

`BillGenerateServiceImpl` 当前行为：

- OFP 主订单查询选择 `h.order_code`、`h.biz_order_no`、`h.waybill_no`、`h.master_waybill_no`，尚未把 `delivery_order_code` 作为生成字段。
- `businessOrderNo()` 优先取 `h_biz_order_no`，再回退 `h_order_code`。
- `buildMainOrder()` 和 `buildFeeBase()` 的尾程运单号取 `h_waybill_no`。
- 订单费、附加费、独立返款费用等存在多处共用或直接赋值，不能只改页面字段或单个 SQL 别名。

### 3.3 现存违规跨库查询

`ArBillServiceImpl.loadArSourceOrderMap()` 和 `RefundBillServiceImpl.loadRefundSourceOrderMap()` 当前均在 OFP 连接内直接：

- `LEFT JOIN cxms.ob_shipping_package_header`；
- 按旧关系 `sale_order_header.order_code = ob_shipping_package_header.platform_order_no`；
- 通过 `MAX(id)` 只保留一条包裹记录。

该实现同时违反“禁止直接跨库关联”、新关联字段和一对多完整落库三项要求。应收与 COD 返款链路均纳入本次，必须同步拆分并统一规则。

### 3.4 前端回退风险

前端当前使用 `item.businessOrderNo || item.sourceBizNo || '-'`。如果 OFP `delivery_order_code` 缺失，页面会再次显示旧的 `sourceBizNo`，从而掩盖数据异常并破坏新口径。建议改为只展示 `businessOrderNo || '-'`。

## 4. 数据库只读核验结果

核验日期为 2026-08-03，连接信息仅从 `aidocs/technical-caliber/bms/deployment/env.md` 读取，未修改任何环境文件或数据库数据。所有核验均为单库查询，没有执行跨库 JOIN。

### 4.1 OFP 业务单号

`ofp_ofdb1.sale_order_header`：

- 总行数：1,253,107。
- `delivery_order_code` 空值/空串：0。
- 非空去重数：1,252,216，说明该字段不是全局唯一。
- 字段类型：`varchar(50)`。
- 可用索引：`idx_delivery_order_code(delivery_order_code)`；另有联合索引以 `delivery_order_code` 为首列。
- 全库和历史月份可观察到重复值，但业务已确认同一账单范围内不会出现重复 `delivery_order_code`。

BMS 线上 `main_order` 当前唯一索引为 `uk_main_order_bill_order(bill_type,bill_no,order_no)`，与上述业务约束一致，无需改变唯一键粒度。为避免异常源数据被 `ON DUPLICATE KEY UPDATE` 静默覆盖，生成前仍需校验同一账单批次内 `delivery_order_code` 唯一；发现重复时任务失败并输出脱敏诊断日志，不执行合并。

另需注意：`aidocs/technical-caliber/bms/sql/ddl/init.sql` 中仍记录旧唯一索引 `uk_main_order_no(order_no)`，与当前数据库不一致。实施 DDL 时必须先以目标环境实际结构为基线，并同步修正 DDL 归档，不能直接照搬旧初始化脚本。

### 4.2 CXMS 表结构与索引

`cxms.ob_shipping_package_header`：

- 总行数：1,228,936。
- `erp_order_no varchar(64)`，可空。
- `warehouse_code varchar(32)`，非空；与 OFP `sale_order_header.warehouse_code varchar(64)` 按字符串等值关联。
- `sub_waybill_no varchar(64)`，可空；表注释说明其用于同订单多箱场景。
- `is_archived tinyint` 默认值为 0，字段注释明确“归档的数据只有特殊接口才返回”，本次固定过滤 `is_archived = 0`。
- `status varchar(32)` 的字段注释只列出状态名称；进一步核验 CXMS `sys_dict/sys_dict_detail` 后，已找到 `PACKAGE_STATUS` 权威映射，其中 `990=重置装箱`，其余字典状态属于正常包裹生命周期。
- 单列索引 `idx_erpOrderNo(erp_order_no)`：在只有 `warehouse_code + erp_order_no` 条件时，当前 EXPLAIN 实际选择该索引，再对仓库编码做回表过滤。
- 联合索引 `idx_erp_order_no_status(erp_order_no,status)`：完整条件下属于候选索引，但当前数据分布下优化器未选择。
- 联合索引 `idx_erp_order_no(node_code,warehouse_code,erp_order_no)`：用户推荐使用。实测只有查询同时提供 `node_code`、`warehouse_code`、`erp_order_no` 时才会命中；仅提供后两列时因缺少最左列 `node_code`，优化器仍选择 `idx_erpOrderNo`。
- `idx_sub_waybill_no(sub_waybill_no)` 与唯一索引 `uniq_warehouse_waybill_no(warehouse_code,sub_waybill_no)`：适合反查，不是本次主查询入口。

对目标 SQL 执行 `EXPLAIN`：

```sql
SELECT erp_order_no, warehouse_code, id, sub_waybill_no
FROM ob_shipping_package_header
WHERE warehouse_code = ?
  AND erp_order_no IN (?, ?, ?)
  AND is_archived = 0
  AND status IN (
      '100','670','700','720','724','726','728',
      '900','910','915','920','930','935','940','945','950',
      '954','960','970','972','974','976','978',
      '980','982','984','986','988'
  )
  AND sub_waybill_no IS NOT NULL
  AND sub_waybill_no <> ''
ORDER BY erp_order_no, id;
```

使用 `warehouse_code + erp_order_no + 有效状态` 完整条件执行 EXPLAIN，结果为 `type=range`、`key=idx_erpOrderNo`、`Using index condition; Using where`。补充 `node_code = ?` 后，优化器才选择 `idx_erp_order_no`，其 `key_len=519`，三个索引列均可参与定位。OFP `sale_order_header` 当前没有可与 CXMS 对应的 `node_code` 字段，因此不能为命中索引硬编码节点值；除非 CXMS 业务确认并提供稳定的节点来源，否则生产查询继续让优化器选择 `idx_erpOrderNo`，不使用 `FORCE INDEX`。禁止对关联列使用函数、隐式类型转换或模糊匹配。

### 4.3 一对多与字段容量

抽样结果：

| `erp_order_no` | CXMS 行数 | 去重后子单数 | 逗号拼接长度 |
| --- | ---: | ---: | ---: |
| `260527011` | 20 | 20 | 179 |
| `48599231` | 55 | 50 | 501 |
| `48857377` | 23 | 6 | 65 |

BMS 线上及 DDL 归档中的 `main_order.last_mile_waybill_no`、`fee_detail.last_mile_waybill_no` 均为 `varchar(64)`，且都有普通索引。即使只有 6 个较短子单号，也可能超过 64 字符。

按业务确认，两个字段统一扩容为 `varchar(1000)`。由于 `utf8mb4` 下完整索引 1000 个字符可能超过 InnoDB 单索引键长度，且逗号字段无法高效严格匹配其中一个子单号，现有两个尾程字段上的普通索引不能继续承担单号检索。目标方案保留 `varchar(1000)` 作为展示快照，同时增加规范化子运单关系表，以独立 `sub_waybill_no varchar(64)` 索引支持严格检索。

## 5. 目标方案

### 5.1 两阶段批量查询

```mermaid
flowchart LR
    A["OFP 分页查询 sale_order_header"] --> B["取得 delivery_order_code"]
    B --> C["取得 warehouse_code，按仓库和业务单号去重"]
    C --> D["独立 CXMS 连接，按仓库分组并对 erp_order_no 批量查询"]
    D --> E["Java 按 warehouse_code + erp_order_no 分组、去空、去重、按 id 稳定排序"]
    E --> F["英文逗号拼接 sub_waybill_no"]
    F --> G["回填本批 OFP 内存行"]
    G --> H["写 main_order 与 fee_detail 快照"]
```

具体步骤：

1. 在现有 OFP 主订单分页 SQL 增加 `h.delivery_order_code AS h_delivery_order_code`。
2. 每个已取出的 OFP 批次收集非空的 `h_warehouse_code + h_delivery_order_code` 组合并去重；任一关联字段为空时不查 CXMS，尾程结果保持空。
3. 使用独立 CXMS 连接，先按 `warehouse_code` 分组，每个仓库内再按最多 300 个 `delivery_order_code` 构造 PreparedStatement 的 `erp_order_no IN (...)` 查询；避免把不同仓库的业务单号混在同一结果中。
4. 查询只选择 `id`、`warehouse_code`、`erp_order_no`、`sub_waybill_no`，并追加 `is_archived = 0` 与 `PACKAGE_STATUS` 有效白名单（排除 `990=重置装箱`）；不全表聚合，不在数据库执行全量 `GROUP BY`/`GROUP_CONCAT`。
5. Java 使用强类型 CXMS 子运单 DTO 和以 `warehouse_code + erp_order_no` 组合为键的 `LinkedHashSet<String>` 聚合，不新增以裸 `Map` 作为方法入参/返回值的接口。对 `sub_waybill_no` 执行 `trim`、去空、去重，并依据 SQL 的 `warehouse_code,erp_order_no,id` 顺序稳定拼接。
6. 将拼接结果以新增内存别名（如 `cxms_sub_waybill_nos`）回填到对应 OFP 行。
7. `buildMainOrder()`、订单费用、附加费等应收生成路径统一从：
   - `h_delivery_order_code` 写业务单号；
   - `cxms_sub_waybill_nos` 写尾程运单号；
   - `h_master_waybill_no` 写首程运单号。
8. 写入 `main_order` 与 `fee_detail` 逗号快照的同时，把每个子运单号逐行写入规范化关系表。
9. COD 返款生成、返款导出复用同一 OFP/CXMS 分段查询和聚合规则，不保留旧的 `order_code = platform_order_no` 或 `MAX(id)` 口径。
10. CXMS 查询失败时整个当前账单生成任务失败，不允许把 OFP 旧尾程号或部分查询结果落库。依赖现有任务重跑机制保证一致性。

### 5.2 数据源连接

- OFP 与 CXMS 各自建立只读 JDBC Connection，生命周期限定在批量读取阶段并使用 try-with-resources 关闭。
- 禁止通过 `FROM ofp_table JOIN cxms.table`、视图、临时跨库 SQL 等方式规避拆分要求。
- 不能在代码中硬编码账号、密码、主机或库名。
- 当前 `fee_source_datasource` 只有 OFP 相关记录，没有 CXMS 记录；账单生成运行时也尚未真正按该表解析来源连接。
- 本次确定新增 `CXMS_DB` 配置：`source_system=CXMS`、`default_database/default_schema=cxms`，JDBC URL 指向 `cxms` schema；账号和密码配置复用有 CXMS 查询权限的 OFP 数据库用户。
- 配置数据应通过版本 SQL 使用 `INSERT ... SELECT` 从当前环境 `OFP_DB` 复制连接公共参数，仅替换数据源编码、名称、来源系统、JDBC 默认库和 schema。禁止在版本 SQL 中写明文密码，也不能把开发环境地址复制到其他环境。
- 抽取窄职责的数据源解析组件，按 `OFP_DB`/`CXMS_DB` 从 `fee_source_datasource` 加载连接参数，供 `BillGenerateServiceImpl`、`ArBillServiceImpl`、`RefundBillServiceImpl` 共用。
- 当前表字段名为 `password_cipher`，但现有 `SourceDataMigrationServiceImpl` 实际把它直接作为 JDBC 密码使用，没有解密逻辑。实施前需保持与现网记录一致，不能一边存密文一边直接连接；密码治理可另立安全整改，不在本需求内扩散。
- `fee_source_datasource` 配置读取失败、记录未启用或连接测试失败时任务应快速失败，不允许回退到代码字符串替换 JDBC URL。

`CXMS_DB` 配置至少包含以下内容：

| 字段 | 配置值/生成规则 |
| --- | --- |
| `datasource_code` | `CXMS_DB` |
| `datasource_name` | `CXMS尾程包裹库` |
| `source_system` | `CXMS` |
| `env_code` | 沿用当前部署环境值 |
| `db_type`、`driver_class_name` | 复制本环境有效 `OFP_DB` 配置 |
| `jdbc_url` | 复制 OFP 主机及连接参数，仅把默认 schema 改为 `cxms` |
| `username`、`password_cipher`、`password_mask` | 复制本环境 `OFP_DB` 的可用凭据配置，不在脚本中出现明文 |
| `default_database`、`default_schema` | `cxms` |
| 超时、最大行数、启用标识 | 复制 `OFP_DB` 后按 CXMS 压测结果调整，初始保持启用 |

版本数据脚本必须可幂等执行：不存在时插入，已存在时只更新本需求管理的连接元数据和启用状态，不覆盖运维已轮换的密码。发布前分别验证 `OFP_DB`、`CXMS_DB` 能独立建立连接并执行 `SELECT 1`。

### 5.3 聚合规则

已确认规则如下：

- 关联键严格使用双条件：`sale_order_header.delivery_order_code = ob_shipping_package_header.erp_order_no` 且两表 `warehouse_code` 相等；不做大小写转换、截断或模糊匹配。
- 仅查询 `is_archived = 0`、`status` 属于 CXMS `PACKAGE_STATUS` 有效白名单且 `sub_waybill_no` 非空的数据。白名单包含正常创建、装箱、发运、运输、清关、妥投和退件流程状态，明确排除 `990=重置装箱`；后续 CXMS 字典新增状态时必须评审后更新 BMS 白名单。
- 相同 `sub_waybill_no` 只保留一次。
- 按 CXMS `id` 升序输出，保证重复生成结果稳定。
- 使用英文半角逗号 `,` 分隔，不在逗号两侧增加空格。
- 无有效结果写 `NULL` 并记录批次命中率/空结果数日志，不回退旧字段。
- 同一账单内 `delivery_order_code` 必须唯一；违反约束时终止生成，不合并源订单。

## 6. 数据模型与查询兼容调整

### 6.1 必须调整的字段

按已确认容量，同时修改：

```sql
ALTER TABLE main_order
  MODIFY COLUMN last_mile_waybill_no VARCHAR(1000) NULL COMMENT '尾程运单号，多个子运单号英文逗号分隔';

ALTER TABLE fee_detail
  MODIFY COLUMN last_mile_waybill_no VARCHAR(1000) NULL COMMENT '尾程运单号，多个子运单号英文逗号分隔';
```

以上仅为设计示例，不可直接上线执行。实施时需先删除或调整 `idx_main_order_waybill`、`idx_fee_last_waybill`；`utf8mb4 varchar(1000)` 不应建立完整单列索引。最终 DDL 同步到版本 SQL、`aidocs/technical-caliber/sql/ar_bill.sql` 及 `aidocs/technical-caliber/bms/sql/ddl/init.sql`。

应用聚合完成后还应校验拼接结果长度不超过 1000。若超长，任务失败并输出业务号和子单数量，不允许截断后落库。

### 6.2 单个尾程号规范化检索

业务已确认需要按一个 `sub_waybill_no` 严格检索。逗号字符串只用于快照展示，不能使用 `LIKE '%值%'`、`FIND_IN_SET` 或正则作为长期检索方案，这些方式无法有效利用索引且可能产生子串误命中。

建议新增 `bill_order_waybill_snapshot`（最终表名可按项目命名评审）保存一单多尾程关系：

| 字段 | 建议类型 | 用途 |
| --- | --- | --- |
| `id` | `bigint unsigned` | 主键 |
| `bill_type` | `varchar(16)` | 应收/COD 返款等账单类型隔离 |
| `bill_id` | `bigint unsigned` | BMS 账单 ID |
| `bill_no` | `varchar(64)` | BMS 账单编号 |
| `main_order_id` | `bigint unsigned` | 主订单快照 ID |
| `business_order_no` | `varchar(64)` | OFP `delivery_order_code` 快照 |
| `warehouse_code` | `varchar(64)` | OFP/CXMS 匹配仓库编码快照 |
| `sub_waybill_no` | `varchar(64)` | 单个 CXMS 子运单号 |
| `cxms_package_id` | `bigint` | CXMS 包裹行 ID，便于追溯和稳定排序 |
| `created_at`/`created_by` | 审计字段 | 创建审计 |

建议索引：

- 唯一键 `(bill_type, bill_no, business_order_no, warehouse_code, sub_waybill_no)`，保证重跑幂等并保留来源仓库维度。
- 查询索引 `(bill_id, sub_waybill_no, business_order_no, warehouse_code)`，支持账单详情内按单个尾程号精确命中业务单。
- 关联索引 `(main_order_id, sub_waybill_no)`，支持主订单挂靠校验和清理。

费用明细按单个尾程号过滤时，通过 `bill_id + business_order_no` 对该关系表执行 `EXISTS`，并令 `sub_waybill_no = #{lastMileWaybillNo}`；不得扫描 `fee_detail.last_mile_waybill_no` 逗号串。COD 返款和手工挂靠也复用关系表的精确单号结果。

关系表与 `main_order`、`fee_detail` 必须在同一 BMS 本地事务内写入。若主订单因为幂等键已存在，应先取得实际 `main_order.id`，再执行关系表幂等 upsert；生成任务失败或重跑时按现有账单清理边界同步处理关系行。

### 6.3 现有单值查询兼容调整

以下逻辑当前把尾程字段当作“单值”使用，改为逗号集合后需要一并评审：

- `ArBill-mapper.xml` 中 `countActiveFeeByAttachment`、`countBillOrderByAssociation`、`selectBillOrderByAssociation` 使用 `last_mile_waybill_no = #{associatedNo}`。
- 费用明细筛选使用 `LIKE '%...%'`，存在子串误命中且无法利用普通索引。
- 返款账单查询存在 `IN (last_mile_waybill_no...)` 等单值假设。

上述按单个尾程号判断的逻辑统一优先查询 `bill_order_waybill_snapshot`；只有未回填关系快照的历史账单使用 `FIND_IN_SET` 做完整分段兼容，禁止 `%LIKE%` 子串匹配。页面展示和导出字段继续读取 `varchar(1000)` 拼接快照。

### 6.4 业务单号唯一性保护

业务已确认同一账单不会出现相同 `delivery_order_code`，因此保留线上唯一键 `uk_main_order_bill_order(bill_type,bill_no,order_no)`，不做订单合并、不修改重量、件数和时间聚合规则。生成阶段增加账单内重复检测；异常时终止任务，避免 upsert 覆盖。

## 8. 事务、一致性与性能

### 8.1 一致性

- CXMS 数据属于生成时快照；先完成整个 OFP 批次的 CXMS 补全，再开始该批 BMS 写入。
- CXMS 连接不参与 BMS 本地事务，也不尝试分布式事务。
- CXMS 读取异常、超时或批次返回不完整时抛出异常，使生成任务失败；不得部分成功后用旧字段补齐。
- BMS 拼接快照、规范化子运单关系和主订单快照在同一事务内写入，任何一处失败均回滚。
- 重跑仍以现有 `dedupe_key`、归集标记和账单增量机制为基础，但需专项验证尾程快照是否会更新，以及已存在 `main_order` 的 upsert 结果。
- 历史账单不回填，已存在历史尾程字段保持原快照。

### 8.2 性能规则

- OFP 查询继续按现有分页执行，一页一批补全，避免一次把整账期编号载入内存。
- CXMS 入参先去重，每批不超过 300；使用 PreparedStatement 参数，不拼接业务值。
- CXMS SQL 必须同时过滤 `warehouse_code` 和 `erp_order_no`。在没有可靠 `node_code` 的情况下，当前完整条件 EXPLAIN 使用 `idx_erpOrderNo`；若后续获得可靠节点来源，则增加 `node_code` 条件以命中 `idx_erp_order_no(node_code,warehouse_code,erp_order_no)`。不使用硬编码节点或 `FORCE INDEX`。
- 只查聚合与导出补全所需的 `id, warehouse_code, erp_order_no, sub_waybill_no` 及承运/申报等明确白名单字段，禁止 `SELECT *`。
- 不执行 CXMS 全表 `GROUP BY`。本次核验中，全表按 `erp_order_no` 聚合已出现超时，进一步说明必须限定 IN 批次。
- 日志记录批次数、业务单号数、命中数、无尾程数、去重前后子单数、最大拼接长度和耗时，不打印账号密码或大批完整单号。

## 11. 业务与数据口径确认结论

### 11.1 已确认

1. 同一账单不会出现重复 `delivery_order_code`，不需要合并 OFP 订单。
2. CXMS 仅保留有效数据：`is_archived = 0`，状态取 `PACKAGE_STATUS` 正常生命周期白名单，排除 `990=重置装箱`。
3. 多个 `sub_waybill_no` 按 CXMS `id` 升序、去重后用英文逗号拼接。
4. `main_order`、`fee_detail` 尾程字段统一改为 `varchar(1000)`。
5. 无有效子单号时字段为空，不回退 OFP `waybill_no`。
6. 历史账单不处理。
7. COD 返款账单及返款导出同步调整，保持统一口径。
8. 必须支持单个子运单号严格检索，采用逗号快照 + 规范化关系表。
9. OFP 现有数据库用户具备 CXMS 查询权限；在 `fee_source_datasource` 中补充 `CXMS_DB` 配置并接入运行时解析。
10. CXMS 关联增加仓库条件：`sale_order_header.warehouse_code = ob_shipping_package_header.warehouse_code`。

### 11.2 状态口径维护规则

CXMS 状态名称与代码来自 `sys_dict/sys_dict_detail` 的 `PACKAGE_STATUS`，不是根据数据量推断。BMS 以代码常量维护已评审白名单；CXMS 新增、废弃或改变状态含义时，必须同步评审 BMS 白名单。未知状态默认不采集并记录告警，避免把未来的取消/作废状态误判为有效。

## 12. 风险与回滚

- **唯一键覆盖风险：** 虽然业务保证账单内不重复，代码仍需前置校验，异常时失败而非 upsert 覆盖。
- **字段截断风险：** 应用先发而 DDL 未发会导致生成失败或数据丢失；发布顺序必须是兼容 DDL 在前。
- **状态演进风险：** CXMS 新增状态不会自动进入 BMS 白名单；通过未知状态告警和版本评审避免误采集。
- **查询放大风险：** 禁止 N+1；通过批次去重和 `idx_erpOrderNo` 控制 CXMS 压力。
- **历史口径并存：** 历史数据明确不处理，新旧账单快照会并存，查询不得反向覆盖历史快照。
- **双写一致性：** 逗号快照与规范化关系表必须同事务写入并建立对账测试。
- **下游单值假设：** 手工挂靠、应收、返款和导出必须全部完成关系表回归后发布。

回滚应用时保留已扩容字段不会影响旧版本写入；若需要恢复索引，应在数据长度与索引限制评估后单独执行。已按新口径生成但尚未确认的账单，应使用现有重跑/作废机制重建，不直接手改费用快照。
