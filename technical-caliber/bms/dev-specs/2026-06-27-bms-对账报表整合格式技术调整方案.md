## 2. 第二章需求整理

## 2.1 整合原则

第二章可以收敛为 5 条强约束：

1. 导出文件面向客户与财务对账，不是系统审计报表。
2. 文件结构固定为：
   - Sheet 1：账单基本信息 + 结算币种分桶金额汇总信息
   - Sheet 2：账单明细
   - Sheet 3：往期账单冲正信息
3. 应收账单和返款账单的 Sheet 2 必须使用同一套“统一明细字段”结构。
4. 除【费项展开】外，统一明细字段表中的字段都属于默认导出字段，某账单类型不适用时也要保留列并置空。
5. 【费项展开】不是固定列清单，而是按账单实际存在的费项动态展开金额列。

## 2.2 目标导出结构

按第二章，导出目标结构应统一为：

1. Sheet 1：
   - 应收账单展示账单基本信息、费项结算币种口径汇总
   - 返款账单展示账单基本信息、货款结算币种口径汇总
2. Sheet 2：
   - 应收账单命名为 `费项明细`
   - 返款账单命名为 `返款明细`
   - 固定字段顺序一致
   - 动态费项列放在统一固定字段中的【费项展开】位置
3. Sheet 3：
   - 展示往期账单冲正、调账、追溯信息

## 2.3 统一明细字段的落地解读

第二章中的 Sheet 2 不是“应收一套、返款一套”的双模板，而是“统一基础字段 + 动态费项列”的单一结构：

1. 固定字段分组包括：
   - 单据识别
   - 计费信息
   - 业务识别
   - 物流信息
2. 动态字段分组只有【费项展开】。
3. 应收不适用的返款字段保留空列。
4. 返款不适用的应收字段保留空列。
5. 追加字段只能追加【订单费用报表】中的个别非金额字段，不能追加原始币种金额、汇率快照、财务本位币金额、审核字段等内部字段。

## 3.2 已经落地的能力

结合当前代码，以下能力已经完成，不应再按“待开发”处理：

1. Portal 导出已经切换为真实 `.xlsx`，不再是旧的 HTML 伪 Excel。
2. 应收、返款都已经有专用导出接口：
   - `GET /api/bms/ar-bill/export-data`
   - `GET /api/bms/refund-bill/export-data`
3. Portal 已经通过 `BmsFinanceExportExcelHelper` 统一输出 Excel。
4. BMS 已经新增了专用 DTO：
   - `ArBillFinanceExportRespDTO`
   - `ArBillFinanceExportRowDTO`
   - `ArBillFinanceExportSummaryDTO`
   - `RefundBillFinanceExportRespDTO`
   - `RefundBillFinanceExportRowDTO`
   - `RefundBillFinanceExportSummaryDTO`
5. 应收、返款服务都已经在导出时补查 `sale_order_header` / `sale_order_header_extend`，补出了部分订单、收件、仓库、地址信息。

## 3.3 与第二章的核心差异

虽然导出链路已具备，但当前实现和第二章仍有 7 个明显差异：

1. Sheet 数量不一致：
   - 当前 helper 只输出 `明细`、`汇总` 两个 Sheet
   - 第二章要求 3 个 Sheet，且 Sheet 1 应为汇总、Sheet 2 为明细、Sheet 3 为往期账单冲正信息
2. Sheet 2 命名不一致：
   - 当前固定为 `明细`
   - 第二章要求应收为 `费项明细`，返款为 `返款明细`
3. Sheet 2 结构不统一：
   - 当前 `ArBillFinanceExportRowDTO` 和 `RefundBillFinanceExportRowDTO` 字段集不同
   - 第二章要求两类账单的 Sheet 2 使用统一字段结构
4. 费项列实现方式不一致：
   - 当前使用 `BmsFinanceExportConstants` 把金额归并到固定列
   - 第二章要求【费项展开】按账单实际费项动态展开
5. Sheet 3 缺失：
   - 当前导出响应没有冲正 Sheet 数据
   - 但详情模型里其实已经存在：
     - `ArBillDetailRespDTO.adjustments`
     - `RefundBillDetailRespDTO.adjustmentRecords`
6. 统一明细字段仍有缺口：
   - 当前仍未输出或直接置空的字段包括报关单号、清关单号、计费重量、下单时间、出库时间、签收时间、货物类型、末条轨迹三字段、解款行/收款人信息等
7. 行粒度存在隐含约束：
   - 当前应收和返款导出都是按 `businessOrderNo` 聚合
   - 当订单号为空时，当前实现直接跳过该费用行
   - 本轮已确认：订单号为空的费用行暂不导出

## 3.4 当前实现中已确认的“空值占位”字段

当前代码里以下字段被明确写死为空，属于第二章落地缺口：

1. 应收：
   - `declarationOrderNos`
   - `lastTrajectoryStatus`
   - `lastTrajectoryDesc`
   - `lastTrajectoryTime`
2. 返款：
   - `declarationOrderNos`
   - `remittanceBank`
   - `payeeAccountNo`
   - `payeeName`
   - `lastTrajectoryTime`
   - `lastTrajectoryDesc`

## 3.5 当前实现中与第二章相冲突的点

当前实现里，最需要修订的不是“是否能导出”，而是“导出的结构假设”：

1. `BmsFinanceExportConstants` 预设了固定费项分类列。
2. `BmsFinanceExportExcelHelper` 预设了两套不同的表头数组。
3. `ArBillServiceImpl.exportData()`、`RefundBillServiceImpl.exportData()` 默认把一笔账单整理成“固定金额列横表”。
4. 旧的 `ArBillExportRespDTO + feeNames + feeAmountMap` 虽然已不再使用，但它的“动态列”思路反而更接近第二章。

结论：本轮修订重点不是新增导出入口，而是把当前“固定列双模板”调整为“统一字段 + 动态费项列 + 第三张冲正 Sheet”。

## 4. 技术调整方案

## 4.1 总体思路

建议沿用当前三段式职责边界，不做大拆：

1. `admin_shell`
   - 继续保留现有导出按钮和下载方式
2. `platform-admin`
   - 继续承担 Excel 写出职责
3. `bms`
   - 继续承担结构化导出数据拼装职责

本轮重点调整 4 件事：

1. 把导出结构从 2 Sheet 调整为 3 Sheet。
2. 把 Sheet 2 从“两套固定列”调整为“统一固定字段 + 动态费项列”。
3. 把冲正信息从详情模型收敛到导出模型，生成 Sheet 3。
4. 把第二章缺失字段的来源、空值策略、排除规则明确下来。

## 4.2 BMS 侧调整方案

### 4.2.1 导出模型调整

建议保留应收、返款两个导出入口不变，但补充统一的明细结构表达：

1. 保留：
   - `ArBillFinanceExportRespDTO`
   - `RefundBillFinanceExportRespDTO`
2. 新增或补充：
   - 统一明细固定字段 DTO
   - 动态费项列定义 DTO
   - Sheet 3 冲正信息 DTO

建议不要再把动态费项列继续硬编码成固定字段，而是改为显式结构，例如：

1. `detailBase`
   - 统一固定字段
2. `dynamicFeeColumns`
   - 当前账单实际存在的费项列定义
3. `dynamicFeeItems`
   - 当前行命中的费项金额
4. `adjustmentRows`
   - Sheet 3 数据

这样做的原因：

1. 符合第二章“只有费项列动态展开”的要求。
2. 避免继续维护两套几乎平行的明细表头。
3. 便于 Portal 先算列，再逐行写值。

### 4.2.2 动态费项列生成规则

本轮确认，Sheet 2 的费项列采用“仅当前账单实际费项并集”规则：

1. 先取当前账单下所有有效 `fee_detail`
2. 按展示名称生成动态费项列
3. 按固定顺序写出统一字段
4. 再按动态费项列顺序写金额

建议的列键规则：

1. 展示列头优先使用 `feeName`
2. 如存在重名风险，则内部按 `feeCode + feeName` 去重
3. Portal 展示仍使用中文列头

### 4.2.3 行粒度规则

本轮确认，Sheet 2 按“一行一个订单，`fee_detail` 竖表转横表”实现，规则如下：

1. 默认按 `businessOrderNo` 聚合
2. 同一订单下多条 `fee_detail` 汇总成一行
3. `businessOrderNo` 为空的费用行本轮暂不导出

该口径需要在联调时重点核对“导出金额合计”和“账单金额”的差异是否可接受。

### 4.2.4 Sheet 3 数据来源

本轮确认，Sheet 3 对应收账单和返款账单都要输出，建议优先复用已有详情模型，不重复造数：

1. 应收账单：
   - 来源 `ArBillDetailRespDTO.adjustments`
2. 返款账单：
   - 来源 `RefundBillDetailRespDTO.adjustmentRecords`

若 `exportData()` 不方便直接复用详情接口，可以在 `bms` 内部补一层导出专用组装，把明细、汇总、冲正数据一次性返回。

### 4.2.5 第二章缺失字段补数策略

当前缺口字段按 3 类处理：

1. 直接补查：
   - 清关单号：`cxms.ob_shipping_package_header.clearance_order_no`
   - 报关单号：`cxms.ob_shipping_package_header.declaration_order_no`
   - 计费重量：`sale_order_header.fee_weight`
   - 下单时间：`sale_order_header.place_order_time`
   - 出库时间：`sale_order_header.delivery_time`
   - 签收时间：`sale_order_header.signed_time`
   - 货物类型：`sale_order_header.cargo_type_code`
2. 延续当前已确认留空策略：
   - 暂无来源且本轮不阻断导出的字段
3. 本轮明确不导出：
   - 解款行
   - 收款人帐号
   - 收款人姓名

末条轨迹三字段当前仍无已确认来源，继续按留空处理。

## 4.3 Platform Admin 侧调整方案

`BmsFinanceExportExcelHelper` 建议按第二章改成“统一模板驱动”：

1. Sheet 顺序改为：
   - Sheet 1：汇总
   - Sheet 2：费项明细 / 返款明细
   - Sheet 3：往期账单冲正信息
2. 应收、返款的 Sheet 2 固定字段区使用同一套列定义
3. 动态费项列由 `bms` 返回列定义后再写表
4. Sheet 3 按账单类型分别写冲正行

建议最小改造路径：

1. 保留 `BmsFinanceExportExcelHelper`
2. 把当前两个 `headers` 数组改为：
   - 统一固定字段数组
   - 动态费项字段数组
3. 新增 `writeAdjustmentSheet()`

## 4.4 Admin Shell 侧调整方案

`admin_shell` 本轮不建议做结构性修改：

1. 当前前端只是下载 blob
2. 文件名已经是 `.xlsx`
3. 后续只要后端响应头和二进制格式不变，前端可继续复用

唯一建议保留的动作是：

1. 删除返款页导出方法中的旧 TODO
2. 若 Sheet 命名变化不影响下载，则无需联动页面逻辑

## 5. 调整计划

建议按 4 个阶段推进。

## 5.1 第一阶段：规则确认

目标：

1. 把第二章中的“统一固定字段”定稿
2. 按“仅当前账单实际费项并集”定稿动态费项列规则
3. 把 Sheet 3 的展示字段定稿
4. 把字段补数来源和不导出字段清单定稿

产出：

1. 固定字段清单
2. 动态费项列规则
3. 冲正 Sheet 字段清单
4. 字段来源映射与排除清单

## 5.2 第二阶段：BMS 数据模型调整

目标：

1. 扩展 `exportData()` 返回结构
2. 增加动态费项列定义
3. 增加 Sheet 3 数据
4. 补齐缺失字段与空值/排除规则

涉及模块：

1. `bms/model`
2. `bms/biz`
3. `bms/web`
4. `bms/client`

## 5.3 第三阶段：Portal 写表调整

目标：

1. `BmsFinanceExportExcelHelper` 支持 3 个 Sheet
2. Sheet 2 支持统一固定字段 + 动态费项列
3. Sheet 2 命名符合第二章

涉及模块：

1. `platform-admin/web`

## 5.4 第四阶段：联调与回归

重点验证：

1. 应收与返款 Sheet 2 固定字段顺序是否一致
2. 同一账单的动态费项列是否稳定
3. 没有订单号的费用行是否按本轮口径不导出
4. Sheet 3 金额和详情页调账数据是否一致
5. Excel 是否仍可被财务直接透视和筛选

## 6. 已确认口径

本轮已确认的口径如下：

1. 动态费项列仅在当前账单内按实际费项并集展开，不维护应收/返款全量费项列字典。

2. Sheet 2 按一行一个订单实现，`fee_detail` 竖表转横表。

3. `businessOrderNo` 为空的费用行暂时不导出。

4. Sheet 3 对应收账单和返款账单都要输出。

5. 第二章统一明细字段中，以下字段来源已确认：
   - 清关单号：`cxms.ob_shipping_package_header.clearance_order_no`
   - 报关单号：`cxms.ob_shipping_package_header.declaration_order_no`
   - 计费重量：`sale_order_header.fee_weight`
   - 下单时间：`sale_order_header.place_order_time`
   - 出库时间：`sale_order_header.delivery_time`
   - 签收时间：`sale_order_header.signed_time`
   - 货物类型：`sale_order_header.cargo_type_code`

6. 解款行、收款人帐号、收款人姓名本轮不要导出。

## 6.1 仍需研发落地的缺口

虽然口径已经确认，但研发实现上仍有 4 个缺口：

1. `cxms.ob_shipping_package_header` 的补查链路还未接入当前导出服务。
2. 当前 `BmsFinanceExportExcelHelper` 仍是固定金额列，需要改成统一字段 + 动态费项列。
3. 当前导出仍只有 `明细`、`汇总` 两个 Sheet，需要新增 Sheet 3。
4. 当前 `businessOrderNo` 为空的费用行会被跳过，后续需要确认这类账单在汇总校验上的处理方式。

## 7. 结论

围绕第二章的新口径，当前代码并不是“没有导出能力”，而是“已经有导出能力，但结构假设和第二章不完全一致”。

本轮最关键的修订点有 4 个：

1. 把两张 Sheet 调整为三张 Sheet。
2. 把应收/返款的两套明细表头收敛成统一固定字段结构。
3. 把固定费项金额列改为动态费项展开列。
4. 把往期账单冲正信息纳入导出响应并写入 Sheet 3。

建议后续研发按“先确认规则，再改 `bms` 数据结构，最后改 `platform-admin` 写表”的顺序推进，这样对当前已上线导出链路冲击最小，也最符合现有代码边界。
