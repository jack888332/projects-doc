## 1. 需求概要

### 1.1 目的

在回款返款模式下，一张业务订单包含多个尾程包裹时，不再等待全部包裹录入实收回款。任一包裹已有非空且非零的有效实收回款，即可按业务订单归集返款。

### 1.2 适用范围

- COD 业务订单。
- 返款模式为 `RECEIVED` 回款返款。
- 一票多件场景。

### 1.3 核心结果

1. 首个符合条件的包裹只负责触发整单归集，不承担订单级金额分摊。
2. 订单级应付返款（即代收货款）和订单级机算代收货款手续费按业务订单挂靠并各归集一次。
3. 包裹级导入手续费按尾程包裹挂靠并按导入值单独归集。
4. 其他包裹后续录入或更新实收回款时，只更新对应包裹回款事实，不重复归集订单级金额。

## 2. 修改前后口径

| 业务位置 | 修改前 | 修改后 |
| --- | --- | --- |
| 归集对象 | 返款归集主要按正常签收 COD 包裹组织，未明确一票多件的整单触发方式 | 返款账单按 COD 业务订单归集订单级金额，尾程包裹提供签收和实收回款事实 |
| 回款触发条件 | 回款返款要求包裹满足已回款条件，未明确是否必须等待同单全部包裹回款 | 同一业务订单任一尾程包裹已录入非空且非零的有效实收回款，整张业务订单即满足已回款归集条件 |
| 金额归属 | 订单侧金额与包裹侧金额的形成方式和挂靠边界不够明确 | 应付返款和订单级机算代收货款手续费挂靠业务订单；导入的实收回款和包裹级导入手续费挂靠尾程包裹 |
| 重复归集 | 未明确其他包裹后续回款时是否会重复计入订单金额 | 系统按业务订单去重；后续包裹回款只更新对应包裹事实，不重复计入订单级金额 |

### 3.2 返款账单生成链路现状

主入口为 `BillGenerateServiceImpl.executeRefundTaskInternal`（`BillGenerateServiceImpl.java:2074`），当前流程可概括为：

1. `queryRefundOrderRows`（`BillGenerateServiceImpl.java:2024`）按返款主数据源拉取 OFP `sale_order_header` 宽表订单；回款模式优先使用 `received_time_column`（当前支持 `recovery_time`），否则回退签收/出库时间。
2. `isRefundCandidateOrder`（`BillGenerateServiceImpl.java:2441`）只按订单头金额判断：
   - `resolveRefundDeclaredAmount`（`2446`）：优先 `h_cod_price`，回退 `h_collection_price`。
   - `resolveRefundCollectedAmount`（`2454`）：取 `h_collection_price`。
3. 生成主订单快照、调用 `persistOrderWaybillSnapshots`（`3628`）写 `bill_order_waybill_snapshot`。
4. `buildRefundPrincipalFee`（`2595`）：回款模式 `principalSourceAmount = collectedAmount`，即当前用订单头 `collection_price` 作为已回款返款本金。
5. `buildRefundUncollectedFee`（`2624`）：`gap = declared - collected`，即当前实际是 `cod_price - collection_price`。
6. `buildRefundDeductions`（`2643`）：
   - 只有 `resolveRefundCollectedAmount(orderRow) > 0` 时才继续扣减。
   - 订单级代收货款手续费读取 `h_collection_premium_amount`，按业务订单计一次。
   - 超材/重出费读取上一账期 `sale_order_additional_matter` 或订单头扩展字段。

当前生成链路**没有**读取 `sale_order_package_fee`，也**没有**按“任一包裹实收回款”触发整单归集的逻辑。

## 5. 目标落地方案

### 5.1 总体思路

```text
OFP 主订单查询（保留现有订单级金额/币种/状态）
  -> 按订单批量查询 sale_order_package_fee（type=1）
  -> Java 内按 sale_order_id 归并包裹回款事实和包裹导入手续费
  -> 回款返款：任一包裹满足有效实收回款 => 订单进入候选
  -> 订单级应付返款 / 订单级机算手续费按订单归集一次
  -> 包裹级导入手续费按包裹归集
  -> 写入 fee_detail 时用 sourceTable + sourceId + dedupeKey 防重
```

不改动应收账单生成；不改动签收返款的触发事实；不改动回款管理的包裹级独立判定。

### 5.2 有效包裹回款事实的统一判定

建议在生成层新增一个“包裹回款事实查询 + 有效性判定”能力，语义与回款管理保持一致：

```text
有效包裹回款事实 =
  p.type = 1（应收行）
  AND p.tail_way_bill_no 非空
  AND COALESCE(p.recovery_money, 0) > 0
  AND 订单不属于取消/退件/异常签收（对齐 RefundBillServiceImpl.resolveSignStatus）
```

推荐查询骨架（仅作方案示意，实施时按项目 SQL 规范和 PreparedStatement 分页/批查落地）：

```sql
SELECT p.id,
       p.sale_order_id,
       p.tail_way_bill_no,
       p.recovery_money,
       p.receivable_collection_amount,
       p.create_time,
       p.modify_time,
       h.delivery_order_code,
       h.order_status,
       h.cancel_reason,
       h.signed_time,
       h.cod,
       h.collection_price,
       h.cod_price,
       e.recovery_time
FROM sale_order_package_fee p
LEFT JOIN sale_order_header h ON h.id = p.sale_order_id
LEFT JOIN sale_order_header_extend e ON e.sale_order_id = h.id
WHERE p.type = 1
  AND h.member_code = ?
  AND h.shop_id = ?
  AND (h.sc_id = ? OR h.sc_id IS NULL)
  AND (LOWER(COALESCE(h.cod, '')) = 'y'
       OR COALESCE(h.collection_price, 0) > 0
       OR COALESCE(h.cod_price, 0) > 0)
  AND COALESCE(h.order_type, '') <> 'BILL'
```

约束：

1. 有效性判定必须和 `RefundBillServiceImpl.resolveReceiptStatus` 一致，避免“回款管理显示已回款，但生成层不触发”或反向不一致。
2. 异常签收、取消、退件包裹即使 `recovery_money > 0`，也不形成有效回款事实。
3. 数据隔离三字段 `sc_id / shop_id / user_id` 在 BMS 侧落库时仍必须完整；OFP 源查询使用 `member_code + shop_id + sc_id`。

### 5.3 回款返款候选订单判定

`executeRefundTaskInternal` 中建议改为：

```text
RECEIVED（回款返款）：
  hasEffectivePackageReceipt = 该业务订单任一包裹满足 5.2 有效回款事实
  candidate = resolveRefundPayableAmount(orderRow) > 0
              AND hasEffectivePackageReceipt

SIGNED（签收返款）：
  继续沿用现有正常签收/金额归集条件，不套用“任一包裹回款”规则
```

说明：

1. “应付返款 > 0”仍是进入返款账单的必要前提；没有应付返款的订单不应仅凭包裹回款事实进入返款账单。
2. 若产品确认需要保留旧订单头 `collection_price > 0` 兜底，必须作为显式配置或临时开关处理，不能静默双口径。
3. `validateUniqueBusinessOrderNos` 已保证同任务内业务订单号唯一，继续保留。

### 5.4 金额挂靠层级

| 数据 | 来源 | 挂靠对象 | 本次用途 |
| --- | --- | --- | --- |
| 应付返款 | `sale_order_header.collection_price`（OIS 机算） | 业务订单 | 触发后按订单计入返款账单一次 |
| 订单级代收货款手续费 | `sale_order_header.collection_premium_amount`（OIS 机算） | 业务订单 | 命中直接扣减配置后按订单计入一次 |
| 实收回款 | `sale_order_package_fee.recovery_money`（type=1，导入） | 尾程包裹 | 判断订单是否具备回款返款归集条件，保留包裹事实 |
| 包裹级导入手续费 | `sale_order_package_fee.receivable_collection_amount`（type=1，导入） | 尾程包裹 | 按包裹导入值单独归集 |
| 到付总额 | `sale_order_header.cod_price` | 业务订单 | 仅用于核对，不作为应付返款 |

具体生成建议：

1. 订单级应付返款：
   - 新建/调整金额解析为 `resolveRefundPayableAmount`，直接取 `h_collection_price`。
   - `buildRefundPrincipalFee` 在两种模式下都使用应付返款作为本金来源；回款返款不再用“订单头 collection_price 当已回款金额”的隐含双关。
   - `cod_price` 只进入主订单/导出/回款管理的到付核对字段，不参与返款本金。
2. 订单级机算代收货款手续费：
   - 命中客户级返款配置 `COD_SERVICE_FEE` 且 `collection_premium_amount > 0` 时，按业务订单生成一条 `REFUND_DEDUCTION`。
   - `attachedObject = ORDER`，`sourceTable = sale_order_header`，`sourceId = h_id`，`sourceFeeField = collection_premium_amount`。
   - 去掉当前 `resolveRefundCollectedAmount <= 0` 的前置门，改为“订单已进入归集范围”后再判断。
3. 包裹级导入手续费：
   - 对已进入归集范围订单下所有 `sale_order_package_fee.type = 1` 且 `receivable_collection_amount > 0` 的包裹行，命中直接扣减配置时逐包裹生成一条 `REFUND_DEDUCTION`。
   - `attachedObject = LAST_PACKAGE`，`sourceTable = sale_order_package_fee`，`sourceId = p.id`，`sourceOrderId = p.sale_order_id`，`sourceFeeField = receivable_collection_amount`。
   - `lastMileWaybillNo` 取该包裹 `tail_way_bill_no`，不拼接其他包裹；`businessOrderNo` 取 `delivery_order_code`。
   - 原始币种默认沿用订单目的国币种（`dest_country_currency_code` 优先，回退 `currency_code/currency`），与现有 `resolveRefundSourceCurrency` 一致；若包级字段提供明确币种则按字段确认。
4. 禁止行为：
   - 不把包裹级实收回款复制到同一订单的其他包裹。
   - 不把订单级金额拆分为各包裹金额。
   - 不把包裹级实收回款作为应付返款计算输入。
   - 不因包裹级回款事实更新而自动追加已生成订单级金额。

### 5.5 去重与幂等

1. 订单级去重：
   - `validateUniqueBusinessOrderNos` 保证同任务内一个业务订单只处理一次。
   - 回款返款模式下，首个有效包裹只负责把订单加入候选集合；订单级金额在 `matchedRows` 循环中只生成一次。
2. 费项级去重：
   - 现有 `dedupeKey` 规则为 `COD_REFUND:{billNo}:{feeCode}:{sourceId}:{settlementRole}`。
   - 订单级手续费 `sourceId = 订单 id`，一单一条。
   - 包裹级手续费 `sourceId = 包裹费行 id`，一包裹一条。
3. 重跑：
   - `prepareRefundRetryBill` 已清理同账期失败残留的 `fee_detail`、汇总、汇率和包裹快照，再重建。
   - 新规则继续沿用：同账期重跑先清理再重建，不会在旧明细上追加订单级金额。
4. 后续包裹回款：
   - 订单已生成返款账单后，来源订单被 `e.bms_bill_no` 等标记占用，后续任务不会再次拉取同一订单。
   - 后续包裹的 `recovery_money` 更新只影响回款管理展示和包裹事实，不影响已生成账单。
5. 建议把触发包裹信息写入追溯快照：
   - 可在订单级主订单或应付返款 `fee_detail.source_extra_json` 中保存 `refundTriggerPackageId`、`refundTriggerWaybillNo`、`refundTriggerRecoveryMoney`、`refundTriggerTime`，用于审计“首个包裹触发”事实，不新增物理表。

### 5.6 账期与时间口径

当前回款返款按订单头 `recovery_time`（`sale_order_header_extend.recovery_time`）或配置的回款时间列入池。引入包裹级事实后需要明确：

1. 方案 A（推荐待确认）：仍以订单级回款时间决定账期，包裹回款事实只做候选过滤。优点是改动小、与现有 `resolveRefundOrderTimeField` 一致；缺点是有包裹已回款但订单头 `recovery_time` 缺失/延迟时可能漏单。
2. 方案 B：以包裹级事实时间 `COALESCE(e.recovery_time, p.modify_time, p.create_time)` 决定账期，再拉取所属订单。优点是贴合“包裹回款触发”语义；缺点是订单级金额可能与包裹回款时间不在同一账期，需同步调整上一周期扣减费用查询。
3. 无论选哪种，上一周期直接扣减费用查询的窗口必须和触发时间口径一致，避免订单级/包级手续费回补错期。

### 5.7 存量与生效边界

1. 新规则只用于上线后新发起的返款账单生成，以及按既有机制允许重新生成的未发出待审核账单。
2. `REFUND_RERUN_ALLOWED_STATUSES = {DRAFT, UNDER_REVIEW}`：只有起草中/待审核账单可重跑，已发出、待结清、已结清账单不自动作废、替换或回写。
3. 已生成账单不得因后续包裹回款或本规则上线而静默增加订单金额；差异通过重算、调账、冲正或后续账单承接。
4. 若最终需要新增 DDL（例如触发包裹快照列），必须同步完整 `CREATE TABLE` 到 `aidocs/technical-caliber/sql/ar_bill.sql`，禁止只写 `ALTER` 片段；本文默认不新增物理表。

## 7. 疑问点

### Q-01 应付返款金额字段

PRD 明确 `sale_order_header.collection_price` 是订单侧代收货款本金，`cod_price` 是到付总额；当前代码 `resolveRefundDeclaredAmount` 优先 `cod_price`。本次是否顺带纠正为“应付返款 = collection_price”？

影响：直接决定回款返款和签收返款的本金金额；若只改回款返款会与签收返款产生模式间口径差异。

### Q-02 “有效实收回款”是否要求包裹已正常签收

当前回款管理 `resolveReceiptStatus` 只排除取消/退件/异常，`PENDING` 签收状态但 `recovery_money > 0` 时也判 `SETTLED`。本次生成层是否完全复用该口径，还是要求 `signed_time`/正常签收后才算有效触发？

影响：决定未签收但已导入实收回款的包裹能否触发整单。

### Q-03 包裹回款事实触发时间

订单头 `recovery_time` 缺失或晚于包裹 `modify_time` 时，账期按什么时间归集：订单级 `recovery_time`、包裹级 `modify_time/create_time`、还是 `COALESCE`？

影响：决定漏单风险和上一周期费用回补窗口。

### Q-04 订单级与包裹级手续费并存规则

本次需求文本要求“订单级机算手续费与包裹级导入手续费同时存在时，不做额外冲突判断，按各自挂靠层级同时归集”；但 PRD `19.2.3.6` 表述为“同一笔手续费同时存在时只允许形成一笔返款扣减，阻止重复归集”。以哪个为准？

影响：决定最终扣减金额是同时归集还是去重；若去重，还需确认优先采用订单级还是包裹级。

### Q-05 包裹级导入手续费是否要求该包裹自身已回款

订单由任一包裹触发后，其他包裹的 `receivable_collection_amount` 是否也一并归集，即使这些包裹尚未录入实收回款？

影响：决定包级手续费采集范围。

### Q-06 没有应付返款但有包级手续费

订单 `collection_price = 0`、`cod_price > 0`，但包裹有实收回款和导入手续费时，是否仍进入返款账单并归集包级手续费？

影响：决定候选订单门槛。

### Q-07 未回款费项 `REFUND_UNCOLLECTED`

当前 `buildRefundUncollectedFee` 用 `cod_price - collection_price` 生成“未回款金额”，这与 PRD“cod_price 是到付总额、差额只能表示到付附加费”语义不一致。本次是否保留该费项、改为基于包裹回款事实，还是删除/仅作风险展示？

影响：决定返款账单明细行数量和金额展示。

### Q-08 包级尾程号与 CXMS 子运单号

`sale_order_package_fee.tail_way_bill_no` 是否总是等于 CXMS `sub_waybill_no`？不一致时包级手续费如何挂靠 `bill_order_waybill_snapshot` 和导出包裹行？

影响：决定包级手续费与现有包裹关系表能否直接关联。

### Q-09 包级手续费账期

包级导入手续费按 `p.create_time` 增量归集，还是跟随所属订单进入本期返款账单、无需再按创建时间过滤？是否也需要像订单级手续费一样支持“上一周期费用回补”？

影响：决定包级手续费查询窗口和重跑范围。

### Q-10 历史数据与临时兜底

上线前已有“订单头 collection_price > 0 但无包裹回款事实”的历史订单，是否允许回款返款暂时继续进入账单，还是严格按新规则只等包裹事实？

影响：决定是否引入兼容开关，以及发布回填/重跑范围。

## 8. 风险与验收

### 8.1 风险

1. 金额口径风险：`cod_price` 与 `collection_price` 当前混用，若未确认就改，可能影响签收返款历史结果。
2. 重复归集风险：包级手续费按包生成后，若同一包数据在重跑中未被清理，可能出现重复明细；必须依赖 `dedupeKey` 和重跑清理链路。
3. 漏单风险：订单头回款时间缺失时，包裹已回款但订单不进入账期。
4. 口径不一致风险：回款管理、生成层、导出层对“有效回款”和“包级手续费”语义不一致。
5. 配置冲突风险：`queryRefundFeeDefinitionByName` 按名称取费项，FEE0023 与 FEE0060 同名“代收货款手续费”，按名称解析可能歧义，实施时应用显式费项编码或挂靠对象过滤。

### 8.2 验收清单

1. 同一订单多个包裹，仅一个包裹有非空非零 `recovery_money`，回款返款生成时该订单进入账单，订单级应付返款计一次。
2. 同一订单其他包裹后续录入/更新实收回款，不新增订单级金额，包裹回款管理事实正常更新。
3. 异常签收包裹即使有 `recovery_money > 0`，也不触发所属订单归集。
4. 订单级机算代收货款手续费命中直接扣减配置后按订单计一次。
5. 包裹级导入手续费按包裹 `receivable_collection_amount` 逐条归集；同一订单多个包裹产生多条包级明细。
6. 订单级与包级手续费并存时按最终确认口径执行，不产生无主明细或重复汇总。
7. 签收返款仍按既有正常签收条件触发，不要求先录入实收回款。
8. 只影响新生成和 `DRAFT / UNDER_REVIEW` 重跑；已发出、待结清、已结清账单不自动变化。
9. 生成 SQL、费项来源、币种、汇率、汇总、导出和回款管理口径保持一致。
