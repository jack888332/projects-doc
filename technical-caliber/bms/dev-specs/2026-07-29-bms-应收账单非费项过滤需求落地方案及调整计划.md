# 2026-07-29 BMS 应收账单非费项过滤需求落地方案及调整计划

## 1. 文档目的

本文结合当前 BMS 代码、产品需求文档和开发库实际数据，设计“费项索引的费用类型为非费项时，不得进入应收账单”的落地方案，作为后续开发、数据核对、测试和上线验收依据。

方案已于 2026-07-29 开始实施：业务代码、前端兜底、DDL 文件和 SQL 归档已完成调整；共享开发库 DDL/DML 未执行，需在部署代码前按变更流程执行本方案附带 DDL。

## 2. 需求结论

### 2.1 目标口径

客户侧费项索引 `fee_index.fee_type = 'NON_FEE'` 时：

1. 不参与会员应收账单 `MEMBER_AR` 的自动生成。
2. 不写入应收账单的 `fee_detail`。
3. 不出现在应收账单详情、应收账单导出和应收账单费项统计中。
4. 不参与 `ar_bill_currency_summary`、应收金额、未收金额和核销金额计算。
5. 不允许通过“应收账单补录费项”接口绕过自动生成规则写入账单。
6. 被应收任务拉取后仍需将来源数据标记为已抓取，即 `bms_billed_flag = 1`。
7. 非费项未进入应收账单，因此来源数据的 `bms_bill_no` 保持为空，不得写入虚假账单号。
8. 仍保留在客户侧费项索引和业务场景配置中，供返款账单、回款管理、来源追溯等特定场景使用。

### 2.2 默认实施边界

本方案默认本次调整对象是：

```text
会员应收账单 MEMBER_AR
```

不改变：

1. 返款账单 `COD_REFUND` 对非费项事实数据的展示或弱关联能力；只允许为兼容全局抓取标记调整候选来源防重口径，不改变返款金额计算。
2. 回款管理对 COD 金额、实收回款等事实金额的查询和核对。
3. 客户侧费项索引维护页面对 `NON_FEE` 类型的维护能力。
4. 成本费项索引及后续成本账单逻辑。
5. 已归档历史任务快照的审计内容。

### 2.3 验收定义

满足以下条件才视为需求完成：

1. 新建、增量追加、失败重试和整账重跑生成的应收账单均不产生 `NON_FEE` 明细。
2. 只有非费项规则的业务配置不会因为非费项生成应收账单费用。
3. 混合配置下，正常应收费项照常生成，非费项被跳过。
4. 应收账单手工补录选择列表不展示非费项；即使绕过前端直接调用接口，后端也拒绝写入。
5. 非费项来源被成功拉取后写 `bms_billed_flag = 1`，但不写应收账单号。
6. 返款账单和回款管理原有非费项使用方式不受影响。

## 3. 依据

### 3.1 产品口径

`aidocs/product-caliber/bms/prd/财务系统.PRD.md` 已有如下明确口径：

1. `9.5.7`：费用类型为非费项时，不纳入任何账单核销范围。
2. `9.5.8`：非费项不写入任何账单的可核销明细。
3. `9.6.8`：非费项仅在特定位置弱关联展示，不进入应收、未收和核销汇总。
4. `10.7`：非费项不进入任何账单的可核销明细。
5. `18.2.3`：非费项仅作为业务事实、返款核对或资金核对信息呈现。

本次需求是在应收账单侧进一步收紧为：

> 非费项不形成应收账单费用明细，而不是“形成明细后只排除汇总”。

### 3.2 当前技术文档

`aidocs/technical-caliber/bms/dev-specs/bms-bill-generation-task-current-flow.md` 当前记录：

> `fee_type = NON_FEE` 的明细会保留在账单详情中，但在重建 `ar_bill_currency_summary` 时会被排除。

该描述是当前代码现状，与本次新需求冲突。业务代码调整完成时必须同步更新该文档。

## 4. 当前代码与数据现状

### 4.1 当前生成调用链

会员应收账单主要调用链为：

```text

  -> BillGenerateMapper.queryFeeRules()
  -> 固化 fee_rule_snapshot_json

BillGenerateServiceImpl.executeTask()
  -> executeTaskInternal()
  -> buildConfigSnapshotContext()
  -> resolveFeeRules()
  -> executeBillGroup()
     -> buildOrderFee() / buildAdditionalFee() / buildClaimFee()
     -> buildFeeBase()

  -> refreshBillAmountFromCurrencySummary()
```

涉及的主要文件：

### 4.2 当前规则读取口径

`BillGenerateMapper.queryFeeRules()` 当前从以下对象读取：

```text
business_type_fee_index btfi
  -> fee_source_rule fsr
  -> fee_source_dataset fsd
```

生成逻辑读取的是 `business_type_fee_index.fee_type` 快照字段，当前没有连接 `fee_index` 校验主档费用类型，也没有排除 `NON_FEE`。

`FeeIndexServiceImpl.save()` 修改费项主档时会调用：

```text
feeIndexMapper.syncBusinessTypeFeeSnapshot(feeIndex)
```

因此正常维护路径下，`fee_index.fee_type` 会同步到 `business_type_fee_index.fee_type`；但生成查询仍应以客户侧费项主档为最终边界，并对新旧任务快照统一执行规则分流。

### 4.3 当前非费项处理方式

当前代码不是“不生成非费项”，而是“生成后不汇总”：

1. `buildFeeBase()` 会把 `rule.getFeeType()` 原样写入费用明细。
2. `insertFeeDetail()` 没有排除 `NON_FEE`。
3. `signedAmount()` 遇到 `NON_FEE` 时返回 `0`。
4. `selectCurrencySummarySourceByBillId()` 使用以下条件排除非费项：

```sql
AND (fee_type IS NULL OR fee_type <> 'NON_FEE')
```

5. `refreshBillAmountFromCurrencySummary()` 在刷新财务币种金额时也排除 `NON_FEE`。

现状后果：

```text
NON_FEE
  -> 可以写入 fee_detail
  -> 可以出现在应收账单详情
  -> 不进入币种汇总和核销金额
```

新需求要求改为：

```text
NON_FEE
  -> 在应收账单有效规则集合中被排除
  -> 不构建应收费用
  -> 不写 fee_detail
  -> 不出现在应收账单
```

### 4.4 手工补录旁路

应收账单补录费项当前存在绕过风险：

1. `admin_front/src/views/billing/receivableBill/index.vue` 从费项管理通用 `options` 接口加载全部费项。
2. 通用选项包含 `NON_FEE`，补录下拉框当前没有过滤。
3. `ArBillServiceImpl.manualFee()` 会查询 `fee_index.fee_type`，但只用于调整金额正负方向。
4. `ArBillMapper.insertManualFeeDetail()` 最终将补录明细的 `fee_type` 固定写为 `'AR'`。

因此用户当前可以选择一个非费项主档，并将其作为 `AR` 手工写入应收账单。后续实现必须同时增加前端过滤和后端强校验，不能只处理自动生成链路。

## 5. 目标技术方案

### 5.1 总体策略

采用“规则分流 + 来源抓取留痕 + 手工补录拦截”：

```text
第一层：任务创建时保留完整规则快照
  -> NON_FEE 继续参与来源扫描和抓取留痕

第二层：任务执行时按费用类型分流
  -> billableFeeRules 允许构建应收费用
  -> nonFeeRules 只做来源抓取和打标，不构建 fee_detail

第三层：来源抓取后记录 NON_FEE_FETCH
  -> bms_billed_flag = 1
  -> bms_bill_no = NULL
  -> 不创建虚假账单关联

第四层：应收账单手工补录时拒绝
  -> 防止人工操作和直接接口调用绕过生成规则
```

不采用“先写入 `fee_detail`，再在详情查询中隐藏”的方案。只隐藏展示会留下错误账单关系、错误任务计数和错误来源归集状态。

### 5.2 自动生成规则过滤

#### 5.2.1 Mapper 层

调整：

```text
bms/dao/src/main/java/com/szt/supplychain/bms/dao/mapper/BillGenerateMapper.java
BillGenerateMapper.queryFeeRules()
```

建议在现有查询中关联 `fee_index`，以主档费用类型构建任务快照，但不在 SQL 中排除 `NON_FEE`：

```sql
JOIN fee_index fi
  ON fi.id = btfi.fee_index_id
```

设计说明：

1. 以 `fee_index` 主档类型作为任务创建时的费用类型判断依据。
2. `NON_FEE` 必须保留在任务快照中，否则无法识别哪些来源已被拉取并完成抓取打标。
3. 不删除、不停用 `NON_FEE` 主档或场景绑定。
4. 不把过滤条件加到通用费项索引查询中，避免影响返款账单、回款管理和费项配置页面。
5. 本次只调整非费项分流，不顺带调整停用费项、来源完整性等其他规则。

#### 5.2.2 Service 层

调整：

```text
bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/BillGenerateServiceImpl.java
```

增加应收规则分流方法，例如：

```java
private ReceivableFeeRuleGroup classifyReceivableFeeRules(List<FeeCollectRule> feeRules)
```

分流结果：

```text
allFeeRules
  -> billableFeeRules: feeType != NON_FEE
  -> nonFeeRules: feeType = NON_FEE
```

需要覆盖：

1. `createTask()` 保留完整的新任务快照。
2. `buildCurrentFeeRuleSnapshot()` 保留完整的当前配置快照。
3. `resolveFeeRules()` 读取任务快照或实时规则后统一分流。
4. 默认配置和分支配置均执行相同分流。
5. 来源查询策略使用完整规则集合，不能因排除非费项而漏掉需要打抓取标记的来源。
6. `buildOrderFee()`、`buildAdditionalFee()` 和 `buildClaimFee()` 只遍历 `billableFeeRules`。
7. `nonFeeRules` 只用于判断来源是否已被拉取以及写抓取标记。

调整前已经创建的 `PENDING / NEED_RETRY` 任务无需改写快照，执行时同样按上述规则分流。

#### 5.2.3 空规则保护

当 `billableFeeRules` 为空、但 `nonFeeRules` 不为空时：

1. 仍按完整规则集合查询候选来源。
2. 对成功拉取且命中非费项规则的来源写抓取标记。
3. 不创建 `ar_bill`。
4. 不写 `main_order` 账单快照。
5. 不写 `fee_detail`。
6. 任务按“已抓取非费项来源，无可出账费项”成功结束。

该保护同时满足“非费项需要标识已被抓取”和“非费项不能生成空应收账单”两个要求。

### 5.3 来源数据和打标处理

非费项来源被应收任务成功拉取后：

1. 不调用非费项的 `buildOrderFee()`、`buildAdditionalFee()` 或 `buildClaimFee()`。
2. 不调用非费项的 `insertFeeDetail()`。
3. 回写来源表 `bms_billed_flag = 1`，表示该来源已经被 BMS 拉取。
4. 回写来源表 `bms_bill_no = NULL`，因为该来源没有进入应收账单。
5. 在 `bill_source_collect_mark` 记录 `collect_type = 'NON_FEE_FETCH'`。
6. 抓取轨迹关联 `generate_task_id` 和账单配置，不强制关联 `bill_id/bill_no`。
7. 如果同一订单还有正常应收费项，订单按正常费项进入应收账单并使用现有账单来源轨迹；不重复写 `NON_FEE_FETCH`。

建议增加专用方法：

```text
markNonFeeOrderSourceFetched()
markNonFeeAdditionalSourceFetched()
markNonFeeClaimSourceFetched()
```

其源表更新口径为：

```sql
SET bms_billed_flag = 1,
    bms_bill_no = NULL
```

不能复用现有 `markOrderSource()` 并传入虚假账单号，否则会形成不存在的账单关联。

#### 5.3.1 应收与返款的抓取兼容

开发库实际的来源轨迹唯一键包含 `bill_type`：

```text
source_system
+ source_table
+ source_id
+ collect_type
+ bill_type
```

这表示同一来源可以分别由 `MEMBER_AR` 和 `COD_REFUND` 留痕。

但当前 `queryRefundOrderRows()` 复用订单宽表查询，仍使用全局条件：

```text
bms_billed_flag = 0
AND bms_bill_no 为空
```

如果应收任务先按 Q-04 将非费项来源更新为 `bms_billed_flag = 1`，返款任务将无法继续读取该来源。为同时满足“已抓取要打标”和“返款/回款能力保留”，必须收口以下语义：

1. 来源表 `bms_billed_flag = 1` 表示该来源至少被 BMS 某一流程拉取过。
2. 不同账单类型是否已经处理，以 `bill_source_collect_mark.bill_type` 为准。
3. `COD_REFUND` 候选来源查询不得只因全局 `bms_billed_flag = 1` 排除来源。
4. 返款侧应结合本地来源轨迹判断是否已有有效的 `COD_REFUND` 处理记录。
5. 应收先执行、返款后执行，以及返款先执行、应收后执行，都必须分别完成各自业务处理且不重复。

本次只做满足上述兼容所需的最小查询调整，不改变返款本金、扣减项、应返金额和核销计算。

### 5.4 手工补录过滤

#### 5.4.1 后端强校验

调整：

```text
bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/ArBillServiceImpl.java
ArBillServiceImpl.manualFee()
```

建议处理顺序：

1. 根据 `feeCode` 查询 `fee_index.fee_type`。
2. 费项不存在时按现有兼容口径处理或提示费项不存在。
3. 类型为 `NON_FEE` 时立即抛出业务异常：

```text
非费项不能补录到应收账单
```

4. 校验通过后再计算金额、写入明细和刷新汇总。

后端校验是最终边界，不能只依赖前端隐藏。

#### 5.4.2 前端选项过滤

调整：

```text
admin_front/src/views/billing/receivableBill/index.vue
loadManualFeeIndexOptions()
```

只在应收账单补录弹窗本地过滤：

```text
feeType !== 'NON_FEE'
```

不修改通用费项管理 `options` 接口，因为该接口同时服务费项配置等其他业务场景，必须继续返回非费项。

### 5.5 汇总层保留兜底

以下现有过滤暂时保留：

1. `BillGenerateMapper.selectCurrencySummarySourceByBillId()` 对 `NON_FEE` 的排除。
2. `BillGenerateMapper.refreshBillAmountFromCurrencySummary()` 对 `NON_FEE` 的排除。

虽然新数据不再写入非费项明细，但保留汇总兜底可以防止历史数据、旧版本服务或异常写入污染账单金额。

本次不删除 `BmsConstants.FEE_TYPE_NON_FEE`，该常量仍被费项配置、返款和回款相关场景使用。

## 6. 数据库设计

### 6.1 设计结论

本次不新增业务表或业务字段，但需要调整 `bill_source_collect_mark` 的账单关联可空性。

原因：

1. `bms_billed_flag` 已确认为“是否被 BMS 拉取”，非费项成功拉取后必须置为 `1`。
2. 非费项不进入应收账单，因此没有合法的 `bill_id` 和 `bill_no`。
3. 当前 `bill_source_collect_mark.bill_id`、`bill_no` 都是 `NOT NULL`，无法记录“已抓取但未入账”。
4. 使用 `0`、空字符串或伪造账单号会污染账单关系、补偿查询和审计数据，不予采用。

相关字段：

| 表 | 字段 | 用途 |
| --- | --- | --- |
| `fee_index` | `fee_type` | 客户侧费项主档费用类型，`NON_FEE` 为本次判断依据 |
| `business_type_fee_index` | `fee_type` | 场景绑定时固化的费项类型快照 |
| `business_type_fee_index` | `fee_index_id` | 关联客户侧费项主档 |
| `fee_detail` | `fee_type` | 已生成费用明细的费用类型快照 |
| `fee_detail` | `bill_id` / `bill_no` | 费用与账单关联 |
| `bill_generate_task` | `fee_rule_snapshot_json` | 任务创建时的费项规则快照 |
| `bill_source_collect_mark` | `collect_type` | 新增语义值 `NON_FEE_FETCH`，表示非费项来源已抓取 |
| `bill_source_collect_mark` | `bill_id` / `bill_no` | 非费项抓取轨迹允许为空 |
| 来源表 | `bms_billed_flag` | 是否已被 BMS 拉取 |
| 来源表 | `bms_bill_no` | 实际进入账单时才保存账单号 |

建议 DDL：

```sql
ALTER TABLE `bill_source_collect_mark`
  MODIFY COLUMN `collect_type` varchar(32) NOT NULL
    COMMENT '归集类型：MAIN_ORDER主订单，ADDITIONAL_FEE附加费，ADDITIONAL_INCREMENT附加费增量，CLAIM_ORDER理赔，NON_FEE_FETCH非费项已抓取',
  MODIFY COLUMN `bill_id` bigint(20) unsigned DEFAULT NULL
    COMMENT '账单ID；NON_FEE_FETCH未进入账单时为空',
  MODIFY COLUMN `bill_no` varchar(64) DEFAULT NULL
    COMMENT '账单编号；NON_FEE_FETCH未进入账单时为空';
```

结构调整约束：

1. 实施时必须新增本次变更 DDL 文件。
2. 实施时必须同步更新 `aidocs/technical-caliber/sql/ar_bill.sql` 中 `bill_source_collect_mark` 的完整最新结构。
3. 不调整 `fee_detail` 表结构、唯一键和索引。
4. 不给 `fee_detail` 增加数据库级 `CHECK` 约束，因为 `fee_detail` 同时承载多种账单和结算角色，不能全局禁止 `NON_FEE`。
5. 开发库实际唯一键 `uk_source_collect(source_system, source_table, source_id, collect_type, bill_type)` 继续生效，防止同一账单类型重复记录同一来源，同时允许应收和返款分别留痕。
6. `idx_collect_task(generate_task_id, mark_status)` 可支持按任务查询无账单抓取轨迹，本次无需新增索引。
7. 来源库不需要 DDL，现有 `bms_billed_flag` 和 `bms_bill_no` 已能表达“已抓取但未入账”。
8. 当前 `aidocs/technical-caliber/sql/ar_bill.sql` 中 `uk_source_collect` 尚未包含开发库实际存在的 `bill_type`，实施时必须以目标环境实际结构为基线核对并修正归档，不能用旧归档覆盖现有唯一键。

### 6.3 历史数据策略

开发库当前没有 `fee_detail.fee_type = 'NON_FEE'` 的数据，因此开发库无需执行清理。

上线前对目标环境执行只读核对：

```sql
SELECT fd.fee_status,
       fd.settlement_role,
       COUNT(1) AS row_count,
       COUNT(DISTINCT fd.bill_id) AS bill_count
FROM fee_detail fd
WHERE fd.fee_type = 'NON_FEE'
GROUP BY fd.fee_status, fd.settlement_role;
```

```sql
SELECT b.bill_status,
       COUNT(DISTINCT b.id) AS bill_count,
       COUNT(fd.id) AS non_fee_count
FROM ar_bill b
JOIN fee_detail fd
  ON fd.bill_id = b.id
 AND fd.fee_type = 'NON_FEE'
 AND fd.fee_status <> 'VOID'
WHERE b.bill_type = 'MEMBER_AR'
  AND b.is_deleted = 0
GROUP BY b.bill_status;
```

默认不自动修改历史账单，原因：

1. 已发送、已确认或已核销账单属于历史财务结果。
2. 非费项当前已被金额汇总排除，不能为了页面隐藏直接物理删除审计数据。
3. 清理还涉及 `fee_detail` 状态、来源归集标记、主订单快照和账单导出的一致性。

如果产品要求历史应收账单也完全不可见，应单独制定迁移方案：

1. `DRAFT / GENERATED` 且未核销账单可通过整账重跑生成新账单。
2. 已确认、待结清、部分核销或已结清账单不得直接删除明细，应采用只读隐藏或财务确认后的专项迁移。
3. 迁移前后必须校验账单金额、币种汇总和核销余额不变。

### 6.4 任务快照处理

不批量改写历史 `bill_generate_task.fee_rule_snapshot_json`。

处理原则：

1. 新任务：继续在快照中保留 `NON_FEE`，用于来源扫描和抓取留痕。
2. 旧 `PENDING / NEED_RETRY` 任务：执行时将快照规则分为可出账规则和非费项抓取规则。
3. 已成功、已失败或已取消任务：保留原始快照作为审计证据。

## 10. 风险与控制

### 10.1 旧任务快照风险

只改 Mapper 查询无法处理调整前已创建的任务快照。

控制：

```text
Mapper 创建期固化主档类型 + Service 执行期统一分流
```

### 10.2 手工补录绕过风险

只处理自动生成时，用户仍可通过补录弹窗或直接接口把非费项写入应收账单。

控制：

```text
前端隐藏 + 后端强校验
```

### 10.3 空账单风险

配置只有非费项时，如果仍先扫描订单并创建账单，会形成无费用空账单。

控制：

```text
仍扫描和标记非费项来源，但在创建 ar_bill 前按 billableFeeRules 短路
```

### 10.4 来源数据重复扫描风险

非费项不写账单号；如果只保持 `bms_bill_no = NULL` 而不更新 `bms_billed_flag`，来源数据会被后续任务重复读取。

控制：

1. 成功拉取后写 `bms_billed_flag = 1`。
2. 保持 `bms_bill_no = NULL`，明确其未进入账单。
3. 使用 `NON_FEE_FETCH` 留存本地抓取轨迹并提供幂等保护。

### 10.5 抓取轨迹表兼容风险

将 `bill_source_collect_mark.bill_id/bill_no` 改为可空后，原有查询、重跑和补偿代码如果默认字段必有值，可能产生空指针或错误回退。

控制：

1. 原有 `MAIN_ORDER / ADDITIONAL_FEE / ADDITIONAL_INCREMENT / CLAIM_ORDER` 仍强制传账单ID和账单号。
2. 只有 `NON_FEE_FETCH` 允许账单关联为空。
3. 按账单重跑的查询排除 `NON_FEE_FETCH`，非费项抓取轨迹按 `generate_task_id` 管理。
4. 增加原有有账单轨迹的完整回归测试。

### 10.6 返款和回款回归风险

风险包括：

1. 如果在通用费项索引接口、全局 `fee_detail` 查询或数据库约束层直接禁止 `NON_FEE`，可能破坏返款和回款场景。
2. 如果应收任务把全局 `bms_billed_flag` 置为 `1`，而返款任务继续只查询 `bms_billed_flag = 0`，返款来源会被误跳过。

控制：

1. 非费项明细过滤只放在 `MEMBER_AR` 费用构建和应收补录边界。
2. 不同账单类型的防重复以 `bill_source_collect_mark.bill_type` 为准。
3. 对应收先执行和返款先执行两个顺序做双向回归。
