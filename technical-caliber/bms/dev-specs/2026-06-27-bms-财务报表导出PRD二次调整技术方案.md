# BMS 财务报表导出 PRD 二次调整技术方案（2026-06-27）

## 1. 文档目的

本文基于 `aidocs` 仓库中的以下两个提交，结合当前 `bms`、`platform-admin`、`admin_shell` 代码现状，整理财务报表导出链路的二次调整方案：

1. `5fae0770c1552a0dfcbb8f636747188ba78aa1fc`
2. `d3a633e8b18f1fbffd93761452ee368cfedce58c`

本文输出 4 类内容：

1. 两个提交的变更内容整理。
2. 最新 PRD 最终口径收敛。
3. 结合现有代码的技术调整方案与实施计划。
4. 当前仍需产品、财务、研发共同确认的疑问点。

本文默认继承以下已有文档背景，但只聚焦“6 月 27 日 PRD 二次收口后，还需要对现有导出实现做哪些增量调整”：

1. `aidocs/technical-caliber/bms/dev-specs/2026-06-26-bms-应收账单与返款账单财务报表导出调整技术方案.md`
2. `aidocs/technical-caliber/bms/dev-specs/2026-06-26-bms-财务报表导出字段映射与开发任务清单.md`

## 2. Git 提交变更整理

## 2.1 提交 `5fae0770c1552a0dfcbb8f636747188ba78aa1fc`

### 2.1.1 涉及文件

1. `aidocs/product-caliber/bms/prd/derivant/财务报表导出格式.md`
2. `aidocs/product-caliber/bms/prd/财务系统.PRD.md`

### 2.1.2 变更要点

该提交的核心动作是“首次把财务导出格式从零散样本整理成明确 PRD 规则”，并同步把导出范围写回主 PRD。

#### A. 新增独立导出格式文档

`财务报表导出格式.md` 在该提交中首次形成完整结构，明确了：

1. 应收账单导出格式。
2. 返款账单导出格式。
3. 应收与返款的统一明细字段。
4. 统一删除规则。

#### B. 首次明确导出总体原则

新增文档中首次明确：

1. 只保留影响金额、归属、追溯的字段。
2. 删除大面积空白列、占位列、图片占位列。
3. 头部区、明细区、汇总区要分开。
4. 导出金额口径以“结算币种金额”为准。
5. 导出文件不展示原始币种金额、汇率、财务本位币金额或历史快照。

#### C. 在主 PRD 中补充“导出范围”

`财务系统.PRD.md` 在该提交中新增或强化了以下口径：

1. 应收账单详情页增加“导出当前账单明细”能力。
2. 导出只面向当前账单结果。
3. 导出不支持历史快照导出。
4. 历史快照只用于审计、追溯和防回写，不作为客户或财务导出对象。
5. 验收标准新增“导出不包含历史快照”。

### 2.1.3 对研发的直接影响

这个提交把“是否需要导出历史快照”和“是否展示汇率/原币金额”从可讨论问题变成了明确约束：

1. 不能导出历史快照。
2. 不能对外导出原币金额、汇率、财务本位币金额。
3. 导出应围绕当前账单结果组织。

## 2.2 提交 `d3a633e8b18f1fbffd93761452ee368cfedce58c`

### 2.2.1 涉及文件

1. `aidocs/product-caliber/bms/prd/derivant/财务报表导出格式.md`

### 2.2.2 变更要点

该提交不是新增一个新方向，而是在前一版导出格式文档基础上继续“收口”和“减法”。

#### A. 统一明细字段被大幅收敛

原先第三章中较长的一整套字段清单，被收敛成“基础列 + 动态费项列”的结构：

1. 基础列固定。
2. 费项列不再要求预先全部写死。
3. 非适用字段明确要求填 `--`。

#### B. 明确“费项展开”是动态列

这是该提交最关键的变化之一：

1. 【费项展开】不是固定列清单。
2. 导出时按当前账单实际存在的费项动态展开。
3. 应收账单动态列金额统一为“费项结算币种金额”。
4. 返款账单动态列金额统一为“货款结算币种金额”。

#### C. 明确禁止追加的字段类型

该提交把“不应该导出的字段”进一步写死：

1. 不得追加金额类扩展字段。
2. 不得追加汇率类字段。
3. 不得追加财务本位币字段。
4. 不得追加快照字段。
5. 不得追加内部审核、内部任务、源表技术字段。

#### D. 汇总使用规则从“金额口径说明”切到“透视维度说明”

新的文档更强调客户如何用导出结果做汇总，而不是让导出本身承载大量内部技术解释：

1. 按业务板块、目的国、业务日期汇总。
2. 按订单号、承运单号、转单号码回查订单。
3. 应收与返款不能混成一个净额字段。

### 2.2.3 对研发的直接影响

这个提交直接推翻了“把所有可能金额列、汇率列、内部追溯列一次性全导出去”的实现思路，导向变成：

1. 基础业务字段固定。
2. 费项金额列动态展开。
3. 内部技术字段从导出模板中剔除。

## 2.3 两个提交合并后的 PRD 最终结论

结合两个提交，当前财务报表导出最终口径可以收敛为 7 条：

1. 导出对象只面向当前账单结果，不导出历史快照。
2. 导出文件对外只展示财务/客户可理解的业务字段。
3. 明细区默认采用“基础字段固定 + 费项金额动态展开”。
4. 金额展示口径统一为结算币种金额，不展示原币金额、汇率、财务本位币金额。
5. 不适用字段需要保留列结构，但值统一按约定占位。
6. 技术型字段、内部审核字段、源表技术字段不应进入最终客户导出模板。
7. 导出文件需要兼容客户后续自行透视、筛选、汇总。

## 3. 结合现有代码的现状判断

## 3.1 当前代码已完成的部分

对照 6 月 26 日方案与当前仓库代码，以下内容已经落地，不需要推倒重来：

1. `bms` 已提供专用导出接口：
   - `ArBillServiceImpl.exportData(...)`
   - `RefundBillServiceImpl.exportData(...)`
2. `platform-admin` 已从旧 HTML 伪 Excel 迁移到真实 `.xlsx` 输出：
   - `BmsFinanceExportExcelHelper.writeArExport(...)`
   - `BmsFinanceExportExcelHelper.writeRefundExport(...)`
3. `admin_shell` 已切到 `.xlsx` 下载文件名：
   - 应收账单：`应收账单明细-{billNo}.xlsx`
   - 返款账单：`返款账单明细-{billNo}.xlsx`
4. 当前导出链路没有提供“历史快照版本导出”入口，这一点与 6 月 27 日主 PRD 一致。

## 3.2 当前代码与最新 PRD 的主要差距

虽然导出链路已经有一版实现，但当前实现更接近“6 月 26 日版本”，与 6 月 27 日二次收口后的 PRD 还有明显差距。

### 3.2.1 仍在导出原币、汇率、财务本位币字段

当前 `BmsFinanceExportExcelHelper` 明细 sheet 仍输出以下字段：

1. 原币金额。
2. 原币到结算币汇率。
3. 结算币到财务本位币汇率。
4. 财务本位币。
5. 财务本位币金额。

这与最新 PRD 中“导出账单只展示计算后的结算币种金额，不展示原始币种金额、汇率、财务本位币金额”的口径冲突。

### 3.2.2 仍在导出内部技术字段

当前应收导出仍输出：

1. `来源系统`
2. `来源表`
3. `来源单据号`
4. `录入人`

而最新 PRD 已经明确限制：

1. 源表技术字段不应进入最终导出模板。
2. 内部审核、内部任务、内部技术字段不应对外导出。

这里至少说明当前实现需要做“对外模板字段瘦身”。

### 3.2.3 当前仍是固定费项列，不是动态费项展开

当前实现中：

1. 应收账单写死了 `运费 / 派送费 / 进店 / 打包 / 应收货款 / 代收手续费 / 代收回款 / 其它费用`
2. 返款账单写死了 `运费 / 派送费 / 代收款 / 代收手续费 / 回款 / 退款金额/应退金额 / 超商取件费 / 附加服务项目/其他收入 / 其它费用`

这与最新 PRD 的“按当前账单实际存在费项动态展开”不一致。

### 3.2.4 当前返款导出缺少二次收口后的基础字段

最新 PRD 第三章新增或强化了返款独有字段：

1. 返款模式
2. 签收时间
3. 回款时间

当前 `RefundBillFinanceExportRowDTO` 与 Excel 输出中并未体现这几个字段。

### 3.2.5 当前空值策略与 PRD 不一致

最新 PRD 要求：

1. 除费项展开外，基础字段固定保留。
2. 某类账单不适用字段填 `--`。

当前代码大多数场景仍是：

1. 不适用直接输出空字符串。
2. 没有统一的 `--` 占位策略。

### 3.2.6 当前导出粒度与 PRD 文案存在潜在冲突

当前 `bms` 实现是：

1. 底层以 `fee_detail` 为来源。
2. 服务层按订单聚合。
3. 最终一行一个订单。

但最新 PRD 中同时存在两种表述：

1. “以 `fee_detail` 为主线，一行对应一条 `fee_detail`”
2. “基础列固定 + 费项动态展开”

这两种表述并不完全一致。当前代码延续的是“一行一个订单”的实现路径，因此这里必须单独挂牌为疑问点，而不能默认视为已完全满足 PRD。

## 4. 二次调整的推荐技术方案

## 4.1 总体原则

本轮建议采用“在现有导出链路上做增量收口”的策略，不再重复做 6 月 26 日那种从零搭建式改造。

原则如下：

1. 保持现有导出入口 URL 不变。
2. 保持 `bms -> platform-admin -> admin_shell` 现有调用链不变。
3. 优先调整 DTO 字段口径和 Excel 模板，不扩大到无关模块。
4. 只围绕 6 月 27 日 PRD 新增约束做减法和收口。

## 4.2 推荐的最终导出模型

建议把导出数据模型收敛为：

1. 账单头部字段。
2. 基础固定字段。
3. 动态费项金额列。
4. 汇总字段。

不再在最终 Excel 模板中输出以下内容：

1. 原币金额。
2. 汇率字段。
3. 财务本位币及金额。
4. 历史快照相关字段。
5. 源表技术字段。
6. 内部操作人与内部审核类字段。

## 4.3 BMS 模块调整方案

### 4.3.1 DTO 口径调整

建议保留现有导出接口方法名不变，但调整导出 DTO 的表达方式。

推荐方向：

1. 保留现有：
   - `ArBillFinanceExportRespDTO`
   - `RefundBillFinanceExportRespDTO`
2. 将“固定金额列”逐步改造为：
   - `baseFields`
   - `dynamicFeeHeaders`
   - `dynamicFeeAmountMap`

这样做的原因：

1. 现有接口链路已经打通，继续沿用接口最稳。
2. 动态费项列如果仍用写死字段，后续每加一个费项都要改 DTO、Service、Helper。
3. 最新 PRD 已经明确要求费项列按账单实际数据动态展开。

### 4.3.2 服务层数据组装调整

应收与返款服务都建议按以下思路调整：

1. 底层仍以 `fee_detail` 为主线取数。
2. 先保留当前订单补数逻辑，不推翻现有外部订单补查。
3. 将费用分类结果从“固定金额属性赋值”调整为“动态列收集”。
4. 最终对外返回：
   - 基础字段集合
   - 动态费项表头集合
   - 每行的费项金额映射

### 4.3.3 对外字段白名单收口

建议在 `bms` 侧就明确“对外导出字段白名单”，避免 Helper 再自行判断。

应从导出响应中剔除或不再用于最终模板输出的字段包括：

1. 原币金额相关字段。
2. 汇率相关字段。
3. 财务本位币金额相关字段。
4. `sourceTable` 之类的源表技术字段。
5. 内部录入人、内部审核痕迹字段。

### 4.3.4 返款账单补齐新增基础字段

返款账单建议在现有 DTO 基础上补齐：

1. `refundMode`
2. `signedTime`
3. `receivedTime`

这三个字段属于最新 PRD 第三章已经明确的返款独有基础字段，且与客户合并透视直接相关。

## 4.4 Platform Admin 模块调整方案

### 4.4.1 Excel Helper 改为“固定基础列 + 动态费项列”

`BmsFinanceExportExcelHelper` 建议改为两段式列构建：

1. 先输出固定基础列。
2. 再按 `dynamicFeeHeaders` 输出动态金额列。

不要继续把费项金额列硬编码在 Helper 中。

### 4.4.2 模板字段做减法

Helper 层应同步删除以下输出：

1. 原币金额列。
2. 汇率列。
3. 财务本位币与财务本位币金额列。
4. `来源系统 / 来源表 / 来源单据号` 这类技术字段。
5. `录入人` 等内部字段。

### 4.4.3 统一占位规则

对最新 PRD 指定为“某账单不适用”的基础列，建议在 Helper 写出阶段统一输出 `--`，不要再按空字符串写出。

原因：

1. 这属于展示层规则。
2. 同一服务 DTO 可避免同时承载真实空值与展示占位值。

## 4.5 Admin Shell 模块调整方案

`admin_shell` 本轮建议只做最小联动：

1. 保持导出入口不变。
2. 保持当前 `.xlsx` 下载方式不变。
3. 删除返款页面中“TODO: 替换为后端实际导出的字段映射”的陈旧注释，避免误导。

本轮不建议在前端重新拼导出字段，也不建议在页面层维护列映射。

## 5. 实施计划

建议按 4 个步骤推进。

## 5.1 Step 1：最终口径冻结

目标：

1. 基于 `5fae...` 与 `d3a...` 两次提交冻结最终字段口径。
2. 把“保留字段 / 动态字段 / 禁止导出字段”三类分清。

动作：

1. 确认基础固定字段清单。
2. 确认动态费项列命名规则。
3. 确认不适用字段统一输出 `--`。

1. 最终字段白名单。
2. 最终禁止导出字段清单。

目标：

1. 把现有固定金额字段模式调整为动态费项列模式。
2. 删除与最新 PRD 冲突的对外字段。

动作：

1. 调整应收/返款导出 DTO。
2. 改造服务层费项聚合结果。
3. 补齐返款模式、签收时间、回款时间。

交付物：

1. `bms` 导出响应结构更新。

## 5.3 Step 3：Platform Admin 导出模板调整

目标：

1. 让实际 Excel 模板与最新 PRD 一致。

动作：

1. `BmsFinanceExportExcelHelper` 改为动态列写法。
2. 删除原币、汇率、财务本位币、技术字段列。
3. 统一 `--` 占位规则。

交付物：

1. 最新版应收/返款财务导出 `.xlsx`。

## 5.4 Step 4：联调与验收

至少验证以下场景：

1. 应收账单含多个实际费项时，动态列是否按实际费项输出。
2. 返款账单含不同返款模式时，返款模式、签收时间、回款时间是否正确输出。
3. 不适用字段是否统一为 `--`。
4. 模板中是否已彻底移除原币金额、汇率、财务本位币金额。
5. 模板中是否已彻底移除内部技术字段。

## 7. 疑问点

以下问题建议在开发前确认，否则容易在“现有实现”和“最新 PRD 字面描述”之间反复返工。

### 7.1 明细粒度到底是一行一个订单，还是一行一条 `fee_detail`

当前冲突点：

1. 现有代码是一行一个订单。
2. 最新 PRD 在应收费项兼容规则里写的是“一行对应一条 `fee_detail`”。
3. 但最新 PRD 第三章又改成“基础字段固定 + 费项动态展开”，这更像订单横表。

建议确认：

1. 最终是否继续按“一行一个订单”落地。
2. 还是要改成真正的 `fee_detail` 粒度导出。

### 7.2 `来源系统 / 来源表 / 来源单据号` 是否最终保留

当前文档内部存在潜在冲突：

1. 第一章兼容规则中仍把来源链路列为保留字段。
2. 第三章整合原则又明确说不补充源表技术字段。

建议确认：

1. `来源系统` 是否属于客户可见字段。
2. `来源表` 是否必须从最终导出模板剔除。
3. `来源单据号` 是否保留为追溯字段。

### 7.3 不适用字段是填 `--` 还是保留空值

最新 PRD 文案写的是填 `--`，但样例表中很多位置仍是空白。

建议确认：

1. 财务实际是否要求 `--`。
2. 还是接受空白值，只要列结构固定即可。

### 7.4 动态费项列的命名归并规则由谁拍板

当前代码里已经有一版分类常量，但最新 PRD 变成“实际费项动态展开”后，需要确认：

1. `运费` 和 `基础运费` 是否合并。
2. `代收回款` 和 `回款金额` 是否合并。
3. `退款金额` 和 `应退金额` 是否合并。
4. `附加服务项目`、`其他收入`、`其它费用` 的边界如何划分。

如果没有这张归并表，动态列最终仍会漂移。

### 7.5 汇总区的“备注 / 付款凭证 / 汇兑损益金额”是否本轮必须落地

当前 PRD 汇总区仍保留这些字段，但现有代码并未完整承接。

建议确认：

1. 本轮是否必须新增这些汇总字段。
2. 还是允许继续作为后续增量项。

## 8. 结论

6 月 27 日这两次提交对财务报表导出的影响，不是重新开一条新导出链路，而是把已经做出来的一版导出继续“收口”为真正的对外财务模板：

1. 从“固定费项列”收口为“固定基础列 + 动态费项列”。
2. 从“导出大量内部计算字段”收口为“只导出客户可理解字段”。
3. 从“可讨论是否展示快照/汇率/原币金额”收口为“明确不展示”。

因此本轮最合适的实施方式不是推翻现有实现，而是：

1. 在 `bms` 侧收紧导出 DTO 口径。
2. 在 `platform-admin` 侧重写列构建规则。
3. 在 `admin_shell` 侧维持最小联动。

这样改动范围最小，也最符合当前仓库已经完成了一轮导出改造的实际情况。
