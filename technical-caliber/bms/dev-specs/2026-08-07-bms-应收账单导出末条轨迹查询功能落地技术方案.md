# 2026-08-07 BMS 应收账单导出「末条轨迹」查询功能落地技术方案

## 1. 文档目的

本文基于当前仓库实现与数据库实测，整理「应收账单（及返款账单）财务导出中末条轨迹状态、末条轨迹描述、末条轨迹时间三字段落地查询」的技术方案、调整计划与待确认问题。

本方案只讨论财务导出链路中「末条轨迹」三字段的数据接入，不扩展其他导出字段、不调整账单状态机。

## 2. 结论先行

1. 末条轨迹三字段当前在 `bms` 导出拼装层被**硬编码置空**，属于"无数据源接入"的占位实现，不是数据查询失败。
2. 轨迹数据在 **`lfc_basedb` 库**（`tms_waybill_trajectory_info` + `tms_waybill_status`），与 cxms 不在同一逻辑查询路径，需要**跨库拆分查询**：先在 cxms 取订单尾程运单号，再用运单号列表到 lfc_basedb 批量取"每单号最新一条轨迹"。
3. cxms 与 lfc_basedb 位于**同一 RDS 实例**，`CXMS_DB` 数据源连接可直接访问 `lfc_basedb`，**无需新增数据源配置**，SQL 中使用全限定表名 `lfc_basedb.tms_waybill_trajectory_info` 即可。
4. 实测数据现状：cxms 最近 1000 个尾程运单号中仅 19 个（约 1.9%）能在轨迹表命中，且命中的基本为测试/历史单号——**功能实现后多数订单的末条轨迹可能为空，属源数据问题**，需与 LFC 侧核对（见疑问点 Q3）。
5. 用户提供的参考 SQL 方向正确，但存在两个隐患：① 同一 `waybill_no` 若存在多条 `op_time` 相同的轨迹会返回多行；② `tms_waybill_status.waybill_status` 非唯一（同名多承运商），直接 JOIN 会行数膨胀。方案给出修正 SQL（见 5.2），实测 `EXPLAIN` 更优。

## 4. 数据调研结论（实测）

### 4.1 关联关系与字段来源

```
cxms.ob_shipping_package_header.sub_waybill_no = lfc_basedb.tms_waybill_trajectory_info.waybill_no   -- 1 对多
```

| 导出列 | 来源字段 |
|---|---|
| 末条轨迹时间 | `lfc_basedb.tms_waybill_trajectory_info.op_time`（datetime） |
| 末条轨迹描述 | `lfc_basedb.tms_waybill_trajectory_info.outer_op_desc`（varchar(255)） |
| 末条轨迹状态 | `lfc_basedb.tms_waybill_status.waybill_status_name`，经轨迹表 `waybill_status` 关联 |

### 4.2 `lfc_basedb.tms_waybill_trajectory_info` 表结构与索引

- 33 列，关键列：`id`(PK, auto_increment)、`waybill_no` varchar(50) NOT NULL、`carrier_code` varchar(32)、`warehouse_code`、`op_time` datetime NOT NULL、`waybill_status` varchar(50) NOT NULL、`outer_op_code`/`outer_op_name`/`outer_op_desc`、`op_code`/`op_name`/`op_desc`、`source`、`create_time` 等。
- 索引：
  - `PRIMARY (id)`
  - `idx_waybill_no (waybill_no)`
  - `no_code (waybill_no, carrier_code, warehouse_code)`
  - `IDX_TMS_WAYBILL_TRAJECTORY_INFO_WAYBILL_NO (warehouse_code, waybill_no)`
  - `IDX_TMS_WAYBILL_TRAJECTORY_INFO_CREATE_TIME (warehouse_code, op_code, create_time)`、`idx_syn (create_time, company_code, op_code)` 等
- **没有 `(waybill_no, op_time)` 联合索引**：`WHERE waybill_no IN (...)` 命中 `idx_waybill_no`/`no_code`（range + Using index condition），但 `MAX(op_time)` 需要回表取 op_time。
- 数据量：约 **568 万行**，op_time 范围 2021-09 ~ 2026-07；单运单轨迹条数实测 ≤11 条（近期样本 1~11 条），回表成本可控。

### 4.3 `lfc_basedb.tms_waybill_status` 表结构与索引

- 16 列：`id`(PK)、`waybill_status` varchar(32)、`waybill_status_name` varchar(50)、`waybill_status_desc` varchar(255)、`carrier_code` varchar(32)、`standard_status`、`sort_order` 等。
- 仅 `PRIMARY (id)`，**`waybill_status` 无索引、非唯一**：实测同名 `waybill_status` 有多行（如 `'611'` 6 行 / 3 个不同 name / 4 个 carrier；`'OTHER'` 3 行）。
- 全表仅 **212 行**，可整表加载到 Java 内存做映射，或 SQL 侧 `GROUP BY waybill_status` 取 `MAX(waybill_status_name)` 兜底（与用户参考 SQL 一致）。

### 4.4 数据现状风险（实测）

1. **匹配率极低**：cxms 最近 1000 个 `sub_waybill_no` 中仅 19 个在轨迹表命中（1.9%），且命中的均为 `HK190xxx`/`DF2025...`/`YUDAN...`/`AB003481` 等测试/历史单号；生产数字单号（如 `1157761743`）未命中。最近 30 天轨迹表仅 54 个 distinct 运单号。
2. **`op_time` 相同时刻多条轨迹**：近期样本 `(waybill_no, op_time)` 分组无重复，但 568 万行历史数据不能保证；且 `waybill_status` 同名多 carrier 直接 JOIN 会行膨胀——"取最新一条"必须带决胜键（推荐 `id` 最大），不能只按 `op_time` 关联。
3. **同一运单号跨仓库重复（用户确认的优化点，已实测）**：近期 218 个 `waybill_no` 同时出现在多个 `warehouse_code` 下（如 `SZT2026072002` 同时存在于 `'TMcang'` 与 `'30'`，轨迹内容不同）。**必须按 `(warehouse_code, waybill_no)` 组合查询**，仅按运单号会取到错误仓库的轨迹。
4. **`warehouse_code` 编码两库一致**：cxms `'TMcang'` 等编码在 lfc 轨迹表可直接命中（`'TMcang'` 共 11524 行）；lfc 轨迹表另有大量 `TMYT-*`（约 510 万行）与少量数字型编码，未参与本功能查询。
5. 轨迹表存在 `outer_*`（外部）与 `op_*`（内部）两套字段，当前口径取 `outer_op_desc` + `op_time`（与用户要求一致）。

### 4.5 SQL 实测 EXPLAIN 与版本约束

RDS 实测版本 **MySQL 5.7.43**（不支持窗口函数）。在 `waybill_no IN (3 个)` 场景下：

- 用户参考 SQL（`MAX(op_time)` 派生表 + `op_time` 关联）：外层对 `a` 走 `idx_waybill_no`（ref，rows≈4），派生表走 `no_code`（range + Using index condition）。可用，不漏行；同 `op_time` 多条时会返回多行。
- 曾尝试 `MAX(op_time)` + `MAX(id)` 派生表 + `op_time,id` 双条件关联：实测**会漏行**——`DF20250000061` 的 `MAX(op_time)` 行 id=217334368、`MAX(id)`=217334369 不是同一行，双条件关联查不到该运单。**已废弃该写法**。
- 落地版 = 用户参考 SQL + SELECT 带 `id`，同运单同 `op_time` 多行由 Java 侧按 `id` 最大决胜（见 5.2.1）。实测对 `DF20250000061`/`SZT2026072002`/`HK190630` 返回与手工核对（`op_time DESC, id DESC` 取首行）完全一致。

## 5. 技术方案

### 5.1 总体链路（跨库拆分查询，不跨库 JOIN）

```
Step1  cxms 库（现有 CxmsShippingPackageQueryService.queryAggregates 已产出，无需改动）
       (warehouse_code, erp_order_no) → sub_waybill_no 集合（1 订单 N 运单，同属一个 warehouse_code）
Step2  lfc_basedb 库（LfcWaybillTrajectoryQueryService）
       收集全部订单的 (warehouse_code, sub_waybill_no) 去重 → 分批（≤300 组）→ 每键最新一条轨迹 + 状态名；
       无仓库信息的运单号（sourceOrder 缺失时的 fee_detail 兜底）按 waybill_no IN (...) 查询
Step3  bms 服务层按订单聚合（订单内所有轨迹 op_time 最大）→ 回填 ArBillFinanceExportRowDTO / RefundBillFinanceExportRowDTO 三字段
Step4  platform-admin Excel 写出（表头已存在，仅修复返款状态列硬编码）
```

连接方式：复用 `SourceDatasourceConnectionProvider` + `CXMS_DB` 配置（同实例 root 可访问 lfc_basedb），SQL 写全限定名 `lfc_basedb.tms_waybill_trajectory_info` / `lfc_basedb.tms_waybill_status`，**不新增数据源配置**（避免改 `fee_source_datasource` 表）。

### 5.2 SQL 设计

#### 5.2.1 取每个 (仓库, 运单号) 最新一条轨迹（落地版）

同一运单号可能跨仓库重复（实测 `SZT2026072002` 在 `'TMcang'` 与 `'30'` 下轨迹不同），
因此查询键为仓库编码 + 运单号，命中轨迹表联合索引
`IDX_TMS_WAYBILL_TRAJECTORY_INFO_WAYBILL_NO (warehouse_code, waybill_no)`：

```sql
SELECT a.id, a.warehouse_code, a.waybill_no, a.outer_op_desc AS trajectory_desc,
       a.op_time AS trajectory_time, a.waybill_status
FROM lfc_basedb.tms_waybill_trajectory_info a
INNER JOIN (
    SELECT warehouse_code, waybill_no, MAX(op_time) AS max_op_time
    FROM lfc_basedb.tms_waybill_trajectory_info
    WHERE (warehouse_code, waybill_no) IN ((?, ?), (?, ?), ...)   -- 分批 ≤300 组
    GROUP BY warehouse_code, waybill_no
) latest
    ON a.warehouse_code = latest.warehouse_code
   AND a.waybill_no    = latest.waybill_no
   AND a.op_time       = latest.max_op_time
```

要点（含两轮实测修正）：

1. **必须带 `warehouse_code`**：仅按运单号查询会把跨仓库重复的轨迹混为一组，`MAX(op_time)` 可能取到错误仓库的轨迹（实测 `SZT2026072002` 按运单号全局查取到 `'TMcang'` 2026-07-23 的轨迹，按 `('30', ...)` 组合查才取到 `'30'` 仓库 2026-07-20 的正确轨迹）。
2. **不要用 `MAX(op_time)` + `MAX(id)` 双聚合决胜**：两个独立聚合不保证来自同一行。实测 `DF20250000061` 的 `MAX(op_time)` 行 id=217334368、`MAX(id)`=217334369，双条件关联会**漏掉该运单**。落地版只按 `op_time = MAX(op_time)` 关联（不漏行）。
3. **同键、同 `op_time` 多条轨迹的决胜在 Java 侧做**：SQL 返回带 `id`，`LfcWaybillTrajectoryQueryService` 对同一 `(warehouse_code, waybill_no)` 多行取 `id` 最大（防重复，确定性）。近期样本无重复，属兜底。
4. **MySQL 版本约束**：RDS 实测 **5.7.43**，不支持窗口函数，不能用 `ROW_NUMBER() OVER (...)`；row constructor `(a,b) IN ((?,?),...)` 在 5.7 可用且实测命中 `IDX_TMS_WAYBILL_TRAJECTORY_INFO_WAYBILL_NO`（range，Using index condition / Using where，与 OR 展开等价）。
5. **无仓库信息的兜底**：`sourceOrder` 缺失时 fee_detail 运单号无仓库编码，单独按 `waybill_no IN (...)` 查询（命中 `idx_waybill_no`/`no_code`），由 `queryLatestByWaybillNoBatch` 处理。

#### 5.2.2 状态名映射（全表 212 行，直接查一次构建内存 Map）

```sql
SELECT waybill_status, MAX(waybill_status_name) AS waybill_status_name
FROM lfc_basedb.tms_waybill_status
GROUP BY waybill_status
```

- 与用户参考 SQL 的兜底口径一致；因同名多 carrier 取 MAX(name)。
- 也可改为按 `(waybill_status, carrier_code)` 精确映射（轨迹表有 `carrier_code`）——见疑问点 Q4。

#### 5.2.3 性能与索引利用说明

- IN 分批 ≤300（沿用现有 `QUERY_BATCH_SIZE`），单批派生表扫描行数 = 命中运单号数 × 平均轨迹数（实测 ≤11），总量可控。
- 当前无 `(waybill_no, op_time)` 联合索引，`MAX(op_time)` 需回表；568 万行 + 单号轨迹少，现状可接受。**可选优化：请 DBA 评估新增 `(waybill_no, op_time, id)` 覆盖索引**，可将派生表变为纯索引扫描（Using index），但不属于本次代码改动（见疑问点 Q5）。

### 5.4 聚合口径（订单级，待确认 Q1）

Excel 一行 = 一个订单（`businessOrderNo`），一个订单对应 cxms 1..N 个 `sub_waybill_no`，每个运单 1 条最新轨迹。**默认口径：取订单下所有运单轨迹中 `op_time` 最大的一条**（全局最新），与该行"承运单号"列展示的多个运单号语义一致。备选：主运单（首个 sub_waybill_no）。

### 5.5 异常与降级

- 轨迹查询失败（连接异常、超时、SQL 错误）**不影响主导出**：`try/catch` 捕获后按该订单轨迹为空处理并 `log.warn`，三字段输出空字符串（与现状一致），保证导出主流程稳定。
- 运单号为空/查无轨迹：三字段输出空字符串。
- 时间格式：`op_time` 用现有 `formatDateTime` 格式化为字符串（与 `signedTime` 等一致）。
