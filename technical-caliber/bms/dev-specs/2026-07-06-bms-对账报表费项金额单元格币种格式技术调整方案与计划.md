### 2.2 新增需求的可执行口径

本次变更只针对对账报表 Sheet 2 中由“费项展开”生成的动态费项金额单元格，要求同时满足：

1. 单元格视觉效果为“金额 + 空格 + 费项结算币种”，例如 `10.00 USD`。
2. 币种必须通过 Excel 数字格式展示，不能把单元格写成字符串。
3. 单元格底层值必须保持数值类型，以便继续使用 `SUM`、筛选、排序和数据透视。
4. 币种不能写入动态费项列标题。
5. 币种不能拆成额外导出列。
6. 币种口径是该笔费项的结算币种：应收账单对应 `fee_detail.bill_currency`，返款账单对应返款费项明细的 `billCurrency`，不是原始币种或财务本位币。
7. 本次要求同时覆盖应收账单的 `费项明细` 和返款账单的 `返款明细`。

### 2.3 不在本次提交中改变的内容

1. 三 Sheet 结构不变：汇总、明细、往期账单冲正信息。
2. 动态费项列规则不变：实际发生多少种费项就展开多少列。
3. 非费项金额单元格没有被要求追加币种。
4. 前端交互、下载入口和接口 URL 没有新增要求。
5. 不要求修改数据库表结构。

## 3. 当前实现盘点

### 3.1 调用链

```mermaid
flowchart LR
    A["admin_shell 账单页面"] --> B["platform-admin 导出 Controller"]
    B --> C["BMS Feign 导出接口"]
    C --> D["BMS Service 按订单聚合费项"]
    D --> E["FinanceExportRespDTO"]
    E --> F["BmsFinanceExportExcelHelper"]
    F --> G["三 Sheet .xlsx 文件"]
```

当前主实现已经不是旧版 HTML 伪 `.xls`：

- `admin_shell/src/views/billing/receivableBill/index.vue`、`refundBill/index.vue` 负责触发下载，不生成 Excel 内容。
- `platform-admin` 的 `BmsArBillController`、`BmsRefundBillController` 调用 BMS 导出接口。
- `platform-admin/.../BmsFinanceExportExcelHelper.java` 使用 Apache POI 生成真实 `.xlsx`，并建立“汇总 / 费项明细或返款明细 / 往期账单冲正信息”三个 Sheet。
- `bms` 已提供 `ArBillFinanceExportRespDTO`、`RefundBillFinanceExportRespDTO` 及对应行 DTO。

### 3.2 当前动态费项生成方式

应收和返款当前均采用相同的抽象：

1. `feeColumns: List<String>` 保存动态费项列名。
2. 行 DTO 的 `feeAmountMap: Map<String, BigDecimal>` 保存“费项列名 -> 结算金额”。
3. BMS Service 按订单聚合费项金额：
   - 应收使用 `ArBillFeeDetailDTO.amountBillCurrency`；
   - 返款使用 `RefundBillFeeDetailDTO.amount`。
4. Excel Helper 遍历 `feeColumns`，从 `feeAmountMap` 取金额并调用 `writeAmount(...)`。

### 3.3 当前缺口

| 层级 | 当前实现 | 与 PRD 的差异 |
| --- | --- | --- |
| 数据源 | 费项明细已有 `billCurrency` | 数据具备，但聚合时没有按动态单元格保留 |
| BMS 聚合 | 只合并费项金额 | 同名费项若出现不同结算币种，会直接做无意义跨币种相加 |
| 导出 DTO | `feeColumns` 只有名称，`feeAmountMap` 只有金额 | 无法知道具体单元格应显示哪个结算币种 |
| Excel Helper | 所有金额共用 `0.0000` 样式 | 动态费项单元格不会显示币种，且财务要求精确到 3 位小数 |
| Excel 单元格 | 底层是数值 | 这一点符合 PRD，应继续保持 |
| Admin Shell | 只下载文件 | 无须承担币种格式逻辑 |

当前 `Styles.amount` 的格式为 `0.0000`。如果简单拼成 `10.00 USD` 再写入，虽然视觉上接近要求，但单元格会变成字符串，违反“可计算金额”的明确要求。

## 4. 技术调整方案

### 4.1 总体原则

1. BMS 负责提供每个动态费项单元格的金额和结算币种。
2. Platform Admin 负责把币种转换为 Excel 数字格式。
3. Admin Shell 保持现有下载入口、接口和文件名逻辑不变。
4. 不新增或修改数据库结构。
5. 不把币种拼进列标题，不新增币种列，不把金额转换成文本。
6. 不继续扩散现有 `Map` 类型的跨层协议；本次新增结构使用显式 DTO。

### 4.2 推荐数据模型

新增通用费项导出单元格 DTO：

```java
/** 对账报表动态费项单元格。 */
public class FinanceExportFeeCellDTO {
    /** 费项显示名称。 */
    private String feeName;
    /** 费项结算金额。 */
    private BigDecimal settlementAmount;
    /** 费项结算币种，使用 ISO 4217 三位代码。 */
    private String settlementCurrency;
}
```

在 `ArBillFinanceExportRowDTO` 和 `RefundBillFinanceExportRowDTO` 中新增：

```java
/** 动态费项单元格列表。 */
private List<FinanceExportFeeCellDTO> feeCells = new ArrayList<>();
```

兼容策略：

- 第一阶段保留现有 `feeAmountMap`，避免旧调用方立即受影响；Excel Helper 优先读取 `feeCells`，缺失时回退到 `feeAmountMap` 的纯金额展示。
- 完成全链路验证后，再单独评估删除旧字段；本次不做顺手清理。
- 本次不引入 `feeColumnKey`，继续按现有费项名称定位动态列；没有费项编码的场景先展示当前能够取得的费项名称等信息。

### 4.3 BMS 聚合规则

#### 4.3.1 应收账单

在 `ArBillServiceImpl.exportData()` / `buildArFinanceExportRow()` 中：

1. 金额取 `ArBillFeeDetailDTO.amountBillCurrency`。
2. 币种取 `ArBillFeeDetailDTO.billCurrency`。
3. 同一订单、同一费项可以聚合，但参与聚合的明细必须具有相同结算币种。
4. 同一订单、同一费项出现多个结算币种时禁止直接相加，也不允许按币种拆成多个动态列，应按 4.3.3 作为数据或代码异常处理。

#### 4.3.2 返款账单

在 `RefundBillServiceImpl.exportData()` / `buildRefundFinanceExportRow()` 中：

1. 金额取 `RefundBillFeeDetailDTO.amount`。
2. 币种取 `RefundBillFeeDetailDTO.billCurrency`。
3. 本金项与扣减费项均按各自明细的结算币种生成费项单元格。
4. 不使用 `currency`、`snapshotOriginalCurrency` 或 `finCurrency` 代替结算币种。

#### 4.3.3 同一费项多结算币种处理

已确认不按结算币种拆列。一个订单的一种费项只对应一个 Excel 单元格，因此同一聚合单元格只能有一种结算币种：

1. 动态列继续按费项名称生成，不把币种写入字段名，不生成额外币种列。
2. 每个金额单元格独立应用自己的 Excel 显示格式，例如底层数值为 `10.000`，格式附加 `USD`。
3. 聚合前校验同一订单、同一费项的所有明细结算币种一致。
4. 新账单出现多种结算币种时视为代码或数据生成漏洞，导出应明确失败并输出账单号、订单号、费项名称及冲突币种，禁止跨币种相加。
5. 历史账单不做专项数据治理，仅按现有可取得的信息尽力展示。

### 4.4 Excel 单元格格式

新增币种金额写入方法，保持 `setCellValue(double)`：

```java
private static void writeCurrencyAmount(Row row, int columnIndex, BigDecimal value,
                                        String currency, Styles styles) {
    Cell cell = row.createCell(columnIndex);
    cell.setCellStyle(styles.currencyAmount(currency));
    if (value == null) {
        cell.setBlank();
        return;
    }
    cell.setCellValue(value.doubleValue());
}
```

数字格式推荐使用：

```text
#,##0.000 "USD"
```

注意事项：

1. 币种代码必须先校验和转义，只接受规范化后的三位大写字母；不允许把任意业务文本直接拼入格式字符串。
2. 新账单的费项结算币种不允许为空；发现为空时应阻断导出并检查账单生成或导出聚合代码漏洞，不允许静默使用账单头币种兜底。
3. 历史账单不承诺补齐缺失信息，按能够取得的金额、币种和费项信息尽力展示。
4. 空金额单元格保持空白，不应显示 `0.000 USD`。
5. 负数、零值和小数仍保持数值类型。
6. 为避免 POI 单元格样式爆炸，`Styles` 内按币种缓存 `CellStyle`，同一币种复用一个样式。
7. 财务金额显示精确到 3 位小数，统一使用 `#,##0.000`。

建议缓存结构仅作为 Excel Helper 内部实现细节，可使用 `Map<String, CellStyle>`，不作为 Controller、Service 或 Feign 的参数/返回值。

## 5. 调整计划

### 阶段 1：已确认口径固化

1. 不按币种拆列，每个动态费项金额单元格独立设置币种显示格式。
2. 金额显示精确到 3 位小数。
3. 新账单结算币种不允许缺失，缺失时检查代码漏洞。
4. 没有稳定费项编码时先展示现有可取得的费项信息。
5. 返款本金纳入相同单元格格式规则。
6. Microsoft Excel 与 WPS 均纳入验收。
7. 只保证功能上线后生成的新账单，历史账单尽力展示。

交付物：疑问点书面结论、验收样例。

### 阶段 2：BMS 数据模型与聚合调整

1. 新增 `FinanceExportFeeCellDTO`。
2. 应收、返款导出行 DTO 增加 `feeCells`。
3. 两个 Service 从明细的 `billCurrency` 取结算币种。
4. 加入跨币种聚合保护。
5. 保留旧字段兼容，不改接口 URL。

交付物：包含金额与结算币种的结构化导出响应。

### 阶段 3：Platform Admin Excel 格式调整

1. 增加币种金额样式缓存。
2. `费项明细`、`返款明细` 的动态费项循环改用 `writeCurrencyAmount`。
3. 普通重量、单价、汇总金额继续使用原金额样式。
4. 校验生成文件中动态费项单元格的类型为 Numeric。

交付物：满足 PRD 的 `.xlsx` 文件。

### 阶段 4：联调与回归

1. Admin Shell 原入口下载应收、返款报表。
2. 使用 Excel/WPS 打开并检查显示格式。
3. 对动态费项列执行 `SUM`、排序、筛选、透视。
4. 校验三 Sheet、列名、列顺序和往期冲正信息未被破坏。
5. 校验大账单下样式数量不会随行数增长。

## 6. 验收标准

| 场景 | 预期结果 |
| --- | --- |
| USD 金额 10 | 显示 `10.000 USD`，底层为 Numeric |
| EUR 负数 -2.5 | 显示 `-2.500 EUR`，可参与求和 |
| 金额为 0 | 显示 `0.000 USD`，底层为 Numeric |
| 金额为空 | 单元格保持空白，不显示币种 |
| 同币种多明细聚合 | 聚合后金额正确，币种不变 |
| 新账单同订单同费项多币种 | 阻断导出并提示异常，绝不拆列或跨币种求和 |
| 新账单费项结算币种缺失 | 阻断导出并定位账单生成或导出代码漏洞 |
| 非动态金额字段 | 保持当前纯金额格式，不追加币种 |
| 动态列标题 | 只显示费项名称，不追加币种，不新增币种列 |
| Excel 计算 | `SUM`、排序、筛选、透视均正常 |
| 应收/返款 | 两种账单导出均满足相同规则 |

建议自动校验 POI 生成结果：

1. `cell.getCellType()` 为 `NUMERIC`。
2. `cell.getNumericCellValue()` 与 DTO 金额一致。
3. `cell.getCellStyle().getDataFormatString()` 包含对应币种代码。
4. 同一币种的多个单元格复用样式。

## 7. 风险与回滚

1. **跨币种误聚合风险**：当前代码以费项名称为键直接相加，本次若只改 Excel 样式会掩盖更严重的金额口径问题，必须先处理聚合唯一键。
2. **样式数量风险**：逐单元格创建样式会快速触及 Excel 样式上限，必须按币种缓存。
3. **币种格式注入风险**：币种字符串必须限制为受信任的三位大写字母。
4. **兼容风险**：旧 Feign 消费方可能仍读取 `feeAmountMap`，首期保留兼容字段。
5. **精度风险**：POI 最终用 double 写值是当前实现方式；本次不改变金额计算和数据库精度口径。
6. **工作区风险**：相关仓库当前存在未提交修改，实施时必须基于最终合并后的代码复核，避免覆盖他人改动。

回滚只需恢复 Excel Helper 对 `writeAmount` 的调用并停止填充新 DTO 字段；数据库无变更，不涉及数据回滚。

## 9. 结论

本次不是前端页面调整，主改造面是 `bms + platform-admin`：BMS 必须把动态费项的结算币种保留到单元格级，Platform Admin 再用 Excel 自定义数字格式显示币种。Admin Shell 仅做下载回归。

最关键的实现约束有三个：一是单元格必须保持 Numeric；二是不按币种拆列；三是同一订单同一费项的不同结算币种绝不能直接相加，应作为新账单的数据或代码异常处理。可按“DTO 与聚合 → Excel 样式 → Excel/WPS 联调验收”的顺序实施。
