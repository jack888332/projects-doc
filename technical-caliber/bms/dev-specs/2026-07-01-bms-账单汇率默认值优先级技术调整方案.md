# 2026-07-01 BMS 账单汇率默认值优先级技术调整方案

## 1. 文档说明

本文基于 `aidocs` 提交 `1921ec17652c8389b500cbafb99f70f3066d5dd9`，对照当前 BMS 后端、Platform Admin、Admin Shell 和数据库结构，梳理账单汇率默认值优先级变化带来的代码调整范围、实施计划及待确认问题。

本次只输出技术方案，不修改业务代码、前端代码和数据库结构。当前工作区存在未提交的客户级汇率及账单生成调整，本文按“当前工作区实际代码”评估，而不是仅按 Git 已提交基线评估。

## 2. PRD 提交变化摘要

提交同时修改：

1. `product-caliber/bms/prd/财务系统.PRD.md`
2. `product-caliber/bms/prd/derivant/财务系统验收标准.md`

核心变化如下：

1. 账单生成前的默认汇率改为：`客户特调汇率表 > 基准汇率表 > 店铺汇率表`。
2. 店铺汇率不写入基准汇率表，但作为客户特调和基准汇率均不可用时的第三级来源。
3. 百分比缩放、固定汇率差只以基准汇率为基础；基准不可用时该客户特调规则不生效，继续按基准级、店铺级、`1` 的顺序回退，不允许在店铺汇率上叠加客户调整。
4. 三类默认来源均不可用时，异币种汇率固定按 `1` 处理，不阻断账单生成或重算。
5. 账单汇率快照需要记录客户规则、基准汇率、店铺汇率、推导关系、最终汇率及缺失原因。
6. 本期只调整账单费项明细中的汇率默认值来源：`账单级 > 客户特调级 > 基准级 > 店铺级 > 1`；费项级汇率仅保留概念，不开发。
7. 应收账单生成、返款账单生成、账单侧重算均需遵循相同口径。
8. 验收标准 `AC-08-05`、`AC-08-06`、`AC-13-03` 和 `RR-13` 已同步加入店铺汇率与按 `1` 兜底要求。

## 3. 口径拆分

PRD 中存在两层相关但不同的优先级，代码实现时不能混为一条判断链。

### 3.1 默认汇率解析层

用于账单尚未形成锁定汇率时生成默认值：

```text
客户特调汇率
  > 基准汇率
  > 店铺汇率
  > 固定汇率 1
```

其中：

1. 固定客户特调不依赖基准汇率或店铺汇率。
2. 百分比和固定差只以基准汇率为基础；基准不可用时本条客户特调规则不参与本次命中。
3. 客户规则未命中时，直接按基准、店铺、`1` 的顺序获取默认值。

### 3.2 账单费项明细默认值层

用于生成或重算费用明细金额：

```text
同币种直接按 1
  > 账单级汇率配置
  > 客户特调汇率
  > 基准汇率
  > 店铺汇率
  > 固定汇率 1
```

默认汇率解析结果内部再执行 3.1 的顺序。

同币种按 `1` 属于无需查询的直接换算，不应创建无意义的缺失汇率记录。

## 4. 当前代码核对结果

### 4.1 已部分具备的能力

1. `BillGenerateServiceImpl.resolveBillExchangeRate(...)` 已覆盖应收和返款账单生成入口。
2. 当前工作区已初步接入：`账单快照 > 客户特调/基准 > 店铺汇率`。
3. `BmsConstants` 已存在 `CUSTOMER`、`BASE`、`SHOP` 来源常量。
4. 固定客户特调已调整为可在没有基准汇率时独立生效。
5. `ArBillServiceImpl`、`RefundBillServiceImpl` 已具备账单级和客户汇率预览的基础判断结构，但仍保留本期不开发的费项级旧分支。
6. 店铺汇率远程接口和加载逻辑已经存在，无需新增跨服务依赖。
7. `bill_exchange_rate` 已能保存最终汇率、换算方向、来源和人工/系统类型。

### 4.2 必须修改的缺口

| 模块 | 当前情况 | 与新 PRD 的差距 | 调整建议 |
| --- | --- | --- | --- |
| 账单生成 | 店铺汇率缺失时抛出异常 | 要求按 `1` 继续生成 | 返回明确的 `FALLBACK_ONE` 决策并写快照 |
| 应收重算 | 已加载店铺汇率，但解析方法未使用店铺 Map，最终仍抛异常 | 未落实店铺兜底和按 `1` | 统一调用默认汇率解析服务 |
| 返款重算 | 与应收重算存在相同问题 | 未落实店铺兜底和按 `1` | 与应收共用同一解析结果模型 |
| 客户百分比/固定差 | 基准汇率不存在时，客户汇率服务返回空，生成服务继续回退店铺汇率 | 基本符合确认口径，但需要明确记录客户规则未生效原因 | 不在店铺汇率上应用客户调整，按层级继续回退 |
| 基准推导 | 当前仅支持直接货币对和反向倒数 | PRD 允许通过两条 CNY 锚点汇率相除推导外币对外币 | 增加 `CNY_CROSS` 推导 |
| 基准数据范围 | 当前基准汇率实体、请求、查询和唯一键包含 `sc_id/shop_id/user_id` | 已确认基准汇率与供应链等业务对象无关 | 移除业务范围匹配，唯一约束改为全局货币对当前生效唯一 |
| 店铺匹配 | 生成服务当前只匹配店铺直连货币对 | 反向是否可倒数未明确，且无法记录推导关系 | 产品确认后实现直接/反向策略 |
| 快照追溯 | `bill_exchange_rate` 只有 `rate_source` 等通用字段 | 无法完整记录规则ID、基准ID、店铺来源、推导关系和缺失原因 | 扩展快照字段或增加结构化来源快照 |
| 费项级概念 | 重算链路仍识别 `FEE`，生成链路没有统一费项级来源 | 本期明确无需开发 | 不新增费项级能力；旧逻辑是否保留仅做兼容性评估 |
| 前端展示 | 应收、返款页面只翻译 `FEE/BILL/SHOP/DIRECT` 和 `MANUAL/SHOP/SYSTEM` | `CUSTOMER/BASE/FALLBACK_ONE` 会直接显示英文 | 补充中文标签和缺失原因展示 |
| 历史保护 | 已生成账单一般读取账单快照 | 需要确认重算时是否允许重新读取最新默认来源 | 按账单状态和锁定状态明确边界 |

### 4.3 当前模型与 PRD 的既有冲突

以下问题并非本次提交新引入，但会影响验收：

1. PRD 仍描述客户规则的账单类型维度，但已确认本期不需要账单类型，当前删除状态保持不变。
2. 已确认百分比和固定差需要支持“上浮/下浮”，当前模型缺少调整方向字段，必须补充。
3. PRD 要求基准汇率存在待确认、生效、停用和当前生效记录；当前实现更接近启用/停用的单记录模型。
4. PRD 要求缺失汇率按 `1`，此前技术方案和部分代码仍采用缺失即失败。
5. PRD 要求记录来源和推导详情，当前表结构无法完整承载。

这些冲突需要产品确认后再决定是否纳入本轮，避免恢复此前已明确删除的字段。

## 5. 建议技术设计

### 5.1 统一默认汇率解析服务

建议由 `CustomerExchangeRateService` 提供统一的默认汇率解析能力，避免生成、应收重算、返款重算各写一套判断。

建议新增明确 DTO，不使用 `Map`：

```text
DefaultExchangeRateResolveReqDTO
DefaultExchangeRateDecisionDTO
```

请求至少包含：

- `scId/shopId/userId`
- `customerNo/memberCode`
- `sourceCurrency/targetCurrency`

决策至少返回：

- 最终有效汇率
- 命中级别和来源类型
- 客户规则ID、调整方式、调整方向、调整值
- 基准汇率ID和原始方向
- 店铺汇率记录ID或可追溯来源标识
- 推导类型：`DIRECT/REVERSE/CNY_CROSS/NONE`
- 推导表达式或参与推导的货币对
- 是否按 `1` 兜底
- 兜底原因

### 5.2 默认汇率解析算法

```text
1. 同币种 -> 直接返回 1/DIRECT
2. 查询客户规则
3. 固定客户规则 -> 直接返回固定值/CUSTOMER
4. 查直接或反向基准汇率
5. 直接/反向均无结果时，尝试 CNY 交叉推导
6. 命中百分比或固定差客户规则：
   6.1 有基准结果 -> 基于基准计算客户汇率
   6.2 无基准结果 -> 当前客户特调规则不生效，继续执行后续来源回退
7. 未命中客户规则：
   7.1 有基准结果 -> 返回 BASE
   7.2 无基准结果 -> 返回 SHOP
8. 店铺仍无结果 -> 返回 1/FALLBACK_ONE，并记录缺失原因
```

### 5.3 账单费项明细默认汇率算法

账单生成和重算入口统一执行：

```text
1. 同币种 -> 1
2. 有账单级汇率配置 -> BILL
3. 调用默认汇率解析服务 -> CUSTOMER/BASE/SHOP/FALLBACK_ONE
4. 将最终决策固化到 `bill_exchange_rate` 和 `fee_detail` 汇率快照
```

账单快照一旦形成，同一账单后续费用应优先复用该货币对快照，避免同一账单因配置变化出现多个汇率。

### 5.4 快照结构建议

建议评估为 `bill_exchange_rate` 增加：

| 字段 | 用途 |
| --- | --- |
| `hit_level` | `BILL/CUSTOMER/BASE/SHOP/FALLBACK_ONE/DIRECT` |
| `customer_rule_id` | 命中的客户特调规则ID |
| `base_rate_id` | 命中的基准汇率ID |
| `source_rate_value` | 调整或推导前的基础汇率 |
| `adjust_type` | `FIXED/PERCENT/DELTA` |
| `adjust_direction` | `UP/DOWN`；固定汇率使用 `NONE` |
| `adjust_value` | 客户调整值 |
| `derivation_type` | `DIRECT/REVERSE/CNY_CROSS/NONE` |
| `derivation_expression` | 推导表达式或来源货币对摘要 |
| `fallback_reason` | 按 `1` 兜底原因 |

来源追溯必须使用结构化字段，不使用 JSON，确保可按规则、基准汇率、来源类型和推导方式关联查询。

同时需要调整客户特调规则结构：

| 表 | 字段调整 | 说明 |
| --- | --- | --- |
| `customer_exchange_rate_rule` | 新增 `adjust_direction` | `UP/DOWN`；固定汇率可为空或固定为 `NONE` |
| `customer_exchange_rate_rule_log` | 新增 `before_adjust_direction/after_adjust_direction` | 保留修改前后方向 |
| `base_exchange_rate` | 移除 `sc_id/shop_id/user_id` | 基准汇率改为全局基础数据 |
| `base_exchange_rate` | 重建当前生效货币对唯一约束 | 不再按供应链、店铺、用户拆分唯一性 |

基准汇率迁移前必须先检查不同业务范围下是否已经存在重复启用货币对；如存在，不能直接创建全局唯一键，需要先由财务确认保留记录。

数据库调整交付物必须同时包含：

1. `aidocs/technical-caliber/sql/ar_bill.sql` 中变更后的完整最新建表定义。
2. 可直接执行的增量 `ALTER TABLE` SQL。
3. 新字段默认值、历史数据回填或兼容读取策略。
4. 索引调整和查询影响说明。
5. 对账单生成、应收重算、返款重算、账单详情、导出和核销等关联业务的影响清单。

关联代码至少核对：

1. Platform Admin 当前向基准汇率请求强制写入 `scId` 的逻辑。
2. 基准汇率分页、保存、重复校验、匹配和重算客户规则的 Mapper 条件。
3. 客户特调规则保存、编辑、日志和前端调整方向控件。
4. `bill_exchange_rate` 查询、保存、详情、导出和重算 Mapper 映射。
5. 应收、返款账单详情中的命中级别和来源展示。
6. 历史快照没有新增来源字段时的兼容展示和查询逻辑。

涉及表结构调整时，同步更新 `aidocs/technical-caliber/sql/ar_bill.sql` 的完整建表定义。

### 5.5 店铺汇率调用

1. 按 `scId + shopId` 查询启用店铺汇率。
2. 匹配实际账单货币对，不将店铺汇率复制到基准汇率表。
3. 店铺汇率配置是现有功能，本方案不重新定义其维护、方向、异常和可用性规则，只按现有接口结果参与第四级取值。
4. 店铺汇率变更不触发 BMS 任何动作；后续账单生成或重算时再按既定层级读取。

### 5.6 前端调整

应收和返款账单详情的汇率列表需要：

1. 增加 `CUSTOMER`、`BASE`、`FALLBACK_ONE` 的命中级别中文映射。
2. 增加客户特调、基准汇率、按 `1` 兜底的来源中文映射。
3. 按 `1` 兜底不增加高风险警告交互；财务在人工审核账单时负责确认汇率是否正确。
4. 对倒数、CNY 交叉推导提供可查看的来源说明。
5. 不提供修改历史已结清账单来源快照的入口。

客户级汇率配置页本次无需增加店铺汇率维护区；店铺汇率属于独立来源，只在账单默认汇率解析中参与兜底。

## 7. 调整计划

### 阶段一：口径冻结

1. 以第 9 节已确认决策作为实施口径。
2. 固化账单费项明细默认值顺序：`账单级 > 客户特调级 > 基准级 > 店铺级 > 1`。
3. 明确费项级仅预留概念、本期不开发；店铺汇率沿用现有功能规则。

### 阶段二：统一解析模型

1. 新增汇率解析请求和决策 DTO。
2. 将基准汇率解析调整为全局数据，不携带供应链、店铺和用户条件。
3. 实现客户固定、客户调整、基准直接、基准倒数、CNY 交叉、店铺和按 `1` 决策。
4. 为每个分支补充来源和推导信息。

### 阶段三：生成链路接入

1. 应收和返款账单共用生成入口接入统一决策。
2. 落实账单级、客户特调级、基准级、店铺级和按 `1` 的完整优先级。
3. 写入账单汇率与费用明细快照。
4. 验证同账单同货币对只形成一条稳定快照。

### 阶段四：重算链路接入

1. 应收账单重算替换现有分散判断。
2. 返款账单重算替换现有分散判断。
3. 统一店铺兜底和按 `1` 处理。
4. 确保重算不回写客户、基准或店铺配置。

### 阶段五：快照和前端

1. 扩展客户调整方向、规则日志和账单快照字段及 Mapper 映射。
2. 输出增量 ALTER SQL、重复数据检查 SQL、历史兼容策略和完整 SQL 归档。
3. 调整基准汇率全局唯一约束并移除业务范围匹配。
4. 前端补充调整方向、来源、命中级别和推导说明。
5. 保持人工账单级调整优先级不变。

### 阶段六：验证

至少覆盖：

1. 账单级覆盖客户特调级。
2. 固定客户汇率无基准时直接命中。
3. 百分比/固定差按上浮和下浮方向基于基准计算。
4. 百分比/固定差在无基准时不应用客户调整，继续回退店铺汇率。
5. 无客户规则时命中基准。
6. 无客户和基准时命中店铺。
7. 四级均无结果时按 `1` 并记录原因。
8. 基准反向倒数。
9. 外币对外币通过全局 CNY 锚点交叉推导。
10. 同币种固定为 `1` 且不新增配置快照。
11. 应收和返款生成结果一致。
12. 应收和返款重算时已有系统来源快照保持账单级最高优先。
13. 历史已结清账单不被最新配置回写。
14. 账单不会自动审核，必须由财务人工审核确认汇率。

## 8. 风险

1. 按 `1` 静默兜底可能产生重大财务偏差，必须保留来源并支持监控。
2. 生成与重算若不共用解析服务，会出现同一货币对不同结果。
3. CNY 交叉推导存在方向和除法精度风险，必须统一有效汇率语义。
4. 店铺汇率变化频繁，若不及时固化账单快照，同一账单可能出现漂移。
5. 当前工作区已有在途调整，实施前需按文件逐项合并，避免覆盖未提交代码。
6. 新增调整方向和快照追溯字段会影响数据库唯一约束、Mapper、查询、导出和历史数据兼容，实施时必须同步提供 SQL 与关联影响分析。

## 9. 已确认决策

1. 客户特调规则不需要`账单类型`字段，应收和返款账单共用同一客户货币对规则。
2. 百分比和固定差需要支持`上浮/下浮`，必须补充调整方向字段和计算逻辑。
3. 费项级汇率目前仅预留概念，本期不开发。
4. 本期准确口径为：账单费项明细中的汇率默认值来源按`账单级 > 客户特调级 > 基准级 > 店铺级 > 1`取值。
5. 店铺汇率配置是现有功能，本 PRD 和本方案不重新定义其需求。
6. 百分比和固定差在基准不可用时，不允许以店铺汇率为基础继续叠加客户调整；客户特调不生效后继续按层级回退。
7. 按 `1` 兜底不需要财务二次确认。
8. 按 `1` 兜底不需要新增任务监控告警。账单不会自动审核，必须由财务人工审核并确认汇率。
9. 店铺汇率接口异常和匹配规则沿用现有功能口径，不在本方案中重新定义。
10. 基准汇率与供应链、店铺、用户等业务对象无关，是全局基础数据；CNY 推导不增加供应链归属要求。
11. 账单级锁定汇率即账单汇率配置，此配置无法关闭；应清理或禁用现有“关闭后按1”的旧语义和入口。
12. 账单重算时，已有系统来源快照始终作为账单级最高优先，仍按`账单级 > 客户特调级 > 基准级 > 店铺级 > 1`执行。
13. `bill_exchange_rate` 使用新增结构化字段记录来源，不使用 JSON；实施必须输出增量 SQL、完整 DDL 和关联业务影响分析。
14. 店铺汇率变更不触发 BMS 任何动作；后续账单生成或重算时按现有店铺汇率结果参与取值。
15. 按 `1` 兜底不需要额外风险警告样式，财务审核账单时负责确认汇率无误；账单详情仍允许按既有规则维护账单级汇率配置。

## 10. 结论

当前代码只部分满足提交 `1921ec1`：账单生成已经初步接入客户、基准和店铺来源，但按 `1` 兜底、调整方向、全局基准模型、CNY 交叉推导、完整结构化来源快照、生成与重算统一以及前端来源展示仍需调整。

第 9 节口径已经确认，可以按第 7 节分阶段实施；实施前需先完成数据库字段、增量 SQL 和关联业务影响设计评审。

## 11. 实施结果（2026-07-01）

### 11.1 已完成

1. 基准汇率改为全局基础数据，代码移除 `scId/shopId/userId`，数据库唯一约束改为无方向货币对全局唯一。
2. 客户特调规则增加 `adjust_direction`，支持 `UP/DOWN/NONE`，规则日志同步记录调整前后方向。
3. 基准汇率支持直接、反向倒数和 CNY 锚点交叉推导。
4. 固定客户特调不依赖基准；百分比和固定差仅基于基准计算，缺少基准时继续回退店铺级。
5. 应收和返款共用生成入口按`账单级 > 客户特调级 > 基准级 > 店铺级 > 1`生成并固化汇率。
6. 应收和返款重算保留已有账单快照最高优先，并补齐店铺和按 `1` 回退。
7. `bill_exchange_rate` 增加规则ID、基准ID、基础汇率、调整参数、推导类型、推导表达式和兜底原因等结构化字段。
8. 新保存的账单级汇率强制启用，前端移除关闭开关；历史关闭记录仍保留兼容读取逻辑。
9. 前端增加上浮/下浮交互，并补充客户、基准、店铺和按 `1` 来源中文展示。
10. 已输出增量迁移 SQL：`technical-caliber/bms/sql/ddl/2026-07-01_exchange_rate_priority_alter.sql`。
11. 已同步 `technical-caliber/sql/ar_bill.sql` 完整表结构和多币种设计文档。

### 11.2 关联业务影响

1. **账单生成**：异币种缺少所有配置时不再失败，按 `1` 生成并进入财务人工审核。
2. **账单重算**：已有账单快照仍最高优先，不因客户、基准或店铺配置变化自动刷新。
3. **基准维护**：保存基准汇率会重算所有启用的非固定客户规则，以覆盖反向和 CNY 交叉影响。
4. **店铺汇率**：变更不触发 BMS 任何动作，只在后续生成或重算需要且没有更高优先级时读取。
5. **账单详情**：不再允许关闭账单级汇率；仍允许财务修改汇率值和方向。
6. **历史账单**：不回填无法追溯的客户规则ID、基准ID和推导表达式，仅按已有 `rate_source` 补 `hit_level`。
7. **导出与核销**：金额字段和币种桶结构未改变，不需要修改核销算法；导出如需展示新增来源字段，可在后续单独扩展。
