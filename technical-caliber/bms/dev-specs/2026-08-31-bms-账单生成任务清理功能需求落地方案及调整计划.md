## 1. 背景与目标

BMS 任务流水页当前只能查看任务详情、重试失败任务和跳转关联账单，缺少“任务清理”入口。调试、测试或误跑产生的账单生成任务及其账单、费用、来源轨迹和源表打标残留，目前只能由运维手工执行 Python 脚本清理。

本次目标是把 `cleanup_ar_bill_task_v2.py` 的安全清理能力做成项目功能：

1. 在“账单生成任务”“源数据同步任务”两个页签上提供单任务“清理”入口和表格多选“批量清理”入口。
2. 清理一个任务时，连带物理删除该任务产生的账单、费用明细、订单快照、来源归集轨迹、币种汇总、汇率快照、尾程包裹关系快照和导出任务引用。
3. 清理后按来源轨迹恢复源表 `bms_billed_flag`、`bms_bill_no`、`bms_billed_at`，让来源数据可以被重新生成任务再次拉取；无账单但有 `NON_FEE_FETCH` 等来源轨迹的“源数据同步任务”同样恢复。
4. 保留脚本已有的安全检查：任务状态、账单状态、已核销金额、外部费用关联、导出任务、下游核销/返款/调账记录等不满足条件时禁止清理。
5. 保留“共享账单”和“外部费用挂靠”两类高风险场景的拦截，只在用户显式确认后纳入清理。
6. 清理改为“批量提交 + 异步执行 + 进度轮询”模式，避免大任务量场景下 HTTP 同步超时。
7. 清理动作写入 `bms_operation_log`，并展示在现有“账单操作审计”页面。
8. 新增独立按钮权限码 `bill_generate_task_cleanup`。
9. 来源表恢复逻辑改为配置驱动，后续 `fee_source_rule`/`fee_source_dataset` 新增来源表时可自动覆盖，无需改 Java 代码。

## 5. 共享账单与外部费用挂靠说明

原疑问点 5 的表述不够直白，这里用业务场景和界面行为重新解释，便于产品/测试直接判断。

### 5.1 共享账单

核心一句话：**一张账单可能同时被多个“生成任务”写入数据，并不是一张账单只对应一个任务。**

生成代码按“配置 + 账期 + 拆单维度”复用已有账单。比如同一个客户同一个账期，先跑“全量任务 A”生成了应收账单 X，后来又跑“增量任务 B”往同一张 X 补新费用，于是 X 的数据里既有 A 写的部分，也有 B 写的部分。

举例（金额为示意）：

```text
任务 A（先跑） -> 生成应收账单 X，写入费用 a1=60、a2=40
任务 B（增量） -> 复用同一张 X，追加费用 b1=20
账单 X 合计 = 120 元，其中 A 写了 100 元，B 写了 20 元
```

为什么不能只清理其中一个：

1. 只清理任务 B：X 里还剩任务 A 的 100 元，但 B 的 20 元被删了，X 的金额、费用明细和来源记录对不上，变成“半张残单”。
2. 只清理任务 A：同样会破坏 B 和 X。
3. 系统无法猜测哪些费用该留、哪些该删，只能把整张账单连同写入它的任务一起处理。

界面行为：

1. 检测到 X 同时被 A、B 写入时，默认不允许清理，并提示“账单 X 同时属于任务 A、B”。
2. 用户勾选“一并清理相关任务”后，A 和 B 一起进入清理范围，整张 X 连同 A、B 一起删除。
3. 批量清理时如果用户同时选中了 A 和 B，说明两个任务都在本次范围内，不会拦截。

### 5.2 外部费用挂靠

核心一句话：**有些费用不是本次任务生成的，而是“挂靠”在目标账单下的其他费用；删除目标账单后，它们会变成指向不存在账单的孤儿。**

费用明细表 `fee_detail` 上有 `related_bill_id/related_bill_no/related_bill_type` 等 `related_*` 字段，表示这笔费用与某张账单有关联。典型场景是手工补录费用时选择挂到某张账单，或另一张账单的费用关联到目标账单。

举例：

```text
手工费用 M：金额 50 元，related_bill_id = X（挂靠到应收账单 X）
本次清理任务 A：准备删除 X
```

M 不是任务 A 生成的，清理时不会删除 M；但如果直接删掉 X，M 的 `related_bill_id` 仍指向一张不存在的账单，后续查询、导出会出现悬空引用。

界面行为：

1. 默认不允许清理，提示“有 N 条外部费用挂靠到目标账单”。
2. 用户勾选“解除外部费用关联”后，先清空这些费用的 `related_bill_id/related_bill_no` 等 `related_*` 字段（费用本身保留），再删除 X。

### 5.3 两种场景对照

| 场景 | 含义 | 默认行为 | 勾选后行为 |
| --- | --- | --- | --- |
| 共享账单 | 多个生成任务写同一张账单 | 拦截，提示相关任务 | 相关任务一并纳入清理并整单删除 |
| 外部费用挂靠 | 其他费用通过 `related_*` 关联到目标账单 | 拦截，提示挂靠数量 | 清空 `related_*` 字段，费用保留，再删除账单 |

### 5.4 默认策略（已确认）

按第二轮确认第 2 条采用推荐口径：**默认拦截 + 显式勾选 + 输入确认短语“确认清理”**。清理是不可逆的物理删除，勾选动作本身就是用户对高风险范围的显式知情确认。

## 6. 落地方案

### 6.1 总体架构

```text
admin_front billGenerateTask/index.vue
  -> /portal/bms/billGenerateTask/cleanupPreview          （同步只读预览）
  -> /portal/bms/billGenerateTask/cleanupSubmit           （创建批次并提交异步任务，立即返回）
  -> /portal/bms/billGenerateTask/cleanupProgress         （轮询批次进度）
  -> BmsBillGenerateTaskController（platform-admin）
  -> BillGenerateTaskRemoteService（bms client，Feign）
  -> BillGenerateTaskController（bms web）
  -> BillGenerateTaskCleanupService（bms biz）
  -> BillGenerateTaskCleanupMapper（bms dao + XML）
  -> SourceDatasourceConnectionProvider（来源打标恢复，配置驱动）
  -> BillGenerateTaskCleanupBatchMapper（bms dao + XML，批次进度）
  -> BmsOperationLogMapper（操作审计）
  -> AsyncTaskService.submit(AsyncTaskQO)（platform-admin）
  -> BillGenerateTaskCleanupAsyncTask（platform-admin 异步执行器，逐任务调 BMS cleanupExecute）
```

预览是同步只读接口；真正删除走异步批次。异步执行器逐任务调用 BMS 的单任务清理接口，每个任务内部仍按脚本语义做加锁、校验、来源恢复、物理删除和审计；单任务失败不中断整批（已确认），批次最终状态为 `PARTIAL_SUCCESS`。

### 6.2 后端接口

| 方法 | 路径 | 说明 |

### 6.5 清理范围与安全校验

#### 6.5.1 范围加载与批量扩展

主范围：

```text
ar_bill.generate_task_id = taskId
或通过 fee_detail / main_order / bill_source_collect_mark 的 generate_task_id 关联到的 ar_bill
```

批量预览/执行按脚本 `expand_shared_scope` 的语义做闭包扩展：

```text
账单 -> 写入这些账单的其他 generate_task_id -> 相关任务
任务 -> 这些任务写入的其他 bill_id -> 相关账单
```

扩展规则：

1. 选中任务集合内互相共享的账单不触发拦截，直接纳入。
2. 扩展发现选中集合之外的任务时，未勾选 `includeRelatedTasks` 则阻断；勾选后自动纳入本次清理，并在预览中单独列出。
3. 自动纳入的任务必须与所属共享账单的主任务 `bill_type` 一致；跨类型轨迹由“剩余 MARKED 占用”逻辑保护，不允许跨类型整单删除。
4. 所有纳入任务必须与当前 `scId` 一致。

#### 6.5.2 安全校验（逐任务执行时重新校验）

1. 任务存在且 `scId` 一致。
2. 任务状态在允许集合内。
3. 账单状态和核销金额满足条件。
4. 无未结束导出任务；删除部分导出项后按脚本逻辑刷新导出任务计数并作废文件。
5. 无核销、返款、支付回写、调账、支付记录等下游引用。
6. 本任务费用未被派生为其他任务/手工红冲费用。
7. 来源轨迹的 `source_table` 能在来源恢复配置中解析；解析不到则阻断。
8. 存在其他任务写入共享账单时，未勾选 `includeRelatedTasks` 则阻断；勾选后所有相关任务都必须纳入本次清理。
9. 存在手工费用或手工订单快照挂靠目标账单时阻断，脚本不自动删除。
10. 存在外部费用 `related_bill_id` 指向目标账单时，未勾选 `clearExternalLinks` 则阻断；勾选后解除 `related_*` 字段。

### 6.6 来源打标恢复（配置驱动）

脚本中 `KNOWN_SOURCE_TABLES`、`SOURCE_PRIMARY_KEY`、`SOURCE_CLEAR_BILLED_AT` 三个硬编码白名单改为配置读取：

1. 从 `fee_source_dataset`（`main_table`、`source_database`、`datasource_code`、`billed_flag_column`、`bill_no_column`）读取来源表和打标列。
2. 从 `fee_source_rule`（`source_id_column`、`dataset_code`）推导来源表主键列；同一来源表存在多条规则时校验主键列一致，重复规则直接合并。线上 `fee_source_rule` 无 `enabled` 列，查询不依赖该列过滤。
3. 来源表等于数据集 `main_table` 时直接使用规则的 `source_id_column`；来源表是数据集 `join_sql` 中的关联表时，从 `join_sql` 的 `ON` 条件推导关联表外键列（如 `sale_order_header_extend` 推导为 `sale_order_id`），支持 `db`.`table`、`db.table`、`` `table` ``、`table` 四种 JOIN 写法。
4. `bill_source_collect_mark.source_database` 为空时取数据集配置的 `source_database`。
5. 运行时构建“来源表恢复元数据缓存/查询”，预览和执行共用。
6. 组合 SQL 前对表名、列名做 `^[A-Za-z0-9_]+$` 白名单校验，防止配置注入；数据源编码通过 `SourceDatasourceConnectionProvider` 映射到 `OFP_DB/CXMS_DB/LFC_DB`。

恢复动作与脚本一致：

1. 同一 `(source_database, source_table, source_id)` 仍存在其他任务/账单类型的 `MARKED` 轨迹时：不恢复未打标，把源表 `bms_bill_no` 刷新为剩余轨迹中最近一条的 `bill_no`。
2. 无任何剩余 `MARKED` 轨迹时：`bms_billed_flag = 0, bms_bill_no = NULL`；对 `CLEANUP_SOURCE_TABLES_CLEAR_BILLED_AT` 白名单内的来源表（当前为 `claim_order`，与脚本 `SOURCE_CLEAR_BILLED_AT` 一致）同时清空 `bms_billed_at`。白名单后续新增来源表时同步维护常量，不通过 BMS 数据源查询 `information_schema`。
3. 按第二轮确认，恢复未打标时默认清理源数据打标字段，不依赖配置开关。

这样后续 `fee_source_rule`/`fee_source_dataset` 新增来源表时，只需配置数据，Java 代码零改动即可自动覆盖。

### 6.7 事务与跨库一致性

确认结论：有跨库访问权限，但可能没有跨库事务。方案不依赖单连接跨库事务，采用“两阶段提交顺序 + 补偿校验”：

1. 单任务执行使用 `@Transactional(rollbackFor = Exception.class)` 管理 BMS 事务。
2. 先通过 `SourceDatasourceConnectionProvider` 打开来源连接，`autoCommit = false` 执行来源打标恢复/刷新。
3. BMS 事务内完成导出任务清理、外部费用关联解除、各表物理删除、轨迹删除、账单删除、任务删除。
4. 提交顺序：先提交 BMS 事务，再提交来源连接；任一步失败则回滚另一侧。
5. 提交后校验来源表最终标记状态（对齐脚本 `remaining_flag` 校验）；校验失败记录审计与告警，提示按清理计划人工核对。
6. 若 BMS 提交失败，来源连接回滚，业务数据原样保留。
7. 若来源提交失败而 BMS 已提交，通过“补偿重跑来源恢复”接口幂等重放（同一来源恢复动作可重复执行），并写入失败日志。
8. 执行前先 `SELECT bill_generate_task ... FOR UPDATE`，再对目标 `ar_bill` 行 `FOR UPDATE`，执行时重新加载范围并重跑校验，避免预览后状态变化。

该方案不引入新的连接配置，复用 `SourceDatasourceConnectionProvider`，与生成链路现有的来源连接方式一致。

## 9. 风险与回滚

| 风险 | 控制措施 |
| --- | --- |
| 跨库一致性 | 不依赖跨库事务；来源连接先恢复、BMS 事务先提交、来源后提交；失败走补偿重放与人工核对 |
| 误删共享账单 | 默认拦截，必须显式勾选并输入确认短语 |
| 误删已核销/已结清账单 | 后端校验核销金额、状态和下游引用，不依赖前端 |
| 清理耗时过长 | 批量异步执行，前端轮询进度；批次上限防止一次提交过多 |
| 异步任务中断 | 批次明细表持久化进度；单任务清理幂等（任务已删则跳过），可重新提交批次 |
| 新增表/字段评审 | 仅新增两张批次执行表，独立于业务表，可单独回滚；`fee_source_dataset` 不新增字段 |
| 审计查询性能 | `bms_operation_log` 已有 `idx_operation_biz`；按 `scId` 过滤时走 JSON 提取，数据量大可后续评估加隔离列 |

回滚策略：清理功能为增量接口和前端按钮，可独立下线；不改变任务生成、重试、导出等现有链路。批次表保留执行记录，不影响业务表。

## 11. 结论

清理功能可以完全复用 `cleanup_ar_bill_task_v2.py` 的范围和校验规则，代码上新增一套 BMS 清理服务 + Mapper/XML + 批次进度表 + 门户接口 + 平台异步执行器 + 前端多选清理与进度弹窗即可落地。按已确认口径：任务与账单物理删除、支持批量、源数据同步任务恢复打标、新增按钮权限码、审计页展示清理日志、来源表配置驱动自动覆盖、异步任务方式执行。首版建议采用“批量预览确认 + 异步逐任务清理 + 两阶段跨库一致性 + 默认拦截高风险场景”的实现路径，并在上线前用开发库做脚本与接口的对照验证。
