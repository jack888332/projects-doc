# 2026-08-28 BMS 返款账单生成资格校验与回款事实去重调整方案

## 0. 实施状态

2026-08-28 已按本方案完成代码调整：

- `isRefundOrderEligibleForBill` 将 `dest_country_surcharge_amount` NULL 归一为 0 参与公式校验，仅保留 `cod_price`、`collection_price` 缺字段拦截。
- `executeRefundTaskInternal` 新增有效回款事实去重：按 `sale_order_id + warehouse_code + tail_way_bill_no` 归一化，回款汇率冲突校验、触发包裹、回款汇率快照、汇兑损益统一消费去重后事实。
- `buildRefundDeductions` 仍消费原始包裹费行，包级 `receivable_collection_amount` 手续费采集范围不变。
- `hasConflictingRefundReceiptRate` 仅统计 `recovery_money > 0` 的有效行。
- `bms` 的 `dao`、`biz` 模块已通过 Maven `test-compile` 编译验证。

本方案不修改数据库表结构，不迁移历史数据。

## 1. 背景与目标

配置 17（`RCB-OG0863-Scheme-20260828083011903-v1`，成员 `461856`，客户 `OG0863`，`refund_mode=RECEIVED`）在两个账期的候选订单均满足返款条件，但任务未生成任何返款账单。

根因有两处：

1. `ofp_ofdb1.sale_order_header.dest_country_surcharge_amount` 在多数订单为 NULL，`BillGenerateServiceImpl.isRefundOrderEligibleForBill` 把 NULL 当作“缺少到付附加费总额”，直接拦截全部候选订单。
2. `sale_order_package_fee` 对同一尾程单同时存在 type=1、type=2 两行，且两行的 `payment_collect` 不同；`queryRefundPackageFeeRows` 自 2026-08-20 起不再限定 type，`hasConflictingRefundReceiptRate` 因此把 179 的全部候选订单判定为“多个不同回款汇率”。

目标：

- 到付附加费为 NULL 时按 0 参与资格校验和金额链路，不再拦截。
- 同一订单、仓库、尾程单号只保留一条有效回款事实，解决回款汇率冲突和回款汇率快照重复插入问题。
- 不改变包级代收货款手续费等扣减费项的采集范围。
- 不引入表结构变更，不做历史数据迁移。

## 2. 问题定位与数据事实

### 2.1 候选订单与 NULL 到付附加费

按任务 SQL 复算：

- 179 应有 14 个匹配订单：`21870610, 21870618, 22271267, 22271279, 22389425, 22467901, 22533160, 22648968, 22716542, 22895555, 22895574, 22963564, 22963567, 22963579`。
- 180 应有 8 个匹配订单：`23026778, 23131381, 23131384, 23131386, 23131426, 23196922, 23196924, 23196925`。

生产库核对结果：

- 22 个订单中 20 个 `dest_country_surcharge_amount IS NULL`，且 `cod_price = collection_price`。
- 2 个订单有到付附加费：`22271267` 为 205、`22533160` 为 276，均满足 `cod_price - dest_country_surcharge_amount = collection_price`。

结论：NULL 在业务上等价于 0，不应作为缺字段拦截。

### 2.2 双行回款事实

22 个订单在 `sale_order_package_fee` 共 80 行。同一订单、仓库、尾程单号下通常存在 type=1（应收）、type=2（成本）两行：

- 179 的 14 个订单，同一个有效尾程单上 type=1、type=2 的 `recovery_money` 都大于 0，且 `payment_collect` 不同，例如订单 `21870610` 的尾程 `JC10121516-3`：type=1 为 607.21，type=2 为 611.62。
- 180 的 8 个订单，只有 type=2 行 `recovery_money > 0`，type=1 行为 0。

结论：type=1/type=2 是同一尾程单的并行费用行，不是两笔独立回款；按订单、仓库、尾程单号去重后，22 个订单每个只剩 1 个有效包裹和 1 个 `payment_collect`，回款汇率冲突可消除。

## 3. 口径调整

### 3.1 到付附加费 NULL 视为 0

`dest_country_surcharge_amount IS NULL` 时按 0 参与以下口径：

```text
cod_price - COALESCE(dest_country_surcharge_amount, 0) = collection_price
```

仍然保留差异拦截：`cod_price` 或 `collection_price` 缺失、或公式结果不一致时，订单不进入返款账单。

### 3.2 有效回款事实去重

有效回款事实定义：`recovery_money > 0`。

按以下键去重：

```text
sale_order_id + warehouse_code + tail_way_bill_no
```

同一键内存在多条 `recovery_money > 0` 时，按优先级保留一条：

1. `recovery_money` 等于订单 `collection_price` 的行；
2. 仍并列时，保留带 `receivable_collection_amount > 0` 的行（应收侧手续费行）；
3. 仍并列时，保留 `p_id` 最小的行。

当前数据下该规则的效果：

- 179 的 14 个订单均保留 type=1 行，`recovery_money` 与应付返款本金一致，且保留包级代收货款手续费。
- 180 的 8 个订单仅 type=2 行有正回款，因此保留 type=2 行。

## 4. 推荐落地方案

### 4.1 到付附加费 NULL 按 0 校验

调整 `BillGenerateServiceImpl.isRefundOrderEligibleForBill`：

```java
BigDecimal codAmount = decimalValue(read(orderRow, "h_cod_price"));
BigDecimal additionalFeeAmount = defaultAmount(decimalValue(read(orderRow, "h_dest_country_surcharge_amount")));
BigDecimal payableAmount = decimalValue(read(orderRow, "h_collection_price"));
if (codAmount == null || payableAmount == null) {
    orderRow.put("h_refund_block_reason", "缺少到付金额或应付返款本金");
    return false;
}
if (scale4(codAmount.subtract(additionalFeeAmount)).compareTo(scale4(payableAmount)) != 0) {
    orderRow.put("h_refund_block_reason", "到付金额-到付附加费总额与应付返款不一致");
    return false;
}
```

说明：

- 只把到付附加费 NULL 归一为 0，`cod_price`、`collection_price` 仍保留缺字段拦截。
- 后续 `prepareRefundAmountChain` 已对 `h_refund_additional_fee_amount` 使用 `defaultAmount`，无需再改。
- 阻断原因文案同步去掉“缺少到付附加费总额”。

### 4.2 有效回款事实去重

在 `executeRefundTaskInternal` 中新增“有效回款事实”归一化步骤：

1. 保留原始 `packageFeeRowsByOrderId`，供 `isRefundCandidateOrder` 和 `buildRefundDeductions` 使用，包级手续费采集不变。
2. 新增 `deduplicateRefundReceiptFacts`，按 3.2 规则生成去重后的有效回款事实列表，并重新按订单分组为 `effectiveReceiptRowsByOrderId`。
3. `isRefundOrderEligibleForBill` 的回款汇率冲突校验改用去重后的有效回款事实。
4. 生成循环内：
   - `buildRefundDeductions` 继续使用原始 `packageRows`；
   - `annotateRefundTriggerPackage`、`persistRefundReceiptRateSnapshots`、`persistRefundExchangeProfit` 改用 `effectiveReceiptRowsByOrderId` 对应的列表。
5. `hasConflictingRefundReceiptRate` 增加 `recovery_money > 0` 过滤，避免无回款但 `payment_collect > 0` 的脏行参与冲突判断。

涉及代码位置：

| 方法 | 现有位置 | 调整 |
| --- | --- | --- |
| `executeRefundTaskInternal` | `BillGenerateServiceImpl.java:2211` | 增加去重步骤，拆分原始包费行和有效回款事实 |
| `isRefundOrderEligibleForBill` | `BillGenerateServiceImpl.java:3681` | NULL 按 0；冲突校验改喂去重后事实 |
| `hasConflictingRefundReceiptRate` | `BillGenerateServiceImpl.java:3724` | 仅统计 `recovery_money > 0` 的有效行 |

| `persistRefundReceiptRateSnapshots` | `BillGenerateServiceImpl.java:3917` | 改喂去重后事实 |
| `buildRefundDeductions` / `filterPackageFeeRows` | `BillGenerateServiceImpl.java:2825` / `3179` | 不变，仍消费原始包费行 |

### 4.3 不做的调整

- 不改 `sale_order_package_fee` 表结构、不改源 SQL 的 type 限定。
- 不做历史账单重算。
- 不清理已有 `refund_receipt_rate_snapshot` 数据。
- 不新增数据库字段。

## 5. 影响分析

### 5.1 任务结果

在币种规则、收款账户、TWD->CNY 汇率等其余校验均通过的前提下：

- 179 预期 matched=14；
- 180 预期 matched=8。

### 5.2 金额与汇率

- 到付附加费 NULL 订单以 `additional_fee_amount = 0` 进入金额链路，汇总、详情、导出均显示 0。
- 179 回款汇率采用 type=1 的 `payment_collect`（例如 607.21）；若后续确认 type=2/成本侧为权威口径，179 的 `refund_receipt_rate_snapshot` 和汇兑损益会切换为另一组值。
- 180 回款汇率采用 type=2 的 `payment_collect`。

### 5.3 快照与扣减

- `refund_receipt_rate_snapshot` 唯一键为 `(bill_no, tail_way_bill_no)`，去重后每个尾程单只插入一条，避免 duplicate key。
- 包级代收货款手续费仍按 `receivable_collection_amount` 从原始 type=1 行采集，179 的 `6.18/6.20/7.21/13.39` 等手续费不丢失。
- 180 的 type=1/type=2 均无正手续费，本次无扣减变化。

### 5.4 回归风险

- 修改仅影响返款账单生成路径，历史已生成账单不重算。
- 同一订单存在多个不同尾程单且 `payment_collect` 不同时，仍按业务口径拦截，不做“取一个”兜底。
