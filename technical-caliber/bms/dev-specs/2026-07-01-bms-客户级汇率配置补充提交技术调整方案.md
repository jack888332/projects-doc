### 2.3 新命中顺序

账单汇率决策应统一为：

1. 同币种：固定为 `1`，不要求维护配置。
2. 费项级已锁定汇率。
3. 当前账单已存在的账单级锁定汇率或人工汇率。
4. 同客户、同账单类型、同货币对的启用特调规则。
5. 同客户、通用账单类型、同货币对的启用特调规则。
6. 当前生效基准汇率直接命中。
7. 同一 CNY 锚点货币对反向倒数推导。
8. 两条 CNY 锚点汇率相除，推导外币 A 到外币 B。
9. 以上均不可用时返回汇率 `1`，命中级别记为缺汇率兜底，并固化未命中原因。

固定汇率客户规则不依赖基准汇率；百分比和固定差值规则先按第 6～8 步获得基准汇率，再执行上浮或下浮。若基础汇率仍不可得，则最终按 `1` 兜底，不得抛异常阻断账单。

## 4. 技术调整方案

### 4.1 统一模型与常量

在 `common` 中补充并复用明确常量或枚举，禁止在 Service、XML 和前端散落魔法值：

- 财务本位币：`CNY`
- 账单类型：`MEMBER_AR`、`COD_REFUND`、`ALL`
- 调整方式：`PERCENT`、`DELTA`、`FIXED`
- 调整方向：`UP`、`DOWN`；固定汇率可为空
- 基准汇率确认状态：`PENDING`、`EFFECTIVE`、`DISABLED`
- 获取方式：`MANUAL_IMPORT`、`MANUAL_ADD`、`MANUAL_UPDATE`；`SYSTEM_FETCH` 仅预留
- 命中级别：`FEE_DETAIL`、`BILL`、`CUSTOMER_FIXED`、`CUSTOMER_ADJUST`、`BASE_DIRECT`、`BASE_REVERSE`、`BASE_CNY_CROSS`、`DIRECT`、`FALLBACK_ONE`

不建议继续用 `conversion_direction=MUL/DIV` 表达货币对本身的方向。`source_currency -> target_currency` 已经明确方向，`exchange_rate` 直接表示 1 单位源币兑换多少目标币；倒数与相除应由解析器完成。若必须兼容现有字段，应先规范其唯一语义，避免币种方向和 MUL/DIV 两套方向信息互相矛盾。

### 4.2 数据库调整

#### 4.2.1 `base_exchange_rate`

建议至少包含：

- 数据隔离：`sc_id`、`shop_id`、`user_id`
- 货币对：`source_currency`、`target_currency`
- 汇率：`exchange_rate DECIMAL(18,8)`
- 来源：`rate_source`、`acquire_type`、`source_time`
- 状态：`confirm_status`、`is_current_effective`
- 审计：确认人/时间、停用人/时间、操作原因、创建/更新字段、逻辑删除

约束：

1. `source_currency <> target_currency`。
2. `source_currency = 'CNY' XOR target_currency = 'CNY'`。
3. 同一数据隔离范围、同一有向货币对只能有一条“当前生效”记录，但可以保留多条待确认、停用或历史记录。
4. 修改建议按“原记录停用/取消当前生效 + 新记录确认”保留轨迹；若产品坚持原地修改，也必须写完整操作日志。

#### 4.2.2 `customer_exchange_rate_rule`

在现有字段上新增或调整：

- `bill_type`：应收、返款或通用
- `adjust_direction`：上浮/下浮
- `source_currency`、`target_currency`：允许任意不同币种，不再限定 CNY
- `base_exchange_rate`、`customer_exchange_rate`：可作为当前预览缓存，但不能代替账单快照
- `operation_reason`：最近操作原因

启用唯一约束应覆盖数据隔离、客户唯一标识、账单类型和有向货币对。由于客户目前同时存在 `customer_no`、`member_code`，落库前必须先确定唯一主键口径，不能仅靠两个可空字段拼接产生模糊匹配。

#### 4.2.3 操作日志

日志需覆盖基准汇率和客户规则的导入、添加、修改、移除、确认、启用、停用，至少保存业务主键、操作类型、操作原因、操作人、操作时间、变更前 JSON 和变更后 JSON。日志属于内部审计，不进入客户对账导出。

#### 4.2.4 `bill_exchange_rate` 快照扩展

建议增加：

- `base_rate_id`、`customer_rate_rule_id`
- `base_exchange_rate`
- `adjust_type`、`adjust_direction`、`adjust_value`
- `default_exchange_rate`
- `derive_type`：直接、倒数、CNY 交叉、无配置按 1
- `derive_expression`：例如 `USD/CNY ÷ TWD/CNY`
- `derive_source_rate_ids`：参与推导的基准汇率 ID，可使用明确长度的字符串或独立子表
- `fallback_reason`

历史账单始终读取该快照；任何基准汇率或客户规则变更都不得批量更新历史快照。

所有最终 DDL 需在实施时同步更新 `aidocs/technical-caliber/sql/ar_bill.sql` 中对应表的完整最新结构，不能只追加零散 ALTER。

### 4.3 汇率解析服务

在 `CustomerExchangeRateService` 内收敛一个内部批量解析能力，避免应收、返款各自复制规则：

```java
CustomerExchangeRateDecision resolveDefaultRate(CustomerExchangeRateResolveReqDTO reqDTO);
```

决策对象应明确返回最终汇率、命中级别、账单类型、客户规则、基准记录、调整参数、推导类型、推导表达式和兜底原因，不使用 `Map`。

基准解析算法：

1. 对币种代码大写、去空格；相同币种直接返回 1。
2. 查当前生效的 `source -> target`，直接返回。
3. 查当前生效的 `target -> source`，返回倒数；除数必须大于 0。
4. 若两端均非 CNY，分别解析 `source -> CNY` 和 `target -> CNY` 的等价汇率，再计算 `sourceToCny / targetToCny`。
5. 禁止递归到任意第三方币种，跨币种推导只能经过 CNY，避免环路和不可解释路径。
6. 全部失败时返回 1 和结构化 `FALLBACK_ONE` 决策，不抛缺汇率异常。
7. 汇率统一保留 8 位小数、`HALF_UP`；账单金额仍按既有金额精度处理。

客户规则计算：

- 上浮百分比：`baseRate * (1 + value / 100)`
- 下浮百分比：`baseRate * (1 - value / 100)`
- 上浮固定差：`baseRate + value`
- 下浮固定差：`baseRate - value`
- 固定汇率：`value`

调整值必须非负，最终汇率必须大于 0。固定汇率不要求基准记录；百分比和固定差缺少基础汇率时按 1 兜底，并在决策中明确“规则已命中但基础汇率不可得”，不能伪装成正常客户特调结果。

### 4.4 应收与返款账单接入

调整 `ArBillServiceImpl`、`RefundBillServiceImpl`：

1. 调用统一解析服务时传入明确 `billType`。
2. 保留费项级和当前账单锁定汇率优先级。
3. 客户/基准汇率命中后统一调用 `persistDefaultRateSnapshotIfNeeded` 固化决策，不再沿用 `persistShopRateSnapshotIfNeeded` 命名。
4. 缺汇率时写入汇率 1 的账单快照和原因，继续账单生成或重算。
5. 删除无效的 `loadShopRateMap` 调用和店铺汇率直接兜底分支；若其它页面仍需要店铺建议汇率，只保留展示职责。
6. 同一账单内相同有向货币对只解析和持久化一次，批量加载客户规则及 CNY 锚点基准汇率，避免按每条费项查询数据库。
7. 已有账单快照优先，保证配置修改不改变历史账单；只有状态允许的显式账单侧重算才更新当前账单快照。

## 6. 风险与控制

1. **按 1 兜底存在财务金额风险**：必须可检索、可告警、可导出内部核对清单，但不得混入客户对账字段。
2. **方向双重表达风险**：币种对方向与 `MUL/DIV` 并存容易造成二次倒数，应统一语义。
3. **当前生效并发风险**：确认新记录时需在同一事务中锁定同货币对记录，先取消旧当前生效再确认新记录，并用数据库唯一约束兜底。
4. **逐费项查询风险**：账单可能包含大量明细，必须按客户、账单类型和货币对批量预取。
5. **历史污染风险**：配置表中的预计算结果不能被账单运行时动态读取后覆盖已有快照。
6. **在途代码冲突风险**：当前多个仓库均有未提交改动，开发前应先确认这些改动的归属和合并基线，禁止覆盖或回退用户已有工作。

## 7. 待确认疑问点

### 7.1 产品口径

1. 基准汇率“修改、移除”是否允许原地覆盖/逻辑删除，还是必须生成新记录并保留旧记录？PRD 同时要求可修改移除和保留操作轨迹，建议采用新记录或完整前后值日志。
2. 同一货币对“多个来源或多条记录”中，是否允许多条生效但仅一条当前生效，还是其余必须进入停用状态？
3. 缺汇率按 1 后，账单是否仍允许直接进入待审核，还是必须显示强提示并由财务确认？建议至少增加可筛选风险标记。
4. 百分比下浮是否限制最大值小于 100？固定差下浮只要最终汇率大于 0 是否即可？
5. 客户规则“编辑后影响仍允许账单侧重算的账单”是指仅在财务主动点击重算时读取新规则，还是配置保存后自动触发草稿账单重算？本文按“仅主动重算、不自动触发”设计。
6. 基准汇率手工导入的模板字段、允许币种集合、重复行处理和部分成功策略尚未明确。

### 7.2 数据与技术口径

1. 客户唯一标识最终使用 `customer_no`、`member_code` 还是独立客户 ID？当前两个字段均存在且可空，无法形成可靠唯一约束。
2. `sc_id/shop_id/user_id` 在基准汇率中是全局、供应链级还是店铺级？PRD 表述为财务统一基准，当前 DDL 又允许店铺/用户隔离，需要明确查找优先级。
3. `source_currency -> target_currency` 的汇率是否统一定义为“1 单位源币 = N 单位目标币”？若确认，应废弃或仅兼容读取 `conversion_direction`。
4. `bill_exchange_rate` 的推导来源 ID 是用 JSON/字符串保存，还是增加子表保存两条 CNY 锚点记录？考虑查询和审计，建议结构化字段或子表。
5. 按 1 兜底是否需要写入账单任务监控告警表；当前仅写快照可能不足以主动提醒财务。
6. 账单类型代码应复用现有 `bill_type` 哪组值，需要与应收、返款现有常量核对后落库，避免新造 `MEMBER_AR/COD_REFUND` 与现有值不一致。
7. 当前基准汇率精度使用 `DECIMAL(18,8)`，PRD 未定义最终精度；需确认是否满足小币种和交叉汇率场景。
8. Admin Shell 路由权限码 `bms_customer_exchange_rate` 是否已在菜单权限系统登记，需由菜单管理侧确认。

## 8. 完成标准

1. 指定提交中的全部新口径均有对应数据结构、接口、Service 规则、页面交互和验收用例。
2. 应收与返款使用同一套汇率解析算法，且账单类型专属规则优先于通用规则。
3. 基准汇率支持 CNY 在任意一端，并可通过倒数或 CNY 双锚点推导外币对外币。
4. 所有汇率缺失场景不再阻断账单，而是按 1 固化完整原因并可被内部检索。
5. 店铺汇率不再作为账单生成直接兜底。
6. 配置变更不自动重跑或回写历史账单。
7. DDL、实体、Mapper、DTO、快照字段和 `ar_bill.sql` 结构归档一致。
8. 不使用 `Map` 作为 Controller/Service 参数或返回值；写操作事务、字段注释、Controller 注释和数据隔离符合项目规范。
