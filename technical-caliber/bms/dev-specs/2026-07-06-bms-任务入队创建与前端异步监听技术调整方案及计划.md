## 2. 本次提交内容整理

提交标题为“BMS任务创建于进入轮候执行队列那一刻，而非开始执行那一刻”。提交实际包含两组需求。

### 2.1 主需求：任务入队即创建

1. BMS 任务在进入轮候队列时创建，而不是执行器真正开始处理时创建。
2. 任务创建后立即进入 `PENDING`（待执行）状态。
3. 创建任务时立即固化账单配置、分支范围、费项规则、币种模板和费项结算币种规则等快照，禁止延迟到执行阶段固化。
4. 执行器后续领取任务时，才将状态从 `PENDING` 切换为 `RUNNING`。
5. 同客户、同账期、同配置组存在 `PENDING`、`RUNNING` 或 `NEED_RETRY` 活动任务时，不允许重复创建。
6. 定时生成和财务手工生成都只负责创建任务并入队；任务执行完成后才形成账单结果。

### 2.2 前端需求：任务创建后异步监听

1. 创建接口成功后，前端应基于返回的任务标识异步监听任务状态。
2. 任务流水列表和详情需持续刷新：任务状态、执行耗时、错误摘要、错误详情和关联账单结果。
3. 列表、详情中的“开始时间”统一改名为“任务创建时间”，展示任务创建并进入轮候的时间。
4. “执行耗时”从执行器真正领取并开始执行时起计，不统计排队时间；`PENDING` 阶段保持“待执行”，执行耗时展示 `-`。
5. 页面在任务成功后应能进入关联账单；失败或待重试时按权限进入重试或补偿链路。

### 2.3 同提交附带需求：对账报表金额统一三位小数

1. 客户对账报表所有金额字段均按 3 位小数展示并保留 Excel 数值精度。
2. 范围覆盖 Sheet 1 结算币种分桶汇总、Sheet 2 固定金额字段与动态费项金额列、Sheet 3 往期账单冲正金额。
3. 动态费项金额单元格示例由 `10.00 USD` 调整为 `10.000 USD`。
4. 只调整导出展示和单元格数值精度，不改变系统内部 `DECIMAL(18,4)`、汇率换算、账单金额和核销计算精度。

该附带需求已经由同目录文档 `2026-07-06-bms-对账报表费项金额单元格币种格式技术调整方案与计划.md` 分析。实施时应将该文档从“仅动态费项币种格式”扩展为“全部导出金额三位小数”的统一口径，不在本方案中重复设计两套导出实现。

### 3.2 后端任务创建链路

主要代码：

- `bms/biz/.../BillGenerateServiceImpl.java`
- `bms/dao/.../BillGenerateMapper.java`
- `bms/biz/.../BillGenerateTaskMonitorServiceImpl.java`
- `bms/biz/.../BillGeneratePlanJob.java`
- `bms/biz/.../BillGenerateTaskExecuteJob.java`

当前实际链路：

```text
手工生成 / 定时计划 / 失败重试
  -> BillGenerateService.generate()
  -> createTask() / createRefundTask()
  -> 校验活动任务
  -> 固化任务快照与来源 SQL 快照
  -> INSERT 或重置 bill_generate_task，状态 PENDING
  -> 返回 BillGenerateRespDTO.taskId

BillGenerateTaskExecuteJob
  -> executePendingTasks()
  -> executeTask(taskId)
  -> claimTask：PENDING/NEED_RETRY -> RUNNING
  -> 生成账单
  -> SUCCESS / FAILED / NEED_RETRY
```

这说明提交标题要求的核心后端模型已经存在，不需要重新设计任务表或再新增一套队列。调整重点应是统一所有触发入口和时间字段语义。

### 3.3 仍需处理的后端差异

#### 3.3.1 时间字段语义不一致

表 `bill_generate_task` 同时存在：

- `created_at`：任务记录创建时间，即进入轮候的时间。
- `started_at`：现有命名通常表示被执行器领取并真正开始执行的时间。
- `finished_at`：执行结束时间。
- `duration_ms`：当前持久化执行耗时。

`BillGenerateTaskMonitorServiceImpl.normalizeTaskTime()` 当前在 `startedAt == null` 时临时回填 `createdAt`。这虽然让 `PENDING` 任务能显示时间，却把“入队时间”和“执行开始时间”合并为同一个 DTO 字段，且数据库值、接口值、字段名的含义不一致。

确认保留真实时点，不覆盖原始含义：

| 字段 | 建议语义 | 数据来源 |
| --- | --- | --- |
| `queuedAt` | 任务创建并进入轮候时间 | `created_at` |
| `executionStartedAt` | 执行器领取并开始执行时间 | `started_at` |
| `finishedAt` | 任务终态时间 | `finished_at` |
| `durationMs` | 真正执行耗时 | `finished_at/当前时间 - started_at` |

对现有前端兼容可采用两阶段方案：

1. `BillGenerateTaskDTO` 新增 `queuedAt`、`executionStartedAt`，保留 `startedAt` 一个版本并标记兼容字段。
2. 页面列名由“开始时间”改为“任务创建时间”，展示 `queuedAt`；本次不新增“执行开始时间”列。
3. 删除 `normalizeTaskTime()` 对 `startedAt` 的语义覆盖，改为显式组装 `queuedAt`。
4. 不修改底层金额、账单或核销时间逻辑。

4. `PENDING` 阶段不计算排队耗时，页面执行耗时展示 `-`；进入 `RUNNING` 后才按 `started_at` 起算执行耗时。

#### 3.3.2 个别入口仍同步领取执行

现有 `generate()` 已只创建任务，但以下调用需逐一核实并统一：

1. `generateCurrentPeriodForEnabledConfigs()` 仍是 `enqueueCurrentPeriodForEnabledConfigs()` 后立即 `executePendingTasks()`。
2. `regenerate()` 创建重跑任务后会直接调用 `executeTask()`。
3. 旧版 `admin_shell/src/views/billing/setting/` 下仍存在 `/portal/rerunBilling/generateBilling` 老链路，和新 BMS `/portal/bms/billConfig/generateBill` 并存。

调整原则：新 BMS 交互入口一律只返回已创建的 `taskId`，实际执行统一由 `BillGenerateTaskExecuteJob` 领取；`regenerate()` 本次明确改为异步。`generateCurrentPeriodForEnabledConfigs()` 存在外部同步兼容调用方，必须保留原有“创建后立即消费”的兼容语义；定时计划仍走 `enqueueCurrentPeriodForEnabledConfigs()`。旧 `/portal/rerunBilling/generateBilling` 是生产入口，必须保留并做兼容回归。

#### 3.3.3 快照时点已正确，但需补回归验证

`createTask()` 当前已经在插入任务前查询并固化：

- 账单配置快照；
- 配置范围快照；
- 费项规则快照；
- 选中币种模板及费项结算币种规则；
- 主订单和附加费来源 SQL 快照。

本次不建议重写该逻辑，只需增加验证：任务创建后、领取前修改最新配置，不应影响该任务的历史快照和执行口径。

#### 3.3.4 Mapper 历史实现与当前规范的关系

`BillGenerateMapper` 当前大量使用 `@SelectProvider/@InsertProvider` 和 `Map<String, Object>` 组装任务参数，与现行“SQL 优先放 XML、Controller/Service 不用 Map 参数返回值”的开发规范不一致。

本次需求不应顺手做全 Mapper 重构，否则风险和改动量远超任务入队语义调整。若本次确需新增查询，新增部分应使用显式 DTO 和 XML；历史 Provider 迁移另立技术债任务。

### 3.4 前端现状与差异

#### 3.4.1 任务流水页

文件：`admin_shell/src/views/billing/billGenerateTask/index.vue`。

已有能力：

- 展示 `PENDING/RUNNING/SUCCESS/FAILED/NEED_RETRY/CANCELED`；
- 列表、统计、详情和重试接口已接入；
- 列表可展示 `startedAt`、`durationMs`、错误摘要和关联账单；
- 详情可展示错误信息、快照和来源 SQL。

缺口：

- `mounted()` 只调用一次 `queryTasks()`；
- 没有 `setInterval`、递归 `setTimeout` 或统一轮询控制器；
- 详情弹窗打开后不会刷新；
- `RUNNING/PENDING/NEED_RETRY` 的耗时不会随时间变化；
- 页面切换、组件销毁时无轮询生命周期管理；
- 同一次请求较慢时没有防重入控制。

#### 3.4.2 账单配置页手工生成

文件：`admin_shell/src/views/billing/billConfig/index.vue`。

当前 `generateBill()`：

1. 调用 `/portal/bms/billConfig/generateBill`；
2. 忽略响应中的 `taskId`；
3. 提示“账单生成任务已执行”；
4. 关闭弹窗，不进入任务追踪。

应调整为：

1. 接收并保存 `taskId`；
2. 提示“任务已创建，正在排队执行”；
3. 不自动跳转任务流水页，在当前页展示通知卡片并基于 `taskId` 监听；
4. 通知卡片提供可选“查看任务”入口，用户主动点击时才进入任务流水页；
5. 任务成功后在卡片中提供关联账单入口，失败后展示错误摘要；
6. 不等待账单同步生成后才关闭配置弹窗。

## 4. 技术调整方案

### 4.1 方案原则

1. 复用现有 `bill_generate_task` 和执行 Job，不新增消息队列。
2. 创建接口只负责落任务和快照，返回 `taskId`、任务编号和初始状态。
3. 执行器只领取 `PENDING/NEED_RETRY`，使用原子状态更新避免重复执行。
4. 显式区分入队时间与真正执行开始时间。
5. 前端通知卡片采用可停止、可退避、无请求重叠的轮询，不做无限高频刷新；`NEED_RETRY` 不自动轮询。
6. 页面隐藏、组件销毁、任务进入终态时立即停止无用轮询。
7. 导出三位小数只改变导出 DTO/Excel 单元格，不改变内部金额精度。

### 4.2 后端接口与 DTO 调整

#### 4.2.1 创建响应

复用 `BillGenerateRespDTO`，至少确保创建成功时返回：

| 字段 | 说明 |
| --- | --- |
| `taskId` | 后续状态查询主键 |
| `taskNo` | 便于用户识别和任务页定位 |
| `taskStatus` | 固定初始值 `PENDING` |
| `queuedAt` | 创建并进入轮候的时间 |
| `message` | “任务已创建，正在排队执行” |

若现有 DTO 缺少字段，应直接增加显式字段，不使用 `Map` 扩展返回值。

#### 4.2.2 单任务状态接口

现有详情接口：

```text
GET /portal/bms/billGenerateTask/detail?id={taskId}&taskCategory={category}
```

它会返回大体积 JSON 快照和 SQL，不适合 2～5 秒高频轮询。建议在 BMS Client/Controller 增加轻量接口：

```text
GET /api/bms/bill-generate-task/status?id={taskId}
```

返回显式 `BillGenerateTaskStatusRespDTO`：

- `taskId/taskNo/taskStatus`；
- `queuedAt/executionStartedAt/finishedAt`；
- `durationMs`，仅表示真正执行耗时；
- `errorSummary`；
- `billNo/billStatus` 或 `billNos`；
- `updatedAt`。

Admin 代理层按现有 `/portal/bms/billGenerateTask/status` 风格透传。详情接口只在用户打开详情或任务进入失败终态时调用。

#### 4.2.3 时间计算

推荐服务端返回稳定业务值，前端只做秒级显示：

```text
PENDING:
  queuedAt = created_at
  executionStartedAt = null
  durationMs = null，前端展示“-”

RUNNING:
  queuedAt = created_at
  executionStartedAt = started_at
  durationMs = now - started_at

SUCCESS/FAILED/NEED_RETRY/CANCELED:
  durationMs = finished_at - started_at
```

避免把 `updated_at` 无条件当结束时间，因为任务中间统计更新也可能改变它。历史数据缺少 `finished_at` 时才使用兼容兜底，并在代码注释中明确。

### 4.3 后端入口统一

| 入口 | 目标行为 |
| --- | --- |
| 手工生成 | 创建 `PENDING`，立即返回任务信息 |
| 定时计划 | 批量创建 `PENDING`，不在计划 Job 内执行业务生成 |
| 执行 Job | 扫描并原子领取任务，切换 `RUNNING` |
| 失败重试 | 创建或重置为 `PENDING`，由执行 Job 领取 |
| 账单重跑 | 完成重跑准备后创建 `REGENERATE` 任务，不同步调用 `executeTask()`，本次明确改为异步 |
| 配置变更/财务调整 | 若触发生成，统一走创建任务接口 |
| `generateCurrentPeriodForEnabledConfigs()` | 保留同步兼容语义；新增链路不得继续依赖该兼容方法 |
| 旧 `/portal/rerunBilling/generateBilling` | 生产入口继续保留，回归既有调用和返回结构 |

所有写操作保留或补充 `@Transactional(rollbackFor = Exception.class)`。金额生成仍使用现有程序化事务与失败状态独立落库策略，不因本次异步化削弱失败可追溯性。

### 4.4 前端轮询设计

#### 4.4.1 任务流水页轮询

在 `billGenerateTask/index.vue` 中增加页面级轮询控制：

1. 当前标签为“任务流水”，且当前页含 `PENDING/RUNNING` 时启动轮询；`NEED_RETRY` 不触发自动轮询。
2. 默认 5 秒刷新一次列表和统计；连续多次无变化可退避到 10 秒。
3. 请求尚未完成时不发起下一次请求。
4. `document.hidden` 时暂停；重新可见后立即刷新一次。
5. 切换到配置监控时改为刷新监控接口，不并行刷新两个标签。
6. `beforeDestroy()` 清除 timer 和事件监听。
7. 任务全部进入终态后停止自动轮询，保留手工刷新。

Vue 2 可使用递归 `setTimeout`，比固定 `setInterval` 更容易避免请求重叠。

#### 4.4.2 详情弹窗轮询

1. 打开 `PENDING/RUNNING` 任务详情时，只轮询轻量状态接口；进入 `NEED_RETRY` 后立即停止。
2. 状态或 `updatedAt` 变化时再刷新完整详情。
3. 进入终态或关闭弹窗时停止。
4. 失败终态刷新完整错误信息；成功终态刷新关联账单。
5. 页面列表与详情共用同一轮询调度，避免对同一任务重复请求。

#### 4.4.3 手工生成后的交互

确认采用“当前页通知卡片追踪”模式：

```text
生成成功
  -> 提示“任务已创建，正在排队执行”
  -> 关闭生成弹窗，在当前页展示任务通知卡片
  -> 通知卡片按 taskId 轮询轻量状态接口
  -> SUCCESS 后展示“账单”入口
  -> FAILED/NEED_RETRY 后停止轮询，展示错误摘要和重试入口
  -> 用户点击“查看任务”时才进入任务流水页
```

通知卡片应为非阻塞组件，生成弹窗关闭后仍可查看；底层状态查询和状态格式化逻辑应复用，避免配置页和任务页形成两套状态口径。

#### 4.4.4 前端 API 归属

新增状态查询定义继续放在 `admin_shell/src/api/billing.js`，组件通过项目现有 `@/utils/request` 调用，不直接使用 axios，不硬编码独立服务地址。

### 4.5 并发与幂等

1. 创建前的活动任务查询只能改善提示，最终并发安全仍应依赖唯一约束或原子写入。
2. 当前 `uk_task_period` 包含 `trigger_type`，不同触发方式可能创建同配置同账期的两条记录；当前业务级活动任务查询必须覆盖不同触发方式。
3. 对唯一键冲突应转换为明确的“已有活动任务”业务异常，不将数据库异常直接返回前端。
4. `claimTask()` 必须保持条件更新：仅 `PENDING/NEED_RETRY` 可切换为 `RUNNING`。
5. 前端重复点击生成时，按钮 loading 只能防单页面重复点击，后端幂等仍是最终保障。

### 4.6 导出三位小数的衔接方案

该项按导出专项方案实施，但需补充以下统一规则：

1. 在 `BmsFinanceExportConstants` 增加导出金额精度 `3`、舍入方式 `HALF_UP` 和基础 Excel 数字格式 `0.000`。
2. `ArBillServiceImpl.exportData()` 与 `RefundBillServiceImpl.exportData()` 输出到导出 DTO 的所有金额统一 `setScale(3, HALF_UP)`。
3. 动态费项保留 `BigDecimal` 数值类型，单元格显示格式使用 `0.000 XXX`，不能拼成字符串。
4. Sheet 1、Sheet 2、Sheet 3 使用同一格式策略，不只修改动态费项列。
5. 内部账单、汇率、核销、数据库字段继续保持既有 4 位或 8 位精度。

## 7. 验收标准

### 7.1 后端

1. 创建接口事务提交后即可在 `bill_generate_task` 查询到 `PENDING` 任务。
2. 创建响应包含可用于跟踪的 `taskId`，推荐同时包含 `taskNo/taskStatus/queuedAt`。
3. 执行器领取前 `started_at` 为空且执行耗时展示 `-`；领取成功后写真实执行开始时间并转 `RUNNING`。
4. 任务创建后修改配置，任务详情中的快照和实际执行口径不变。
5. 同客户同账期活动任务不会因并发请求重复创建。
6. 重试、重跑等确认范围内的入口不在 HTTP 请求线程同步生成账单。
7. 轻量状态接口不返回快照 JSON 和 SQL 大字段。

### 7.2 前端

1. 创建成功提示为“任务已创建/已提交”，不得提示“账单已生成”或“任务已执行”。
2. 通知卡片及任务页对 `PENDING/RUNNING` 自动刷新，进入 `NEED_RETRY` 后停止自动轮询。
3. 列表“开始时间”改名为“任务创建时间”，展示 `created_at/queuedAt`。
4. 运行中耗时自动变化，任务结束后固定。
5. 成功后无需手工刷新即可出现关联账单入口。
6. 失败后自动显示错误摘要，详情可查看完整错误。
7. 页面离开、隐藏或任务全部终态后不继续无效轮询。
8. 任一时刻同一轮询源最多一个在途请求。

### 7.3 导出

1. 三个 Sheet 的全部金额显示 3 位小数。
2. 动态费项显示类似 `10.000 USD`，实际单元格仍为数值。
3. Excel 中 `SUM`、筛选和透视可正常使用。
4. 系统内部金额、汇率和核销计算精度不因导出改动而变化。

## 8. 已确认口径

### 8.1 任务与前端交互

1. 执行耗时从任务真正开始执行时起计，不统计排队耗时；排队阶段状态保持“待执行”。
2. 页面“开始时间”改名为“任务创建时间”，展示入队创建时点。
3. 手工生成后不自动跳转，留在当前页通过通知卡片监听；只提供用户主动点击的“查看任务”入口。
4. `regenerate()` 改为纯异步，创建重跑任务后不再同步调用 `executeTask()`。
5. `generateCurrentPeriodForEnabledConfigs()` 存在外部依赖，必须保持同步兼容语义。
6. 旧 `/portal/rerunBilling/generateBilling` 是生产入口，必须保留并做兼容回归。
7. `NEED_RETRY` 不自动轮询，进入该状态后停止并展示处理入口。
8. 本次不新增任务详情 SQL、快照的独立权限控制。

### 8.2 对账报表导出

1. “所有金额字段”包括固定列中的实收、未收、冲正、货款、手续费、汇总金额及动态费项金额。
2. 3 位小数统一使用 `HALF_UP`。
3. 先按系统内部 4 位精度计算和汇总，最后在导出边界舍入到 3 位。
4. Sheet 汇总金额不要求与三位小数明细逐行相加绝对一致，不做尾差分摊；验收允许总误差不超过 `0.1` 元。

## 9. 风险与回滚

| 风险 | 控制措施 |
| --- | --- |
| 轮询导致接口压力上升 | 轻量状态接口、5 秒起步、无活动任务停止、页面隐藏暂停、禁止请求重叠 |
| 时间字段语义改变影响旧页面 | 新增显式字段，旧 `startedAt` 保留过渡，不直接改数据库字段含义 |
| 重跑异步化后旧页面误判成功 | 创建响应统一为任务已提交，终态由任务页展示 |
| 多入口并存造成行为不一致 | 新入口异步化，同时为同步兼容方法和旧生产入口建立回归样例 |
| 并发创建重复任务 | 业务活动任务校验 + 数据库唯一约束 + 冲突转业务提示 |
| 导出舍入造成汇总尾差 | 先按内部精度汇总后在导出边界舍入，验收总误差不超过 0.1 元 |

回滚策略：前端轮询和新状态接口均为增量能力，可独立关闭；后端保留执行 Job 和现有任务表，不涉及核心账单数据迁移。若重跑纯异步化出现兼容问题，可临时回滚该入口调用方式，但不得回滚任务快照和状态记录。

## 10. 最终建议

本次不需要重建后端任务框架。现有代码已经具备“创建 `PENDING` 任务、固化快照、执行器领取”的主体能力，最小且正确的实施路径是：

1. 统一所有新 BMS 触发入口为只入队；
2. 显式拆分入队时间和执行开始时间；
3. 增加轻量状态接口，执行耗时仅从 `RUNNING` 开始计算；
4. 让账单配置页使用返回的 `taskId`，在当前页由通知卡片监听，用户主动操作时再进入任务流水页；
5. 将提交附带的“三位小数”合并进现有导出专项方案，避免重复改动同一导出链路。
