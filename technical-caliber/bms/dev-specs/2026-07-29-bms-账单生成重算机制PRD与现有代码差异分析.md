### 2.1 账单生成/重算章节结构调整

新章节将账单处理拆分为七个步骤：

1. 判断什么情况下创建任务。
2. 确定本次任务使用的配置和规则快照。
3. 筛选并锁定可处理的来源数据。
4. 将费用同步至 `BMS费项池`。
5. 首次生成、起草期追加或账单重算。
6. 保存结果并更新账单状态。
7. 账单形成后发生差异时，按状态选择处理路径。

### 2.2 术语调整

提交后统一采用以下术语：

| 原表述 | 新表述 | 产品含义 |
| --- | --- | --- |
| 增量归集 | 起草期追加 | 只向起草中账单追加尚未进入账单的新费项，并重新汇总当前账单。 |
| 账单侧重算 | 账单重算 | 基于当前账单快照、已有有效费项和本次明确补入的费项，重新计算允许修改的范围。 |
| 环节一至环节七 | 第一步至第七步 | 业务语义基本不变，主要改善阅读顺序。 |

### 2.3 语义有所加强的内容

虽然本次提交大部分属于结构和表达优化，但以下口径变得更明确：

1. 成本费项必须按成本账单规则单独归集，不参与应收和返款分流。
2. 起草期追加与账单重算是两种不同处理方式。
3. 重算不重新拉取并按最新规则解释全部来源数据。
4. 失败或待重试任务重新发起时应创建新任务，并保留原任务记录。
5. 已结清账单不得重新打开或直接重算覆盖，但可以按权限形成反核销、退款或反向资金轨迹。
6. 单号追溯只服务于成本业务，不适用于应收和返款账单的费项归集与账单生成。

## 3. 当前代码主链路

### 3.1 账单任务创建

当前手工生成入口为：

```text
admin_front
    -> platform-admin
    -> BillGenerateRemoteService
    -> BillGenerateController
    -> BillGenerateServiceImpl.generate
    -> BillGenerateServiceImpl.createTask
```

`BillGenerateServiceImpl#createTask` 当前执行：

1. 根据账单类型分流应收或返款任务。
2. 读取账单配置、账期和当前费项规则。
3. 查询同客户、同账期活动任务，防止重复创建。
4. 保存账单配置、分支范围、费项规则和来源 SQL 快照。
5. 新建任务，或将历史已结束任务重置为增量任务。
6. 立即返回 `PENDING` 状态，由后台任务异步执行。

主要代码位置：

- `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/BillGenerateServiceImpl.java:141`
- `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/BillGenerateServiceImpl.java:154`
- `bms/biz/src/main/java/com/szt/supplychain/bms/biz/service/impl/BillGenerateServiceImpl.java:1974`

### 3.2 任务执行

任务执行流程为：

```text
BillGenerateTaskExecuteJob
    -> BillGenerateServiceImpl.executePendingTasks
    -> BillGenerateServiceImpl.executeTask
    -> 原子抢占任务
    -> 解析任务快照
    -> 拉取主订单及附加费
    -> 生成或追加账单、订单和费项
    -> 刷新币种汇总和账单金额
    -> 更新任务状态
```

当前代码已经区分：

- 全量拉取：`FULL`
- 增量拉取：`INCREMENTAL`
- 应收账单：`MEMBER_AR`
- 返款账单：`COD_REFUND`

### 3.3 账单后续修正入口

当前代码存在多种名称相近、实际行为不同的入口：

| 入口 | 当前行为 |
| --- | --- |
| 整单重新跑 `regenerate` | 删除旧费项和汇总、撤销来源打标、归档旧账单，再按原账期创建新任务。 |
| 汇率轻量重算 `exchange-rate/recalculate` | 重算费项结算币种金额、财务本位币金额和币种汇总。 |
| 订单重新生成 `regenerate-order` | 对订单增加“重新生成”备注并刷新账单汇总，未重新拉取和重新构造订单全部费项。 |
| 订单重整 `adjustment/rebuild` | 生成重整调账记录，标记订单重整，并刷新目标账单金额。 |
| 调账 `adjustment` | 写入调账记录后直接调整账单金额。 |

这些入口不能统一等同于 PRD 定义的“账单重算”。

## 5. 主要差异清单

### 5.1 高优先级差异

| 编号 | PRD要求 | 当前代码 | 差异结论 |
| --- | --- | --- | --- |
| G-01 | 源数据同步任务每日可独立执行，只负责将费用写入费项池，不必生成账单。 | 当前 `SOURCE_SYNC` 通过任务是否生成 `ar_bill` 反向分类；没有独立的源数据同步任务实体和执行链路。 | 未真正实现独立源数据同步。 |
| G-02 | 费用先进入独立的 `BMS费项池`，再由应收、返款或成本账单归集。 | 当前生成过程直接插入已经绑定 `bill_id`、`bill_no` 的 `fee_detail`。 | 费项池与账单明细边界不清。 |
| G-03 | 来源数据应经过 `null -> locked -> synced` 状态，锁定期间禁止其它任务重复采集。 | 当前上游使用 `bms_billed_flag`，BMS使用 `PENDING/MARKED/FAILED`归集标记；读取候选来源前没有明确的来源行抢占状态。 | 来源状态机与PRD不一致。 |
| G-04 | 账单重算只读取账单快照、已关联有效费项和本次明确补入的费项，不重新解释全部来源。 | 当前整单“重新跑”会撤销来源打标、删除旧费项和汇总、归档旧账单，再重新扫描来源。 | 整单重跑不等于PRD账单重算。 |
| G-05 | 财务补录、调账、冲正必须先形成费项池记录，再影响账单。 | 当前 `adjustment()` 写调账记录后直接调用 `applyAdjustment` 修改账单金额。 | 存在绕过费项池直接修改账单汇总的路径。 |
| G-06 | 失败或待重试任务重新发起时创建新任务，并使用原任务快照。 | 当前 `retry()` 复制配置ID和账期，再由 `createTask()` 重新读取当前配置和费项规则。 | 重试执行口径可能因配置变化而漂移。 |
| G-07 | `NEED_RETRY` 任务人工处理后可以重新发起。 | 未找到将任务状态写成 `NEED_RETRY` 的业务路径；活动任务防重又将 `NEED_RETRY` 视为未结束任务。 | 待重试状态当前难以形成完整闭环。 |
| G-08 | 已结清账单可以按权限反核销，原账单和原资金流水继续保留。 | 应收账单 `reversePayment()` 明确禁止 `PAID` 状态反核销。 | 与PRD已结清反核销口径冲突。 |
| G-09 | 成本中心统一处理成本单号类型、标准化、唯一命中、多目标、范围型单号和关系快照。 | 当前 `bms` 仅发现 `COST_AP` 账单类型常量，未发现完整成本账单、成本池、供应商账单导入和统一单号追溯实现。 | 成本单号追溯需求基本未落地。 |

## 6. 关键差异详细说明

### 6.1 “源数据同步任务”当前只是展示分类

PRD中的源数据同步任务具有独立业务含义：

1. 每日可以单独执行。
2. 到达归集时点后，将新费用写入费项池。
3. 同步成功不代表立即生成账单。
4. 按客户、来源数据集和同步窗口防重。

当前 `BillGenerateTaskMonitorServiceImpl#detail` 通过以下方式判断任务分类：

```text
任务生成了 ar_bill -> BILL_GENERATE
任务没有生成 ar_bill -> SOURCE_SYNC
```

`BillGenerateTaskMonitorMapper#whereTask` 也通过 `EXISTS/NOT EXISTS ar_bill` 过滤两个标签。

因此，当前页面上的“源数据同步任务”更接近“没有生成账单的账单生成任务”，与PRD定义的独立同步任务不同。

### 6.2 费项池与账单明细没有完全解耦

PRD要求：

```text
来源记录
    -> BMS费项池
    -> 应收/返款/成本分流
    -> 账单明细
```

当前主要实现为：

```text
来源记录
    -> 生成账单
    -> 直接插入带 bill_id、bill_no 的 fee_detail
    -> 刷新账单汇总
```

现有 `fee_detail` 同时承担来源费用快照、账单明细和部分费项池职责。这能够支撑当前账单展示和去重，但难以完整满足：

- 一笔费项先入池、后决定账单归属。
- 应收和返款对同一费项进行互斥分流。
- 成本费项使用独立索引和归属规则。
- 调账、冲正先进入费项池再影响账单。
- 后续账单承接原账期差异。

### 6.3 “重新跑账单”与“账单重算”边界不同

当前前端明确提示：

> 重新跑账单会作废原账单、回滚源单打标并重新生成新账单。

当前后端整单重新跑会：

1. 撤销来源 `bms_billed_flag`。
2. 删除旧 `fee_detail`。
3. 删除币种汇总和账单汇率。
4. 清理订单与账单关联。
5. 将归集标记改为 `REGENERATED`。
6. 将旧账单归档并逻辑删除。
7. 按原账期创建新的生成任务。

PRD定义的账单重算则要求：

1. 原账单仍是处理对象。
2. 只处理当前账单允许修改的范围。
3. 使用账单快照和已有有效费项。
4. 不重新按最新规则解释全部来源。
5. 不覆盖已审核、已核销、已回款或已返款记录。

因此后续设计和验收时必须保留两个概念：

- **整单重跑：** 当前实现的作废旧账单并重新生成。
- **账单重算：** PRD定义的账单内范围重算。

不应仅通过接口名称或页面文案将两者视为同一能力。

### 6.4 待重试任务存在闭环问题

当前任务状态枚举和页面支持 `NEED_RETRY`，但代码核查发现：

1. 任务执行异常后主要写入 `FAILED`。
2. 未找到将任务业务状态主动写为 `NEED_RETRY` 的路径。
3. `retry()` 允许 `FAILED` 和 `NEED_RETRY`。
4. 创建新任务前的活动任务查询将 `NEED_RETRY` 视为活动任务。
5. 因此从 `NEED_RETRY` 发起新任务时，可能被“同客户同账期已有活动任务”拦截。
6. 即使能够创建新任务，也会重新读取当前配置，而不是直接复用原任务快照。

这与PRD“人工处理后按原快照重新发起新任务”的口径不一致。

### 6.5 已结清反核销口径冲突

PRD允许已结清账单按权限执行反核销，但要求：

- 不删除原核销流水。
- 新增反向轨迹。
- 原账单历史费项、汇率和审核状态不被静默刷新。
- 是否继续保持已结清或形成新的差异承接，应有明确业务轨迹。

当前反核销代码虽然保留原核销流水并更新其状态，但在账单为 `PAID` 时直接拒绝反核销。因此当前只能对尚未完全结清的账单反核销。

### 6.6 成本单号追溯本次只完成文档迁移

本次提交将单号追溯从财务系统附录迁移到成本中心附录，并明确：

## 8. 风险判断

### 8.1 来源数据重复采集风险

当前来源数据在查询阶段没有明确的 `locked` 抢占状态。两个任务如果在来源打标前同时读到相同记录，仍可能发生并发竞争。

现有任务防重和 `fee_detail` 去重键可以降低重复生成概率，但不能完全替代来源行锁定状态。

### 8.2 重试口径漂移风险

失败任务重新发起时读取最新配置，可能出现：

- 原任务失败前后的费项规则不同。
- 币种模板或客户汇率配置不同。
- 默认方案和分支范围不同。
- 相同账期重试产生不同金额。

这会降低任务失败重放的可解释性。

### 8.3 整单重跑历史追溯风险

整单重跑会删除旧费项明细和汇总，再归档旧账单。虽然旧任务、来源归集标记和归档账单仍可提供部分轨迹，但原账单完整明细是否可直接恢复和对比，需要依赖额外审计数据。

### 8.4 调账绕过费项池风险

直接修改账单汇总会导致：

- 调账金额与费项池明细难以一一对应。
- 币种桶和订单级归属可能不完整。
- 后续重算难以只依据有效费项重建结果。
- 应收与返款分流无法统一处理调账记录。

### 8.5 产品术语混用风险

当前系统同时使用：

- 增量
- 追加
- 重跑
- 重算
- 重新生成订单
- 重整

如果没有统一业务定义，开发、测试和财务可能将不同操作视为同一种处理，造成状态边界和验收预期不一致。

## 9. 差异优先级建议

本文不直接形成开发计划，但从业务闭环和数据一致性角度，建议后续按以下顺序确认：

### 第一优先级：统一业务概念

1. 明确“整单重跑”和“账单重算”是否同时保留。
2. 明确 `fee_detail` 是费项池、账单明细，还是同时承担两者。
3. 明确源数据同步任务是否必须建设为独立任务。
4. 明确已结清账单反核销后的状态口径。

### 第二优先级：任务闭环

1. 补齐 `NEED_RETRY` 产生规则。
2. 解决待重试任务重新发起被活动任务防重拦截的问题。
3. 重试必须复用原任务快照，或明确记录使用新配置的原因。
4. 补齐待执行取消和页面重试入口。
5. 增加结构化失败阶段和处理建议。

### 第三优先级：数据归集闭环

1. 建立独立源数据同步和来源行锁定状态。
2. 确定费项池与账单明细的分层。
3. 调账、冲正和补录统一先形成费项池记录。
4. 建立后续账单承接原账期差异的关联模型。

### 第四优先级：成本中心建设

1. 建设统一单号追溯接口。
2. 建设候选目标、唯一命中和范围型单号判定。
3. 建设供应商单号关系和历史快照。
4. 建设成本池、直接成本和间接成本归属链路。

## 11. 最终结论

提交 `03c8aa670a0d017136f492f1e4641b8c10218b35` 本身不是代码需求增量提交，主要目的是优化“账单生成/重算机制”的阅读结构和业务表达。

但按照提交后的最新口径，当前实现仍存在四类核心差异：

1. **任务模型差异：** 源数据同步任务没有独立实现，待重试和取消流程未闭环。
2. **数据分层差异：** 费项池与账单明细未完全解耦，调账仍可直接影响账单汇总。
3. **操作语义差异：** 当前整单重新跑、汇率重算、订单重整和PRD账单重算是不同能力，尚未形成统一范围重算模型。
4. **成本能力差异：** 单号追溯需求虽然迁移并强化到成本中心，但现有BMS代码尚未形成完整实现。

当前已经具备异步任务、配置快照、增量附加费、汇率轻量重算、任务监控和基础状态流转能力，可以作为后续建设基础；但不能据此判定最新PRD中的账单生成、源数据同步、账单重算和成本单号追溯已经全部落地。
