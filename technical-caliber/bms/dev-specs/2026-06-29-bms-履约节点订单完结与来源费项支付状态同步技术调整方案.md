# 2026-06-29 BMS 履约节点“订单完结”与来源费项支付状态同步技术调整方案

## 1. 文档目的

本文基于 aidocs 提交 9553e80073330525e282e777655b0fe095d4dfec（“应收账单配置中的【履约节点】选项用【订单完结】取代【签收】”），结合当前 bms、admin-front、admin_shell 代码和 BMS SQL 归档，整理已确认的技术调整方案和实施计划。

该提交实际包含两组需求：

1. 应收账单履约节点由【出库、签收】调整为【出库、订单完结】，不再支持【核重】或【签收】。
2. 应收账单和返款账单核销完毕、进入【已结清】后，将账单关联的来源费项支付状态同步为【已支付】，但不回写金额、币种、汇率和历史账单结果。

## 2. PRD 变更整理

### 2.1 履约节点

1. 应收账单配置只允许【出库】和【订单完结】。
2. 主订单归集口径由“出库/签收/回款”改为“出库/订单完结/回款”。
3. PRD 给出的新编码为 ORDER_COMPLETED；时间表达式由数据集配置维护。
4. SIGN 不再作为新应收账单配置选项。
5. 返款账单的“签收返款”模式不属于本次删除范围，不能随应收履约节点误删。

### 2.2 已结清后的支付状态同步

1. 触发点是账单核销完毕并进入已结清。
2. 来源费项范围保持现有实现，只同步 `sale_order_additional_matter` 和 `claim_order`。
3. 应收账单和返款账单都要支持。
4. 只更新支付状态。
5. 来源状态在整单已结清后同步；已结清状态不支持反核销，不执行来源状态回退。

## 3. 现有代码盘点

### 3.1 履约节点：尚未实现新口径

后端现状：

1. bms/model/.../ContractNodeEnum.java 仍为 WEIGHT_OUTBOUND/出库、SIGN/签收。
2. bms/client/.../ContractNodeEnum.java 仍返回相同两项。
3. BillConfigServiceImpl.options() 直接遍历枚举，因此 options API 仍向前端下发【签收】。
4. BillConfigServiceImpl.buildBillConfig() 未校验传入节点是否属于允许集合；即使前端隐藏 SIGN，旧客户端仍可提交。
5. BillGenerateServiceImpl 仍以 SIGN/SIGNED 选择 signed_time：
   - resolveCommonOrderTimeField() 读取 order.time.field.sign；
   - selectPropertyByContractNode() 识别 SIGN/SIGNED；
   - defaultOrderTimeFieldByContractNode() 将其默认到 signed_time；
   - normalizeOrderTimeField() 没有明确的订单完结时间字段。
6. bms/disconf/download/bill_generate_conf.properties 仍配置 order.time.field.sign=signed_time。
7. fee_source_dataset 仍使用 sign_time_column 和 SIGN 支持节点，没有独立的订单完结时间列。

结论：这不是页面文案替换。SIGN 已进入配置保存、数据集、Disconf 和账单生成 SQL 选择链路，必须成套调整。

前端现状：

1. admin-front 的结算设置下拉来自后端 options，但两处说明仍写“出库或签收”。
2. admin_shell 的 SettlementSettingPanel.vue 本地写死 WEIGHT_OUTBOUND/出库、SIGN/签收；当前即使后端返回新项，也会重置为本地旧项。
3. admin_shell 的 billConfig/index.vue 仍将 SIGN/SIGNED 显示为【签收】。
4. admin_shell 的费项数据集页面仍围绕 signTimeColumn 和 SIGN 展示。

### 3.2 支付状态同步：应收已有局部实现，返款尚未接入

应收现有能力：

1. ArBillServiceImpl 在某一币种汇总全额核销时调用 writebackSourcePaymentAfterCurrencyPaid()。
2. ArBillMapper.selectSourceWritebackCandidates() 当前限定：
   - bill_type = MEMBER_AR；
   - 按 bill_no + bill_currency 查询；
   - 只支持 sale_order_additional_matter、claim_order。
3. 当前回写转换：
   - sale_order_additional_matter.fee_pay_status：waiting_pay -> paid；
   - claim_order.payment_status：1 -> 3。
4. source_payment_writeback 已保存回写记录并有幂等写入基础，可继续复用。
5. 当前反核销会直接将来源状态改回 waiting_pay 或 1。

返款现状：

1. RefundBillServiceImpl 会把账单更新为 SETTLED。
2. 目前没有与应收等价的来源支付状态同步调用。

差异汇总：

| 对比项 | 当前实现 | PRD 新口径 |
| :--- | :--- | :--- |
| 触发点 | 单币种全额核销 | 整张账单进入已结清 |
| 账单类型 | 仅应收 MEMBER_AR | 应收 + 返款 |
| 来源范围 | 仅两张来源表 | 保持现有两张来源表不变 |
| 反核销 | 直接回退来源状态 | 已结清不支持反核销，不回退来源状态 |
| 一致性 | 核销事务中直接更新来源库 | 账单先结清，来源同步失败只记录日志和操作轨迹 |

## 4. 技术调整方案

### 4.1 履约节点方案

#### 4.1.1 编码与历史兼容

使用新编码 ORDER_COMPLETED，不把旧 SIGN 偷换语义为“订单完结”。

原因：

1. PRD 已明确写出 ORDER_COMPLETED。
2. 签收与订单完结不是同一业务事件，复用 SIGN 会污染历史配置和任务快照。
3. 返款账单仍有 SIGNED 签收返款模式，必须与应收节点分开。

兼容策略：

1. 新建和编辑应收配置只允许 WEIGHT_OUTBOUND、ORDER_COMPLETED。
2. 历史 SIGN 配置不迁移、不补数，本次只约束新建和后续编辑的配置。
3. 已生成任务和历史账单数据不做任何修改。

#### 4.1.2 枚举、选项与保存校验

调整：

1. model 和 client 的 ContractNodeEnum 新增 ORDER_COMPLETED/订单完结。
2. options API 对新应收配置只返回出库、订单完结。
3. BillConfigServiceImpl 增加服务端白名单校验，拒绝新提交的 SIGN、SIGNED 和未知编码。
4. 默认节点继续使用 WEIGHT_OUTBOUND；需求没有要求改变默认项。
5. RefundModeEnum.SIGNED 保持不变。

#### 4.1.3 数据集与时间字段

为 fee_source_dataset 新增 order_completed_time_column，不把 sign_time_column 改成订单完结含义：

1. weight_outbound_time_column：出库时间，现为 h.delivery_time。
2. order_completed_time_column：订单完结时间，固定配置为 `e.order_completed_time`，来源为 `sale_order_header_extend.order_completed_time`。
3. sign_time_column：仅供返款签收模式或历史配置使用。
4. 应收主订单 supported_contract_nodes 调整为 WEIGHT_OUTBOUND,ORDER_COMPLETED。
5. 返款专用数据集继续按返款模式独立维护。

配套调整：

1. FeeSourceDatasetDTO、FeeSourceDatasetSaveDTO 增加字段和 JavaDoc。
2. FeeIndexMapper、BillGenerateMapper 增加查询、写入和显式映射。
3. FeeIndexServiceImpl 校验：声明支持 ORDER_COMPLETED 时必须配置完结时间表达式。
4. 在 aidocs/technical-caliber/bms/sql/ddl 增加结构及数据修正 SQL，并同步 init.sql、fee_source_dataset_create.sql。
5. 时间范围继续使用“>= 开始时间且 < 结束时间”，不在 WHERE 列上套日期函数。

#### 4.1.4 账单生成

BillGenerateServiceImpl 调整：

1. 增加 ORDER_COMPLETED 分支，从数据集 orderCompletedTimeColumn 选择 `e.order_completed_time`；字段非空即表示订单已完成。
2. Disconf 增加语义明确的 order.time.field.completed，不复用 order.time.field.sign。
3. normalizeOrderTimeField() 对订单完结只允许 `e.order_completed_time`，不接受任意 SQL 表达式。
4. 任务快照保存数据集、节点编码和实际时间字段，后续配置变化不能覆盖历史任务。
5. 不迁移、不重算历史 SIGN 配置及历史账单。

#### 4.1.5 前端

admin-front：

1. 下拉继续通过 src/api/ 的 options 接口获取，不新增组件内直连请求。
2. 两处说明改为“应收账单仅支持出库、订单完结两个履约节点”。
3. 历史 SIGN 回显带历史标识；再次保存时要求用户改选有效节点。

admin_shell：

1. SettlementSettingPanel.vue 改为 WEIGHT_OUTBOUND/出库、ORDER_COMPLETED/订单完结，并优先采用后端 options。
2. billConfig/index.vue 增加 ORDER_COMPLETED 显示；SIGN 仅用于历史回显。
3. 费项数据集页面增加订单完结时间表达式，移除新建数据时的 SIGN 支持项。
4. API 仍经 src/api/ 和现有 request 封装，不硬编码基础 URL。

### 4.2 来源支付状态同步方案

#### 4.2.1 统一触发点

1. 更新核销及支付快照后重新查询整张账单。
2. 仅当账单从非 SETTLED 首次进入 SETTLED 时创建来源支付同步任务。
3. 不再以单个币种汇总全额核销作为最终业务触发点。
4. 应收、返款共用一个触发服务。

#### 4.2.2 统一同步服务

从 ArBillServiceImpl 抽出 SourcePaymentWritebackService，职责如下：

1. 按 billNo + billType 查询账单下全部有效 fee_detail。
2. 按 source_system + source_database + source_table + source_id 去重。
3. 通过“来源表类型 -> 状态字段/前值/后值”白名单更新，禁止从业务数据拼接任意表名或字段名。
4. 先落 source_payment_writeback，再执行来源更新；记录前状态、目标状态和失败原因。
5. 幂等键至少包含 bill_no + bill_type + source_table + source_id + target_status，不只依赖某次 writeoff_no。
6. 本期不实现自动或人工重试；失败时记录 ERROR 日志，并写入账单操作轨迹。

#### 4.2.3 应收与返款接入

1. ArBillServiceImpl：整张账单首次进入 SETTLED 后调用统一服务。
2. RefundBillServiceImpl：updateBillPaymentSnapshot() 把返款账单改为 SETTLED 后调用同一服务。
3. 查询候选项不能继续写死 bill_type = MEMBER_AR。
4. 返款账单进入 SETTLED 后，按与应收“已支付”相同的上游状态值执行同步。
5. 调账或重算导致状态变化时，不重复创建已成功任务。

#### 4.2.4 来源表白名单

| 来源表 | 当前字段 | 当前转换 | 方案 |
| :--- | :--- | :--- | :--- |
| sale_order_additional_matter | fee_pay_status | waiting_pay -> paid | 保持现有实现，应收、返款共用 |
| claim_order | payment_status | 1 -> 3 | 保持现有实现，应收、返款共用 |

本期不扩大来源表范围，不修改主订单及其他来源表的状态。

#### 4.2.5 跨库一致性

采用“账单先结清、来源同步后执行、失败留痕”的方式，不强依赖分布式事务：

1. BMS 本地事务完成账单结清和同步任务落库。
2. 账单进入已结清后执行来源更新；来源同步失败不能阻止账单进入已结清。
3. 失败记为 FAILED，控制台打印 ERROR 日志，并向账单操作轨迹写入失败原因。
4. 本期不提供失败重试和人工补偿入口。

#### 4.2.6 反核销

来源状态只在账单已结清后同步。已结清状态不支持反核销，因此：

1. 不回退上游支付状态。
2. 不删除、不覆盖已经成功的来源同步记录。
3. 不新增反向补偿流程。

#### 4.2.7 操作轨迹与服务拆分

1. 来源同步成功或失败后，都向对应账单的操作轨迹写入记录。
2. 操作轨迹至少记录账单编号、账单类型、同步结果、来源记录数量、操作时间和失败原因；失败原因同时打印 ERROR 日志。
3. 账单详情沿用现有操作轨迹区域展示，不新增独立任务监控页面。
4. 将 `source_payment_writeback` 访问和同步逻辑拆到独立 Mapper/Service，供应收与返款复用。
5. 拆分只移动来源同步职责，不改变核销金额计算、账单状态计算及现有来源状态转换。

## 7. 验收清单

### 7.1 履约节点

1. 新建应收配置只能选出库、订单完结。
2. 后端拒绝新提交的 SIGN 和未知节点。
3. ORDER_COMPLETED 使用权威完结时间，不使用 signed_time。
4. WEIGHT_OUTBOUND 继续使用 delivery_time。
5. 历史 SIGN 配置和历史账单保持原样，不迁移、不重算。
6. 返款签收模式不受影响。

### 7.2 支付状态同步

1. 单币种结清而整单未结清时不回写来源已支付。
2. 应收整单首次 SETTLED 时生成一组幂等同步任务。
3. 返款整单首次 SETTLED 时执行同样流程。
4. 重复请求不重复改写上游。
5. 只修改支付状态，不改来源金额、币种、汇率和 BMS 历史快照。
6. 同步失败不影响账单已结清状态，控制台有 ERROR 日志，账单操作轨迹展示失败原因。
7. 本期不提供自动重试、人工重试或反向补偿。
8. 历史已结清账单不补数、不触发来源同步。

## 8. 风险

1. `sale_order_header_extend.order_completed_time` 由上游新增，发布前必须确认目标环境字段已上线且数据正常写入。
2. 历史 SIGN 和历史账单明确不处理，实施时不得批量迁移或重算。
3. 应收与返款若共享 sign_time_column，偷换列语义会破坏返款签收模式。
4. 现有按币种提前回写会导致多币种账单在整单未结清时已有部分来源费项标记已支付。
5. 来源范围保持现有两张表，不能借本次调整扩大到主订单或其他来源表。
6. 来源同步失败不回滚账单结清，当前又不提供重试，因此必须保证控制台日志和操作轨迹足以人工定位。
7. 已结清状态不支持反核销，现有来源状态反向回退逻辑不能在新触发链路中继续调用。
8. admin_shell 当前已有用户未提交修改：package-lock.json、src/utils/request.js、vue.config.js；后续实现不得覆盖或夹带。

## 9. 已确认口径

### 9.1 开发前置口径

1. `sale_order_header_extend.order_completed_time` 非空即表示订单已完成，不再组合判断主订单或尾程包裹状态。
2. 权威订单完结时间字段为上游新增的 `sale_order_header_extend.order_completed_time`。
3. 新履约节点编码确定为 ORDER_COMPLETED。
4. 历史 SIGN 配置和历史账单不迁移、不补数、不重算。
5. 来源费项范围及状态值保持现有实现：`sale_order_additional_matter.fee_pay_status` 从 waiting_pay 改为 paid；`claim_order.payment_status` 从 1 改为 3。
6. 来源支付状态只在整张账单已结清后同步，单币种结清不触发。
7. 返款账单进入已结清后，按与应收已支付相同的上游状态值同步。
8. 已结清状态不支持反核销，不回退上游支付状态。
9. 来源同步发生在账单已结清之后；同步失败不阻止或回滚账单已结清状态。

### 9.2 本期实施口径

1. 同步成功或失败结果展示在账单详情的操作轨迹中，失败记录具体原因。
2. 本期不实现定时重试或人工重试；失败时打印控制台 ERROR 日志并保留操作轨迹记录。
3. 历史已结清账单数据不可修改，不执行来源状态补同步。
4. `source_payment_writeback` 拆分到独立 Mapper/Service，供应收与返款共用，但不得改变原有核销、状态计算及来源转换逻辑。

## 10. 结论

本次变更应作为两条完整链路实施：

1. 以 ORDER_COMPLETED 建立新的应收履约节点，固定使用 `sale_order_header_extend.order_completed_time`，同步配置、数据集、生成逻辑和两个前端，且不处理历史数据。
2. 将现有“应收单币种触发”的回写能力收口为“整单已结清后触发、应收/返款共用、来源范围保持不变、失败不影响结清并写入操作轨迹”的统一机制。

全部开发前置口径已经确认，可以按阶段计划进入实现。
