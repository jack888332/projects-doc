# BMS 账单状态机 PRD 变更技术调整方案（2026-06-26）

## 1. 文档目的

本文基于 `aidocs/product-caliber/bms/prd/财务系统.PRD.md` 在以下两次提交中的调整，结合当前仓库代码现状，整理 BMS 账单状态机相关的技术调整方案、实施计划与待确认问题。

1. `2ad6c20a7f676ac0568d20d2bef2ccb237299abd`
   - 优化【应收账单状态机】描述
2. `db79b5ed7449a1fbe6b519a5c01ed5c3f382283c`
   - 优化【返款账单状态机】描述

本方案只讨论“账单状态机、展示口径、接口动作、核销保留规则”这条主链路，不扩展到无关业务改造。

## 2. PRD 变更摘要

结合当前 PRD 第 `9.5`、`9.6`、`10.4`、`11.4`、`12.5.2` 节，本轮变化可归纳为 5 点：

1. 应收账单主状态收敛为 `起草中 -> 待审核 -> 待结清 -> 已结清`。
2. `逾期未结清` 在应收账单中不是主状态，只是 `待结清` 下的筛选条件和展示标签。
3. 返款账单状态机与应收账单同构，但返款账单不设置 `逾期未结清` 口径。
4. 应收账单、返款账单都支持因客户异议从 `待结清` 折返回 `待审核`。
5. 折返时必须保留既有核销/回款/返款记录、币种、金额、汇率快照和操作轨迹，只能基于修正后的账单结果继续处理未结清余额。

## 3. 现状盘点

## 3.1 应收账单后端现状

当前 `bms` 后端对应收账单已经做过一轮状态收敛，和新版 PRD 是“部分对齐”关系。

已对齐的点：

1. `bms/common/src/main/java/com/szt/supplychain/bms/common/constant/BmsConstants.java`
   - 真实状态已经收敛为 `DRAFT / GENERATED / PENDING_SETTLEMENT / PAID / VOID`
   - `OVERDUE_UNSETTLED` 已被定义为虚拟筛选条件

2. `bms/model/src/main/java/com/szt/supplychain/bms/model/dto/ArBillQueryReqDTO.java`
   - `billStatus=PENDING_SETTLEMENT` 与 `billStatus=OVERDUE_UNSETTLED` 的含义已经区分

3. `bms/dao/src/main/java/com/szt/supplychain/bms/dao/mapper/ArBillMapper.java`
   - 列表过滤已经按 `PENDING_SETTLEMENT` 与 `OVERDUE_UNSETTLED` 分流
   - 核销后账单主状态统一回写为 `PENDING_SETTLEMENT` 或 `PAID`

4. `admin_shell/src/views/billing/receivableBill/index.vue`
   - 状态 Tab 已经是 `待复核 / 待结清 / 逾期未结清 / 已结清 / 起草中 / 全部`
   - 不再把“部分待结算”作为独立筛选值

未对齐的点：

1. 术语仍然大量使用“待复核”，而 PRD 已统一为“待审核”
   - 后端常量注释、前端标签、页面提示语都存在该问题

2. 应收账单缺少“待结清 -> 待审核”的专用折返动作
   - `ArBillRemoteService` / `ArBillController` / `BmsArBillController` 只有 `confirm / send / payment / reversePayment / adjustment`
   - 没有 `returnToReview` 或等价接口

3. 当前“调整账单”不承接待结清折返场景
   - `ArBillServiceImpl.adjustment()` 仅允许 `DRAFT / GENERATED`
   - `BmsConstants.ADJUST_ALLOWED_STATUSES` 也只允许 `DRAFT / GENERATED`

4. 应收账单状态推导仍与 `confirmed_at` 强绑定
   - `ArBillMapper.refreshBillAfterCurrencySummary()`
   - `ArBillMapper.reversePaymentOnBill()`
   - 以上 SQL 都以 `confirmed_at IS NULL ? GENERATED : PENDING_SETTLEMENT` 推导状态
   - 如果后续新增折返动作但不处理 `confirmed_at`，账单在后续核销/反核销/重算后会被重新推回 `PENDING_SETTLEMENT`

5. 当前这轮实际开发前端不在 `admin-front`，而是在 `admin_shell/src/views/billing`
   - 因此本方案的主实施面以前者为次、以后者为主
   - `admin-front` 中即使存在应收账单页面，也不作为本轮主交付范围

## 3.2 返款账单后端现状

返款账单当前实现与新版 PRD 的差距比应收账单更大。

已对齐的点：

1. `bms/common/.../BmsConstants.java`
   - 返款主状态已存在 `UNDER_REVIEW / PENDING_SETTLEMENT / SETTLED`

2. `admin_shell/src/views/billing/refundBill/index.vue`
   - 主状态 Tab 已经收敛为 `待审核 / 待结清 / 已结清 / 全部`

3. `RefundBillServiceImpl.confirm()/payment()`
   - 返款后状态仍停留 `PENDING_SETTLEMENT`
   - 全部结清后进入 `SETTLED`

未对齐的点：

1. 返款账单后端仍保留“逾期未返”口径
   - `BmsConstants.VIRTUAL_REFUND_BILL_STATUS_OVERDUE_UNREFUNDED`
   - `RefundBill-mapper.xml` 中存在 `billStatus == 'OVERDUE_UNREFUNDED'` 的过滤分支
   - `RefundBillPageRespDTO` 仍包含 `overdueUnrefundedCount / overdueUnrefundedAmount`

2. 返款账单文案仍有“待复核”表达
   - `RefundBillServiceImpl.statusLabel()` 当前返回 `"待复核"`

3. 返款账单也缺少“待结清 -> 待审核”的专用折返动作
   - `RefundBillRemoteService` / `RefundBillController` / `BmsRefundBillController` 只有 `confirm / send / payment`
   - 没有 `returnToReview` 或等价接口

4. 返款账单页面摘要口径仍偏“待返款/逾期未返”
   - `admin_shell/src/views/billing/refundBill/index.vue`
   - 摘要字段仍使用 `pendingRefundCount / overdueUnrefundedCount`
   - 假数据中仍有 `PENDING_REFUND / OVERDUE_UNREFUNDED`

## 3.3 Portal 层现状

`platform-admin` 当前只是透传现有 BMS 能力，没有承接折返动作。

1. `platform-admin/web/src/main/java/com/szt/supplychain/platform/admin/web/controller/BmsArBillController.java`
2. `platform-admin/web/src/main/java/com/szt/supplychain/platform/admin/web/controller/BmsRefundBillController.java`

两个 Controller 都没有“退回待审核”入口，因此即使 BMS Service 层补齐，也需要同步开放 Portal 接口。

3. 部分提示语仍使用“待结算”旧术语

返款页还要补这几项：

1. 去掉“逾期未返”作为账单页面状态/摘要口径
2. `pendingRefundCount` 页面语义改为“待结清账单数”
3. 增加“退回待审核”操作

### Admin Front

`admin-front` 仓库内虽然存在应收账单页面，但根据当前开发口径，本轮不把它作为主交付前端。

## 4. 技术调整目标

本轮改造目标如下：

1. 应收账单：
   - 统一主状态展示为 `起草中 / 待审核 / 待结清 / 已结清`
   - `逾期未结清` 仅保留为虚拟筛选条件和标签

2. 返款账单：
   - 统一主状态展示为 `起草中 / 待审核 / 待结清 / 已结清`
   - 账单页面移除 `逾期未返` 口径

3. 两类账单：
   - 新增 `待结清 -> 待审核` 的折返动作
   - 折返时不删除任何既有核销/回款/返款流水及汇率快照

4. 前端展示：
   - `通知失败` 从账单状态维度剥离，继续作为通知状态展示
   - `部分待结算` 不再作为主状态 Tab，只允许作为金额进度描述

## 5. 技术调整方案

## 5.1 总体设计原则

本轮建议采用“编码尽量不改、展示与动作补齐、最小化影响现有数据”的策略。

具体原则：

1. 不改数据库中的既有状态码
   - 应收继续使用 `DRAFT / GENERATED / PENDING_SETTLEMENT / PAID / VOID`
   - 返款继续使用 `DRAFT / UNDER_REVIEW / PENDING_SETTLEMENT / SETTLED / VOID`

2. 统一改展示文案
   - `GENERATED -> 待审核`
   - `UNDER_REVIEW -> 待审核`
   - `PENDING_SETTLEMENT -> 待结清`
   - `PAID / SETTLED -> 已结清`

3. 应收保留 `OVERDUE_UNSETTLED` 虚拟筛选
4. 返款账单移除 `OVERDUE_UNREFUNDED` 账单口径
5. 待结清折返待审核使用独立动作，不复用现有 `adjustment`

## 5.2 应收账单调整方案

### 5.2.1 后端动作设计

建议新增独立接口：

1. `POST /api/bms/ar-bill/return-to-review`
2. `POST /portal/bms/arBill/returnToReview`

建议沿用 `ArBillActionReqDTO`，复用现有字段：

1. `billNo / billNos`
2. `reason`
3. `remark`
4. `operator`

Service 规则建议：

1. 仅允许 `PENDING_SETTLEMENT` 状态账单执行
2. 必填 `reason`
3. 加行锁处理，批量时逐单校验
4. 仅回退账单审核状态，不动核销流水、不动 payment_receipt、不动 payment_writeoff_detail、不动 ar_bill_currency_summary 的已收金额

### 5.2.2 应收账单回退时的字段处理

建议在折返时执行以下回写：

1. `bill_status = GENERATED`
2. `confirmed_at = NULL`
3. `confirmed_by = NULL`
4. `bill_send_date = NULL`
5. `updated_by / updated_at` 更新为当前操作人和当前时间

这样做的原因：

1. `ArBillMapper.refreshBillAfterCurrencySummary()`、`reversePaymentOnBill()` 等逻辑仍依赖 `confirmed_at` 推导状态
2. 如果不清空 `confirmed_at`，后续核销重算会把账单重新推回 `PENDING_SETTLEMENT`
3. 如果不清空 `bill_send_date`，前端当前的通知状态推导会误判“当前版本已发送”

这部分属于本轮最关键的技术收口点。

### 5.2.3 应收账单受影响代码

后端：

1. `bms/common/.../BmsConstants.java`
   - 新增 `RETURN_TO_REVIEW_ALLOWED_STATUSES`
   - 更新注释文案为“待审核”

2. `bms/client/.../ArBillRemoteService.java`
3. `bms/web/.../ArBillController.java`
4. `platform-admin/web/.../BmsArBillController.java`
5. `bms/biz/.../ArBillService.java`
6. `bms/biz/.../ArBillServiceImpl.java`
7. `bms/dao/.../ArBillMapper.java`
   - 新增专用 mapper：`returnToReviewByBillNo`

前端：

1. `admin_shell/src/api/billing.js`
2. `admin_shell/src/views/billing/receivableBill/index.vue`

### 5.2.4 应收账单展示调整

1. `待复核` 全部改为 `待审核`
2. `待结算 / 部分待结算` 从主状态 Tab 中移除，统一收敛到 `待结清`
3. `逾期未结清` 继续保留为快捷筛选和标签
4. `通知失败` 不再作为账单状态 Tab，保留在通知状态列或角标

## 5.3 返款账单调整方案

1. `POST /api/bms/refund-bill/return-to-review`

1. 仅允许 `PENDING_SETTLEMENT` 状态返款账单执行

3. 折返时不删除 `refund_payment_record`、`refund_payment_allocation`、`ar_bill_currency_summary` 中已付款快照
4. 仅将账单重新置为 `UNDER_REVIEW`

3. 但回款管理页不保留“逾期未返/逾期”视角，不再提供逾期标签、逾期筛选和逾期汇总口径

## 5.5 是否涉及数据库结构调整

本轮主方案不要求新增表或改表结构。

原因：

1. 状态回退只需要新增接口和更新现有账单字段
2. PRD 强制要求保留的是核销/回款/返款记录，不是新增一套状态历史表

但如果产品后续要求“可视化查看每次 待审核 -> 待结清 -> 待审核 的完整轨迹”，建议二期新增账单状态流转记录表，本轮不必强绑。

## 6. 调整计划

建议分 4 步执行。

### Step 1：后端主链路调整

1. 新增应收账单 `return-to-review` 能力
2. 新增返款账单 `return-to-review` 能力
3. 应收账单清理 `confirmed_at / bill_send_date` 依赖问题
4. 返款账单与回款管理页同时移除 `OVERDUE_UNREFUNDED` 等逾期视角口径

交付物：

1. `bms`
2. `platform-admin`

### Step 2：Admin Shell 同步

1. 应收页把 `待复核` 改 `待审核`
2. 应收页新增“退回待审核”按钮和调用
3. 返款页去掉“逾期未返”账单摘要与状态映射
4. 回款管理页去掉“逾期未返/逾期”相关标签、筛选和映射
5. 返款页新增“退回待审核”按钮和调用

### Step 3：Admin Shell 联调回归

1. 应收账单页面联调折返待审核动作
2. 返款账单页面联调折返待审核动作
3. 校验状态筛选、摘要、按钮权限与接口回包一致
4. 校验回款管理页仍保留包裹级明细，但不再出现任何逾期视角

### Step 4：联调与回归验证

至少验证以下场景：

1. 应收账单 `待审核 -> 待结清 -> 待审核 -> 待结清`
2. 应收账单部分核销后折返待审核，核销流水仍可查询
3. 应收账单折返后重发前，通知状态不应误显示为“已通知”
4. 返款账单 `待审核 -> 待结清 -> 待审核 -> 待结清`
5. 返款账单部分打款后折返待审核，打款记录仍保留
6. 应收账单保留 `逾期未结清` 快捷筛选
7. 返款账单页面不再出现 `逾期未返` 账单口径

## 7. 风险与注意事项

1. 应收账单最大的技术风险不是前端文案，而是 `confirmed_at` 对状态推导的耦合。
2. 如果只加“退回待审核”接口、不清理 `confirmed_at`，账单后续在重算或反核销时会被自动打回 `PENDING_SETTLEMENT`。
3. 回款管理页需要保留包裹级明细能力，但不能把“逾期未返”继续保留为包裹级视角，避免与本轮 PRD 口径冲突。
4. 当前前端主实施面是 `admin_shell/src/views/billing`，不要把 `admin-front` 的页面现状误判成本轮必改项。

## 8. 疑问点

以下问题已确认，可直接按确认结论落地：

1. 应收账单或返款账单从 `待结清` 折返回 `待审核` 时，`bill_send_date` 是否应清空？
   - 已确认：清空。否则当前页面会把旧版本发送结果误当成当前版本已发送。

2. 折返回 `待审核` 后，页面是否需要保留“历史已发送时间/历史审核时间”的可见追溯？
   - 已确认：需要保留。实现上需补充状态流转留痕或历史字段展示方案，不能只保留核销与支付流水。

3. 返款账单页面取消“逾期未返”后，回款管理页面是否仍保留包裹级逾期视角？
   - 已确认：保留包裹级视角，但不保留逾期视角。也就是保留 `tailWaybillNo` 维度的回款/返款进度，不保留任何“逾期未返/逾期”标签、筛选、汇总。

4. 本轮是否只处理 `admin_shell/src/views/billing`，还是要求把其他前端仓库中的同名页面也同步？
   - 已确认：只处理 `admin_shell/src/views/billing`。

5. 业务术语上是否要求把所有“待复核/复核通过”统一替换为“待审核/审核通过”？
   - 已确认：统一用“审核”。当前代码中的接口名 `confirm` 可以不改，但页面文案、注释、按钮文本统一改成“审核”。

## 9. 结论

本轮 PRD 变更对代码的真正影响，不是“改几个状态中文名”，而是三件事：

1. 应收账单要把现有“半对齐”的状态模型彻底收口，尤其补齐 `待结清 -> 待审核` 折返动作。
2. 返款账单要把“逾期未返”从账单状态口径中剥离出去，回款管理页也要同步去掉逾期视角，但继续保留包裹级明细口径，并补齐同样的折返动作。
3. `admin_shell / platform-admin / bms` 需要一起调整，否则状态机会出现“后端新口径、前端旧口径”的分裂。

建议按“后端动作先落地，Shell 联调，再决定 Front 是否顺手切真接口”的顺序推进，这样风险最小、收益最高。
