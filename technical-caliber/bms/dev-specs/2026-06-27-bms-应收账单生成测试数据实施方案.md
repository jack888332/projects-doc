# BMS 应收账单生成测试数据实施方案（2026-06-27）

## 1. 文档目的

本文用于沉淀一套可重复、可扩展、与当前代码实现一致的“应收账单生成前置测试数据方案”，解决以下问题：

1. 需要补哪些前置业务表数据，账单生成逻辑才能真正跑起来。
2. 应该准备什么样的账单配置，才能稳定生成目标账单。
3. 如何一次性覆盖主订单费用、附加费、理赔、分支配置、同账期补采集、账后新增附加费等主要场景。
4. 后续如果要再扩展更多测试数据，应该沿用什么命名和造数方法。

本文只讨论 `MEMBER_AR` 应收账单生成链路，不扩展到返款账单、应付账单或前端页面改造。

### 2.3 当前代码的关键过滤规则

#### 主订单扫描规则

当前代码从 `sale_order_header h` + `sale_order_header_extend e` 读取候选订单，核心过滤条件为：

1. `h.member_code = 当前账单配置.member_code`
2. `h.shop_id = 当前账单配置.shop_id`
3. `(h.sc_id = 当前账单配置.sc_id OR h.sc_id IS NULL)`
4. 命中当前账期时间窗口
5. `COALESCE(e.bms_billed_flag, 0) = 0`
6. `(e.bms_bill_no IS NULL OR e.bms_bill_no = '')`
7. 分支配置会额外按业务类型映射出的 `order_type` 过滤

#### 附加费扫描规则

普通附加费当前核心过滤条件为：

1. `a.sale_order_id IN (本次命中的订单集合)`
2. `a.fee_amount IS NOT NULL AND a.fee_amount <> 0`
3. `a.fee_pay_status = 'waiting_pay'`
4. `COALESCE(a.bms_billed_flag, 0) = 0`
5. `COALESCE(a.bms_after_bill_added_flag, 0) = 0`
6. `fee_item_type` 必须能命中 `fee_source_rule.filter_params_json`

#### 账后新增附加费扫描规则

账后新增附加费当前核心过滤条件为：

1. `a.fee_pay_status = 'waiting_pay'`
2. `COALESCE(a.bms_after_bill_added_flag, 0) = 1`
3. `COALESCE(a.bms_billed_flag, 0) = 0`
4. `(a.bms_bill_no IS NULL OR a.bms_bill_no = '')`
5. `a.fee_amount IS NOT NULL AND a.fee_amount <> 0`

#### 理赔扫描规则

当前理赔入账条件为：

1. `status = 1`
2. `customer_service_audit_status = 2`
3. `finance_audit_status = 2`
4. `payment_status = 1`
5. `update_time` 落在账期内
6. `bms_billed_flag = 0`
7. `bms_bill_no IS NULL`

### 2.4 当前实现的两个重要事实

#### 事实 1：默认配置与分支配置是“分支优先、默认兜底”

当前代码会先匹配分支配置，再把未命中分支的数据归到默认配置，因此测试数据必须同时准备：

1. 会命中分支的数据
2. 会落回默认配置的数据

否则无法验证“同一客户同一账期内多配置互斥归集”。

#### 事实 2：当前应收账单的拆单键，真实上主要靠 `destination_country`

当前代码设计上按 `business_sector + destination_country` 拆单，但主订单宽表 SQL 并未实际查询 `h_business_sector` / `h_business_plate`，因此在当前实现中：

1. `business_sector` 经常会回退为 `DEFAULT`
2. `destination_country` 才是现阶段最稳定的拆单维度

所以测试数据设计中，如果目标是“稳定生成多张应收账单”，不要只依赖业务板块差异，必须显式造不同的 `country_code` / `country`。

## 3. 总体造数策略

## 3.1 不建议直接复用历史客户做完整测试

当前库里虽然已有可用配置与历史数据，例如：

1. `bill_config.id = 8`，`member_code = 700127`
2. `bill_config.id = 52`，`member_code = 20260507-002`

但这些数据存在以下问题：

1. 已有历史账单和来源打标，容易混入旧数据。
2. 附加费状态分布较杂，很多是 `paid` / `waiting_settlement`，并不命中当前代码的 `waiting_pay` 规则。
3. 不利于后续手工测试复核、结算、核销等功能时做干净回归。

因此：

> 推荐单独创建一组专用测试客户与专用订单数据，不要继续往现有历史客户上叠加完整场景数据。

## 7. 预期生成结果

## 7.1 配置 A1 的预期

### 第二次同账期生成

在插入 A2 批次订单后再次执行同账期生成，预期：

1. 不新建新的目标账单分组
2. 将 `ORD-021`、`ORD-022` 追加进原账单
3. 账单金额增大

### 第三次增量附加费生成

在插入 A3 批次附加费后再次执行同账期生成，预期：

1. 账单可追加时，附加费追加到原账单
2. `fee_detail.source_table = sale_order_additional_matter`
3. `bill_source_collect_mark.collect_type = ADDITIONAL_INCREMENT`

## 7.2 配置 B1/B2/B3 的预期

同一账期内，预期生成 3 张账单：

1. US 分支账单
2. JP 分支账单
3. 默认兜底账单

当前实现下更稳的判断口径是：

1. 至少应按 `destination_country` 拆成多张账单
2. 分支账单和默认账单对应的订单集合不应重叠

## 7.3 配置 C1 的预期

预期：

1. `signed_time` 命中账期的订单可生成账单
2. 仅 `measure_time` 命中、`signed_time` 不命中的订单，不应被 `SIGN` 配置出账

## 10. 后续扩展规则

为了后续能继续基于本文扩展测试数据，建议遵循以下规则。

## 10.1 命名规则

### 配置编号

建议格式：

`ARB-{测试客户编号}-{配置类型}-{日期}`

例如：

1. `ARB-ARTESTA-DEFAULT-20260627`
2. `ARB-ARTESTB-BRANCH-US-20260627`

### 订单号

建议格式：

`{member_code}-ORD-{三位序号}`

例如：

1. `AR260627A-ORD-001`
2. `AR260627B-ORD-003`

### 附加费编号

建议格式：

`ADD-{客户标识}-{场景}-{序号}`

例如：

1. `ADD-A-001`
2. `ADD-A-INC-001`

### 理赔单号

建议格式：

`CLM-{客户标识}-{序号}`

例如：

1. `CLM-A-001`

## 10.2 扩展更多测试数据时的原则

1. 新增一类场景时，优先新增新的订单号或附加费号，不要复用旧来源行。
2. 如果目的是测试“再次生成补采集”，新增来源数据必须保持：
   - 同一 `member_code`
   - 同一 `shop_id`
   - 同一账期
   - `bms_billed_flag = 0`
3. 如果目的是测试“账后新增附加费”，来源附加费必须显式设置：
   - `bms_after_bill_added_flag = 1`
   - `fee_pay_status = waiting_pay`
4. 如果目的是测试“分支优先”，必须同时造：
   - 命中分支的数据
   - 不命中分支但命中默认配置的数据
5. 如果目的是测试 `SIGN`，必须让 `signed_time` 成为唯一命中时间，不要让 `measure_time` 也落在同一账期内造成混淆。

## 11. 结论

当前 `MEMBER_AR` 账单生成链路，前置测试数据的核心不是“把结果表补出来”，而是：

1. 准备正确的账单配置
2. 准备正确的未归集订单源数据
3. 准备正确状态的附加费和理赔数据
4. 按当前代码真实过滤规则去造数

本方案推荐：

1. 使用三组独立测试客户 `AR260627A / B / C`
2. 通过 A 组覆盖主链路、补采集、增量附加费、理赔
3. 通过 B 组覆盖分支优先与默认兜底
4. 通过 C 组覆盖签收节点

这样生成出来的账单，就足够你后续继续手工测试：

1. 复核
2. 重发
3. 调账
4. 收款登记
5. 核销
6. 导出
7. 任务监控与重试

如果后续要继续扩展新的测试数据，应优先在本文的三组测试客户体系内追加，不要反复污染历史客户数据。
