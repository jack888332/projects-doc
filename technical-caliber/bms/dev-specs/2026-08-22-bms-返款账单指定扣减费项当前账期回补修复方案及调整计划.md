# 2026-08-22 BMS 返款账单指定扣减费项按订单关联附加费采集修复方案及调整计划

## 0. 实施状态

2026-08-24 已按本方案完成代码调整：

- `executeRefundTaskInternal` 改为按本期回款订单采集关联附加费，移除上一周期附加费查询。
- 新增 `queryRefundAdditionalRows` 系列方法，附加费源 SQL 不再使用 `create_time` 窗口。
- `buildRefundDeductions` 移除上一周期订单参数，配置扣减费项过滤逻辑保持不变。
- `queryReceivableFeesForRefundLink` 增加 `settlement_role = 'REFUND_DEDUCTION'` 校验。
- `dao`、`biz` 模块已通过 Maven `test-compile` 编译验证。

## 1. 背景与目标

返款账单配置 `RCB-OG0207-Scheme-20260822120551518-v1` 已配置直接扣减费项：

- 代收货款手续费
- 超材费
- 重出费

实际返款账单 `PCB-OG0207-20260817`（账期 2026-08-17 至 2026-08-23）中，业务订单 `VIP26080704`、`VIP26080701` 的超材费明细显示为 `0.00`。

排查确认：

- `ofp_ofdb1.sale_order_additional_matter` 中超材费行创建于 2026-08-21，`fee_pay_method = account_period_payment`，`fee_pay_status = waiting_settlement`。
- 应收任务已把同一批费用写入 `fee_detail`，费项为 `FEE0045 超材费`，`settlement_role = REFUND_DEDUCTION`，`related_bill_no` 为空，说明应收侧尚未作为可核销金额占用。
- 当前返款生成按附加费 `create_time` 的“上一周期”窗口采集，没有采集本期回款订单关联的附加费，因此返款明细没有生成 `FEE0045` 扣减行。

目标：返款生成改为订单驱动。先确定本期采集到的回款订单，再通过 `ofp_ofdb1.sale_order_header.id = sale_order_additional_matter.sale_order_id` 把这些订单的关联附加费一并采集，作为返款指定扣减候选；不再按附加费 `create_time` 或“上一周期”窗口取数。

## 2. 口径依据

`PRD.账单系统.md` 的分流口径：

- 只有命中返款账单指定扣减规则的费用，才能从返款金额中扣除；未命中的客户应付费用继续按应收账单规则处理。
- 已被返款账单作为扣减金额占用的费项，应收账单只能关联展示，不得再次核销；已经进入应收账单核销的费项，也不得再转为返款扣减。
- 应收账单和返款账单可以不同账期、不同日期生成；代收货款及指定扣减费项可能在回款条件满足后进入后续返款账单，账期不同不影响订单和包裹关联。
- 只有 `payment_method` 为账期支付的附加费才进入应收归集范围。

产品调整口径：返款扣减费项按“本期返款订单”归属，不按附加费 `create_time` 开窗，也不限定只能回补上一周期。

## 3. 现状代码定位

返款生成主链路在 `BillGenerateServiceImpl.executeRefundTaskInternal`：

1. 先通过 `queryRefundOrderRows` 按返款账期采集回款订单。
2. `resolvePreviousCycleRange(startDate, endDate)` 计算上一周期范围，见 `BillGenerateServiceImpl.java:2576`。
3. 仅调用 `queryAdditionalRows(..., previousDeductPeriod[0], previousDeductPeriod[1], ...)` 查询上一周期附加费，见 `BillGenerateServiceImpl.java:2152-2170`。
4. `buildRefundDeductions` 只接收 `previousAdditionalRows`，见 `BillGenerateServiceImpl.java:2738`。
5. 附加费源查询 SQL 使用 `create_time` 窗口、`account_period_payment`、`waiting_pay / waiting_settlement` 和 `bms_after_bill_added_flag = 0`，见 `BillGenerateServiceImpl.java:6531-6547`。

应收侧已经具备与返款扣减互相关联的能力：

- `BillGenerateMapper.queryReceivableFeesForRefundLink` 按 `business_order_no + source_table + source_id + fee_name` 查找尚未关联返款账单的应收费项，见 `BillGenerateMapper.java:686-697`。
- `linkArBillToRefundFee` 和 `linkRefundBillToExistingFee` 分别维护返款费项到应收账单、应收费项到返款账单的关联。
- 应收生成完成后还会执行 `weakLinkRefundFeesToArBill`，对已先生成返款、后生成应收的场景做弱关联，见 `BillGenerateServiceImpl.java:6140-6167`。

因此返款先跑或应收先跑都能通过现有链路补关联，本次修复不需要重做关联逻辑。

## 4. 推荐落地方案

### 4.1 取数规则

返款生成中，当前返款账期已经确定 `matchedRows`（回款订单），则直接采集这些订单的关联附加费：

```sql
SELECT a.id AS a_id,
       a.sale_order_id AS a_sale_order_id,
       a.fee_item_type AS a_fee_item_type,
       a.fee_amount AS a_fee_amount,
       a.fee_amount_currency AS a_fee_amount_currency,
       a.convert_fee_amount AS a_convert_fee_amount,
       a.convert_fee_amount_currency AS a_convert_fee_amount_currency,
       a.fee_pay_status AS a_fee_pay_status,
       a.create_time AS a_create_time,
       a.handle_time AS a_handle_time,
       a.shop_id AS a_shop_id,
       a.country_short_code AS a_country_short_code,
       a.sub_bill_waybill_no AS a_sub_bill_waybill_no,
       a.bill_waybill_no AS a_bill_waybill_no
FROM ofp_ofdb1.sale_order_additional_matter a
JOIN ofp_ofdb1.sale_order_header h ON h.id = a.sale_order_id
WHERE a.sale_order_id IN (...)
  AND a.fee_amount IS NOT NULL
  AND a.fee_amount <> 0
  AND COALESCE(h.order_type, '') <> 'BILL'
  AND a.fee_pay_status IN ('waiting_pay', 'waiting_settlement')
  AND a.fee_pay_method = 'account_period_payment'
ORDER BY a.id
LIMIT ? OFFSET ?
```

关键调整：

1. 不再使用附加费 `create_time` 作为采集窗口。
2. 不再查询上一周期订单或上一周期附加费。
3. 通过 `sale_order_header.id = sale_order_additional_matter.sale_order_id` 关联，按本期返款订单采集其全部符合条件的附加费。
4. `bms_after_bill_added_flag` 建议不再作为过滤条件，统一由 `bill_source_collect_mark` 按 `COD_REFUND` 已打标状态防重；如需保留该字段过滤，需产品再次确认。
5. 订单头扩展字段 `overmaterial_amount` 仍保留为兜底：只有当前订单没有关联附加费时才读取。

候选与配置扣减的关系：

- 上面 SQL 采集的是“订单关联且符合账期支付资格”的候选附加费，不是最终返款扣减结果。
- 最终是否进入返款扣减，必须继续按返款账单配置快照 `directDeductFeeItems` 过滤，只有命中配置的费项才生成 `REFUND_DEDUCTION` 明细。
- 本次配置中的 `超材费（FEE0005）`、`重出费（FEE0052）`会命中；`转板费`、`税金`等未配置费项即使被源 SQL 采集到，也只会继续走应收规则，不会进入返款扣减。
- 当前代码的 `containsRefundDeductFee` + `filterAdditionalRowsByFeeName` 已实现这层过滤，本次修复保留该逻辑，不把源 SQL 候选直接等同于返款扣减费项。

### 4.2 代码调整

在 `executeRefundTaskInternal` 中，把“上一周期附加费查询”替换为“按当前返款订单查询关联附加费”：

```text
// 原实现：上一周期窗口
previousDeductPeriod = resolvePreviousCycleRange(startDate, endDate);
previousOrderRowById = queryRefundOrderRows(... previousDeductPeriod ...);
previousAdditionalRowsByOrderId = queryAdditionalRows(... previousDeductPeriod ...);

// 调整后：当前回款订单驱动
deductionAdditionalRowsByOrderId =
    groupRowsByKey(
        queryRefundAdditionalRows(matchedOrderIds, shadowConfig, taskId),
        "a_sale_order_id"
    );
```

具体调整点：

1. 新增 `queryRefundAdditionalRows` 私有方法：只按 `orderIds` 采集关联附加费，不再接收 `startDate / endDate / create_time` 参数。
2. 新增或调整附加费源 SQL 构造方法：去掉 `AND create_time >= ? AND create_time < ?`，保留费用资格条件和订单关联条件。
3. `queryRefundAdditionalRowsFromSource` 继续按 `COD_REFUND` 的 `bill_source_collect_mark` 过滤已归集来源行，分页循环仍按 `pageSize` 执行。
4. `buildRefundDeductions` 入参从 `previousAdditionalRows` 改为 `deductionAdditionalRows`，并移除 `previousOrderRow` 参数，统一使用当前订单行。
5. `resolvePreviousCycleRange` 不再用于返款附加费采集；如果其他链路仍在使用，则保留该方法。
6. 保留 `markAdditionalSource`，采集成功的附加费继续写 `bill_source_collect_mark`，避免后续返款账单重复采集。
7. 配置过滤保持不变：`buildRefundDeductions` 仍按 `snapshot.getDirectDeductFeeItems()` 判断哪些候选附加费可以进入返款扣减，未配置费项不得写入返款明细。

### 4.3 防串账补充建议

`queryReceivableFeesForRefundLink` 目前只按 `bill_type = MEMBER_AR`、`related_bill_no IS NULL`、来源表和费项名匹配，没有校验 `settlement_role`。

建议在本次调整中增加条件：

- 只允许关联 `settlement_role = REFUND_DEDUCTION` 的应收费项。
- 已进入应收核销的 `RECEIVABLE` 费项不得被返款扣减关联。

这是对 PRD“已经进入应收账单核销的费项，不得再转为返款扣减”的落地保护。

## 5. 防重与边界

1. 附加费不再按时间窗口分页，而是按本期返款订单集合采集；同一订单的多条附加费行都进入候选。
2. `queryRefundAdditionalRowsFromSource` 已按 `bill_type = COD_REFUND` 过滤 `bill_source_collect_mark` 中 `MARKED` 的来源行，已归集到其他返款账单的附加费不会再次进入候选。
3. `fee_detail.dedupeKey` 已包含 `COD_REFUND + billNo + feeCode + sourceId + REFUND_DEDUCTION`，同一账单内不会重复写明细。
4. 重跑沿用现有 `regenerate` 入口，只允许 `DRAFT / UNDER_REVIEW` 状态；已发出、待结清、已结清账单不自动回写。
5. 应收侧费项一旦 `related_bill_no` 已关联返款账单，不会再次进入应收核销；已经参与应收核销的费项不会转入返款扣减。
6. 只有返款账单配置中指定的直接扣减费项才能形成 `REFUND_DEDUCTION`；源 SQL 采集到的其他账期支付附加费不会自动变成返款扣减。

```sql
       a.fee_pay_method, a.fee_pay_status, a.create_time

WHERE a.sale_order_id IN (SELECT id FROM ofp_ofdb1.sale_order_header
                          WHERE biz_order_no IN ('VIP26080704', 'VIP26080701'))
  AND a.fee_item_type = '超材费';

-- BMS 应收侧返款扣减费项
SELECT id, bill_no, fee_code, fee_name, settlement_role,
       related_bill_no, amount_bill_currency

WHERE business_order_no IN ('VIP26080704', 'VIP26080701')
  AND fee_code = 'FEE0045'
  AND fee_status <> 'VOID';
```

修复前预期：OFP 有超材费行；`fee_detail` 有 `MEMBER_AR + REFUND_DEDUCTION` 且 `related_bill_no IS NULL`；返款账单没有对应 `COD_REFUND + FEE0045` 行。

### 7.3 回归用例

- 场景一：同一返款订单有多条不同 `create_time` 的关联附加费，确认全部按订单采集。
- 场景二：附加费 `create_time` 在返款账期之外，确认仍能随订单进入本次返款扣减候选。
- 场景三：同一附加费行已被其他返款账单打标，确认不会重复归集。
- 场景四：应收先生成、返款后生成，确认双向关联建立。
- 场景五：返款先生成、应收后生成，确认 `weakLinkRefundFeesToArBill` 弱关联生效。
- 场景六：应收侧费项已作为 `RECEIVABLE` 参与核销，确认不会被关联为返款扣减。
- 场景七：订单同时存在配置内外的附加费，确认只有配置命中的费项进入返款扣减，其余继续走应收规则。

2. 附加费资格是否仍限定 `fee_pay_status IN ('waiting_pay', 'waiting_settlement')`？当前推荐保留；如果已支付或已核销状态也需要进入返款扣减，需产品确认。
3. 本次问题账单 `PCB-OG0207-20260817` 状态为 `UNDER_REVIEW`，可直接重跑；如果实际状态已发出或已结清，需按产品口径走调整或后续账期承接。
